## 2. Địa chỉ Bitcoin và tính giả danh / Bitcoin Addresses and Pseudonymity

### 2.1. Tính giả danh (Pseudonymity)

![Pseudonymity](https://images.ctfassets.net/0idwgenf7ije/69Dy9mUxabhXrgTCSSpfbX/168739d1e062a4bc38097939b3fb9235/Gemini-What_Is_Cryptojacking_.png?fm=webp)

- **Pseudonymity (giả danh)** là trạng thái _gần như ẩn danh_: người dùng không công khai danh tính thật, mà dùng một "bút danh".
- Bitcoin là blockchain **permissionless** (không cần xin phép): bạn **không cần đăng ký tài khoản**. Ví (wallet) tự sinh ra cặp khóa **private key** (khóa bí mật) và **public key** (khóa công khai).
- **Địa chỉ (address)** đóng vai trò "bút danh" của bạn trong các giao dịch.

![Pseudonym analogy](https://i.ibb.co/TBBWVtRp/image.png)

**Phép so sánh với nhà văn:** Gửi/nhận Bitcoin giống việc một tác giả viết sách dưới bút danh. Nếu bút danh bị gắn với danh tính thật, **mọi cuốn sách** viết dưới bút danh đó đều bị gắn với tác giả. Tương tự, nếu một địa chỉ bị liên kết với danh tính của bạn, **mọi giao dịch** của địa chỉ đó đều truy ra được bạn.

**Cách giảm rủi ro:** Bản white paper của Satoshi Nakamoto khuyến nghị dùng **một cặp khóa mới cho mỗi giao dịch** để các giao dịch không bị gom về một chủ sở hữu chung [1]. Điều này giống việc viết mỗi cuốn sách dưới một bút danh khác nhau. Ví hiện đại tự động làm việc này.

> 💡 **Giả danh ≠ ẩn danh.** Toàn bộ giao dịch Bitcoin là **công khai** trên blockchain. Các công ty phân tích blockchain có thể gom nhóm địa chỉ để suy ra danh tính. Vì vậy Bitcoin thường được mô tả là _pseudonymous_, không phải _anonymous_ [1][3].

### 2.2. Địa chỉ Bitcoin là gì?

- Địa chỉ Bitcoin được tạo ra từ **public key**. Public key được sinh bằng **ECDSA** (Elliptic Curve Digital Signature Algorithm — thuật toán chữ ký số dùng đường cong elliptic, đường cong `secp256k1`) [3].
- Cụ thể hơn: địa chỉ **không phải là public key nguyên bản**, mà là kết quả **băm (hash)** của public key (SHA-256 rồi RIPEMD-160, gọi là _HASH160_), sau đó mã hóa thành chuỗi dễ đọc (Base58Check hoặc Bech32) [3][4][7].
- Một ví có thể chứa **rất nhiều địa chỉ**.

**Ví dụ minh họa bằng Golang** — sinh cặp khóa và địa chỉ (cài thư viện: `go get github.com/btcsuite/btcd/btcec/v2 github.com/btcsuite/btcd/btcutil github.com/btcsuite/btcd/chaincfg`) [6]:

```go
package main

import (
	"fmt"

	"github.com/btcsuite/btcd/btcec/v2"
	"github.com/btcsuite/btcd/btcutil"
	"github.com/btcsuite/btcd/chaincfg"
)

func main() {
	// 1. Sinh private key (số ngẫu nhiên trên đường cong secp256k1)
	priv, err := btcec.NewPrivateKey()
	if err != nil {
		panic(err)
	}

	// 2. Suy ra public key từ private key (chỉ đi một chiều)
	pub := priv.PubKey()

	// 3. Băm public key: RIPEMD160(SHA256(pubkey))
	pubKeyHash := btcutil.Hash160(pub.SerializeCompressed())

	// 4. Mã hóa thành địa chỉ SegWit (Bech32, bắt đầu bằng "bc1")
	addr, err := btcutil.NewAddressWitnessPubKeyHash(pubKeyHash, &chaincfg.MainNetParams)
	if err != nil {
		panic(err)
	}

	fmt.Println("Địa chỉ:", addr.EncodeAddress())
}
```

> **Vì sao băm public key mà không dùng thẳng?** (1) Địa chỉ ngắn hơn, (2) thêm một lớp bảo vệ: public key chỉ lộ ra khi bạn chi tiêu coin.

## 3. UTXO — Đơn vị cơ bản của giao dịch Bitcoin / Unspent Transaction Output

### 3.1. Khái niệm

**UTXO** (_Unspent Transaction Output_ — đầu ra giao dịch chưa chi tiêu) là **đơn vị cơ bản** của Bitcoin. Bitcoin **không lưu "số dư tài khoản"** như ngân hàng; "số dư" của bạn thực chất là **tổng giá trị các UTXO** thuộc về bạn [2][3].

**Phép so sánh:** UTXO giống những **tờ tiền mệnh giá khác nhau** trong ví. Muốn trả 15 nghìn mà chỉ có tờ 20 nghìn, bạn đưa tờ 20 nghìn và nhận lại 5 nghìn tiền thối. Điểm khác tiền giấy: Bitcoin chia nhỏ được (đơn vị nhỏ nhất là **satoshi** = 0,00000001 BTC).

![UTXO](https://i.ibb.co/Y4NtzKvq/image.png)

### 3.2. Ví dụ có số liệu

Ross muốn gửi **0,15 BTC** cho Joey. Ví của Ross có 3 UTXO: **0,2 BTC**, **0,1 BTC** và **3 BTC** (tổng **3,3 BTC**).

1. Ross chọn UTXO **0,2 BTC** làm input (0,1 BTC không đủ, còn 3 BTC thì thừa quá nhiều).
2. UTXO 0,2 BTC bị **"tiêu hủy"** (đánh dấu đã chi tiêu hoàn toàn — không thể dùng lại).
3. Giao dịch tạo **2 output mới**: **0,15 BTC** cho Joey và **0,05 BTC** quay về ví Ross (**tiền thối / change**).
4. Số dư mới của Ross: 0,1 + 3 + 0,05 = **3,15 BTC** (chưa tính phí giao dịch).

### 3.3. Mô phỏng UTXO bằng Golang

Ví dụ đơn giản (dùng đơn vị satoshi, kiểu số nguyên để tránh sai số số thực; bỏ qua phí giao dịch và chữ ký):

```go
package main

import (
	"errors"
	"fmt"
)

// UTXO: một "tờ tiền" chưa chi tiêu
type UTXO struct {
	ID     string
	Amount int64 // đơn vị: satoshi (1 BTC = 100_000_000 satoshi)
}

// Spend chọn UTXO nhỏ nhất đủ trả, trả về (output cho người nhận, tiền thối, UTXO đã dùng)
func Spend(wallet []UTXO, amount int64) (paid, change int64, used UTXO, err error) {
	var best *UTXO
	for i := range wallet {
		if wallet[i].Amount >= amount && (best == nil || wallet[i].Amount < best.Amount) {
			best = &wallet[i]
		}
	}
	if best == nil {
		return 0, 0, UTXO{}, errors.New("không có UTXO đơn lẻ đủ lớn (thực tế sẽ gộp nhiều UTXO)")
	}
	return amount, best.Amount - amount, *best, nil
}

func main() {
	ross := []UTXO{
		{"utxo-a", 20_000_000},  // 0,2 BTC
		{"utxo-b", 10_000_000},  // 0,1 BTC
		{"utxo-c", 300_000_000}, // 3 BTC
	}

	paid, change, used, err := Spend(ross, 15_000_000) // gửi 0,15 BTC
	if err != nil {
		panic(err)
	}
	fmt.Printf("Dùng %s (%d sat) -> Joey nhận %d sat, Ross nhận lại %d sat\n",
		used.ID, used.Amount, paid, change)
}
```

> Đây chỉ là mô phỏng để học. Ví thực tế còn phải gộp nhiều UTXO khi cần, tính phí và dùng các thuật toán chọn coin (_coin selection_) phức tạp hơn.

## 4. Cấu trúc giao dịch Bitcoin / Bitcoin Transaction Structure

Một giao dịch gồm **input** và **output** [2]:

1. **Input (đầu vào):** tham chiếu tới **UTXO** mà người gửi từng nhận trước đó và chưa chi tiêu, kèm **chữ ký** chứng minh quyền sở hữu.
2. **Output (đầu ra):** mỗi output gồm **số tiền (amount)** và **điều kiện khóa** (thường gắn với địa chỉ người nhận). Một giao dịch có thể có **nhiều output**:
    - Output cho **người nhận**.
    - Output **tiền thối** quay về địa chỉ của người gửi — trở thành UTXO mới của người gửi.
3. **Phí giao dịch (fee)** = tổng input − tổng output. Phí không phải một output riêng; thợ đào (miner) nhận phần chênh lệch này [2].

![Transaction structure](https://i.ibb.co/fGnBN93m/image.png)

> . Thực tế: người gửi **ký (sign)** giao dịch bằng **private key của mình**; mọi người dùng **public key của người gửi** để **xác minh chữ ký**. Địa chỉ người nhận (dẫn xuất từ public key của họ) chỉ được dùng để **khóa output**.

## 5. Giao dịch dạng Input – Output (kế toán kép) / Inputs and Outputs

Cấu trúc giao dịch Bitcoin giống **kế toán kép** (double-entry bookkeeping): tiền đi vào bằng tiền đi ra (cộng phí). Chuỗi giao dịch có thể biểu diễn như một dãy input/output nối tiếp nhau.

![Input output](https://i.ibb.co/gqWCJ1D/image.png)

**Ví dụ:** Ross nhận 100 BTC. Ross gửi **40 BTC** cho Rachel và **60 BTC** cho Joey.

- Giao dịch của Ross có **1 input** (100 BTC) và **2 output** (40 và 60).
- Sau đó Rachel gửi **30 BTC** cho Mark: input là UTXO 40 BTC của Rachel, output là 30 BTC cho Mark và **10 BTC tiền thối** về Rachel. Quá trình này tiếp diễn trên toàn blockchain.

> Ví dụ này bỏ qua phí giao dịch cho đơn giản; thực tế tổng output luôn nhỏ hơn tổng input một chút.

## 6. Quy trình một giao dịch mẫu / A Sample Transaction

Kịch bản: **Ross gửi 5 BTC cho Joey.**

![Transaction flow](https://i.ibb.co/P0BMVNR/image.png)

1. **Joey** chia sẻ **địa chỉ** của mình cho Ross.
2. **Ross** tạo thông điệp giao dịch, ghi địa chỉ Joey và số tiền 5 BTC.
3. Ross **ký** giao dịch bằng **private key** của mình; chữ ký cùng public key của Ross được đính kèm để mạng **xác minh**.
4. Ross **phát (broadcast)** giao dịch lên mạng Bitcoin. Các node kiểm tra và đưa giao dịch vào khối mới do thợ đào tạo ra.

**Ví dụ ký và xác minh bằng Golang** (minh họa ý tưởng bước 3; thực tế Bitcoin ký trên hash của một cấu trúc dữ liệu giao dịch chuẩn, không phải chuỗi văn bản tùy ý):

```go
package main

import (
	"crypto/sha256"
	"fmt"

	"github.com/btcsuite/btcd/btcec/v2"
	"github.com/btcsuite/btcd/btcec/v2/ecdsa"
)

func main() {
	rossPriv, _ := btcec.NewPrivateKey()
	rossPub := rossPriv.PubKey()

	// Nội dung giao dịch (đơn giản hóa)
	tx := []byte("Ross -> Joey: 5 BTC")
	hash := sha256.Sum256(tx)

	// Ross ký bằng private key
	sig := ecdsa.Sign(rossPriv, hash[:])

	// Bất kỳ node nào cũng xác minh được bằng public key của Ross
	fmt.Println("Chữ ký hợp lệ:", sig.Verify(hash[:], rossPub))

	// Nếu nội dung bị sửa, xác minh thất bại
	tampered := sha256.Sum256([]byte("Ross -> Joey: 500 BTC"))
	fmt.Println("Sau khi sửa nội dung:", sig.Verify(tampered[:], rossPub))
}
```

## 7. Vấn đề chi tiêu hai lần / The Double Spending Problem

### 7.1. Vấn đề

**Double spending** là việc **dùng cùng một khoản Bitcoin trong nhiều giao dịch**. Ví dụ: Joey có 5 BTC nhưng cố gửi 5 BTC cho Rachel **và** 5 BTC cho Monica. Với tiền số, đây là rủi ro đặc biệt vì dữ liệu có thể bị sao chép dễ dàng [1][5].

![Double spending](https://i.ibb.co/bj0txp4g/image.png)

### 7.2. Blockchain ngăn chặn như thế nào?

![Prevent double spending](https://i.ibb.co/cKthPYmD/image.png)

- **Phát giao dịch tới mọi node:** giao dịch được broadcast cho toàn mạng.
- **Sổ cái phân tán (distributed ledger):** mỗi node giữ **bản sao riêng** của blockchain đang liên tục dài ra.
- **Chống sửa đổi:** mỗi khối chứa hash của khối trước. Sửa một khối buộc phải **tính lại toàn bộ các khối sau nó** (với Proof-of-Work, việc này đòi hỏi lượng công việc tính toán khổng lồ) và phải thuyết phục đa số mạng chấp nhận chuỗi mới (**đồng thuận — consensus**) [1].
- **Ai cũng kiểm tra được:** bất kỳ node nào cũng có thể xác thực giao dịch, nên một UTXO đã bị tiêu thì giao dịch thứ hai dùng lại nó sẽ bị **từ chối** [5].

> Thực tế: nếu hai giao dịch xung đột cùng xuất hiện, chỉ một giao dịch được đưa vào chuỗi chính. Càng nhiều khối xác nhận phía sau (**confirmations**), giao dịch càng khó bị đảo ngược. Vì vậy người bán thường chờ vài confirmation với khoản tiền lớn [1][5].

**Ví dụ Golang minh họa nguyên lý "mỗi UTXO chỉ tiêu một lần":**

```go
package main

import "fmt"

type Ledger struct {
	spent map[string]bool // các UTXO đã bị tiêu
}

func NewLedger() *Ledger { return &Ledger{spent: map[string]bool{}} }

// Validate trả về lỗi nếu UTXO đã bị chi tiêu
func (l *Ledger) Validate(utxoID string) error {
	if l.spent[utxoID] {
		return fmt.Errorf("double spending: %s đã được chi tiêu", utxoID)
	}
	l.spent[utxoID] = true
	return nil
}

func main() {
	l := NewLedger()
	fmt.Println(l.Validate("joey-utxo-5btc")) // <nil>: gửi cho Rachel hợp lệ
	fmt.Println(l.Validate("joey-utxo-5btc")) // lỗi: gửi cho Monica bị từ chối
}
```

## 9. Nội dung mở rộng / Extended Content

1. **Mempool:** nơi các node giữ giao dịch đã nhận nhưng **chưa vào khối**. Giao dịch có phí cao thường được thợ đào chọn trước [2].
2. **Race attack & 51% attack:** các kịch bản tấn công double spending. 51% attack cần kiểm soát đa số sức mạnh băm của mạng nên rất tốn kém với Bitcoin [1][5].
3. **Script & loại địa chỉ:** output thực chất chứa một _script_ (ngôn ngữ lập trình đơn giản) quy định ai được chi tiêu. Các loại địa chỉ phổ biến: P2PKH (bắt đầu bằng `1`), P2SH (`3`), SegWit/Bech32 (`bc1…`), Taproot (`bc1p…`) [3][7].
4. **Mô hình tài khoản (account model) của Ethereum:** khác UTXO, Ethereum lưu số dư theo tài khoản. Hai mô hình có ưu/nhược điểm khác nhau (UTXO dễ xử lý song song, tài khoản dễ viết hợp đồng thông minh).
5. **Bài tập Golang gợi ý:** mở rộng mô phỏng ở mục 3.3 để (a) gộp nhiều UTXO khi không đủ, (b) tính phí, (c) kết hợp với chữ ký ở mục 6.
6. **Bảo mật:** không bao giờ chia sẻ private key hoặc cụm từ khôi phục (seed phrase). Mất private key = mất quyền kiểm soát coin.
