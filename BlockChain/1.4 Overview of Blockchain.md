## 1. Các thành phần của ứng dụng Blockchain / Blockchain Application Components

Một ứng dụng blockchain gồm **bốn thành phần logic** quan trọng [1]:

|#|Thành phần|Vai trò|
|---|---|---|
|1|**Node application** (ứng dụng nút)|Phần mềm mà mỗi máy tính muốn tham gia hệ sinh thái phải cài và chạy|
|2|**Shared ledger** (sổ cái dùng chung)|Cấu trúc dữ liệu được quản lý bên trong node application|
|3|**Consensus algorithm** (thuật toán đồng thuận)|Luật để cả mạng thống nhất một "cách nhìn" duy nhất về sổ cái|
|4|**Virtual machine** (máy ảo)|Môi trường thực thi các chỉ thị, ví dụ smart contract|

### 1.1 Node application

Mỗi máy tính kết nối Internet muốn tham gia một hệ sinh thái đều phải **cài phần mềm dành riêng cho hệ sinh thái đó** [1]. Với Bitcoin, đó là phần mềm nút Bitcoin; khi chạy nó, máy bạn tuân theo **bộ luật được viết sẵn trong mã nguồn** của phần mềm.

>Chính xác hơn, phần mềm tham chiếu là **Bitcoin Core**, vừa là **nút đầy đủ** (xác thực mọi khối và giao dịch), vừa **có kèm ví**. Hai chức năng này khác nhau: ví chỉ quản lý khóa riêng và tạo giao dịch, còn nút mới là thành phần kiểm tra luật [2].

### 1.2 Shared ledger

Sổ cái này nằm **bên trong** node application; khi ứng dụng chạy, bạn xem được nội dung của nó [1]. Mỗi hệ sinh thái chỉ có **một** sổ cái dùng chung, nhưng nhiều nút cùng giữ bản sao của nó (xem lại bài 1.3, mục _Distributed Ledger_).

### 1.3 Consensus algorithm

Đây là **"luật chơi"** để cả hệ sinh thái đi đến **một cách nhìn duy nhất** về sổ cái, và được cài đặt ngay trong node application [1]. Việc tham gia xây dựng đồng thuận cũng là cách xác định **trạng thái thế giới (world state)** của hệ sinh thái, tức là "bây giờ sổ cái nói gì". Các loại đồng thuận đã học: **Proof of Work, Proof of Stake, Proof of Elapsed Time, PBFT**.

### 1.4 Virtual machine

Máy ảo là một **sự trừu tượng hóa** của một cỗ máy thực thi chỉ thị, cũng được cài trong node application mà **mọi người tham gia đều chạy** [1]. Nó cho phép hệ sinh thái thực thi **nhiều hơn các giao dịch đơn giản**.

**Ví dụ thực tế:** **Ethereum Virtual Machine (EVM)** thực thi mã smart contract **theo cùng một cách trên mọi nút Ethereum**. Với cùng trạng thái trước đó và cùng tập giao dịch hợp lệ, EVM luôn tính ra **cùng một trạng thái mới** (tính xác định, deterministic). Đó là lý do mọi nút đều đồng ý với nhau về kết quả [3].

### 1.5 Phác thảo bằng Go / A Go Sketch

Bốn thành phần có thể ánh xạ gần như trực tiếp thành code Go (đây là phác thảo khái niệm, không phải client thật):

```go
package main

import "fmt"

// Shared ledger: dữ liệu mà các nút cùng giữ.
type Ledger struct {
	Blocks []string
}

// Consensus algorithm: luật quyết định khối nào được chấp nhận.
type Consensus interface {
	Accept(block string, ledger *Ledger) bool
}

// Virtual machine: thực thi chỉ thị để tính trạng thái mới.
type VM interface {
	Execute(tx string, state map[string]int) error
}

// Node application: gói cả ba thành phần trên.
type Node struct {
	Ledger    *Ledger
	Consensus Consensus
	VM        VM
}

func (n *Node) Receive(block string) {
	if n.Consensus.Accept(block, n.Ledger) {
		n.Ledger.Blocks = append(n.Ledger.Blocks, block)
	}
}

// Cài đặt tối giản để minh họa.
type AcceptAll struct{}

func (AcceptAll) Accept(string, *Ledger) bool { return true }

type NoopVM struct{}

func (NoopVM) Execute(string, map[string]int) error { return nil }

func main() {
	n := &Node{Ledger: &Ledger{}, Consensus: AcceptAll{}, VM: NoopVM{}}
	n.Receive("block-1")
	fmt.Println(len(n.Ledger.Blocks))
}
```

**Vì sao thiết kế bằng interface?** Mỗi blockchain chọn đồng thuận và VM khác nhau (ví dụ Bitcoin dùng PoW, Ethereum dùng PoS và EVM). Dùng `interface` cho phép thay từng thành phần mà không phải viết lại phần còn lại.

## 3. Khóa công khai và chữ ký số / Public Key and Digital Signature

### 3.1 Khái niệm

Chữ ký số dựa trên **một cặp khóa**:

- **Khóa riêng (private key):** bí mật, chỉ chủ sở hữu giữ; dùng để **ký**.
- **Khóa công khai (public key):** công bố cho mọi người; dùng để **kiểm tra chữ ký**.
- **Chữ ký số (digital signature):** dữ liệu sinh ra từ _(nội dung giao dịch + khóa riêng)_. Ai có khóa công khai cũng kiểm tra được chữ ký có thật sự do chủ khóa riêng tạo ra hay không, và nội dung có bị sửa sau khi ký hay không.
- **Địa chỉ (address):** thường là **hash của khóa công khai** (có rút gọn). Đây là "số tài khoản" người khác dùng để chuyển tiền cho bạn.

**Ví dụ đời thực:** Khóa riêng giống **con dấu cá nhân**, chữ ký số giống **dấu đóng trên hợp đồng**, khóa công khai giống **mẫu dấu lưu ở ngân hàng** để ai cũng đối chiếu được.

### 3.2 Ví dụ Go: ký và kiểm tra giao dịch

```go
type Tx struct {
	From, To string // địa chỉ = hash của public key (rút gọn)
	Amount   int
}

func (t Tx) Digest() [32]byte {
	return sha256.Sum256([]byte(t.From + "|" + t.To + "|" + strconv.Itoa(t.Amount)))
}

func Address(pub *ecdsa.PublicKey) string {
	b := elliptic.MarshalCompressed(pub.Curve, pub.X, pub.Y)
	h := sha256.Sum256(b)
	return hex.EncodeToString(h[:])[:16]
}

func partA() {
	priv, _ := ecdsa.GenerateKey(elliptic.P256(), rand.Reader)
	addr := Address(&priv.PublicKey)

	tx := Tx{From: addr, To: "bob", Amount: 5}
	d := tx.Digest()
	sig, _ := ecdsa.SignASN1(rand.Reader, priv, d[:])
	fmt.Println("chu ky hop le:", ecdsa.VerifyASN1(&priv.PublicKey, d[:], sig))

	tx.Amount = 500 // kẻ gian sửa số tiền
	d2 := tx.Digest()
	fmt.Println("sau khi sua  :", ecdsa.VerifyASN1(&priv.PublicKey, d2[:], sig))
}
```

Kết quả thực tế:

```text
chu ky hop le: true
sau khi sua  : false
```

**Phân tích:**

- Giao dịch được băm trước rồi mới ký, nên **chỉ cần sửa 1 ký tự** (ở đây là số tiền 5 → 500) thì chữ ký không còn hợp lệ.
- Chỉ người có **khóa riêng** mới tạo được chữ ký hợp lệ, nên không ai mạo danh bạn được.

> **Lưu ý kỹ thuật:** Ví dụ dùng đường cong **P-256** vì có sẵn trong thư viện chuẩn Go (`crypto/ecdsa`). Bitcoin dùng đường cong khác (**secp256k1**) và định dạng địa chỉ riêng (Base58/Bech32); muốn dùng secp256k1 trong Go cần thư viện ngoài. Địa chỉ ở đây chỉ là bản rút gọn để minh họa.

## 5. Kiểm tra kiến thức / Knowledge Check

**Câu 1.** Thuật toán đồng thuận nào đạt hiệu quả nhờ định hướng thông điệp ngang hàng (peer-to-peer) với độ trễ tối thiểu? **Đáp án:** Practical Byzantine Fault Tolerance (PBFT). **Giải thích:** PBFT hoạt động bằng **trao đổi thông điệp giữa các nút** (pre-prepare → prepare → commit) và chốt kết quả ngay khi đủ phiếu, không cần "đào" hay đặt cọc (xem bài 1.3, mục 1.3).

**Câu 2.** Mã được tạo ra bằng cách lấy một đầu vào và biến đổi thành đầu ra mật mã bằng thuật toán toán học là gì? **Đáp án:** Hash (mã băm). **Giải thích:** Blockchain dùng hàm băm mật mã (như SHA-256) trong các cơ chế như Proof of Work. _Lưu ý:_ "hash code" trong lập trình thông thường (ví dụ bảng băm) khác với hash mật mã; xem bài 1.2.

**Câu 3.** Miner là gì? **Đáp án:** Một **nút (node)** xử lý và xác thực các giao dịch blockchain. **Giải thích:** Miner xác thực giao dịch, gom vào khối và thực hiện Proof of Work để khối được chấp nhận. _Chỉnh lại:_ đáp án gốc nói "ứng dụng" (application); chính xác hơn miner là **người tham gia/nút** chạy phần mềm đó, và chỉ có trong các mạng PoW.

**Câu 4.** Thuật toán nào tránh tiêu tốn tài nguyên bằng cơ chế "xổ số"? **Đáp án:** Proof of Elapsed Time (PoET). **Giải thích:** Mỗi nút chờ một thời gian ngẫu nhiên; nút thức dậy đầu tiên được tạo khối. Cần **môi trường thực thi tin cậy (Intel SGX)** để chống gian lận về thời gian chờ (bài 1.3, mục 1.2).

**Câu 5.** Giá trị được chọn sao cho hash của khối có chuỗi số 0 đứng đầu gọi là gì? **Đáp án:** Nonce. **Giải thích:** Nonce (_number used once_) là giá trị miner thay đổi cho tới khi hash khối thỏa điều kiện. _Chỉnh lại:_ đề gốc gọi là "số ngẫu nhiên"; thực tế miner thường **tăng dần** nonce (0, 1, 2, ...) chứ không nhất thiết chọn ngẫu nhiên.

**Câu 6.** Trong bốn thành phần logic của ứng dụng blockchain, thành phần nào cho phép chạy smart contract? **Đáp án:** Virtual machine (ví dụ EVM của Ethereum) [3].

**Câu 7.** Bạn sửa dữ liệu của một khối ở giữa chuỗi. Điều gì xảy ra với các khối sau nó? **Đáp án:** Hash của khối bị sửa đổi, `PrevHash` của khối kế tiếp không còn khớp, nên **các khối sau đều không hợp lệ** cho tới khi được đào lại.

## 6. Dự án cuối bài: Mạng Blockchain / Lesson-End Project: Blockchain Network

### 6.1 Đề bài / Problem Statement

Bạn là nhân viên của một công ty và được giao nhiệm vụ **tạo một mạng blockchain để minh họa cách blockchain hoạt động**.

**Bước 4.** Tiếp tục thêm peer và khối tương tự để hình thành mạng blockchain.

## 7. Mô phỏng bằng Go / Simulating the Project in Go

Để hiểu rõ hơn trang demo hoạt động thế nào bên trong, ta mô phỏng lại bằng Go: mỗi peer có một chuỗi, sửa dữ liệu làm khối bị "đỏ", đào lại thì hợp lệ, và peer mới **đồng bộ** từ peer có chuỗi hợp lệ dài hơn.

```go
const prefix = "000"

type Block struct {
	Name     string
	Data     string
	PrevHash string
	Nonce    int
	Hash     string
}

func (b *Block) Calc() string {
	s := b.Name + b.Data + b.PrevHash + strconv.Itoa(b.Nonce)
	h := sha256.Sum256([]byte(s))
	return hex.EncodeToString(h[:])
}

func (b *Block) Mine() {
	b.Nonce = 0
	for {
		b.Hash = b.Calc()
		if strings.HasPrefix(b.Hash, prefix) {
			return
		}
		b.Nonce++
	}
}

type Peer struct {
	Name  string
	Chain []*Block
}

func NewPeer(name string) *Peer {
	g := &Block{Name: "GENESIS BLOCK", Data: "Welcome", PrevHash: "0"}
	g.Mine()
	return &Peer{Name: name, Chain: []*Block{g}}
}

func (p *Peer) AddBlock(data string) {
	prev := p.Chain[len(p.Chain)-1]
	b := &Block{Name: fmt.Sprintf("BLOCK #%d", len(p.Chain)), Data: data, PrevHash: prev.Hash}
	b.Mine()
	p.Chain = append(p.Chain, b)
}

// Edit sửa Data rồi tính lại hash nhưng KHÔNG đào lại (giống khi gõ vào ô Data).
func (p *Peer) Edit(i int, data string) {
	p.Chain[i].Data = data
	p.Chain[i].Hash = p.Chain[i].Calc()
}

// Remine tương đương bấm nút đào lại: cập nhật PrevHash rồi đào.
func (p *Peer) Remine(i int) {
	p.Chain[i].PrevHash = p.Chain[i-1].Hash
	p.Chain[i].Mine()
}

// Status trả về trạng thái hợp lệ ("ok") hay lý do lỗi cho từng khối.
func (p *Peer) Status() []string {
	out := make([]string, len(p.Chain))
	for i, b := range p.Chain {
		switch {
		case b.Hash != b.Calc() || !strings.HasPrefix(b.Hash, prefix):
			out[i] = "DO (hash khong hop le)"
		case i > 0 && b.PrevHash != p.Chain[i-1].Hash:
			out[i] = "DO (sai PrevHash)"
		default:
			out[i] = "ok"
		}
	}
	return out
}

func (p *Peer) Valid() bool {
	for _, s := range p.Status() {
		if s != "ok" {
			return false
		}
	}
	return true
}

// Sync: nhận chuỗi của peer khác nếu nó hợp lệ và dài hơn.
func (p *Peer) Sync(other *Peer) bool {
	if other.Valid() && len(other.Chain) > len(p.Chain) {
		p.Chain = make([]*Block, len(other.Chain))
		for i, b := range other.Chain {
			c := *b
			p.Chain[i] = &c
		}
		return true
	}
	return false
}
```

Kịch bản chạy:

```go
a := NewPeer("Peer A")
a.AddBlock("Alice -> Bob: 5")
a.AddBlock("Bob -> Carol: 2")
a.AddBlock("Carol -> Dave: 1")
fmt.Println("A:", a.Status())

a.Edit(1, "Alice -> Bob: 500")
fmt.Println("A sau khi sua BLOCK #1:", a.Status())

a.Remine(1)
a.Remine(2)
a.Remine(3)
fmt.Println("A sau khi dao lai    :", a.Status())

b := NewPeer("Peer B")
b.AddBlock("Peer B only")
fmt.Println("B dong bo tu A:", b.Sync(a), "| do dai B:", len(b.Chain), "| hop le:", b.Valid())
```

Kết quả thực tế:

```text
A: [ok ok ok ok]
A sau khi sua BLOCK #1: [ok DO (hash khong hop le) DO (sai PrevHash) ok]
A sau khi dao lai    : [ok ok ok ok]
B dong bo tu A: true | do dai B: 4 | hop le: true
```

**Phân tích và lý do thiết kế:**

- **`Edit` chỉ tính lại hash mà không đào lại:** giống thao tác gõ vào ô _Data_; hash mới không còn bắt đầu bằng `000` nên khối bị đỏ ("hash không hợp lệ").
- **Khối kế tiếp báo "sai PrevHash":** vì `PrevHash` của nó vẫn trỏ tới hash _cũ_ của khối vừa sửa. Đây là hash pointer đang hoạt động.
- **Vì sao BLOCK #3 vẫn "ok" ở bước 2?** Trong mô phỏng, hash lưu sẵn của BLOCK #2 chưa đổi nên BLOCK #3 vẫn khớp. Hiệu ứng "đỏ lan tới cuối chuỗi" xuất hiện khi BLOCK #2 được đào lại và hash của nó thay đổi. Trang demo thể hiện theo cách khác (đỏ ngay cả BLOCK #3), nhưng nguyên lý giống nhau.
- **`Sync` chọn chuỗi hợp lệ và dài hơn:** đây là phiên bản rất đơn giản của quy tắc "chọn chuỗi tốt nhất". Bitcoin thật chọn chuỗi có **tổng công việc tích lũy lớn nhất** [4], không chỉ đếm số khối.

## 8. Nội dung mở rộng / Extended Topics

### 8.1 Blockchain như một cỗ máy trạng thái / Blockchain as a State Machine

Ethereum thường được mô tả là **cỗ máy trạng thái phân tán** (distributed state machine): trạng thái chứa mọi tài khoản và số dư, và EVM định nghĩa luật chuyển từ trạng thái cũ sang trạng thái mới khi có giao dịch hợp lệ [3]. Cách nhìn này giúp hiểu "world state" ở mục 1.3: sổ cái là lịch sử các thay đổi, còn trạng thái là kết quả hiện tại.

### 8.2 Nút đầy đủ, nút nhẹ và ví

|Loại|Làm gì|Ví dụ|
|---|---|---|
|**Full node**|Tải và xác thực toàn bộ khối, giao dịch|Bitcoin Core [2]|
|**Light client**|Chỉ tải header khối, dùng Merkle proof để kiểm tra (bài 1.3, mục 3.4 và 8.2)|Ví trên điện thoại|
|**Ví (wallet)**|Giữ khóa riêng, ký giao dịch|Có thể là phần của full node hoặc ứng dụng độc lập|

### 8.3 Các mạng khác nhau, máy ảo khác nhau

Bitcoin chỉ hỗ trợ một ngôn ngữ kịch bản giới hạn cho giao dịch (Bitcoin Script), còn Ethereum có **EVM** chạy được smart contract phức tạp hơn nhiều [3]. Chính vì vậy Ethereum được xem là nền tảng lập trình hợp đồng thông minh.

> _Ghi chú:_ Nhận định về Bitcoin Script là kiến thức chung, tôi chưa mở nguồn riêng để kiểm chứng trong phiên làm việc này.

### 8.4 Thử thêm demo trực quan

Nếu muốn xem một bản demo nổi tiếng khác, hãy tìm **"Blockchain 101 – A Visual Demo"** của Anders Brownworth: demo này minh họa SHA-256, khối, đào, chuỗi khối, sổ cái phân tán và cả giao dịch token [5].

### 8.5 Bài tập gợi ý

1. Chạy mô phỏng ở mục 7, thêm hàm `Fork()` tạo hai chuỗi khác nhau từ một khối chung, rồi cho hai peer `Sync` lẫn nhau. Quan sát chuỗi nào thắng.
2. Mở rộng `Block` để chứa danh sách giao dịch **có chữ ký** (mục 3). Khi thêm khối, kiểm tra chữ ký từng giao dịch và từ chối giao dịch sai.
3. Thay `prefix` từ `"000"` thành `"0000"` và `"00000"`, đo thời gian `AddBlock`. Độ khó tăng như thế nào?
4. Thêm một interface `Consensus` thật (ví dụ PoW và "chấp nhận mọi khối") vào phác thảo ở mục 1.5 rồi hoán đổi giữa hai cách.
