# Error Handling trong Go: Panic, Recover và Chiến lược Xử lý Lỗi

---

### Panic và Recover (Dành cho lỗi nghiêm trọng)

`panic` được dùng khi chương trình gặp tình huống không thể phục hồi và không nên tiếp tục thực thi — ví dụ: vi phạm bất biến nội bộ (invariant violation), lỗi lập trình (index out of range, nil pointer dereference), hoặc thiếu tài nguyên bắt buộc ngay khi khởi động (không kết nối được database lúc boot). `recover` dùng để bắt một `panic` đang lan truyền, thường tại biên hệ thống (ví dụ: middleware HTTP), để chương trình không bị sập hoàn toàn.

Nguyên tắc: **ưu tiên trả về `error` thông thường** cho mọi tình huống lỗi có thể dự đoán. `panic`/`recover` không phải cơ chế thay thế cho `try/catch`.

---

### Cơ chế dòng chảy bất thường

#### `defer`

`defer` đăng ký một lời gọi hàm để thực thi ngay trước khi hàm hiện tại kết thúc (return bình thường hoặc panic). Dùng để:

- Giải phóng tài nguyên: đóng file, đóng kết nối, unlock mutex.
- Đảm bảo cleanup luôn chạy dù hàm thoát theo nhánh nào.

**Thứ tự thực thi:** LIFO (Last In, First Out) — `defer` đăng ký sau sẽ chạy trước.

```go
func readFile(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close() // luôn chạy khi readFile kết thúc

    // xử lý file...
    return nil
}
```

**Lưu ý:** Tham số truyền vào hàm defer được đánh giá (evaluate) ngay tại thời điểm gọi `defer`, không phải lúc thực thi. Biến return có tên (named return) có thể bị `defer` thay đổi giá trị.

```go
func double(n int) (result int) {
    defer func() { result *= 2 }() // thay đổi named return
    result = n
    return // trả về n*2, không phải n
}
```

#### `panic`

`panic` dừng ngay luồng thực thi hiện tại, bắt đầu unwind stack, và chạy tất cả các `defer` đã đăng ký theo thứ tự LIFO. Nếu không có `recover` nào bắt được, chương trình in stack trace và thoát.

**Khi nào nên dùng `panic`:**

- Lỗi lập trình không thể phục hồi: index out of range, nil dereference (runtime tự panic).
- Vi phạm bất biến nội bộ của package: dữ liệu bị corrupt, trạng thái không hợp lệ không thể tiếp tục.
- Lỗi bootstrap: thiếu cấu hình bắt buộc, không thể khởi tạo dependency cốt lõi khi start.

**Vì sao không dùng `panic` cho lỗi nghiệp vụ thông thường:**

- Không thể xử lý cục bộ (caller không thể quyết định cách phản hồi).
- Phá vỡ contract của hàm — caller trông đợi `(value, error)`, không trông đợi chương trình sập.
- Khó test và debug hơn so với `error` thông thường.

---
#### `recover`

`recover` chỉ có tác dụng khi được gọi **bên trong một hàm `defer`**. Nó bắt giá trị được truyền vào `panic` và dừng quá trình unwind stack. Ngoài `defer`, `recover()` luôn trả về `nil` và không có tác dụng.

```go
func safeHandler(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                log.Printf("recovered panic: %v\n%s", rec, debug.Stack())
                http.Error(w, "Internal Server Error", http.StatusInternalServerError)
            }
        }()
        next(w, r)
    }
}
```

**Giới hạn của `recover`:**

- Chỉ bắt được `panic` trong cùng goroutine. Một goroutine con bị panic mà không có `recover` sẽ làm sập toàn bộ chương trình.
- Không nên dùng `recover` như cơ chế xử lý lỗi thường ngày — chỉ dùng tại biên hệ thống (HTTP middleware, worker pool, top-level goroutine).

### Phân loại và thiết kế lỗi trong dự án

#### Sentinel Error

Sentinel error là giá trị lỗi cố định được khai báo ở cấp package, dùng để so sánh bằng identity.

```go
var ErrNotFound = errors.New("not found")
var ErrPermissionDenied = errors.New("permission denied")
```

**Khi nào nên dùng:**

- Lỗi được caller kiểm tra trực tiếp (`if err == ErrNotFound`), hoặc dùng với `errors.Is()`.
- Số lượng trạng thái lỗi hữu hạn, không cần mang thêm dữ liệu.

**Khi nào không nên lạm dụng:**

- Khi lỗi cần kèm ngữ cảnh (ID, path, query...) — dùng typed error thay thế.
- Khi sentinel error bị export từ package internal — tạo coupling không cần thiết giữa package.

```go
// So sánh sentinel error
if errors.Is(err, ErrNotFound) {
    // xử lý không tìm thấy
}
```

---

#### Typed Error (Lỗi có kiểu)

Typed error là struct hoặc kiểu tùy chỉnh implement interface `error`, cho phép mang thêm dữ liệu để caller xử lý chi tiết hơn.

```go
type ValidationError struct {
    Field   string
    Message string
}

func (e *ValidationError) Error() string {
    return fmt.Sprintf("validation failed on field %q: %s", e.Field, e.Message)
}

// Dùng errors.As để lấy thông tin chi tiết
var valErr *ValidationError
if errors.As(err, &valErr) {
    fmt.Println("Field lỗi:", valErr.Field)
}
```

**Dùng khi:** lỗi cần mang thêm metadata (field, code, path, HTTP status...) để caller xử lý theo từng trường hợp cụ thể.

#### Domain Error / Business Error

Tách lỗi thành hai lớp:

- **Lỗi kỹ thuật (technical error):** lỗi I/O, database, network — không nên lộ ra ngoài.
- **Lỗi nghiệp vụ (business/domain error):** vi phạm quy tắc nghiệp vụ — cần thông báo rõ ràng cho layer trên hoặc người dùng.

```go
type DomainError struct {
    Code    string // mã lỗi nghiệp vụ, ví dụ: "INSUFFICIENT_BALANCE"
    Message string // thông báo an toàn cho client
}

func (e *DomainError) Error() string {
    return fmt.Sprintf("[%s] %s", e.Code, e.Message)
}

// Tại service layer: map lỗi kỹ thuật thành domain error
func (s *PaymentService) Transfer(from, to string, amount float64) error {
    if err := s.repo.Debit(from, amount); err != nil {
        if errors.Is(err, repo.ErrInsufficientFunds) {
            return &DomainError{Code: "INSUFFICIENT_BALANCE", Message: "Số dư không đủ"}
        }
        return fmt.Errorf("transfer failed: %w", err) // lỗi kỹ thuật, wrap lại
    }
    return nil
}
```

#### Lỗi từ thư viện chuẩn và hệ sinh thái

Các lỗi thường gặp và cách xử lý:

```go
// os / io
if errors.Is(err, os.ErrNotExist) { /* file không tồn tại */ }
if errors.Is(err, io.EOF)         { /* đọc hết dữ liệu */ }

// net
var netErr net.Error
if errors.As(err, &netErr) && netErr.Timeout() { /* timeout mạng */ }

// json
var syntaxErr *json.SyntaxError
if errors.As(err, &syntaxErr) {
    fmt.Println("JSON lỗi tại offset:", syntaxErr.Offset)
}

// context
if errors.Is(err, context.Canceled)         { /* request bị hủy */ }
if errors.Is(err, context.DeadlineExceeded) { /* quá thời gian chờ */ }
```

`context.Canceled` và `context.DeadlineExceeded` xuất hiện rất thường xuyên trong các service có giao tiếp mạng hoặc xử lý bất đồng bộ — cần xử lý riêng thay vì log như lỗi thông thường.

### Chiến lược xử lý lỗi chuẩn Go

#### 1. Return early / Guard clause

Trả lỗi ngay khi phát hiện, tránh lồng `if` nhiều tầng. Code hợp lệ nằm ở luồng chính (happy path), không bị chôn vùi trong các nhánh điều kiện.

```go
// Không nên
func process(data []byte) error {
    if data != nil {
        if len(data) > 0 {
            // xử lý...
        } else {
            return errors.New("empty data")
        }
    } else {
        return errors.New("nil data")
    }
    return nil
}

// Nên
func process(data []byte) error {
    if data == nil {
        return errors.New("nil data")
    }
    if len(data) == 0 {
        return errors.New("empty data")
    }
    // xử lý...
    return nil
}
```

---

#### 2. Không nuốt lỗi

Không dùng `_` để bỏ qua lỗi trừ khi có lý do rõ ràng và được comment giải thích. Nuốt lỗi che giấu sự cố và gây debug cực kỳ khó.

```go
// Sai
data, _ := io.ReadAll(r)

// Đúng
data, err := io.ReadAll(r)
if err != nil {
    return fmt.Errorf("đọc request body thất bại: %w", err)
}
```

---
#### 3. Log lỗi đúng chỗ

- **Log tại điểm xử lý cuối cùng** (entry point của request, top-level goroutine, main) — nơi có đầy đủ ngữ cảnh.
- **Chỉ return (wrap) lỗi** ở các layer bên dưới (repository, service) — không log lặp lại.
- Log lặp nhiều tầng làm noise và khó tìm root cause.

```go
// Repository layer — không log, chỉ wrap
func (r *UserRepo) FindByID(id int) (*User, error) {
    user, err := r.db.QueryRow(...)
    if err != nil {
        return nil, fmt.Errorf("UserRepo.FindByID id=%d: %w", id, err)
    }
    return user, nil
}

// Handler layer — log một lần tại đây
func (h *UserHandler) GetUser(w http.ResponseWriter, r *http.Request) {
    user, err := h.service.GetUser(id)
    if err != nil {
        log.Printf("GetUser: %v", err)
        http.Error(w, "Internal Server Error", 500)
        return
    }
    // ...
}
```

#### 4. Lỗi trong concurrency

Goroutine không thể trả `error` trực tiếp về caller. Các cách gom lỗi phổ biến:

**Dùng channel:**

```go
errc := make(chan error, 1)
go func() {
    errc <- doWork()
}()
if err := <-errc; err != nil {
    // xử lý
}
```

**Dùng `errgroup` (golang.org/x/sync/errgroup) — khuyến nghị:**

```go
g, ctx := errgroup.WithContext(context.Background())

g.Go(func() error { return fetchUser(ctx) })
g.Go(func() error { return fetchOrder(ctx) })

if err := g.Wait(); err != nil {
    // trả về lỗi đầu tiên xảy ra
}
```

**Dùng `errors.Join()` (Go 1.20+) khi cần gộp nhiều lỗi:**

```go
err1 := validateName(name)
err2 := validateAge(age)

if combined := errors.Join(err1, err2); combined != nil {
    return combined // chứa cả hai lỗi
}
```

### Câu hỏi phỏng vấn

**1. Go xử lý lỗi như thế nào? Có hỗ trợ try/catch không?**

Go không có try/catch/finally. Lỗi được trả về như giá trị thông thường qua multiple return values: `(result, error)`. Caller có trách nhiệm kiểm tra và xử lý lỗi ngay tại nơi gọi. Cách tiếp cận này buộc lỗi phải được xử lý tường minh, tránh bỏ sót lỗi ngầm như trong các ngôn ngữ dùng exception.

```go
result, err := doSomething()
if err != nil {
    return fmt.Errorf("context: %w", err) // wrap với %w để giữ chain
}
```

**2. Sự khác biệt giữa `defer`, `panic` và `recover`**

||`defer`|`panic`|`recover`|
|---|---|---|---|
|Mục đích|Đảm bảo cleanup luôn chạy|Dừng thực thi, báo lỗi không phục hồi|Bắt panic, ngăn crash|
|Thời điểm chạy|Trước khi hàm return|Ngay lập tức|Chỉ trong `defer`|
|Thường dùng cho|Đóng file, unlock, rollback|Lỗi lập trình, bootstrap failure|Middleware, worker boundary|

**3. `errors.Is()` và `errors.As()` khác nhau như thế nào?**

- `errors.Is(err, target)`: kiểm tra xem `err` (hoặc bất kỳ lỗi nào trong chain) có **bằng** `target` không. Dùng với sentinel error.
- `errors.As(err, &target)`: kiểm tra xem `err` có thể **ép kiểu** thành kiểu của `target` không. Dùng với typed error để lấy thông tin chi tiết.

Cả hai đều duyệt toàn bộ error chain (qua `Unwrap()`), không chỉ kiểm tra lớp ngoài cùng.

**4. Khi nào dùng `fmt.Errorf` với `%w` thay vì `%v`?**

- `%w`: wrap lỗi gốc vào lỗi mới, giữ nguyên error chain. Caller có thể dùng `errors.Is()` / `errors.As()` để inspect lỗi gốc.
- `%v`: chỉ in chuỗi mô tả lỗi gốc, **không** giữ error chain — lỗi gốc không thể unwrap.

Dùng `%w` khi caller cần phân biệt loại lỗi. Dùng `%v` khi lỗi gốc là chi tiết triển khai không cần expose ra ngoài.

**5. Làm thế nào để xử lý lỗi từ nhiều goroutine đồng thời?**

Dùng `errgroup` từ `golang.org/x/sync/errgroup`: quản lý vòng đời goroutine, tự động cancel context khi có lỗi, và trả về lỗi đầu tiên xảy ra. Nếu cần thu thập tất cả lỗi (không dừng sớm), dùng mutex hoặc channel để gom vào slice, rồi `errors.Join()`.

> Bổ sung: Bản gốc thiếu câu trả lời cho cả 2 câu hỏi có sẵn, và câu 3 để trống hoàn toàn. Đã viết đầy đủ 5 câu hỏi phỏng vấn thường gặp thực tế.

## Đề xuất mở rộng

Các nội dung dưới đây vượt ra ngoài phạm vi cơ bản của tài liệu nhưng có giá trị với developer đang làm dự án thực tế:

- **Structured logging với lỗi:** Dùng `slog` (Go 1.21+) hoặc `zap`/`zerolog` để log lỗi kèm context dạng key-value thay vì chuỗi thuần — dễ query hơn trên hệ thống log tập trung (ELK, Loki).
- **Error observability:** Tích hợp với Sentry hoặc OpenTelemetry để trace lỗi qua nhiều service trong hệ thống microservice.
- **Custom error interface với HTTP status:** Định nghĩa interface mở rộng `StatusCoder` để layer HTTP tự map domain error sang HTTP status code mà không cần switch-case thủ công.
- **`errors.Join` vs `multierr`:** `errors.Join` (stdlib Go 1.20+) phù hợp cho trường hợp đơn giản. `go.uber.org/multierr` cung cấp API phong phú hơn (append, combine) cho các usecase phức tạp.
