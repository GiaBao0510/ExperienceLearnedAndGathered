# Go Defer

Trong Go, từ khóa `defer` dùng để **trì hoãn việc thực thi** của một hàm, phương thức, hoặc hàm ẩn danh cho đến khi **hàm chứa nó kết thúc** — dù kết thúc bình thường hay do lỗi (panic).

Điểm quan trọng cần phân biệt ngay từ đầu:

- **Đối số** của hàm defer được **đánh giá (evaluate) ngay tại thời điểm gặp câu lệnh defer**.
- Nhưng **thân hàm** đó chỉ **thực thi khi hàm chứa nó trả về**.

## 1. Cú Pháp

```go
// Defer một hàm thông thường
defer funcName(args)

// Defer một phương thức
defer receiver.methodName(args)

// Defer một hàm ẩn danh (anonymous function)
defer func() {
    // code
}()
```

## 2. Hoạt Động Cơ Bản

### Ví dụ 1 — defer thực thi sau cùng

```go
package main

import "fmt"

func mul(a1, a2 int) int {
    res := a1 * a2
    fmt.Println(res)
    return 0
}

func show() {
    fmt.Println("Lập trình cùng tôi")
}

func main() {
    mul(5, 10)      // gọi bình thường, thực thi ngay
    defer mul(8, 10) // defer: đối số (8, 10) được ghi nhận ngay,
                     // nhưng thân hàm chạy sau khi main() kết thúc
    show()           // gọi bình thường, thực thi ngay
}
```

Output:

```
50
Lập trình cùng tôi
80
```

Luồng thực thi:

```
main() bắt đầu
  → mul(5, 10) chạy ngay     → in 50
  → defer mul(8, 10) đăng ký (chưa chạy)
  → show() chạy ngay         → in "Lập trình cùng tôi"
main() kết thúc
  → defer mul(8, 10) chạy   → in 80
```

## 3. Nhiều defer — Thứ Tự LIFO

Khi có nhiều câu lệnh `defer` trong cùng một hàm, chúng được thực thi theo thứ tự **LIFO (Last-In, First-Out)** — defer nào được đăng ký sau sẽ chạy trước. Cơ chế này giống như một **stack (ngăn xếp)**: lệnh defer cuối cùng được đẩy vào stack sẽ là lệnh đầu tiên được lấy ra thực thi.

### Ví dụ 2 — nhiều defer xếp chồng

```go
package main

import "fmt"

func mul(a1, a2 int) int {
    res := a1 * a2
    fmt.Println(res)
    return 0
}

func main() {
    defer mul(5, 10) // đăng ký thứ nhất  → chạy cuối cùng
    defer mul(6, 10) // đăng ký thứ hai   → chạy thứ hai
    defer mul(7, 10) // đăng ký thứ ba    → chạy đầu tiên

    fmt.Println("Hello World")
}
```

Output:

```
Hello World
70
60
50
```

Thứ tự stack defer:

```
Đăng ký:           Stack:          Thực thi:
defer mul(5,10) →  [mul(5,10)]
defer mul(6,10) →  [mul(5,10), mul(6,10)]
defer mul(7,10) →  [mul(5,10), mul(6,10), mul(7,10)]
main() kết thúc →  lấy ra lần lượt từ trên xuống:
                   mul(7,10) → 70
                   mul(6,10) → 60
                   mul(5,10) → 50
```

## 4. Đối Số Được Đánh Giá Ngay Lập Tức

Đây là điểm dễ nhầm lẫn nhất khi mới học `defer`. Đối số được tính toán **tại thời điểm gặp lệnh defer**, không phải tại thời điểm defer thực thi.

### Ví dụ 3 — minh họa thời điểm đánh giá đối số

```go
package main

import "fmt"

func main() {
    x := 10
    defer fmt.Println("Giá trị x trong defer:", x) // x được chốt = 10 ngay tại đây

    x = 99 // thay đổi x sau khi đã đăng ký defer
    fmt.Println("Giá trị x hiện tại:", x)
}
```

Output:

```
Giá trị x hiện tại: 99
Giá trị x trong defer: 10
```

Giải thích: tại thời điểm gặp lệnh `defer fmt.Println(...)`, Go lập tức tính toán và lưu lại giá trị `x = 10`. Dù sau đó `x` thay đổi thành `99`, defer vẫn dùng giá trị đã được chốt từ trước.

Nếu muốn defer đọc giá trị `x` tại thời điểm thực thi (không phải lúc đăng ký), dùng hàm ẩn danh để bắt giá trị theo tham chiếu:

```go
package main

import "fmt"

func main() {
    x := 10
    defer func() {
        fmt.Println("Giá trị x trong defer:", x) // đọc x tại thời điểm main() kết thúc
    }()

    x = 99
    fmt.Println("Giá trị x hiện tại:", x)
}
```

Output:

```
Giá trị x hiện tại: 99
Giá trị x trong defer: 99
```

## 5. Ứng Dụng Phổ Biến: Đóng Tài Nguyên

Một trong những use case phổ biến nhất của `defer` là **đảm bảo tài nguyên luôn được giải phóng** sau khi sử dụng xong — dù hàm kết thúc bình thường hay gặp lỗi.

### 5.1. Đóng file

```go
package main

import (
    "fmt"
    "os"
)

func readFile(filename string) error {
    file, err := os.Open(filename)
    if err != nil {
        return err
    }
    defer file.Close() // đảm bảo file luôn được đóng khi hàm kết thúc

    // xử lý file...
    fmt.Println("Đang đọc file:", filename)
    return nil
}

func main() {
    err := readFile("data.txt")
    if err != nil {
        fmt.Println("Lỗi:", err)
    }
}
```

Không có `defer`, lập trình viên dễ quên gọi `file.Close()` đặc biệt khi có nhiều nhánh `return` khác nhau. Với `defer`, dù hàm kết thúc ở nhánh nào, file cũng được đóng.

### 5.2. Unlock mutex

```go
package main

import (
    "fmt"
    "sync"
)

type SafeCounter struct {
    mu    sync.Mutex
    count int
}

func (c *SafeCounter) Increment() {
    c.mu.Lock()
    defer c.mu.Unlock() // đảm bảo mutex luôn được mở khóa

    c.count++
    fmt.Println("Count:", c.count)
}

func main() {
    counter := &SafeCounter{}
    counter.Increment()
    counter.Increment()
}
```

## 6. defer Và panic

### 6.1. defer vẫn chạy khi có panic

Khi chương trình gặp `panic`, Go vẫn thực thi tất cả các hàm defer đã được đăng ký trước đó trước khi dừng hẳn. Đây là cơ chế quan trọng để dọn dẹp tài nguyên ngay cả trong tình huống lỗi nghiêm trọng.

```go
package main

import (
    "fmt"
    "log"
)

func mul(a1, a2 int) int {
    res := a1 * a2
    fmt.Println(res)
    return 0
}

func main() {
    log.Println("Timeline 1")
    defer mul(5, 10)  // defer được đăng ký trước panic
    panic("Oh no Panic")
}
```

Output:

```
2026/05/11 21:59:49 Timeline 1
50
panic: Oh no Panic

goroutine 1 [running]:
main.main()
        main.go:20 +0xa5
exit status 2
```

Giải thích: dù chương trình panic, `defer mul(5, 10)` vẫn được thực thi (in ra `50`) trước khi Go in thông báo panic và thoát. Đây là lý do defer thường được dùng kết hợp với `recover` để xử lý panic một cách có kiểm soát.

### 6.2. Panic lan rộng nếu không xử lý

Khi một hàm panic mà không có cơ chế xử lý, panic sẽ **lan ngược lên call stack** cho đến khi gặp một defer+recover hoặc làm sập toàn bộ chương trình.

```go
package main

import "log"

func order() {
    log.Println("START API ORDER")
    sendEmail()
    sendSMS()           // không bao giờ được gọi vì sendEmail() đã panic
    log.Println("END API ORDER")
}

func sendEmail() {
    log.Println("START API SEND EMAIL")
    panic("sendEmail Error") // panic lan lên order() rồi lan lên main()
    log.Println("END API SEND EMAIL") // không bao giờ chạy
}

func sendSMS() {
    log.Println("START API SEND SMS")
    log.Println("END API SEND SMS")
}

func main() {
    log.Println("START API")
    order()
    log.Println("END API") // không bao giờ chạy
}
```

Output:

```
START API
START API ORDER
START API SEND EMAIL
panic: sendEmail Error

goroutine 1 [running]:
main.sendEmail()
        main.go:16 +0x86
main.order()
        main.go:9 +0x78
main.main()
        main.go:28 +0x78
exit status 2
```

Hệ quả: `sendSMS()` không được gọi, `END API ORDER` và `END API` không được in — toàn bộ quy trình bị gãy chỉ vì một lỗi không quan trọng (gửi email thất bại trong khi SMS vẫn có thể gửi được).

Nguyên tắc: chỉ dùng `panic` cho các lỗi **thực sự nghiêm trọng** mà chương trình không thể tiếp tục. Với các lỗi có thể phục hồi, dùng `error` là lựa chọn đúng đắn hơn.

## 7. defer Kết Hợp recover — Khôi Phục Sau Panic

`recover` là hàm built-in của Go dùng để **bắt và xử lý panic**, ngăn nó lan ra ngoài. `recover` **chỉ có hiệu lực khi được gọi bên trong một hàm defer**.

Bộ ba `defer` + `recover` + `panic` hoạt động như cơ chế try-catch của Go:

|Go|Ngôn ngữ khác|
|---|---|
|`panic`|`throw`|
|`recover` (trong defer)|`catch`|
|`defer`|`finally`|

```go
package main

import "log"

func order() {
    log.Println("START API ORDER")
    sendEmail()
    sendSMS() // vẫn được gọi vì panic đã được recover trong sendEmail()
    log.Println("END API ORDER")
}

func sendEmail() {
    log.Println("START API SEND EMAIL")

    defer func() {
        if r := recover(); r != nil {
            // bắt panic, ghi log và tiếp tục — không lan ra ngoài
            log.Println("NOTE: Recovered in sendEmail:", r)
        }
    }()

    panic("sendEmail Error")
    log.Println("END API SEND EMAIL") // không chạy, nhưng panic đã được bắt
}

func sendSMS() {
    log.Println("START API SEND SMS")
    log.Println("END API SEND SMS")
}

func main() {
    log.Println("START API")
    order()
    log.Println("END API")
}
```

Output:

```
START API
START API ORDER
START API SEND EMAIL
NOTE: Recovered in sendEmail: sendEmail Error
START API SEND SMS
END API SEND SMS
END API ORDER
END API
```

Nhờ `defer + recover` trong `sendEmail()`, panic được bắt và xử lý ngay tại chỗ. Quy trình đặt hàng tiếp tục hoàn tất bình thường — `sendSMS()` vẫn được gọi, `END API ORDER` và `END API` vẫn được in.

### Lưu ý khi dùng recover

`recover` chỉ bắt được panic nếu được đặt **trực tiếp trong hàm defer**. Đặt recover bên ngoài defer sẽ không có tác dụng:

```go
// SAI — recover không có tác dụng ở đây
func riskyFunc() {
    r := recover() // đặt ngoài defer, không bắt được panic
    defer fmt.Println(r)
    panic("lỗi")
}

// ĐÚNG — recover phải nằm trong thân hàm defer
func riskyFunc() {
    defer func() {
        if r := recover(); r != nil { // đặt trong defer, bắt được panic
            fmt.Println("Recovered:", r)
        }
    }()
    panic("lỗi")
}
```

## 8. Tổng Kết

| Khía cạnh                 | Nội dung                                                    |
| ------------------------- | ----------------------------------------------------------- |
| Thời điểm đăng ký         | Khi gặp câu lệnh `defer`                                    |
| Thời điểm thực thi        | Khi hàm chứa nó kết thúc (return hoặc panic)                |
| Đánh giá đối số           | Ngay tại thời điểm đăng ký, không phải lúc thực thi         |
| Thứ tự nhiều defer        | LIFO — defer cuối đăng ký, chạy trước tiên                  |
| Ứng dụng phổ biến         | Đóng file, unlock mutex, dọn dẹp tài nguyên                 |
| Kết hợp với panic/recover | Bắt và xử lý lỗi nghiêm trọng mà không làm sập chương trình |

> **Phần tiếp theo:** Chúng ta sẽ tìm hiểu về **Go panic và recover** — cơ chế xử lý lỗi nghiêm trọng trong Go, cách chúng phối hợp với `defer` để xây dựng chương trình ổn định.
