# Error Handling trong Go

Error handling (xử lý lỗi) là một chủ đề quan trọng được đề cập trong mọi ngôn ngữ lập trình. Go có cơ chế xử lý lỗi khác biệt so với `try/catch` trong các ngôn ngữ như Java hay Python: thay vì ném ngoại lệ, Go trả về lỗi như một giá trị trả về thông thường của hàm. Cơ chế này buộc người lập trình xử lý lỗi ngay tại nơi phát sinh, giúp luồng điều khiển trở nên tường minh và dễ đọc hơn.

---

## Triết lý xử lý lỗi trong Go

Trong Go, có hai khái niệm cần phân biệt rõ:

- **Error (lỗi có thể dự đoán):** Là các tình huống bất thường nhưng có thể xảy ra trong quá trình vận hành bình thường, ví dụ: file không tồn tại, kết nối mạng bị ngắt, dữ liệu không hợp lệ. Những tình huống này được xử lý thông qua giá trị `error` trả về.
- **Panic (ngoại lệ không thể dự đoán):** Là các tình huống nghiêm trọng chỉ ra lỗi lập trình (bug) hoặc trạng thái hệ thống không thể phục hồi, ví dụ: truy cập chỉ số ngoài phạm vi slice, nil pointer dereference. Go sử dụng `panic` và `recover` cho trường hợp này.

---
## Kiểu `error` trong Go

Trong Go, `error` là một built-in interface được khai báo trong universe block (phạm vi toàn cục của ngôn ngữ):

```go
type error interface {
    Error() string
}
```

Bất kỳ type nào triển khai phương thức `Error() string` đều thỏa mãn interface `error`. Đây là điểm khởi đầu để hiểu toàn bộ hệ thống xử lý lỗi trong Go.

---

## Cách tạo lỗi cơ bản

### Dùng `errors.New`

Package `errors` cung cấp hàm `New` để tạo lỗi đơn giản từ một chuỗi mô tả:

```go
// Bên trong package errors:
type errorString struct {
    s string
}

func (e *errorString) Error() string {
    return e.s
}

func New(text string) error {
    return &errorString{text}
}
```

Ví dụ dùng `errors.New` để tạo lỗi trong hàm tính căn bậc hai:

```go
func Sqrt(f float64) (float64, error) {
    if f < 0 {
        return 0, errors.New("math: square root of negative number")
    }
    // triển khai tính toán
}
```

Khi gặp lỗi, hàm trả về giá trị zero cho kết quả chính và giá trị lỗi có mô tả:

```shell
0 math: square root of negative number
```

Sử dụng hàm:

```go
f, err := Sqrt(-1)
if err != nil {
    fmt.Println(err) // Gọi err.Error() thông qua interface fmt.Stringer
}
```

### Dùng `fmt.Errorf` để thêm ngữ cảnh

Khi thông điệp lỗi cần chứa giá trị động, dùng `fmt.Errorf`:

```go
if f < 0 {
    return 0, fmt.Errorf("math: square root of negative number %g", f)
}
```

**Nguyên tắc quan trọng:** Thông báo lỗi phải chứa đủ ngữ cảnh để xác định nguồn gốc. Ví dụ: `os.Open` trả về lỗi `"open /etc/passwd: permission denied"` thay vì chỉ `"permission denied"` — người đọc log biết ngay file nào và lỗi gì xảy ra.

## Kiểm tra lỗi

### Kiểm tra cơ bản

Luôn kiểm tra `err` ngay lập tức sau lời gọi hàm. Không bỏ qua lỗi bằng cách gán vào `_`:

```go
file, err := os.Open("filename.txt")
if err != nil {
    log.Fatal(err)
}
// Tiếp tục dùng file
```

### Kiểm tra lỗi với giá trị boolean

Khi chỉ cần biết thao tác có thành công không (không cần chi tiết lỗi), dùng biến boolean `ok`:

```go
if v, ok := m["key"]; ok {
    return v
}
```

Cú pháp này phổ biến khi truy xuất giá trị từ map trong Go.

---

## Wrapping Errors — Bao bọc lỗi

Khi cần truyền lỗi lên tầng trên kèm thêm ngữ cảnh, dùng `fmt.Errorf` với verb `%w`. Cách này bảo toàn lỗi gốc bên trong lỗi mới, cho phép unwrap sau này:

```go
func readConfig(path string) error {
    data, err := os.ReadFile(path)
    if err != nil {
        return fmt.Errorf("readConfig: không đọc được file %s: %w", path, err)
    }
    // xử lý data
    return nil
}
```

Khi log lỗi, chuỗi đầy đủ sẽ là: `"readConfig: không đọc được file config.yaml: open config.yaml: no such file or directory"`.

## `errors.Is` và `errors.As`

Khi lỗi được bọc qua nhiều tầng (`%w`), cần dùng `errors.Is` và `errors.As` thay vì so sánh trực tiếp.

### `errors.Is` — Kiểm tra lỗi cụ thể

`errors.Is` duyệt toàn bộ chuỗi wrap để kiểm tra xem lỗi có khớp với một giá trị lỗi cụ thể không:

```go
var ErrNotFound = errors.New("không tìm thấy bản ghi")

func truyVanDB() error {
    return fmt.Errorf("truyVanDB: %w", ErrNotFound) // bọc lỗi
}

func main() {
    err := truyVanDB()
    if errors.Is(err, ErrNotFound) {
        fmt.Println("Xử lý riêng: không tìm thấy dữ liệu")
    }
}
```

### `errors.As` — Trích xuất loại lỗi cụ thể

`errors.As` duyệt chuỗi wrap để tìm và gán lỗi vào một biến có kiểu cụ thể, cho phép truy cập các trường dữ liệu bổ sung:

```go
type DBError struct {
    Code    int
    Message string
}

func (e *DBError) Error() string {
    return fmt.Sprintf("DB error %d: %s", e.Code, e.Message)
}

func main() {
    err := fmt.Errorf("lớp ngoài: %w", &DBError{Code: 404, Message: "record not found"})

    var dbErr *DBError
    if errors.As(err, &dbErr) {
        fmt.Printf("Mã lỗi DB: %d\n", dbErr.Code) // có thể truy cập Code
    }
}
```

**So sánh `errors.Is` và `errors.As`:**

|          | `errors.Is`                                   | `errors.As`                                     |
| -------- | --------------------------------------------- | ----------------------------------------------- |
| Mục đích | Kiểm tra lỗi có bằng một giá trị cụ thể không | Trích xuất lỗi ra biến có kiểu cụ thể           |
| Dùng khi | Lỗi sentinel (`var ErrX = errors.New(...)`)   | Custom error struct cần truy cập trường dữ liệu |

## Custom Error Types — Kiểu lỗi tùy chỉnh

Khi cần lưu thêm thông tin kèm lỗi (mã lỗi, tên trường, offset...), định nghĩa struct triển khai interface `error`:

### Ví dụ cơ bản

```go
type LoiDuLieu struct {
    Truong     string
    NguyenNhan string
}

func (e *LoiDuLieu) Error() string {
    return fmt.Sprintf("lỗi tại trường %s: %s", e.Truong, e.NguyenNhan)
}

// Sử dụng
func validateAge(age int) error {
    if age < 0 {
        return &LoiDuLieu{Truong: "age", NguyenNhan: "không được âm"}
    }
    return nil
}
```

### Ví dụ từ thư viện chuẩn — `json.SyntaxError`

Package `encoding/json` định nghĩa `SyntaxError` để lưu thêm vị trí byte xảy ra lỗi:

```go
type SyntaxError struct {
    msg    string // mô tả lỗi (unexported)
    Offset int64  // lỗi xảy ra sau khi đọc Offset bytes
}

func (e *SyntaxError) Error() string { return e.msg }
```

Trường `Offset` không xuất hiện trong thông báo lỗi mặc định, nhưng có thể được dùng để tính vị trí dòng và cột:

```go
if err := dec.Decode(&val); err != nil {
    if serr, ok := err.(*json.SyntaxError); ok {
        line, col := findLine(f, serr.Offset)
        return fmt.Errorf("%s:%d:%d: %v", f.Name(), line, col, err)
    }
    return err
}
```

### Ví dụ từ thư viện chuẩn — `net.Error`

Package `net` mở rộng interface `error` để phân biệt lỗi tạm thời và lỗi vĩnh viễn:

```go
package net

type Error interface {
    error
    Timeout() bool   // Lỗi có phải do timeout không?
    Temporary() bool // Lỗi có phải tạm thời không?
}
```

Điều này cho phép caller quyết định có thể retry hay không:

```go
if nerr, ok := err.(net.Error); ok && nerr.Temporary() {
    time.Sleep(time.Second)
    continue // thử lại
}
if err != nil {
    log.Fatal(err) // lỗi vĩnh viễn, dừng lại
}
```

> Lưu ý: Từ Go 1.18+, `net.Error.Temporary()` đã bị deprecated vì khó định nghĩa chính xác "tạm thời" trong thực tế. Khuyến nghị hiện tại là dùng `errors.Is` với các sentinel errors cụ thể hoặc kiểm tra trực tiếp `net.Error.Timeout()`.

## Panic và Recover

`panic` dùng cho các lỗi lập trình nghiêm trọng mà chương trình không thể tiếp tục, ví dụ: logic sai dẫn đến trạng thái không nhất quán. `recover` dùng để bắt panic và ngăn chương trình crash hoàn toàn — thường chỉ dùng ở lớp ngoài cùng (ví dụ: HTTP server middleware) để chuyển panic thành error response.

```go
func safeExecute(fn func()) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("recovered from panic: %v", r)
        }
    }()
    fn()
    return nil
}
```


**Nguyên tắc:** Không dùng `panic/recover` để thay thế error handling thông thường. Chỉ dùng `panic` khi gặp tình huống thực sự không thể phục hồi và không nên tiếp tục thực thi.

## `syscall.Errno` — Mã lỗi hệ thống

Trong trường hợp cần truy cập mã lỗi hệ thống (tương đương `errno` trong C), Go cung cấp `syscall.Errno`:

```go
err := syscall.Chmod(":invalid path:", 0666)
if err != nil {
    log.Fatal(err.(syscall.Errno))
}
```

`syscall.Errno` là kiểu số nguyên triển khai interface `error`, ánh xạ trực tiếp với mã lỗi của hệ điều hành. Thực tế, hầu hết code Go không cần tương tác trực tiếp với `syscall` — package `os` và `net` đã bao bọc các lỗi hệ thống thành dạng dễ sử dụng hơn.

## Thông tin bổ sung

### 1. Quy ước đặt tên và cấu trúc thông báo lỗi trong Go

Cộng đồng Go có một số quy ước quan trọng:

- **Chuỗi lỗi viết thường, không có dấu chấm cuối:** `"something went wrong"` thay vì `"Something went wrong."` — vì thông báo thường được nối với nhau: `"outer: inner: detail"`.
- **Sentinel errors dùng tiền tố `Err`:** `var ErrNotFound = errors.New("not found")`.
- **Custom error type dùng hậu tố `Error`:** `type ValidationError struct{...}`.

### 2. Pattern xử lý lỗi trong dự án thực tế

Trong ứng dụng backend Go theo kiến trúc phân tầng, lỗi thường được định nghĩa tập trung và wrapping theo tầng:

```go
// common/errors.go — định nghĩa sentinel errors
var (
    ErrNotFound     = errors.New("not found")
    ErrUnauthorized = errors.New("unauthorized")
    ErrBadRequest   = errors.New("bad request")
)

// repository layer — wrap lỗi database
func (r *userRepo) FindByID(ctx context.Context, id uint) (*model.User, error) {
    var user model.User
    if err := r.db.First(&user, id).Error; err != nil {
        if errors.Is(err, gorm.ErrRecordNotFound) {
            return nil, fmt.Errorf("userRepo.FindByID: %w", ErrNotFound)
        }
        return nil, fmt.Errorf("userRepo.FindByID: %w", err)
    }
    return &user, nil
}

// service layer — xử lý và re-wrap nếu cần
func (s *userService) GetByID(ctx context.Context, id uint) (*dto.UserResponse, error) {
    user, err := s.repo.FindByID(ctx, id)
    if err != nil {
        return nil, fmt.Errorf("userService.GetByID: %w", err)
    }
    return mapToDTO(user), nil
}

// controller layer — ánh xạ error sang HTTP status
func (h *UserHandler) GetUser(c *gin.Context) {
    user, err := h.service.GetByID(c.Request.Context(), id)
    if errors.Is(err, common.ErrNotFound) {
        c.JSON(http.StatusNotFound, response.Err(err.Error()))
        return
    }
    if err != nil {
        c.JSON(http.StatusInternalServerError, response.Err("internal error"))
        return
    }
    c.JSON(http.StatusOK, response.OK(user))
}
```

### 3. `errors.Join` — Go 1.20+

Từ Go 1.20, có thể gộp nhiều lỗi thành một:

```go
err1 := errors.New("lỗi kết nối database")
err2 := errors.New("lỗi đọc cache")

combined := errors.Join(err1, err2)
fmt.Println(combined)
// lỗi kết nối database
// lỗi đọc cache

fmt.Println(errors.Is(combined, err1)) // true
fmt.Println(errors.Is(combined, err2)) // true
```

Hữu ích khi cần thu thập tất cả lỗi trong một vòng lặp validation trước khi trả về.

### 4. Thư viện bên thứ ba đáng chú ý

- **`github.com/pkg/errors`**: Thư viện phổ biến trước Go 1.13, cung cấp stack trace kèm lỗi. Hiện nay ít cần thiết hơn vì Go chuẩn đã hỗ trợ wrapping.
- **`github.com/hashicorp/go-multierror`**: Tương tự `errors.Join` nhưng ra đời trước Go 1.20, vẫn phổ biến trong nhiều dự án.
