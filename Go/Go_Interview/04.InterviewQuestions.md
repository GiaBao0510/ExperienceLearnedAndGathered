## Câu 1: Golang có OOP không?

### Câu trả lời

**Go có hỗ trợ lập trình hướng đối tượng theo cách riêng**, nhưng **không phải là ngôn ngữ OOP cổ điển** như Java, C# hay C++.

Go có:

- Kiểu dữ liệu tự định nghĩa, thường là `struct`.
- Method gắn với kiểu dữ liệu.
- Interface và polymorphism.
- Tính đóng gói thông qua tên export/unexport.
- Composition bằng struct embedding.

Go không có:

- Class.
- Inheritance theo kiểu class-based.
- Constructor/destructor tích hợp sẵn.
- Abstract class.
- Method overloading.
- Access modifier rõ ràng như `private`, `protected`, `public`.

Thay vì kế thừa, Go khuyến khích **composition over inheritance**, tức là tái sử dụng hành vi bằng cách nhúng struct hoặc định nghĩa interface nhỏ.

### Ví dụ

```go
type Animal struct {
    Name string
}

func (a Animal) Speak() {
    println("Some sound")
}

type Dog struct {
    Animal
}

func main() {
    d := Dog{Name: "Milu"}
    d.Speak()
}
```

Ở đây `Dog` không kế thừa class `Animal`, mà nhúng struct `Animal` để tái sử dụng method.

Interface:

```go
type Shape interface {
    Area() float64
}

type Square struct {
    Side float64
}

func (s Square) Area() float64 {
    return s.Side * s.Side
}
```

`Square` tự động thỏa mãn interface `Shape` vì có method `Area() float64`.

### Mở rộng

- Tính đóng gói trong Go dựa vào tên identifier:
  - Bắt đầu bằng chữ hoa: exported.
  - Bắt đầu bằng chữ thường: unexported.
- Interface trong Go là implicit implementation, không cần từ khóa `implements`.
- Go phù hợp với thiết kế dựa trên interface nhỏ, composition và behavior thay vì class hierarchy.
- Trong phỏng vấn, không nên trả lời “Go không có OOP”. Câu trả lời tốt hơn là: “Go hỗ trợ OOP theo cách riêng, dựa trên struct, method, interface và composition”.

### Nguồn trích dẫn

- Effective Go: https://go.dev/doc/effective_go
- Go FAQ: https://go.dev/doc/faq
- Go Specification: Method sets, Interface types.

## Câu 2: Phiên bản mới nhất của Golang là gì?

### Câu trả lời

Đây là câu hỏi mang tính thời điểm. Phiên bản mới nhất của Go thay đổi theo thời gian, vì vậy không nên ghi nhớ một con số cố định trong tài liệu phỏng vấn.

Cách trả lời tốt:

- Go hiện đang ở chuỗi phiên bản **Go 1.x**.
- Go có chính sách **backward compatibility**: code Go 1.x thường tiếp tục chạy được trên các bản Go 1 mới hơn.
- Go thường phát hành stable release khoảng hai lần mỗi năm.
- Để biết phiên bản mới nhất, nên kiểm tra trang chính thức: `https://go.dev/dl/` hoặc `https://go.dev/doc/devel/release`.
- Trên máy hiện tại có thể kiểm tra bằng lệnh:

```bash
go version
```

### Ví dụ

Kiểm tra phiên bản Go đang cài:

```bash
go version
```

Kết quả ví dụ:

```text
go version go1.22.3 linux/amd64
```

Xem phiên bản trong `go.mod`:

```go
module example.com/myapp

go 1.22
```

### Mở rộng

- Trong phỏng vấn, câu hỏi này có thể không chỉ kiểm tra “phiên bản mới nhất”, mà kiểm tra xem ứng viên có biết cách cập nhật thông tin chính thức hay không.
- Không nên nói một phiên bản cụ thể nếu tài liệu đã cũ. Nên nói: “Em sẽ kiểm tra release notes chính thức; Go phát hành đều đặn và giữ backward compatibility”.
- Khi nâng cấp Go, cần chú ý:
  - Thay đổi trong standard library.
  - Thay đổi trong runtime/GC.
  - Thay đổi trong toolchain.
  - Compatibility của dependencies.

## Câu 3: Làm sao để nối chuỗi trong Go?

### Câu trả lời

Trong Go, có nhiều cách để nối chuỗi. Cách chọn phụ thuộc vào ngữ cảnh:

1. **Toán tử `+`**  
   Phù hợp khi nối một vài chuỗi ngắn, code đơn giản.

2. **`fmt.Sprintf`**  
   Phù hợp khi cần format chuỗi có số, struct hoặc nhiều kiểu dữ liệu khác nhau.

3. **`strings.Join`**  
   Phù hợp khi nối một slice chuỗi với delimiter.

4. **`strings.Builder`**  
   Phù hợp khi nối chuỗi trong vòng lặp hoặc xây dựng chuỗi lớn, vì tránh tạo ra quá nhiều chuỗi trung gian.

### Ví dụ

Nối chuỗi đơn giản:

```go
s := "Hello" + " " + "Go"
fmt.Println(s) // Hello Go
```

Dùng `fmt.Sprintf`:

```go
name := "Go"
version := 1.22
s := fmt.Sprintf("Language: %s, version: %.2f", name, version)
fmt.Println(s)
```

Dùng `strings.Join`:

```go
parts := []string{"Go", "is", "simple"}
s := strings.Join(parts, " ")
fmt.Println(s) // Go is simple
```

Dùng `strings.Builder`:

```go
var sb strings.Builder

for i := 0; i < 5; i++ {
    sb.WriteString("Go ")
}

fmt.Println(sb.String()) // Go Go Go Go Go
```

### Mở rộng

- Không nên dùng `s += ...` trong vòng lặp lớn vì mỗi lần nối chuỗi có thể tạo ra một string mới, gây nhiều allocation.
- `strings.Builder` hiệu quả hơn vì nó ghi vào buffer bên trong.
- Nếu biết trước dung lượng, có thể dùng `sb.Grow(n)` để giảm reallocation.
- String trong Go là immutable, nên mọi thao tác nối chuỗi đều tạo dữ liệu mới ở một mức nào đó.

### Nguồn trích dẫn

## Câu 4: Sự khác nhau giữa nil slice và empty slice là gì?

### Câu trả lời

**Nil slice** và **empty slice** đều có `len = 0` và `cap = 0`, nhưng khác nhau về mặt biểu diễn và ý nghĩa.

### Nil slice

Nil slice là slice chưa được khởi tạo hoặc được gán bằng `nil`.

```go
var s []int
```

Đặc điểm:

- `s == nil` trả về `true`.
- Không có underlying array.
- `len(s) == 0`.
- `cap(s) == 0`.
- Có thể `append` bình thường.
- Khi marshal sang JSON, nil slice thường ra `null`.

### Empty slice

Empty slice là slice có độ dài bằng 0 nhưng không phải nil.

```go
s := []int{}
// hoặc
s := make([]int, 0)
```

Đặc điểm:

- `s == nil` trả về `false`.
- Có underlying array rỗng hoặc không có phần tử.
- `len(s) == 0`.
- `cap(s)` có thể bằng 0 hoặc lớn hơn tùy cách khởi tạo.
- Có thể `append` bình thường.
- Khi marshal sang JSON, empty slice thường ra `[]`.

### Ví dụ

```go
package main

import (
    "encoding/json"
    "fmt"
)

func main() {
    var nilSlice []int
    emptySlice := []int{}

    fmt.Println(nilSlice == nil)   // true
    fmt.Println(emptySlice == nil) // false

    b1, _ := json.Marshal(nilSlice)
    b2, _ := json.Marshal(emptySlice)

    fmt.Println(string(b1)) // null
    fmt.Println(string(b2)) // []
}
```

### Mở rộng

- Để kiểm tra slice có phần tử hay không, nên dùng:

```go
if len(s) == 0 {
    // empty
}
```

Không nên chỉ kiểm tra `s == nil`, vì nil slice và empty slice thường đều được xem là “không có dữ liệu”.

- Trong API JSON, sự khác nhau giữa `null` và `[]` có thể quan trọng với client.
- `append` hoạt động được với cả nil slice:

```go
var s []int
s = append(s, 1)
```

### Nguồn trích dẫn

- Go Specification: Slice types.
- Go FAQ: Nil and empty slices.
- Go Standard Library: `encoding/json`.

## Câu 5: Nil channel để làm gì?

### Câu trả lời

**Nil channel** là channel có giá trị `nil`, tức là chưa được khởi tạo bằng `make`.

```go
var ch chan int
```

Đặc điểm quan trọng:

- Gửi vào nil channel sẽ block forever.
- Nhận từ nil channel sẽ block forever.
- Trong `select`, case liên quan đến nil channel sẽ không bao giờ sẵn sàng.

Nil channel hữu ích khi muốn **vô hiệu hóa một case trong select một cách động**.

### Ví dụ

```go
func consumer(ch <-chan int, done <-chan struct{}) {
    for {
        select {
        case v, ok := <-ch:
            if !ok {
                ch = nil // vô hiệu hóa case này
                continue
            }
            fmt.Println("received:", v)
        case <-done:
            return
        }
    }
}
```

Khi `ch` bị đóng, ta set `ch = nil`. Sau đó case nhận từ `ch` không còn được chọn nữa, nhưng `select` vẫn có thể chờ `done`.

### Ví dụ khác: disable send case

```go
var out chan int

select {
case out <- value:
    fmt.Println("sent")
case <-ctx.Done():
    fmt.Println("cancelled")
}
```

Nếu `out` là nil, case gửi sẽ không bao giờ sẵn sàng. Đây là một kỹ thuật để bật/tắt một hướng giao tiếp trong select.

### Mở rộng

- Nil channel khác closed channel:
  - Nil channel: send/receive đều block.
  - Closed channel: receive trả về zero value và `ok = false`; send panic.
- Không nên gửi/nhận trên nil channel ngoài mục đích blocking có kiểm soát.
- Nil channel thường dùng trong các pattern:
  - Merge channels.
  - Fan-in/fan-out.
  - Worker pool.
  - Disable receive/send sau khi channel đã đóng.

### Nguồn trích dẫn

- Go Specification: Channel types.
- Go Blog: Go Concurrency Patterns.
- Effective Go: Channels.

## Câu 6: Tại sao dùng channel để truyền data trong khi có thể truyền thẳng vào `go func`?

### Câu trả lời

Có thể truyền dữ liệu trực tiếp vào goroutine thông qua tham số hàm:

```go
go func(task Task) {
    process(task)
}(task)
```

Cách này phù hợp khi chỉ cần chạy một tác vụ độc lập với dữ liệu ban đầu.

Tuy nhiên, **channel** được dùng khi cần nhiều hơn việc “chạy một hàm với dữ liệu ban đầu”.

Channel giúp:

1. **Đồng bộ hóa giữa các goroutine**  
   Gửi/nhận trên channel là điểm đồng bộ. Sender và receiver có thể chờ nhau.

2. **Truyền dữ liệu liên tục theo thời gian**  
   Một goroutine có thể gửi nhiều giá trị qua channel trong suốt vòng đời của nó.

3. **Xây dựng pipeline**  
   Dữ liệu có thể đi qua nhiều stage: producer → processor → consumer.

4. **Giới hạn concurrency với worker pool**  
   Channel có thể đóng vai trò hàng đợi công việc.

5. **Backpressure**  
   Unbuffered channel hoặc buffered channel có dung lượng giới hạn giúp kiểm soát tốc độ producer/consumer.

6. **Chuyển quyền sở hữu dữ liệu**  
   Khi gửi dữ liệu qua channel, có thể thiết kế rõ goroutine nào sở hữu dữ liệu tại từng thời điểm.

7. **Tránh chia sẻ bộ nhớ không đồng bộ**  
   Thay vì nhiều goroutine cùng sửa một biến chung, channel giúp truyền dữ liệu một cách an toàn.

### Ví dụ

Truyền thẳng vào goroutine:

```go
go func(task Task) {
    process(task)
}(task)
```

Chỉ phù hợp cho một task độc lập.

Dùng channel cho nhiều task:

```go
func worker(tasks <-chan Task) {
    for task := range tasks {
        process(task)
    }
}

func main() {
    tasks := make(chan Task)

    for i := 0; i < 3; i++ {
        go worker(tasks)
    }

    for _, task := range taskList {
        tasks <- task
    }

    close(tasks)
}
```

Ở đây channel đóng vai trò hàng đợi công việc cho nhiều worker.

### Mở rộng

- Channel không phải lúc nào cũng là lựa chọn tốt nhất.
- Nếu chỉ cần bảo vệ một vùng dữ liệu nhỏ, mutex có thể đơn giản hơn.
- Nếu chỉ cần báo hủy hoặc timeout, `context.Context` thường phù hợp hơn.
- Nguyên tắc phổ biến trong Go:

> Do not communicate by sharing memory; instead, share memory by communicating.

Tuy nhiên, cần hiểu rằng đây là định hướng thiết kế, không phải quy tắc tuyệt đối cho mọi trường hợp.

### Nguồn trích dẫn

- Go Blog: Share Memory By Communicating.
- Go Blog: Go Concurrency Patterns.

## Câu 7: Sự khác nhau giữa data race và race condition là gì?

### Câu trả lời

**Race condition** là khái niệm rộng, mô tả lỗi xảy ra khi kết quả của chương trình phụ thuộc vào thứ tự thực thi không xác định giữa các tác vụ đồng thời.

**Data race** là một dạng lỗi cụ thể ở mức truy cập bộ nhớ: hai hoặc nhiều goroutine truy cập cùng một vùng nhớ đồng thời, trong đó có ít nhất một thao tác ghi, và không có cơ chế đồng bộ phù hợp.

### So sánh

| Tiêu chí | Race condition | Data race |
|---|---|---|
| Phạm vi | Rộng, logic/concurrency nói chung | Cụ thể, truy cập bộ nhớ không đồng bộ |
| Có thể phát hiện tự động không? | Không phải lúc nào cũng phát hiện được | Go race detector có thể phát hiện nhiều trường hợp |
| Xảy ra ở đâu? | Trong một process, nhiều process, hệ phân tán | Thường trong cùng process, giữa các goroutine/thread |
| Ví dụ | Check-then-act, thứ tự xử lý nghiệp vụ | Hai goroutine cùng tăng biến `counter` không lock |

### Ví dụ data race

```go
counter := 0

for i := 0; i < 1000; i++ {
    go func() {
        counter++ // data race
    }()
}
```

Nhiều goroutine cùng ghi vào `counter` mà không có mutex/atomic.

Cách sửa với atomic:

```go
var counter int64

for i := 0; i < 1000; i++ {
    go func() {
        atomic.AddInt64(&counter, 1)
    }()
}
```

### Ví dụ race condition

Bài toán rút tiền:

```text
1. Kiểm tra số dư có đủ không.
2. Nếu đủ, trừ tiền.
```

Nếu hai yêu cầu rút tiền cùng chạy đồng thời, cả hai có thể thấy số dư đủ trước khi một giao dịch kịp trừ tiền. Kết quả là tài khoản có thể bị rút quá số dư.

Đây là race condition về logic nghiệp vụ. Dù có thể có hoặc không có data race ở mức bộ nhớ, lỗi vẫn xảy ra do thứ tự check-then-act.

Cách xử lý:

- Dùng mutex khóa toàn bộ thao tác nghiệp vụ.
- Dùng transaction database.
- Dùng optimistic/pessimistic locking.
- Thiết kế idempotency.
- Dùng hàng đợi tuần tự cho các thao tác nhạy cảm.

### Mở rộng

- Go race detector phát hiện data race, không đảm bảo phát hiện mọi race condition logic.
- Code không có data race vẫn có thể có race condition.
- Trong hệ thống phân tán, race condition có thể xảy ra giữa nhiều service, cần transaction, distributed lock, event ordering hoặc idempotency.
- Data race là lỗi kỹ thuật có thể phát hiện bằng công cụ; race condition thường cần phân tích nghiệp vụ và thiết kế đồng bộ đúng.

## Câu 8: Tại sao dùng Gin framework hoặc framework mà bạn sử dụng?

### Câu trả lời

**Gin** là một web framework phổ biến trong Go, thường được dùng để xây dựng HTTP API, microservice và backend service.

Lý do nhiều đội ngũ chọn Gin:

1. **Hiệu năng tốt**  
   Gin có router nhanh, phù hợp với API cần throughput cao.

2. **Nhẹ và tập trung**  
   Gin không cố trở thành framework MVC quá nặng. Nó tập trung vào routing, middleware, context và binding.

3. **Middleware linh hoạt**  
   Gin cho phép viết middleware cho logging, authentication, recovery, CORS, rate limiting.

4. **Routing mạnh**  
   Hỗ trợ route parameter, route group, wildcard.

5. **Binding và validation**  
   Gin hỗ trợ bind JSON, form, query, URI param và validate dữ liệu.

6. **Context tiện lợi**  
   `gin.Context` giúp quản lý request, response, middleware value, error, JSON render.

7. **Cộng đồng lớn**  
   Gin phổ biến, có nhiều tài liệu, middleware và ví dụ thực tế.

### Ví dụ

```go
package main

import (
    "net/http"

    "github.com/gin-gonic/gin"
)

func main() {
    r := gin.Default()

    r.GET("/ping", func(c *gin.Context) {
        c.JSON(http.StatusOK, gin.H{
            "message": "pong",
        })
    })

    r.Run(":8080")
}
```

Middleware ví dụ:

```go
func LoggerMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()
        c.Next()
        log.Printf("%s %s %v", c.Request.Method, c.Request.URL.Path, time.Since(start))
    }
}
```

### Mở rộng

- Gin không phải lúc nào cũng cần thiết. Với service đơn giản, `net/http` chuẩn có thể đủ.
- Các lựa chọn khác trong Go:
  - `net/http` + `http.ServeMux`
  - Chi
  - Echo
  - Fiber
  - Go-Chi
- Khi chọn framework, cần cân nhắc:
  - Hiệu năng.
  - Middleware.
  - Ease of use.
  - Community.
  - Compatibility với standard library.
  - Graceful shutdown.
  - Observability.
- Trong phỏng vấn, nên trả lời rằng framework chỉ là công cụ; quan trọng là hiểu `net/http`, context, middleware, routing, validation và graceful shutdown.

### Nguồn trích dẫn

- Gin Documentation: https://gin-gonic.com/docs/
- Go Standard Library: `net/http`.
- Go Blog: Using context to carry deadlines.

## Câu 9: Làm sao để monitor được RAM trong ứng dụng Go?

### Câu trả lời

Để monitor RAM trong ứng dụng Go, cần phân biệt:

1. **Bộ nhớ runtime Go quản lý**  
   Ví dụ: heap alloc, heap inuse, heap idle, heap released.

2. **Bộ nhớ process thực tế chiếm**  
   Thường là RSS (Resident Set Size), do OS/container nhìn thấy.

3. **Bộ nhớ cấp phát tích lũy**  
   TotalAlloc, tổng bộ nhớ đã cấp phát từ đầu process.

### Cách 1: Dùng `runtime.MemStats`

```go
var m runtime.MemStats
runtime.ReadMemStats(&m)

log.Printf("HeapAlloc = %d KiB", m.HeapAlloc/1024)
log.Printf("HeapInuse = %d KiB", m.HeapInuse/1024)
log.Printf("HeapIdle = %d KiB", m.HeapIdle/1024)
log.Printf("HeapReleased = %d KiB", m.HeapReleased/1024)
log.Printf("NumGC = %d", m.NumGC)
```

Các trường quan trọng:

- `Alloc`: heap đang giữ object.
- `HeapAlloc`: tương tự `Alloc`, object trên heap.
- `HeapInuse`: byte trong heap đang chứa object.
- `HeapIdle`: byte trong heap chưa chứa object.
- `HeapReleased`: byte trả về OS.
- `Sys`: tổng memory lấy từ OS.
- `NumGC`: số lần GC đã chạy.

### Cách 2: Dùng pprof

```go
import _ "net/http/pprof"

go func() {
    log.Println(http.ListenAndServe("localhost:6060", nil))
}()
```

Sau đó xem heap profile:

```bash
go tool pprof http://localhost:6060/debug/pprof/heap
```

Xem goroutine:

```bash
go tool pprof http://localhost:6060/debug/pprof/goroutine
```

### Cách 3: Dùng Prometheus

Nếu dùng Prometheus, có thể expose metrics:

```go
import (
    "net/http"

    "github.com/prometheus/client_golang/prometheus/promhttp"
)

func main() {
    http.Handle("/metrics", promhttp.Handler())
    http.ListenAndServe(":9091", nil)
}
```

`promhttp.Handler()` cung cấp các metrics Go runtime như:

- `go_memstats_heap_alloc_bytes`
- `go_memstats_heap_inuse_bytes`
- `go_memstats_heap_idle_bytes`
- `go_memstats_heap_released_bytes`
- `process_resident_memory_bytes`
- `go_goroutines`

### Cách 4: Monitor ở OS/container

Trong production, cần monitor thêm:

- RSS của process.
- Memory limit của container.
- OOM kill event.
- cgroup memory usage.
- Swap usage nếu có.

### Mở rộng

- HeapAlloc thấp không có nghĩa là process RSS thấp, vì Go có thể giữ heap idle chưa trả về OS.
- Nếu RSS tăng liên tục, cần kiểm tra:
  - Goroutine leak.
  - Cache/map không giới hạn.
  - HTTP body không đóng.
  - Database rows không đóng.
  - Buffer tăng không kiểm soát.
- Dùng heap profile `inuse_space` để biết object nào đang giữ bộ nhớ.
- Dùng `alloc_space` để biết nơi nào cấp phát nhiều theo thời gian.
- Có thể dùng `GOMEMLIMIT` để giới hạn memory mềm cho Go runtime.

## Câu 10: Quản lý heap thủ công trong Go như thế nào cho hiệu quả?

### Câu hỏi gốc

> Manual management heap như nào cho đỡ lâu

Câu hỏi này nên được hiểu là: **Làm sao tối ưu cấp phát heap và quản lý bộ nhớ trong Go để giảm GC, giảm latency và tăng hiệu năng?**

### Câu trả lời

Go không cho phép quản lý heap thủ công theo kiểu C/C++ như `malloc` và `free`. Bộ nhớ trong Go được quản lý bởi **garbage collector**. Tuy nhiên, lập trình viên vẫn có thể “quản lý” hiệu năng heap bằng cách kiểm soát allocation.

Mục tiêu không phải là tự giải phóng bộ nhớ, mà là:

- Giảm số lần allocation.
- Giảm số object tồn tại ngắn hạn.
- Giảm áp lực GC.
- Tái sử dụng buffer/object khi hợp lý.
- Tránh giữ object lâu hơn cần thiết.

### Các kỹ thuật quan trọng

#### 1. Preallocate slice/map nếu biết trước kích thước

```go
items := make([]Item, 0, len(input))

for _, in := range input {
    items = append(items, transform(in))
}
```

Với map:

```go
m := make(map[string]int, len(input))
```

#### 2. Dùng `strings.Builder` thay vì nối chuỗi bằng `+`

```go
var sb strings.Builder
sb.Grow(estimatedSize)

for _, s := range parts {
    sb.WriteString(s)
}
```

#### 3. Dùng `sync.Pool` để tái sử dụng object ngắn hạn

```go
var bufPool = sync.Pool{
    New: func() any {
        return new(bytes.Buffer)
    },
}

func process() {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()
    defer bufPool.Put(buf)

    // dùng buf
}
```

Lưu ý: `sync.Pool` là cache tạm thời, không đảm bảo object luôn tồn tại.

#### 4. Tránh escape không cần thiết

Biến escape sang heap khi compiler thấy nó có thể được dùng sau khi hàm kết thúc. Có thể kiểm tra bằng escape analysis:

```bash
go build -gcflags="-m" ./...
```

Một số cách giảm escape:

- Trả về value thay vì pointer nếu struct nhỏ.
- Tránh closure giữ biến không cần thiết.
- Hạn chế trả ra ngoài các buffer nội bộ nếu không cần.

#### 5. Giảm pointer-heavy data structure

GC phải scan pointer. Cấu trúc dữ liệu chứa quá nhiều pointer có thể làm GC tốn thời gian hơn.

Ví dụ:

- Nhiều struct nhỏ chứa pointer.
- Slice/map chứa pointer.
- Linked list nhiều node.

Trong một số trường hợp, dùng value type hoặc flat array có thể giảm áp lực GC.

#### 6. Xử lý dữ liệu theo stream/chunk

Không nên đọc toàn bộ file lớn vào memory nếu có thể xử lý từng phần.

```go
reader := bufio.NewReader(file)
scanner := bufio.NewScanner(reader)

for scanner.Scan() {
    line := scanner.Text()
    process(line)
}
```

#### 7. Đóng tài nguyên đúng cách

Các tài nguyên sau nên được đóng để tránh giữ memory/buffer/connection:

- `resp.Body`
- `*os.File`
- `*sql.Rows`
- gRPC stream
- TCP connection

#### 8. Dùng profiling để tối ưu đúng chỗ

Không nên tối ưu mù quáng. Cần đo bằng:

```bash
go test -bench=. -memprofile=mem.out
go tool pprof mem.out
```

Hoặc runtime pprof:

```bash
go tool pprof http://localhost:6060/debug/pprof/heap
```

### Mở rộng

- `sync.Pool` không thay thế memory allocator, chỉ giúp giảm allocation trong một số hot path.
- Không nên dùng finalizer để dọn dẹp tài nguyên quan trọng vì thời điểm chạy không đảm bảo.
- GC trong Go ưu tiên latency thấp, nhưng nếu allocation quá nhiều, GC vẫn gây áp lực.
- Có thể điều chỉnh `GOGC` hoặc `GOMEMLIMIT`, nhưng thường nên tối ưu allocation trước.
- Tối ưu bộ nhớ nên đi kèm benchmark và profiling, không dựa vào cảm giác.

## Câu 11: Làm sao để xử lý dữ liệu bị sai khi ở múi giờ khác nhau?

### Câu trả lời

Lỗi múi giờ thường xảy ra khi hệ thống lưu trữ, truyền hoặc hiển thị thời gian không thống nhất.

Nguyên tắc quan trọng:

1. **Lưu thời gian ở UTC trong database và backend.**
2. **Khi truyền qua API, nên dùng chuẩn RFC3339 có timezone offset.**
3. **Chỉ convert sang timezone địa phương khi hiển thị cho người dùng.**
4. **Không lưu local time không có timezone nếu hệ thống có nhiều múi giờ.**
5. **Cẩn thận với daylight saving time nếu timezone có DST.**

### Ví dụ sai

Lưu chuỗi local time không có timezone:

```text
2026-06-25 09:00:00
```

Chuỗi này không rõ thuộc múi giờ nào. Nếu server ở UTC, client ở Việt Nam, database ở Singapore, hệ thống có thể hiểu sai.

### Ví dụ đúng

Dùng RFC3339:

```text
2026-06-25T09:00:00+07:00
```

Hoặc UTC:

```text
2026-06-25T02:00:00Z
```

### Ví dụ trong Go

Parse thời gian có timezone:

```go
t, err := time.Parse(time.RFC3339, "2026-06-25T09:00:00+07:00")
if err != nil {
    log.Fatal(err)
}

utc := t.UTC()
fmt.Println(utc.Format(time.RFC3339))
```

Chuyển sang timezone địa phương để hiển thị:

```go
loc, err := time.LoadLocation("Asia/Ho_Chi_Minh")
if err != nil {
    log.Fatal(err)
}

local := utc.In(loc)
fmt.Println(local.Format("2006-01-02 15:04:05"))
```

Lưu trữ:

```go
nowUTC := time.Now().UTC()
```

### Ví dụ với database

Nên dùng kiểu thời gian có timezone, ví dụ:

- PostgreSQL: `timestamptz`.
- MySQL: cần cấu hình timezone kết nối cẩn thận.
- MongoDB: Date thường lưu UTC milliseconds.

Trong ứng dụng Go, khi đọc/ghi DB, nên convert về UTC trước khi lưu.

### Mở rộng

- `time.Now()` trả về thời gian với location của server. Không nên mặc định đó là UTC.
- Nếu cần so sánh hai thời điểm, nên convert cả hai về UTC hoặc dùng `time.Time` có timezone rõ ràng.
- Khi làm việc với cron job, billing, báo cáo ngày, cần định nghĩa rõ “ngày” theo timezone nào.
- Với hệ thống đa quốc gia, nên lưu:
  - Thời điểm sự kiện xảy ra ở UTC.
  - Timezone gốc của người dùng hoặc sự kiện nếu cần hiển thị lại chính xác.
- Tránh tự cộng/trừ 7 giờ thủ công cho Việt Nam. Nên dùng location và `time.In()` để tránh lỗi DST hoặc thay đổi offset lịch sử.
