# Bộ câu hỏi phỏng vấn Go – Phần 2

## Câu 1: Defer trong Go dùng để làm gì?

### Câu trả lời

`defer` trong Go dùng để hoãn một lời gọi hàm cho đến khi hàm hiện tại kết thúc, ngay trước khi trả về cho nơi gọi.

`defer` thường được dùng cho các công việc dọn dẹp tài nguyên như:

- Đóng file.
- Đóng kết nối database.
- Release lock của mutex.
- Đóng HTTP response body.
- Ghi log sau khi xử lý xong.
- Gọi `recover()` để xử lý panic.

Các đặc điểm quan trọng của `defer`:

1. **Thực thi theo thứ tự LIFO**  
   Nhiều lệnh `defer` trong cùng một hàm sẽ được thực thi theo thứ tự ngược lại: defer sau chạy trước.

2. **Tham số được đánh giá tại thời điểm khai báo defer**  
   Nếu defer một hàm có tham số, tham số đó được tính ngay khi gặp câu lệnh `defer`, không phải chờ đến khi hàm kết thúc.

3. **Vẫn chạy khi hàm panic**  
   Khi một hàm bị panic, các defer bên trong hàm đó vẫn được thực thi trong quá trình unwind stack.

4. **Không nên lạm dụng defer trong vòng lặp lớn**  
   Nếu vòng lặp tạo ra nhiều tài nguyên và mỗi lần lặp đều `defer Close()`, toàn bộ tài nguyên chỉ được đóng khi hàm kết thúc, có thể gây tốn bộ nhớ hoặc file descriptor.

### Ví dụ

Đóng file sau khi đọc:

```go
func readFile(path string) ([]byte, error) {
    f, err := os.Open(path)
    if err != nil {
        return nil, err
    }
    defer f.Close()

    return io.ReadAll(f)
}
```  

Release mutex:

```go
var mu sync.Mutex
var counter int

func Increase() {
    mu.Lock()
    defer mu.Unlock()

    counter++
}
```

Thứ tự defer:

```go
func example() {
    defer fmt.Println("1")
    defer fmt.Println("2")
    defer fmt.Println("3")
}
```

Kết quả:

```text
3
2
1
```

### Mở rộng

- Nếu cần đóng tài nguyên trong vòng lặp, nên tách logic ra thành một hàm riêng để defer được thực thi sớm hơn:

```go
func processFiles(paths []string) error {
    for _, path := range paths {
        if err := processFile(path); err != nil {
            return err
        }
    }
    return nil
}

func processFile(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close()

    // xử lý file
    return nil
}
```

- `defer` có một chút overhead, nhưng trong đa số ứng dụng bình thường, lợi ích về độ an toàn và dễ đọc quan trọng hơn.
- Trong xử lý panic, `recover()` phải được gọi bên trong một hàm `defer`.

## Câu 2: Khi nào nên sử dụng panic trong Go?

### Câu trả lời

Trong Go, `panic` chỉ nên được sử dụng cho các lỗi nghiêm trọng, không thể phục hồi, thường là lỗi lập trình hoặc vi phạm bất biến hệ thống.

Go khuyến khích xử lý lỗi bằng cách trả về `error`, không khuyến khích dùng `panic` như exception trong Java hay C#.

### Nên dùng panic khi nào?

1. **Lỗi lập trình rõ ràng**  
   Ví dụ: truy cập mảng ngoài phạm vi, nil pointer dereference, kiểu dữ liệu không hợp lệ do lỗi code.

2. **Bất biến quan trọng bị vi phạm**  
   Nếu hệ thống rơi vào trạng thái không thể tiếp tục an toàn, panic có thể chấp nhận được.

3. **Khởi tạo bắt buộc thất bại**  
   Ví dụ: không thể load cấu hình tối thiểu, không thể khởi tạo thành phần sống còn của chương trình.

4. **Middleware phục hồi lỗi ở biên hệ thống**  
   Trong HTTP server, có thể dùng `recover()` trong middleware để tránh crash toàn bộ process khi một handler panic.

### Không nên dùng panic khi nào?

1. Không nên dùng panic cho lỗi nghiệp vụ thông thường.
2. Không nên dùng panic để điều khiển luồng chương trình.
3. Không nên panic cho các lỗi có thể dự đoán và xử lý được.
4. Không nên để panic lan qua nhiều tầng service nếu có thể trả về error.

### Ví dụ

Dùng panic khi trạng thái không thể xảy ra:

```go
func mustParseConfig() Config {
    cfg, err := loadConfig()
    if err != nil {
        panic(fmt.Sprintf("invalid config: %v", err))
    }
    return cfg
}
```

Middleware recover trong HTTP server:

```go
func RecoverMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                log.Printf("panic recovered: %v", rec)
                http.Error(w, "internal server error", http.StatusInternalServerError)
            }
        }()

        next.ServeHTTP(w, r)
    })
}
```

### Mở rộng

- `recover()` chỉ có tác dụng khi được gọi trong deferred function của cùng goroutine đang panic.
- Nếu một goroutine panic mà không recover, toàn bộ process có thể crash.
- Trong thư viện/API công khai, nên trả về `error` thay vì panic để người gọi dễ xử lý.
- Có thể dùng pattern `Must...` cho các hàm khởi tạo đơn giản, nhưng cần cân nhắc trong production.

### Nguồn tham khảo

- Go Blog: Defer, Panic, and Recover.
- Go Wiki: Error handling.

## Câu 3: Select trong Go dùng để làm gì?

### Câu trả lời

`select` trong Go là câu lệnh dùng để chờ và chọn một trong nhiều operation trên channel.

`select` gần giống `switch`, nhưng áp dụng cho channel operation như gửi hoặc nhận dữ liệu.

### Đặc điểm quan trọng

1. **Chờ nhiều channel cùng lúc**  
   `select` có thể chờ nhận/gửi từ nhiều channel khác nhau.

2. **Chọn ngẫu nhiên nếu nhiều case cùng sẵn sàng**  
   Nếu nhiều case có thể thực thi ngay, Go chọn ngẫu nhiên một case, không ưu tiên case xuất hiện trước.

3. **Nếu không có case nào sẵn sàng, select sẽ block**  
   Trừ khi có `default`.

4. **Có thể dùng `default` để non-blocking**  
   Nếu có `default`, select sẽ chạy `default` khi không có case nào sẵn sàng.

5. **Kết hợp tốt với context và timeout**  
   Thường dùng với `ctx.Done()`, `time.After`, `time.Tick`.

### Ví dụ

Chờ dữ liệu từ hai channel:

```go
select {
case v := <-ch1:
    fmt.Println("received from ch1:", v)
case v := <-ch2:
    fmt.Println("received from ch2:", v)
}
```

Kết hợp context cancellation:

```go
select {
case v := <-ch:
    fmt.Println("value:", v)
case <-ctx.Done():
    fmt.Println("context cancelled")
}
```

Kết hợp timeout:

```go
select {
case v := <-ch:
    fmt.Println("value:", v)
case <-time.After(2 * time.Second):
    fmt.Println("timeout")
}
```

Non-blocking receive:

```go
select {
case v := <-ch:
    fmt.Println("received:", v)
default:
    fmt.Println("no value ready")
}
```

### Mở rộng

- Channel `nil` trong select sẽ không bao giờ được chọn nếu chỉ có channel nil.
- Nhận từ channel đã đóng sẽ trả về zero value và `ok = false`.
- Gửi vào channel đã đóng sẽ panic.
- Nếu dùng `default` không cẩn thận, có thể tạo ra busy loop làm tốn CPU.
- `select` là công cụ quan trọng để xây dựng worker pool, pipeline, timeout, cancellation và graceful shutdown.

### Nguồn tham khảo

- Go Specification: Select statements.
- Effective Go: Channels.
- Go Blog: Go Concurrency Patterns.

## Câu 4: Generics trong Go là gì?

### Câu trả lời

**Generics** trong Go là tính năng cho phép viết hàm hoặc kiểu dữ liệu hoạt động trên nhiều kiểu dữ liệu khác nhau mà vẫn giữ được kiểm tra kiểu lúc biên dịch.

Generics được giới thiệu từ **Go 1.18**.

Trước khi có generics, nếu muốn viết hàm dùng cho nhiều kiểu, thường phải:

- Dùng `interface{}` / `any` rồi type assertion.
- Viết nhiều hàm trùng logic cho từng kiểu.
- Dùng code generation.

Generics giúp giảm trùng lặp code và an toàn kiểu tốt hơn.

### Thành phần chính

1. **Type parameter**  
   Tham số kiểu, thường viết trong dấu `[]`.

2. **Type constraint**  
   Điều kiện kiểu dữ liệu phải thỏa mãn. Constraint thường là interface.

3. **Type instantiation**  
   Khi gọi hàm generic hoặc khai báo kiểu generic với một kiểu cụ thể.

### Ví dụ

```go
type Number interface {
    ~int | ~int64 | ~float64
}

func Sum[T Number](values []T) T {
    var total T
    for _, v := range values {
        total += v
    }
    return total
}

func main() {
    fmt.Println(Sum([]int{1, 2, 3}))
    fmt.Println(Sum([]float64{1.5, 2.5}))
}
```

Hàm `Sum` có thể hoạt động với `int`, `int64`, `float64`, miễn là kiểu đó thỏa mãn constraint `Number`.

### Khi nào nên dùng generics?

Nên dùng khi:

- Viết thuật toán tổng quát: sort, map, filter, reduce.
- Viết cấu trúc dữ liệu tổng quát: stack, queue, linked list, cache.
- Muốn tránh lặp code cho nhiều kiểu tương tự.
- Muốn giữ an toàn kiểu tốt hơn so với `any`.

### Khi nào không nên lạm dụng generics?

Không nên dùng generics khi:

- Logic chỉ áp dụng cho một kiểu nghiệp vụ cụ thể.
- Code trở nên khó đọc do constraint quá phức tạp.
- Có thể dùng interface đơn giản là đủ.
- Đội ngũ chưa quen generics và code cần ưu tiên dễ bảo trì.

### Mở rộng

- `any` là alias của `interface{}`, cho phép mọi kiểu.
- `comparable` là constraint cho các kiểu có thể so sánh bằng `==` và `!=`, thường dùng làm key của map.
- Generics trong Go hiện không mạnh bằng C++ templates hoặc Java generics ở một số khía cạnh.
- Go generics hướng đến sự đơn giản, rõ ràng, không khuyến khích lạm dụng quá mức.

### Nguồn tham khảo

- Go Tutorial: Generics.
- Go Specification: Type parameters.
- Go Blog: An Introduction To Generics.

## Câu 5: Viết unit testing trong Go như thế nào?

### Câu trả lời

Unit test trong Go thường được viết bằng package chuẩn `testing`.

Quy tắc cơ bản:

1. File test có đuôi `_test.go`.
2. Hàm test có dạng `func TestXxx(t *testing.T)`.
3. Dùng `t.Errorf`, `t.Fatalf`, `t.Fatalf` để đánh dấu test thất bại.
4. Nên viết test theo phong cách **table-driven test**.
5. Nên dùng subtest với `t.Run`.
6. Test nên độc lập, nhanh, không phụ thuộc môi trường bên ngoài.

### Cấu trúc một unit test tốt

Một test rõ ràng thường gồm 3 phần:

```text
Arrange: chuẩn bị dữ liệu và điều kiện.
Act: gọi hàm cần test.
Assert: kiểm tra kết quả.
```

### Ví dụ

```go
func Add(a, b int) int {
    return a + b
}
```

Test đơn giản:

```go
func TestAdd(t *testing.T) {
    got := Add(2, 3)
    want := 5

    if got != want {
        t.Errorf("Add(2, 3) = %d, want %d", got, want)
    }
}
```

Table-driven test:

```go
func TestAdd(t *testing.T) {
    tests := []struct {
        name string
        a    int
        b    int
        want int
    }{
        {
            name: "positive numbers",
            a:    1,
            b:    2,
            want: 3,
        },
        {
            name: "negative numbers",
            a:    -1,
            b:    -2,
            want: -3,
        },
        {
            name: "zero",
            a:    0,
            b:    0,
            want: 0,
        },
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got := Add(tt.a, tt.b)
            if got != tt.want {
                t.Errorf("Add(%d, %d) = %d, want %d", tt.a, tt.b, got, tt.want)
            }
        })
    }
}
```

### Nguyên tắc viết test tốt

1. **Test hành vi, không test chi tiết triển khai nếu không cần thiết**  
   Hạn chế mock quá mức làm test gắn chặt vào implementation.

2. **Test phải độc lập**  
   Không nên phụ thuộc thứ tự chạy test.

3. **Test phải nhanh**  
   Unit test không nên truy cập network, database thật nếu có thể tránh.

4. **Dùng interface để dễ fake/mock**  
   Nếu hàm phụ thuộc database, cache, HTTP client, nên khai báo interface nhỏ để truyền fake implementation.

5. **Chạy test với race detector**

```bash
go test -race ./...
```

6. **Không chỉ nhìn coverage**  
   Coverage cao không đồng nghĩa test tốt. Test cần bắt được lỗi và mô tả đúng hành vi mong muốn.

### Mở rộng

- Go cũng hỗ trợ benchmark:

```go
func BenchmarkAdd(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Add(1, 2)
    }
}
```

- Go hỗ trợ fuzz testing từ Go 1.18:

```go
func FuzzAdd(f *testing.F) {
    f.Add(1, 2)
    f.Fuzz(func(t *testing.T, a, b int) {
        _ = Add(a, b)
    })
}
```

- Có thể dùng thêm thư viện assertion như `testify`, nhưng standard library vẫn rất phổ biến vì đơn giản và ổn định.

### Nguồn tham khảo

- Go Documentation: Testing package.
- Go Wiki: Table Driven Tests.
- Go Blog: Fuzzing.

## Câu 6: Garbage Collection trong Go hoạt động như thế nào?

### Câu trả lời

**Garbage Collection**, hay GC, là cơ chế tự động thu gom bộ nhớ trong Go. GC sẽ tìm các đối tượng không còn được chương trình sử dụng và giải phóng chúng.

Go sử dụng GC nhằm giúp lập trình viên không phải tự giải phóng bộ nhớ như C/C++.

### Đặc điểm chính của GC trong Go

1. **Concurrent GC**  
   GC chạy đồng thời với chương trình chính, thay vì dừng toàn bộ ứng dụng trong thời gian dài.

2. **Mark-and-sweep**  
   GC đánh dấu các object còn được tham chiếu từ roots, sau đó thu gom các object không còn được đánh dấu.

3. **Tri-color marking**  
   Go dùng thuật toán tri-color marking kết hợp write barrier để giảm thời gian dừng.

4. **Không compact heap theo cách di chuyển object như một số GC khác**  
   Go GC hiện tại không di chuyển object để compact bộ nhớ như GC trong JVM.

5. **Không generational**  
   Go GC không chia bộ nhớ thành young/old generation như JVM.

6. **Mục tiêu là latency thấp**  
   Go ưu tiên pause time ngắn hơn là throughput GC tuyệt đối.

### GC được kích hoạt khi nào?

Go GC có cơ chế pacing để quyết định khi nào chạy. Một yếu tố quan trọng là `GOGC`.

Mặc định:

```text
GOGC=100
```

Nghĩa là GC có thể được kích hoạt khi heap tăng gấp đôi so với heap còn sống sau lần GC trước.

Từ Go 1.19, có thêm `GOMEMLIMIT` để giới hạn bộ nhớ mềm, hữu ích trong container hoặc môi trường có memory limit.

### Ví dụ quan sát GC

Có thể bật pprof để quan sát heap và GC:

```go
import _ "net/http/pprof"

go func() {
    http.ListenAndServe("localhost:6060", nil)
}()
```

Sau đó xem heap profile:

```bash
go tool pprof http://localhost:6060/debug/pprof/heap
```

### Mở rộng

- GC không giải quyết được memory leak logic. Nếu object vẫn còn được tham chiếu, GC sẽ không thu gom.
- Finalizer không nên dùng để dọn dẹp tài nguyên quan trọng vì thời điểm chạy không đảm bảo.
- Để giảm áp lực GC, có thể:
  - Giảm allocation.
  - Tái sử dụng buffer.
  - Dùng `sync.Pool` hợp lý.
  - Tránh tạo object ngắn hạn quá nhiều trong hot path.
  - Dùng slice/map preallocate khi biết trước kích thước.
- Đừng tối ưu GC quá sớm. Trước tiên nên đo bằng profiling.

### Nguồn tham khảo

- Go Documentation: A Guide to the Go Garbage Collector.
- Go Documentation: GOGC and GOMEMLIMIT.
- Go Blog: Getting to Go: The Journey of Go's Garbage Collector.

## Câu 7: Giải thích Go runtime và Go scheduler

### Câu trả lời

### Go runtime là gì?

**Go runtime** là một phần quan trọng được tích hợp trong mọi chương trình Go. Runtime chịu trách nhiệm quản lý nhiều thứ ở tầng thấp để chương trình Go chạy hiệu quả.

Go runtime bao gồm các thành phần hỗ trợ:

- Goroutine scheduling.
- Garbage collection.
- Memory allocation.
- Channel.
- Map.
- Stack management.
- Network poller.
- System call handling.

Nhờ runtime, lập trình viên Go có thể viết code concurrency đơn giản mà không cần tự quản lý thread OS.

### Go scheduler là gì?

Go scheduler là bộ lập lịch của Go runtime, chịu trách nhiệm phân phối các goroutine tới các OS thread để thực thi.

Go scheduler là scheduler mô hình **M:N**:

- **G**: Goroutine.
- **M**: Machine, thường là OS thread.
- **P**: Logical processor, chứa context để chạy goroutine.

Số lượng P thường được quyết định bởi `GOMAXPROCS`. Mặc định `GOMAXPROCS` bằng số CPU core.

### Cách hoạt động đơn giản

1. Khi bạn gọi `go func()`, một goroutine mới được tạo.
2. Goroutine được gắn vào queue của một P.
3. M sẽ lấy goroutine từ P để chạy.
4. Nếu goroutine bị block vì I/O, channel, mutex, scheduler có thể chuyển M sang goroutine khác.
5. Nếu M bị block lâu trong system call, runtime có thể tách P khỏi M và gắn P vào M khác để tiếp tục chạy goroutine khác.
6. Go scheduler dùng cơ chế **work stealing** để cân bằng goroutine giữa các P.

### Ví dụ

```go
package main

import (
    "fmt"
    "sync"
)

func worker(id int, wg *sync.WaitGroup) {
    defer wg.Done()
    fmt.Println("worker", id)
}

func main() {
    var wg sync.WaitGroup

    for i := 0; i < 5; i++ {
        wg.Add(1)
        go worker(i, &wg)
    }

    wg.Wait()
}
```

Ở đây, 5 goroutine được tạo rất nhẹ. Go runtime sẽ lập lịch chúng trên các OS thread phù hợp.

### Mở rộng

- Goroutine không phải OS thread. Goroutine nhẹ hơn nhiều.
- Stack của goroutine ban đầu nhỏ và có thể tăng/giảm động.
- Go có preemptive scheduling từ các phiên bản Go hiện đại, giúp tránh một goroutine CPU-bound chiếm giữ thread quá lâu.
- Netpoller giúp Go xử lý network I/O không blocking ở tầng runtime.
- Khi phỏng vấn, nên phân biệt:
  - Go runtime: toàn bộ phần hỗ trợ thực thi.
  - Go scheduler: thành phần lập lịch goroutine.
  - OS scheduler: scheduler của hệ điều hành cho thread.

### Nguồn tham khảo

- Go Documentation: Runtime package.
- Go Blog: The Go Scheduler.
- Go Blog: Go's work-stealing scheduler.

## Câu 8: Các trường hợp memory leak thường gặp trong Go là gì?

### Câu trả lời

Trong Go, memory leak thường không phải vì GC không hoạt động, mà vì chương trình vẫn còn giữ tham chiếu đến object, khiến GC không thể thu gom.

Memory leak trong Go thường là **logic leak** hoặc **resource leak**.

### Các trường hợp phổ biến

#### 1. Goroutine leak

Goroutine bị block mãi và không bao giờ kết thúc.

Nguyên nhân thường gặp:

- Gửi/nhận channel không có đầu ra.
- Không cancel context.
- Không có timeout khi gọi API hoặc database.
- Worker không có điều kiện thoát.

Ví dụ dễ gây leak:

```go
func worker(ch chan int) {
    for v := range ch {
        fmt.Println(v)
    }
}
```

Nếu không ai đóng `ch`, goroutine có thể chạy mãi.

Cách phòng tránh:

```go
func worker(ctx context.Context, ch chan int) {
    for {
        select {
        case v := <-ch:
            fmt.Println(v)
        case <-ctx.Done():
            return
        }
    }
}
```

#### 2. Không đóng HTTP response body

Khi gọi HTTP client, nếu không đóng `resp.Body`, connection có thể không được tái sử dụng và gây rò rỉ tài nguyên.

```go
resp, err := http.Get(url)
if err != nil {
    return err
}
defer resp.Body.Close()
```

Nếu không đọc hết body, trong một số trường hợp cũng nên đọc và discard để keep-alive hoạt động hiệu quả:

```go
io.Copy(io.Discard, resp.Body)
```

#### 3. Không đóng file, database rows, connection

Các tài nguyên sau cần được đóng:

- `*os.File`
- `*sql.Rows`
- `*sql.Conn`
- gRPC stream
- WebSocket connection
- TCP connection

Ví dụ:

```go
rows, err := db.Query("SELECT id FROM users")
if err != nil {
    return err
}
defer rows.Close()
```

#### 4. Map/cache tăng không giới hạn

Nếu lưu dữ liệu vào map toàn cục mà không bao giờ xóa, bộ nhớ sẽ tăng dần.

Ví dụ:

```go
var cache = make(map[string][]byte)

func Set(key string, value []byte) {
    cache[key] = value
}
```

Nếu không có TTL, eviction hoặc size limit, cache có thể gây memory leak.

Cách xử lý:

- Dùng cache library có TTL.
- Giới hạn kích thước cache.
- Dùng LRU eviction.
- Định kỳ dọn cache.

#### 5. Timer/Ticker không được dừng

`time.NewTicker` hoặc `time.NewTimer` nếu không dừng có thể giữ tài nguyên hoặc gây goroutine leak nếu channel không được xử lý.

```go
ticker := time.NewTicker(time.Second)
defer ticker.Stop()
```

#### 6. Slice vô tình giữ array lớn

Khi slice một mảng lớn và giữ slice nhỏ, underlying array lớn vẫn có thể bị giữ lại.

```go
arr := make([]byte, 1_000_000)
small := arr[:10]
```

Nếu `small` được giữ lâu, toàn bộ `arr` có thể không được thu gom.

Cách xử lý trong một số trường hợp:

```go
small := make([]byte, 10)
copy(small, arr[:10])
```

#### 7. CGO memory không được giải phóng

Nếu dùng CGO và C cấp phát bộ nhớ, GC Go không tự động quản lý vùng nhớ C. Cần gọi free đúng cách.

### Cách phát hiện memory leak

1. Dùng `runtime/pprof`.

```go
import _ "net/http/pprof"

go func() {
    http.ListenAndServe("localhost:6060", nil)
}()
```

Xem heap:

```bash
go tool pprof http://localhost:6060/debug/pprof/heap
```

Xem goroutine:

```bash
go tool pprof http://localhost:6060/debug/pprof/goroutine
```

2. Theo dõi `runtime.MemStats`.
3. Dùng Prometheus metrics nếu có.
4. So sánh heap profile trước và sau khi load test.
5. Kiểm tra số lượng goroutine tăng liên tục.

### Mở rộng

- Memory tăng chưa chắc là leak. Có thể do cache hợp lệ, traffic tăng, hoặc GC chưa chạy.
- Goroutine leak thường nguy hiểm hơn object leak vì mỗi goroutine còn giữ stack và tài nguyên liên quan.
- Context, timeout, cancellation và close tài nguyên đúng cách là các công cụ quan trọng để tránh leak.

### Nguồn tham khảo

- Go Documentation: runtime/pprof.
- Go Blog: Profiling Go Programs.
- Go Documentation: net/http Client and Response.Body.

## Câu 9: Thiết kế graceful shutdown trong Go như thế nào?

### Câu trả lời

**Graceful shutdown** là quá trình dừng chương trình một cách an toàn:

- Không nhận request mới.
- Chờ các request đang xử lý hoàn thành.
- Đóng kết nối database.
- Flush log/metrics.
- Dừng background worker.
- Giải phóng tài nguyên.
- Tránh mất dữ liệu hoặc request bị cắt đột ngột.

Trong thực tế, graceful shutdown rất quan trọng khi deploy, restart, scale down hoặc chạy trong Kubernetes.

### Các thành phần chính

1. **Lắng nghe tín hiệu hệ thống**  
   Thường là `SIGINT` và `SIGTERM`.

2. **Dùng context để báo dừng**  
   Khi nhận tín hiệu, cancel context để các thành phần khác biết cần dừng.

3. **Gọi `http.Server.Shutdown`**  
   `Shutdown` dừng nhận request mới và chờ các request đang xử lý hoàn thành.

4. **Dùng WaitGroup để chờ background worker**  
   Nếu có goroutine chạy nền, cần đảm bảo chúng thoát trước khi chương trình kết thúc.

5. **Có timeout shutdown**  
   Không nên chờ vô hạn. Nếu quá timeout, có thể force close.

### Ví dụ

```go
package main

import (
    "context"
    "errors"
    "log"
    "net/http"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    ctx, stop := signal.NotifyContext(
        context.Background(),
        syscall.SIGINT,
        syscall.SIGTERM,
    )
    defer stop()

    mux := http.NewServeMux()
    mux.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        time.Sleep(3 * time.Second)
        w.Write([]byte("OK"))
    })

    srv := &http.Server{
        Addr:    ":8080",
        Handler: mux,
    }

    serverErr := make(chan error, 1)

    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            serverErr <- err
        }
    }()

    log.Println("server started on :8080")

    select {
    case <-ctx.Done():
        log.Println("shutdown signal received")
    case err := <-serverErr:
        log.Printf("server error: %v", err)
    }

    shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()

    if err := srv.Shutdown(shutdownCtx); err != nil {
        log.Printf("graceful shutdown failed: %v", err)
        if err := srv.Close(); err != nil {
            log.Printf("force close failed: %v", err)
        }
    }

    log.Println("server stopped")
}
```

### Thiết kế graceful shutdown cho worker nền

Nếu có worker chạy nền, nên dùng context và WaitGroup:

```go
func worker(ctx context.Context, wg *sync.WaitGroup) {
    defer wg.Done()

    ticker := time.NewTicker(time.Second)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            // làm việc định kỳ
        }
    }
}
```

Trong `main`:

```go
var wg sync.WaitGroup

ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
defer stop()

wg.Add(1)
go worker(ctx, &wg)

// chờ shutdown
<-ctx.Done()

wg.Wait()
```

### Mở rộng

- Trong Kubernetes, container thường nhận `SIGTERM`. Nếu ứng dụng không xử lý graceful shutdown, request đang xử lý có thể bị mất.
- Có thể kết hợp readiness probe để dừng nhận traffic trước khi shutdown.
- Nếu dùng message queue, cần cân nhắc:
  - Ngừng pull message mới.
  - Chờ message đang xử lý hoàn thành.
  - Commit/acknowledge đúng cách.
- Không nên gọi `os.Exit` trước khi cleanup, trừ trường hợp bất khả kháng.
- Timeout shutdown nên nhỏ hơn termination grace period của môi trường deploy.

### Nguồn tham khảo

- Go Documentation: http.Server.Shutdown.
- Go Documentation: signal package.
- Go Documentation: context package.

## Câu 10: gRPC là gì?

### Câu trả lời

**gRPC** là một framework Remote Procedure Call hiện đại, được phát triển bởi Google. gRPC cho phép client gọi một hàm/service trên server từ xa như thể đang gọi một hàm cục bộ.

gRPC thường dùng trong:

- Microservices.
- Internal API.
- Service-to-service communication.
- Hệ thống cần hiệu năng cao.
- Streaming real-time.
- Mobile hoặc backend giao tiếp với nhiều service.

### Đặc điểm chính của gRPC

1. **Dùng Protocol Buffers làm IDL và format serialization mặc định**  
   Protocol Buffers, hay protobuf, là định dạng nhị phân nhỏ gọn và có schema rõ ràng.

2. **Chạy trên HTTP/2**  
   gRPC tận dụng các tính năng của HTTP/2 như:
   - Multiplexing.
   - Header compression.
   - Streaming.
   - Binary framing.

3. **Contract-first**  
   API được định nghĩa trước trong file `.proto`. Từ đó sinh ra code client/server cho nhiều ngôn ngữ.

4. **Hỗ trợ nhiều kiểu RPC**
   - Unary RPC: client gửi một request, server trả một response.
   - Server streaming: client gửi request, server trả stream dữ liệu.
   - Client streaming: client gửi stream, server trả một response.
   - Bidirectional streaming: cả client và server gửi/nhận stream song song.

### Ví dụ file `.proto`

```proto
syntax = "proto3";

package user;

option go_package = "example.com/user";

message GetUserRequest {
    string user_id = 1;
}

message User {
    string id = 1;
    string name = 2;
    string email = 3;
}

service UserService {
    rpc GetUser(GetUserRequest) returns (User);
}
```

Từ file `.proto`, công cụ `protoc` kết hợp với plugin Go sẽ sinh ra:

- Message structs.
- Code serialize/deserialize.
- Client stub.
- Server interface.

### gRPC khác REST/JSON như thế nào?

| Tiêu chí | gRPC | REST/JSON |
|---|---|---|
| Format | Nhị phân, protobuf | Text, JSON |
| Contract | Mạnh, dùng `.proto` | Có thể dùng OpenAPI nhưng không bắt buộc |
| Transport | HTTP/2 | HTTP/1.1 hoặc HTTP/2 |
| Streaming | Hỗ trợ tốt | Thường khó hơn |
| Hiệu năng | Cao, payload nhỏ | Thường lớn hơn |
| Debug | Khó đọc hơn nếu không có tool | Dễ đọc hơn |
| Phù hợp | Internal service, microservices | Public API, web API |

### Khi nào nên dùng gRPC?

Nên dùng khi:

- Giao tiếp giữa các service nội bộ.
- Cần hiệu năng cao và payload nhỏ.
- Có nhiều service và muốn contract rõ ràng.
- Cần streaming.
- Dùng đa ngôn ngữ nhưng muốn sinh client/server code tự động.

### Khi nào nên cân nhắc REST/JSON hơn?

- API public cho browser hoặc bên thứ ba.
- Hệ thống cần debug đơn giản.
- Đội ngũ quen với REST.
- Browser gọi trực tiếp mà không dùng gRPC-Web hoặc proxy phù hợp.

### Mở rộng

- gRPC có các khái niệm quan trọng:
  - Metadata.
  - Interceptor.
  - Deadline.
  - Error code.
  - Health checking.
  - Reflection.
- Nên đặt deadline cho gRPC call để tránh request treo vô hạn.
- Trong Go, gRPC server thường kết hợp graceful shutdown, interceptor logging/recover/auth.
- gRPC không thay thế hoàn toàn REST. Nhiều hệ thống dùng cả hai: gRPC cho internal service, REST/HTTP JSON cho public API.

### Nguồn tham khảo

- gRPC Official Documentation: https://grpc.io/docs/
- Protocol Buffers Documentation: https://protobuf.dev/
- gRPC Go Documentation: https://github.com/grpc/grpc-go
