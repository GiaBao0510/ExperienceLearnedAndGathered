# Goroutine và Channel Nâng Cao

Bài viết trước đã giới thiệu cách tạo channel, gửi/nhận dữ liệu, và các pattern cơ bản. Bài này đi sâu hơn vào **mối quan hệ giữa Goroutine và Channel**: cơ chế blocking, cách channel điều phối luồng dữ liệu giữa nhiều goroutine, xử lý nhiều channel đồng thời với `select`, và các kỹ thuật quan trọng trong thực tế.

---

## 1. Bản Chất Blocking Của Channel

Hiểu đúng cơ chế blocking là nền tảng để làm chủ channel trong Go.

### 1.1. Unbuffered Channel — Cơ Chế Rendezvous

Unbuffered channel (`make(chan T)`) yêu cầu **bên gửi và bên nhận phải sẵn sàng cùng lúc**. Nếu một bên đến trước, nó phải đứng chờ bên còn lại. Cơ chế này gọi là **Rendezvous** (điểm hẹn).

Hình dung: giống như chuyển tay trực tiếp một vật giữa hai người — người đưa phải cầm vật đó trên tay cho đến khi người nhận cầm lấy. Không ai có thể "đặt xuống đất" để đi làm việc khác.

**Trường hợp gây Deadlock:**

```go
func main() {
    ch := make(chan int) // unbuffered channel
    ch <- 100           // gửi: main goroutine bị block tại đây
                        // chờ ai đó nhận, nhưng không có goroutine nào khác
    fmt.Println(<-ch)   // dòng này không bao giờ được chạy tới
}
```

```
fatal error: all goroutines are asleep - deadlock!
```

Phân tích: chương trình chỉ có một goroutine duy nhất (main). Khi gặp `ch <- 100`, nó bị block để chờ người nhận. Nhưng lệnh nhận `<-ch` nằm ở dòng ngay bên dưới — dòng mà main không bao giờ chạy tới vì đang bị block ở trên. Go runtime phát hiện không còn goroutine nào khác có thể "giải cứu" tình trạng này và báo deadlock.

**Giải pháp — tách gửi và nhận ra hai goroutine:**

```go
func main() {
    ch := make(chan int)

    go func() {
        ch <- 100 // goroutine phụ bị block tại đây, chờ main nhận
    }()

    value := <-ch // main bị block tại đây, chờ goroutine phụ gửi
    fmt.Println(value) // 100
}
```

Luồng thực thi:

```
main goroutine:   tạo ch → khởi động goroutine phụ → block tại <-ch (chờ nhận)
goroutine phụ:   block tại ch <- 100 (chờ main nhận)
"điểm hẹn":      cả hai cùng sẵn sàng → 100 được chuyển qua → cả hai tiếp tục
```

### 1.2. Buffered Channel — Gửi Không Cần Chờ Ngay

Buffered channel (`make(chan T, n)`) có một "kho chứa" với dung lượng `n`. Bên gửi chỉ bị block khi kho đầy; bên nhận chỉ bị block khi kho rỗng.

```go
func main() {
    ch := make(chan int, 3) // kho chứa được 3 giá trị

    // Gửi 3 giá trị liên tiếp — không bị block vì kho chưa đầy
    ch <- 1
    ch <- 2
    ch <- 3
    // ch <- 4 // block: kho đã đầy, phải đợi ai đó nhận trước

    fmt.Println(<-ch) // 1
    fmt.Println(<-ch) // 2
    fmt.Println(<-ch) // 3
}
```

**Bảng so sánh Unbuffered và Buffered:**

|Tiêu chí|Unbuffered|Buffered|
|---|---|---|
|Khi nào sender bị block|Luôn block cho đến khi có receiver|Chỉ block khi buffer đầy|
|Khi nào receiver bị block|Luôn block cho đến khi có sender|Chỉ block khi buffer rỗng|
|Đồng bộ|Chặt chẽ — hai bên gặp nhau cùng lúc|Lỏng hơn — hai bên có thể lệch thời điểm|
|Dùng khi nào|Cần đảm bảo handshake giữa goroutines|Cần giảm blocking, tăng throughput|

## 2. Channel Với Dữ Liệu Phức Tạp

Channel có thể truyền bất kỳ kiểu dữ liệu nào, kể cả struct tự định nghĩa.

```go
package main

import "fmt"

type Course struct {
    Title string
    Price int
}

func main() {
    ch := make(chan Course)

    go func() {
        ch <- Course{Title: "Go Programming", Price: 100}
    }()

    course := <-ch
    fmt.Println("Title:", course.Title) // Go Programming
    fmt.Println("Price:", course.Price) // 100
}
```

Lưu ý: khi truyền struct qua channel, Go tạo một **bản sao** của struct đó. Goroutine nhận có bản sao riêng, goroutine gửi có bản gốc — hai bên không chia sẻ vùng nhớ, nên an toàn. Tuy nhiên nếu truyền **con trỏ** (`*Course`) thì cả hai goroutine cùng trỏ đến một vùng nhớ, cần cẩn thận hơn.

## 3. Ownership Of Channel — Ai Sở Hữu Channel?

Đây là nguyên tắc quan trọng trong thực tế mà tài liệu cơ bản thường bỏ qua.

**Quy tắc:** Goroutine **tạo ra** channel là goroutine **sở hữu** channel đó. Goroutine sở hữu chịu trách nhiệm:

- Khởi tạo channel
- Ghi dữ liệu vào channel
- Đóng channel khi xong

Goroutine khác chỉ nên **đọc** từ channel, không đóng.

Cách thực thi nguyên tắc này là dùng **directional channel** (channel có hướng) trong khai báo hàm:

```go
package main

import "fmt"

// producer sở hữu channel: tạo, ghi, đóng
// trả về receive-only channel để bên ngoài chỉ đọc được
func producer(data []int) <-chan int {
    ch := make(chan int) // tạo channel bên trong, có toàn quyền

    go func() {
        defer close(ch) // chịu trách nhiệm đóng
        for _, v := range data {
            ch <- v
        }
    }()

    return ch // trả ra ngoài dưới dạng receive-only
}

// consumer chỉ nhận (<-chan int), không thể gửi hay đóng
func consumer(ch <-chan int) {
    for v := range ch {
        fmt.Println("Nhận:", v)
    }
}

func main() {
    ch := producer([]int{1, 2, 3, 4, 5})
    consumer(ch)
}
```

Lợi ích của kỹ thuật này: compiler sẽ báo lỗi nếu `consumer` cố tình ghi vào channel hay đóng channel — lỗi được bắt tại compile time thay vì runtime.

## 4. Pattern: Publisher / Subscriber

Một ứng dụng thực tế phổ biến của channel là mô hình **Publisher/Subscriber**: một goroutine phát dữ liệu (publisher), một goroutine khác lắng nghe và xử lý (subscriber).

```go
package main

import (
    "fmt"
    "time"
)

type Message struct {
    OrderID string
    Title   string
    Price   int
}

// publisher gửi orders vào channel rồi đóng lại
func publisher(ch chan<- Message, orders []Message) {
    defer close(ch)
    for _, order := range orders {
        ch <- order
        fmt.Printf("Published: %s\n", order.OrderID)
    }
}

// subscriber đọc từ channel cho đến khi channel đóng
func subscriber(ch <-chan Message, name string) {
    for order := range ch { // range tự dừng khi channel đóng
        fmt.Printf("[%s] Received: %s, Title: %s, Price: %d\n",
            name, order.OrderID, order.Title, order.Price)
    }
}

func main() {
    ch := make(chan Message)

    orders := []Message{
        {OrderID: "1", Title: "Product A", Price: 100},
        {OrderID: "2", Title: "Product B", Price: 200},
        {OrderID: "3", Title: "Product C", Price: 300},
    }

    go publisher(ch, orders)
    go subscriber(ch, "Subscriber-1")

    time.Sleep(2 * time.Second)
    fmt.Println("Done")
}
```

Output (thứ tự có thể thay đổi giữa các lần chạy):

```
Published: 1
[Subscriber-1] Received: 1, Title: Product A, Price: 100
Published: 2
[Subscriber-1] Received: 2, Title: Product B, Price: 200
Published: 3
[Subscriber-1] Received: 3, Title: Product C, Price: 300
Done
```

Lưu ý: cách dùng `time.Sleep` để chờ goroutine xong là không chuẩn và dễ gây lỗi trong môi trường thực tế. Phần 5 và 6 dưới đây trình bày các cách đồng bộ đúng hơn.

## 5. Vấn Đề Khi Đọc Nhiều Channel Tuần Tự

Một tình huống thường gặp khi làm việc với nhiều channel: một goroutine cần lắng nghe từ nhiều channel cùng lúc. Nếu đọc tuần tự, goroutine sẽ bị block tại channel đầu tiên và bỏ lỡ dữ liệu đến từ channel thứ hai.

### 5.1. Vấn đề — Đọc tuần tự gây blocking

```go
package main

import (
    "fmt"
    "time"
)

type Message struct {
    OrderID string
    Title   string
    Price   int
}

func buyTicket(ch chan<- Message, orders []Message) {
    defer close(ch)
    for _, order := range orders {
        ch <- order
        fmt.Printf("Sent buy order: %s\n", order.OrderID)
        time.Sleep(500 * time.Millisecond)
    }
}

func cancelTicket(ch chan<- string, ids []string) {
    defer close(ch)
    for _, id := range ids {
        ch <- id
        fmt.Printf("Sent cancel order: %s\n", id)
        time.Sleep(10 * time.Second) // giả lập xử lý chậm
    }
}

// handlerOrder đọc tuần tự: đọc xong buyChannel mới đọc cancelChannel
func handlerOrder(buyCh <-chan Message, cancelCh <-chan string) {
    for {
        order, buyOK := <-buyCh
        if buyOK {
            fmt.Printf("Handle buy: %s, %s, %d\n", order.OrderID, order.Title, order.Price)
        } else {
            fmt.Println("No more buy orders.")
            break
        }

        // block tại đây cho đến khi cancelCh có dữ liệu
        // nếu cancelCh chậm (10s), toàn bộ handler bị kẹt
        cancelID, cancelOK := <-cancelCh
        if cancelOK {
            fmt.Printf("Handle cancel: %s\n", cancelID)
        } else {
            fmt.Println("No more cancel orders.")
            break
        }
    }
}

func main() {
    buyCh := make(chan Message)
    cancelCh := make(chan string)

    buyOrders := []Message{
        {OrderID: "order-1", Title: "Movie A", Price: 10},
        {OrderID: "order-2", Title: "Movie B", Price: 15},
        {OrderID: "order-3", Title: "Movie C", Price: 20},
        {OrderID: "order-4", Title: "Movie D", Price: 25},
    }
    cancelOrders := []string{"order-2", "order-4"}

    go buyTicket(buyCh, buyOrders)
    go cancelTicket(cancelCh, cancelOrders)
    go handlerOrder(buyCh, cancelCh)

    time.Sleep(5 * time.Second)
    fmt.Println("End of main.")
}
```

Output:

```
Sent buy order: order-1
Handle buy: order-1, Movie A, 10
Handle cancel: order-2         ← chờ 10s mới có
Sent cancel order: order-2
Sent buy order: order-2
Handle buy: order-2, Movie B, 15
End of main.                   ← main hết thời gian, order-3 và order-4 bị bỏ qua
```

Vấn đề: `handlerOrder` bị block tại `<-cancelCh` vì `cancelTicket` chạy chậm (10s/lần). Trong thời gian đó, `buyCh` có dữ liệu mới nhưng không được xử lý. Đây là **sequential blocking** — đọc tuần tự từng channel một.

### 5.2. Giải Pháp — Dùng `select` Để Đọc Song Song

`select` cho phép một goroutine lắng nghe nhiều channel **cùng lúc** và xử lý channel nào có dữ liệu **trước**.

```go
package main

import (
    "fmt"
    "time"
)

type Message struct {
    OrderID string
    Title   string
    Price   int
}

func buyTicket(ch chan<- Message, orders []Message) {
    defer close(ch)
    for _, order := range orders {
        ch <- order
        fmt.Printf("Sent buy order: %s\n", order.OrderID)
        time.Sleep(1 * time.Second)
    }
}

func cancelTicket(ch chan<- string, ids []string) {
    defer close(ch)
    for _, id := range ids {
        ch <- id
        fmt.Printf("Sent cancel order: %s\n", id)
        time.Sleep(10 * time.Second)
    }
}

func handlerOrder(buyCh <-chan Message, cancelCh <-chan string) {
    for {
        select {
        case order, ok := <-buyCh:
            if ok {
                fmt.Printf("Handle buy: %s, %s, %d\n", order.OrderID, order.Title, order.Price)
            } else {
                fmt.Println("No more buy orders.")
                buyCh = nil // set nil để select bỏ qua case này từ đây trở đi
            }

        case cancelID, ok := <-cancelCh:
            if ok {
                fmt.Printf("Handle cancel: %s\n", cancelID)
            } else {
                fmt.Println("No more cancel orders.")
                cancelCh = nil // set nil để select bỏ qua case này từ đây trở đi
            }
        }

        // thoát khi cả hai channel đã đóng
        if buyCh == nil && cancelCh == nil {
            fmt.Println("All channels closed. Exiting handler.")
            break
        }
    }
}

func main() {
    buyCh := make(chan Message)
    cancelCh := make(chan string)

    buyOrders := []Message{
        {OrderID: "order-1", Title: "Movie A", Price: 10},
        {OrderID: "order-2", Title: "Movie B", Price: 15},
        {OrderID: "order-3", Title: "Movie C", Price: 20},
        {OrderID: "order-4", Title: "Movie D", Price: 25},
    }
    cancelOrders := []string{"order-2", "order-4"}

    go buyTicket(buyCh, buyOrders)
    go cancelTicket(cancelCh, cancelOrders)
    go handlerOrder(buyCh, cancelCh)

    time.Sleep(25 * time.Second)
    fmt.Println("End of main.")
}
```

Output:

```
Sent buy order: order-1
Handle buy: order-1, Movie A, 10
Sent cancel order: order-2
Handle cancel: order-2
Sent buy order: order-2
Handle buy: order-2, Movie B, 15
Sent buy order: order-3
Handle buy: order-3, Movie C, 20
Sent buy order: order-4
Handle buy: order-4, Movie D, 25
No more buy orders.
Sent cancel order: order-4
Handle cancel: order-4
No more cancel orders.
All channels closed. Exiting handler.
End of main.
```

Với `select`, handler không bị kẹt tại `cancelCh` nữa. Khi `cancelCh` chưa có dữ liệu, handler vẫn tiếp tục xử lý `buyCh` — không một sự kiện nào bị bỏ qua.

## 6. Kỹ Thuật: Set Channel Về `nil` Trong `select`

Đây là kỹ thuật quan trọng xuất hiện ở phần trên cần giải thích riêng.

**Tại sao cần set channel về `nil`?**

Khi một channel đã đóng, `select` vẫn tiếp tục kích hoạt case đó với giá trị zero và `ok = false` mỗi vòng lặp — gây ra vòng lặp vô hạn không mong muốn.

```go
// Nếu không set nil sau khi channel đóng:
for {
    select {
    case v, ok := <-ch:
        if !ok {
            fmt.Println("closed") // in liên tục vô hạn lần!
        }
    }
}
```

**Set channel về `nil` là giải pháp:** `select` sẽ **bỏ qua hoàn toàn** case có channel `nil`, không kích hoạt case đó nữa.

```go
for {
    select {
    case v, ok := <-ch:
        if !ok {
            ch = nil // từ đây select bỏ qua case này
        } else {
            fmt.Println(v)
        }
    }
}
```

## 7. Pattern: Done Channel — Dừng Goroutine Từ Bên Ngoài

Một trong những vấn đề thực tế quan trọng: làm thế nào để **yêu cầu một goroutine dừng lại** từ bên ngoài? Đây là nơi **done channel** phát huy tác dụng.

```go
package main

import (
    "fmt"
    "time"
)

// worker chạy liên tục cho đến khi nhận tín hiệu từ done channel
func worker(id int, done <-chan struct{}) {
    for {
        select {
        case <-done:
            // nhận tín hiệu dừng
            fmt.Printf("Worker %d: nhận lệnh dừng, thoát.\n", id)
            return
        default:
            // chưa có lệnh dừng, tiếp tục làm việc
            fmt.Printf("Worker %d: đang làm việc...\n", id)
            time.Sleep(500 * time.Millisecond)
        }
    }
}

func main() {
    done := make(chan struct{}) // channel tín hiệu, không cần truyền dữ liệu

    go worker(1, done)
    go worker(2, done)

    time.Sleep(2 * time.Second)

    // Đóng done channel để phát tín hiệu dừng đến TẤT CẢ workers cùng lúc
    close(done)

    time.Sleep(500 * time.Millisecond)
    fmt.Println("Main: tất cả workers đã dừng.")
}
```

Điểm quan trọng: `close(done)` phát tín hiệu đến **tất cả** goroutine đang lắng nghe `done` cùng một lúc. Đây là cơ chế broadcast hiệu quả hơn việc gửi từng tín hiệu riêng lẻ.

Dùng `struct{}` thay vì `bool` cho done channel vì `struct{}` không chiếm bộ nhớ — đây là quy ước phổ biến trong Go.

## 8. Pattern: Timeout Với `select`

Dùng `time.After` để đặt thời hạn tối đa cho một thao tác, tránh chờ đợi vô hạn.

```go
package main

import (
    "fmt"
    "time"
)

func fetchData(ch chan<- string) {
    time.Sleep(3 * time.Second) // giả lập tác vụ chậm
    ch <- "data từ server"
}

func main() {
    ch := make(chan string)
    go fetchData(ch)

    select {
    case result := <-ch:
        fmt.Println("Nhận được:", result)
    case <-time.After(2 * time.Second):
        fmt.Println("Timeout: server không phản hồi trong 2s")
    }
}
```

Output:

```
Timeout: server không phản hồi trong 2s
```

Kết hợp timeout và done channel để xây dựng logic hủy yêu cầu hoàn chỉnh hơn:

```go
func process(done <-chan struct{}) (string, error) {
    result := make(chan string)

    go func() {
        time.Sleep(1 * time.Second)
        result <- "kết quả xử lý"
    }()

    select {
    case res := <-result:
        return res, nil
    case <-done:
        return "", fmt.Errorf("bị hủy từ bên ngoài")
    case <-time.After(2 * time.Second):
        return "", fmt.Errorf("timeout")
    }
}
```

## 9. Các Lỗi Thường Gặp

### 9.1. Send On Closed Channel — Gửi Vào Channel Đã Đóng

```go
// SAI
func main() {
    ch := make(chan int)
    close(ch)
    ch <- 1 // panic: send on closed channel
}

// ĐÚNG — đảm bảo close chỉ gọi sau khi gửi xong
func main() {
    ch := make(chan int, 1)
    go func() {
        defer close(ch) // đóng sau khi goroutine hoàn thành
        ch <- 1
    }()
    fmt.Println(<-ch)
}
```

### 9.2. Goroutine Leak — Goroutine Bị Bỏ Quên

```go
// SAI — goroutine bị kẹt mãi mãi vì không ai gửi vào ch
func leak() {
    ch := make(chan int)
    go func() {
        v := <-ch // chờ mãi, không bao giờ nhận được
        fmt.Println(v)
    }()
    // hàm kết thúc, goroutine bên trong vẫn còn sống — goroutine leak
}

// ĐÚNG — dùng done channel để thoát goroutine khi cần
func noLeak() {
    ch := make(chan int)
    done := make(chan struct{})

    go func() {
        select {
        case v := <-ch:
            fmt.Println(v)
        case <-done:
            return // thoát khi nhận tín hiệu
        }
    }()

    close(done) // phát tín hiệu thoát
}
```

### 9.3. Đóng Channel Hai Lần

```go
// SAI
func main() {
    ch := make(chan int)
    close(ch)
    close(ch) // panic: close of closed channel
}

// ĐÚNG — dùng sync.Once nếu nhiều nơi có thể gọi close
var once sync.Once
closeChannel := func() {
    once.Do(func() { close(ch) })
}
```

## 10. Tổng Kết

|Khái niệm|Điểm cốt lõi|
|---|---|
|Unbuffered channel|Gửi và nhận phải xảy ra đồng thời — Rendezvous|
|Buffered channel|Tách biệt thời điểm gửi và nhận, giảm blocking|
|Channel ownership|Goroutine tạo channel chịu trách nhiệm đóng nó|
|Directional channel|`chan<-` và `<-chan` — giới hạn quyền tại compile time|
|Đọc nhiều channel|Dùng `select`, không đọc tuần tự|
|Set channel về `nil`|Ngăn select kích hoạt case của channel đã đóng|
|Done channel|Phát tín hiệu dừng đến nhiều goroutine cùng lúc|
|Timeout|Kết hợp `select` và `time.After` để tránh chờ vô hạn|
|Goroutine leak|Luôn đảm bảo goroutine có đường thoát|

> **Phần tiếp theo:** Chúng ta sẽ tìm hiểu về **sync.Mutex và sync.RWMutex** — cơ chế đồng bộ hóa bằng khóa khi cần nhiều goroutine cùng truy cập một vùng dữ liệu dùng chung mà channel không phải lựa chọn phù hợp.
