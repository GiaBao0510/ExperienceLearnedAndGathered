# Middleware trong Lập trình Backend

## 1. Bản chất Middleware

##### Middleware là gì?

**Middleware** là phần mềm trung gian dùng để kết nối các thành phần trong hệ thống, phần mềm hoặc service.

Trong [lập trình backend](https://200lab.io/blog/backend-la-gi-tu-hoc-rest-api-golang/), **middleware** nằm giữa **Request** và **Response**, có nhiệm vụ tiếp nhận và xử lý thông tin, hỗ trợ cho các middleware tiếp theo hoặc cho chính Request/Response đó.

![](https://statics.cdn.200lab.io/2022/06/middleware-request-response.jpeg?width=800)

Trong các hệ thống phân tán, middleware là các service trung gian kết nối các thành phần quan trọng với nhau.

![](https://statics.cdn.200lab.io/2022/06/middleware-distributed-system.png?width=800)

##### Phân loại Middleware

Dựa theo [Wikipedia](https://en.wikipedia.org/wiki/Middleware), có 4 loại middleware theo định nghĩa tổng quát trong ngành phần mềm:

- **Transactional**: Xử lý các transaction đồng bộ và bất đồng bộ dưới dạng một nhóm yêu cầu liên kết từ các hệ thống phân tán — ví dụ giao dịch ngân hàng hoặc thanh toán thẻ tín dụng.
- **Message**: Sử dụng trong message queue và các kiến trúc gửi message, hỗ trợ giao tiếp đồng bộ và bất đồng bộ.
- **Procedural**: Các kiến trúc từ xa (remote) và cục bộ (local) để kết nối, chuyển đổi và truy xuất phản hồi của các giao tiếp hệ thống không đồng bộ.
- **Object-oriented**: Tương tự middleware hướng thủ tục (Procedural), nhưng kết hợp thêm các nguyên tắc lập trình hướng đối tượng (OOP) — bao gồm tham chiếu đối tượng, exception, và kế thừa thuộc tính thông qua các yêu cầu đối tượng phân tán.

> **Lưu ý quan trọng:** Bốn loại middleware trên là phân loại **tổng quát** của khái niệm middleware trong toàn ngành phần mềm (bắt nguồn từ các hệ thống enterprise cũ như CORBA, message-oriented middleware, TP monitor...). Phần còn lại của tài liệu này tập trung vào một dạng cụ thể và phổ biến hơn nhiều trong lập trình web hiện đại: **HTTP Middleware** — chuỗi hàm xử lý nằm trong pipeline xử lý request/response của một web server (Gin, Echo, Express...). Loại middleware này không khớp hoàn toàn với 4 phân loại trên, mà gần với khái niệm **request/response interceptor** hơn. 

##### Tại sao phải dùng Middleware?

Mục đích chính của middleware là chia nhỏ các thành phần trong hệ thống, giúp dễ dàng tái sử dụng và lắp ghép cho nhiều trường hợp khác nhau.

Trong phần tiếp theo, tài liệu sẽ tập trung vào middleware trong lập trình backend, cụ thể là [REST API với Golang](https://200lab.io/blog/lap-trinh-rest-api-todo-list-voi-golang/).

Xử lý một request trong REST API bao gồm rất nhiều logic nghiệp vụ. Trong đó có nhiều logic lặp lại ở nhiều request khác nhau như: _Logging_, _Authentication_, _Parse body data_... Để dễ dàng tái sử dụng và phối hợp các logic này, việc sử dụng middleware là rất cần thiết.

Ví dụ với trường hợp **kiểm tra Authorization** (quyền truy cập) cho các request yêu cầu client gửi kèm **access token**: nếu access token không hợp lệ hoặc hết hạn, middleware có thể phản hồi lỗi ngay trước khi request chạm đến các hàm xử lý nghiệp vụ tiếp theo — tiết kiệm tài nguyên và giữ code sạch.

Vì lợi ích này, hầu hết framework xây dựng website và REST API đều hỗ trợ middleware: **Express** (Node.js), **Gin**, **Echo** (Golang), **Laravel** (PHP)...

##### Ưu / Nhược điểm

**Ưu điểm:**

- **Tính mô-đun cao (Modularity):** Tách biệt các mối quan tâm (separation of concerns). Logic nghiệp vụ chính không bị pha trộn với các tác vụ phụ trợ như kiểm tra quyền hoặc xử lý lỗi.
- **Dễ bảo trì và mở rộng:** Dễ dàng thêm, bớt hoặc thay đổi một bước xử lý mà không ảnh hưởng đến luồng code chính hoặc các thành phần khác.
- **Tái sử dụng (Reusability):** Middleware có thể được dùng lại cho nhiều route, hoặc thậm chí chia sẻ giữa các dự án khác nhau.
- **Quản lý luồng linh hoạt:** Cho phép chặn (short-circuit) request ngay lập tức nếu không đáp ứng điều kiện (ví dụ: chưa đăng nhập), mà không cần đi tiếp vào sâu hệ thống.

**Nhược điểm:**

- **Tăng độ trễ (Latency):** Đi qua một chuỗi middleware dài có thể làm chậm thời gian phản hồi tổng thể của hệ thống.
- **Khó gỡ lỗi (Debugging):** Khi xảy ra lỗi, việc truy xuất nguyên nhân có thể phức tạp hơn do request phải đi qua nhiều tầng trung gian trước khi đến đích.
- **Chi phí thiết lập ban đầu:** Cần thiết kế cấu trúc ban đầu phức tạp hơn và tuân thủ quy tắc nghiêm ngặt về **thứ tự thực thi**.

## 2. Kiến trúc Pipeline & Luồng dữ liệu

##### Khái niệm Pipeline (Đường ống)

**Pipeline middleware** là chuỗi các thành phần phần mềm (middleware) được liên kết tuần tự. Khi một request HTTP được gửi đến, nó sẽ đi qua từng middleware trong chuỗi. Mỗi middleware có thể xử lý request và quyết định chuyển tiếp cho middleware tiếp theo, hoặc ngắt pipeline để trả kết quả về ngay cho client.

![](https://images.viblo.asia/d8c71c2f-bed0-4f88-a39c-6c2bdbc49ffb.jpg)

##### Mô hình Củ hành (Onion Model)

**Onion Model (Mô hình củ hành)** trong middleware là cấu trúc nơi các tầng trung gian bao bọc lấy trình xử lý cốt lõi (core handler). Khi có request, luồng xử lý đi từ ngoài vào trong qua từng lớp. Sau khi lõi xử lý xong, luồng lại đi từ trong ra ngoài qua chính các lớp đó theo thứ tự ngược lại.

![](https://encrypted-tbn0.gstatic.com/images?q=tbn:ANd9GcRhNK7V3uw1TCS7Huqzah-OF3A3DGa9GIW_nlcI0fMWWA&s=10)

Mô hình này được ứng dụng rộng rãi trong nhiều framework hiện đại: **Koa** (Node.js), **ASP.NET Core**, **Express.js** (thông qua thư viện bổ sung), và trong Go — ví dụ **Gin**, **Echo**, hay **Chi router**.


**Luồng xử lý (Request/Response Pipeline)**

Luồng hoạt động theo cơ chế **vào → lõi → ra** (Out-In-Out), cho phép chạy logic _tiền xử lý_ (trước khi tới lõi) và _hậu xử lý_ (sau khi lõi tạo response).

- **Lớp ngoài cùng (Lớp 1 — Tiền xử lý):** Nhận request đầu tiên. Thường dùng cho các tác vụ chung như ghi log (logging), xác thực (authentication), hoặc xử lý CORS.
- **Lớp giữa (Lớp 2):** Tiếp tục xử lý hoặc kiểm tra quyền cụ thể (authorization), phân tích dữ liệu đầu vào.
- **Lớp lõi (Core Handler):** Xử lý logic nghiệp vụ chính của ứng dụng và tạo ra kết quả trả về.
- **Lớp giữa (Quay ra — Lớp 2):** Thực hiện hậu xử lý như đo thời gian phản hồi hoặc nén dữ liệu.
- **Lớp ngoài cùng (Quay ra — Lớp 1):** Lớp đầu tiên nhận lại response để thêm header cuối cùng trước khi gửi về client.

**Nguyên lý hoạt động (Mẫu thiết kế Decorator)**

Các middleware hoạt động như những hàm bọc (wrapper), gọi đến middleware tiếp theo thông qua một hàm thường được gọi là `next()`.

```
Client
  │
  ▼
┌─────────────────────────────────────────────────────┐
│ Middleware 1 (Tiền xử lý: Log, Auth)                 │
│  ┌───────────────────────────────────────────────┐  │
│  │ Middleware 2 (Bắt lỗi, Thêm Header)            │  │
│  │  ┌───────────────────────────────────────────┐│  │
│  │  │ Core Handler (Logic nghiệp vụ chính)       ││  │
│  │  └───────────────────────────────────────────┘│  │
│  │ Middleware 2 (Hậu xử lý)                       │  │
│  └───────────────────────────────────────────────┘  │
│ Middleware 1 (Hậu xử lý)                             │
└─────────────────────────────────────────────────────┘
  │
  ▼
Client
```



Ví dụ minh họa bằng code Go (dùng `net/http` thuần, không framework) để thấy rõ cơ chế Decorator:

```go
type Middleware func(http.Handler) http.Handler

// Middleware ghi log — chạy tiền xử lý trước next(), hậu xử lý sau next()
func LoggingMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        log.Printf("→ %s %s", r.Method, r.URL.Path) // tiền xử lý

        next.ServeHTTP(w, r) // gọi middleware/handler kế tiếp trong chuỗi

        log.Printf("← %s %s (%v)", r.Method, r.URL.Path, time.Since(start)) // hậu xử lý
    })
}

// Ghép nhiều middleware lại thành một pipeline
func Chain(h http.Handler, middlewares ...Middleware) http.Handler {
    for i := len(middlewares) - 1; i >= 0; i-- {
        h = middlewares[i](h)
    }
    return h
}
```

Đoạn code trên minh họa rõ cơ chế Decorator: mỗi middleware là một hàm nhận vào `http.Handler` và trả về một `http.Handler` mới đã được "bọc" thêm logic — đúng bản chất của Onion Model.

##### Cơ chế chuyển tiếp và Ngắt dòng (Short-circuit)

Trong pipeline, mỗi middleware có hai lựa chọn tại bất kỳ thời điểm nào:

1. **Chuyển tiếp (Pass-through):** Gọi `next()` (hoặc `c.Next()` trong Gin) để nhường quyền xử lý cho middleware/handler tiếp theo trong chuỗi.
2. **Ngắt dòng (Short-circuit):** Không gọi `next()`, mà trả response trực tiếp cho client ngay tại middleware hiện tại. Các middleware và handler phía sau sẽ **không bao giờ được thực thi**.

Short-circuit là cơ chế quan trọng để middleware có thể "chặn" request sớm, tránh lãng phí tài nguyên xử lý cho các request chắc chắn sẽ bị từ chối. Ví dụ điển hình: middleware xác thực JWT.

```go
// Ví dụ short-circuit trong Gin
func AuthMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        token := c.GetHeader("Authorization")
        if token == "" || !isValidToken(token) {
            // Ngắt dòng: trả lỗi ngay, KHÔNG gọi c.Next()
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{
                "error": "invalid or missing token",
            })
            return // handler phía sau sẽ không được gọi
        }

        // Token hợp lệ → chuyển tiếp cho middleware/handler kế tiếp
        c.Next()
    }
}
```

Trong Gin, việc gọi `c.Abort()` (hoặc các biến thể `c.AbortWithStatus*`) là bắt buộc để thực sự ngắt dòng — chỉ đơn thuần không gọi `c.Next()` là chưa đủ, vì Gin vẫn tiếp tục chạy các middleware tiếp theo đã được đăng ký trong chuỗi nếu không gọi `Abort()` một cách tường minh (đây là điểm khác biệt dễ gây nhầm lẫn so với middleware kiểu `net/http` thuần, nơi việc không gọi `next()` đã đủ để dừng chuỗi).

##### Cơ chế chia sẻ dữ liệu (Context/State Sharing)

Một vấn đề thực tế phát sinh khi dùng middleware: làm sao để middleware **truyền dữ liệu** cho middleware hoặc handler phía sau nó trong cùng một request? Ví dụ: middleware xác thực JWT giải mã token và cần truyền `user_id` cho handler nghiệp vụ phía sau sử dụng.

Trong Go, cơ chế chuẩn để giải quyết bài toán này là `context.Context` — một cấu trúc dữ liệu đi kèm theo mỗi request, cho phép lưu trữ và truy xuất dữ liệu dùng chung xuyên suốt pipeline.

```go
// Middleware lưu user_id vào context sau khi xác thực thành công
func AuthMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        userID := extractUserIDFromToken(r) // giả sử đã xác thực thành công

        // Gắn userID vào context của request
        ctx := context.WithValue(r.Context(), userIDKey, userID)

        // Truyền request mới (mang context đã cập nhật) cho middleware/handler kế tiếp
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

// Handler nghiệp vụ đọc lại user_id đã được middleware phía trước lưu vào context
func ProfileHandler(w http.ResponseWriter, r *http.Request) {
    userID, ok := r.Context().Value(userIDKey).(string)
    if !ok {
        http.Error(w, "unauthorized", http.StatusUnauthorized)
        return
    }
    // Sử dụng userID để xử lý nghiệp vụ...
}
```

Trong Gin, cơ chế tương tự nhưng đơn giản hơn nhờ `gin.Context` đã tích hợp sẵn key-value store nội bộ:

```go
func AuthMiddleware() gin.HandlerFunc {
    return func(c *gin.Context) {
        userID := extractUserIDFromToken(c.Request)
        c.Set("user_id", userID) // lưu vào context của Gin
        c.Next()
    }
}

func ProfileHandler(c *gin.Context) {
    userID, exists := c.Get("user_id") // đọc lại giá trị đã lưu
    if !exists {
        c.AbortWithStatus(http.StatusUnauthorized)
        return
    }
    // Sử dụng userID để xử lý nghiệp vụ...
}
```

**Lưu ý quan trọng:** Khi dùng `context.WithValue` trong Go thuần, nên dùng một kiểu dữ liệu riêng (custom type) làm key thay vì `string` trực tiếp, để tránh xung đột key giữa các package khác nhau:

```go
type contextKey string
const userIDKey contextKey = "user_id"
```

## 3. Thứ tự Middleware

##### Thứ tự lý tưởng của một Pipeline chuẩn

```
Request
   │
   ▼
┌────────────────────┐
│ 1. Recovery          │ ← ngoài cùng, bắt panic từ mọi lớp phía sau
├────────────────────┤
│ 2. RequestID          │ ← gắn UUID cho request
├────────────────────┤
│ 3. RealIP             │ ← xác định IP thật (dùng cho log, rate limit)
├────────────────────┤
│ 4. Logger             │ ← ghi log (cần request_id, real_ip đã có)
├────────────────────┤
│ 5. Metrics            │ ← đo lường số liệu Prometheus
├────────────────────┤
│ 6. Tracing            │ ← tạo span cho distributed tracing
├────────────────────┤
│ 7. Timeout            │ ← giới hạn thời gian toàn bộ pipeline phía sau
├────────────────────┤
│ 8. RateLimiter         │ ← chặn spam TRƯỚC KHI tốn công xác thực
├────────────────────┤
│ 9. CORS               │ ← xử lý preflight OPTIONS
├────────────────────┤
│ 10. SecurityHeaders    │ ← set header bảo mật
├────────────────────┤
│ 11. Auth               │ ← xác thực JWT (chỉ route cần)
├────────────────────┤
│ 12. Authorization       │ ← kiểm tra role (chỉ route cần)
├────────────────────┤
│ 13. Validation          │ ← validate request body (chỉ route cần)
├────────────────────┤
│ 14. Business Handler    │ ← logic nghiệp vụ — trong cùng
└────────────────────┘
   │
   ▼
Response
```

##### Tại sao thứ tự này lại quan trọng?

Thứ tự middleware không phải là quy ước tùy tiện — mỗi vị trí phản ánh một lý do kỹ thuật cụ thể. Dưới đây là các nguyên tắc quan trọng nhất:

- **Recovery phải đứng đầu tiên (ngoài cùng):** Nếu đặt `Authentication` trước `Recovery`, và middleware `Authentication` xảy ra `panic` (ví dụ do parse token lỗi không kiểm soát), toàn bộ server sẽ sập vì không có lớp nào phía ngoài để bắt (`recover()`) lỗi đó. `Recovery` phải bao bọc toàn bộ pipeline để đảm bảo bất kỳ `panic` nào ở tầng dưới đều được chặn lại và trả về lỗi 500 thay vì crash server.
    
- **Logger phải đứng trước Authentication:** Nếu đặt `Logger` sau `Authentication`, các request bị từ chối vì sai token (401 Unauthorized) sẽ **không được ghi log** — vì middleware đã bị chặn (short-circuit) trước khi đến `Logger`. Điều này gây khó khăn khi điều tra các cuộc tấn công brute-force hoặc truy cập trái phép, vì chính xác những request đáng ngờ nhất lại là những request không được log lại.
    
- **RequestID và RealIP nên đứng sớm:** Các middleware phía sau (Logger, Tracing, RateLimiter) đều cần các thông tin này để hoạt động đúng — ví dụ Logger cần `request_id` để gắn vào mỗi dòng log giúp truy vết một request xuyên suốt hệ thống (đặc biệt quan trọng trong kiến trúc microservices).
    
- **CORS phải đứng trước Authentication:** Trình duyệt gửi request `OPTIONS` (preflight request) trước khi gửi request thực sự cho các request cross-origin. Request `OPTIONS` này thường **không mang theo token xác thực**. Nếu đặt `Authentication` trước `CORS`, mọi preflight request sẽ bị từ chối với lỗi 401, khiến trình duyệt chặn luôn request thực sự — lỗi CORS rất phổ biến mà nguyên nhân thực chất là do sai thứ tự middleware.
    
- **Authentication phải đứng trước Authorization:** Về mặt logic, hệ thống cần biết **ai đang gọi request** (Authentication — xác thực danh tính) trước khi có thể quyết định **người đó được phép làm gì** (Authorization — phân quyền). Đảo ngược thứ tự này là vô nghĩa vì Authorization không có dữ liệu định danh người dùng để kiểm tra quyền.

## Bổ sung kiến thức

### 1. Vị trí của RateLimiter — một điểm cần cân nhắc thêm

Thứ tự trong bản gốc đặt `RateLimiter` sau `Timeout` và trước `CORS`. Đây là cách sắp xếp hợp lý cho **rate limit theo IP** (áp dụng đồng đều cho mọi request trước khi biết danh tính người dùng). Tuy nhiên, trong thực tế có hai chiến lược rate limiting khác nhau cần thứ tự khác nhau:

- **Rate limit theo IP (chống DDoS cơ bản):** Nên đặt **sớm nhất có thể** — thậm chí trước cả `Logger` — để từ chối request ngay lập tức với chi phí xử lý tối thiểu, tránh lãng phí tài nguyên ghi log cho traffic tấn công.
- **Rate limit theo user/API key (giới hạn gói dịch vụ):** Bắt buộc phải đặt **sau Authentication**, vì cần biết danh tính người dùng trước mới xác định được hạn mức tương ứng.

Nhiều hệ thống thực tế dùng cả hai lớp rate limiting ở hai vị trí khác nhau trong cùng một pipeline.

### 2. Middleware nên implement dưới dạng interface hay function?

Trong Gin, middleware thường được viết dưới dạng hàm trả về `gin.HandlerFunc` như các ví dụ trên. Tuy nhiên, với các middleware phức tạp cần cấu hình hoặc dependency injection (ví dụ: middleware logging cần một logger instance, middleware rate limit cần một Redis client), nên đóng gói middleware thành struct với method thay vì closure đơn thuần:

```go
type RateLimiterMiddleware struct {
    redisClient *redis.Client
    limit       int
}

func NewRateLimiterMiddleware(client *redis.Client, limit int) *RateLimiterMiddleware {
    return &RateLimiterMiddleware{redisClient: client, limit: limit}
}

func (m *RateLimiterMiddleware) Handle() gin.HandlerFunc {
    return func(c *gin.Context) {
        // logic dùng m.redisClient, m.limit...
        c.Next()
    }
}
```

Cách tiếp cận này giúp middleware dễ test hơn (có thể mock `redisClient`) và tránh biến toàn cục (global variable) — một antipattern phổ biến khi middleware cần truy cập tài nguyên bên ngoài.

### 3. Testing middleware độc lập

Một lợi ích quan trọng của kiến trúc middleware — vốn không được đề cập trong bản gốc — là khả năng **test độc lập** từng middleware mà không cần khởi động toàn bộ ứng dụng:

```go
func TestAuthMiddleware_RejectsMissingToken(t *testing.T) {
    router := gin.New()
    router.Use(AuthMiddleware())
    router.GET("/protected", func(c *gin.Context) {
        c.Status(http.StatusOK)
    })

    req := httptest.NewRequest("GET", "/protected", nil) // không có header Authorization
    w := httptest.NewRecorder()
    router.ServeHTTP(w, req)

    assert.Equal(t, http.StatusUnauthorized, w.Code)
}
```

Vì mỗi middleware là một đơn vị độc lập theo mẫu Decorator, việc viết unit test cho từng middleware riêng biệt (thay vì phải test tích hợp toàn bộ pipeline) giúp phát hiện lỗi sớm và tăng tốc độ phát triển đáng kể.
