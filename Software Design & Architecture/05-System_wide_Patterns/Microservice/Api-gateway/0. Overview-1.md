# Tổng quan về API Gateway

## 1. Đặt vấn đề

Trong kiến trúc microservices, một hệ thống trung bình có thể có từ vài chục đến hàng trăm services độc lập với nhau. Nếu client giao tiếp trực tiếp với từng service, sơ đồ kết nối sẽ trở nên cực kỳ phức tạp và khó quản lý — mỗi client phải tự biết địa chỉ của từng service, tự xử lý xác thực, tự theo dõi trạng thái từng endpoint.

Để giải quyết vấn đề này, **API Gateway** ra đời với vai trò là một cổng trung gian duy nhất đứng giữa client và toàn bộ hệ thống microservices phía sau.

---
## 2. API Gateway là gì?

API Gateway thực chất là một **reverse proxy được mở rộng**, cung cấp nhiều tính năng và khả năng tuỳ chỉnh hơn so với reverse proxy thông thường. Nó hoạt động như "cửa ngõ" duy nhất vào hệ thống: nhận toàn bộ các request từ client, thực hiện xác thực, kiểm tra chính sách, rồi điều hướng đến service phù hợp ở phía sau.

> **Khác biệt với Reverse Proxy thông thường:** Reverse proxy đơn thuần chỉ chuyển tiếp request đến server backend. API Gateway làm được nhiều hơn thế: xác thực, giới hạn tốc độ, biến đổi dữ liệu, ghi log tập trung, phát hiện dịch vụ, v.v.

![Sơ đồ API Gateway](https://images.viblo.asia/7c5add32-77c0-43c4-bb76-f87ec53badaa.png)

Cụ thể, API Gateway chịu trách nhiệm:

- Điều phối (routing) các request đến đúng service backend.
- Áp dụng các chính sách lưu lượng: giới hạn tốc độ (rate limiting), lưu bộ đệm (caching).
- Áp dụng các chính sách bảo mật: xác thực (authentication), phân quyền (authorization).
- Thu thập dữ liệu giám sát: số lượng request, thời gian phản hồi, tỷ lệ lỗi.
- Biến đổi request/response khi cần thiết (ví dụ: chuyển đổi giao thức).

### 3.1. API Security (Bảo mật API)

Khi công khai API ra bên ngoài, bạn cần bảo vệ nó khỏi các truy cập trái phép — chỉ client có đủ quyền mới được tương tác với các dịch vụ tương ứng. Dưới đây là các kỹ thuật bảo mật phổ biến được tích hợp trong API Gateway.

#### 3.1.1. API Key

**API Key** là một chuỗi ký tự duy nhất được cấp cho mỗi client. Chuỗi này được đính kèm vào mỗi HTTP request để Gateway xác minh danh tính của client trước khi cho phép truy cập.

```bash
# Kong Gateway Demo

# Đăng ký consumer (đại diện cho một client/đối tác)
curl -X POST http://localhost:8001/consumers/ \
  --data "username=partner_001"

# Bật plugin key-auth cho service movies
curl -X POST http://localhost:8001/services/movies/plugins \
  --data "name=key-auth" \
  --data "config.key_names=apikey"

# Tạo API key cho consumer vừa đăng ký
curl -X POST http://localhost:8001/consumers/partner_001/key-auth
```

**Lưu ý:** API Key hoạt động tương tự như một chiếc chìa khoá — bất kỳ ai có key đều có thể gọi API. Vì vậy, bạn nên:

- Đặt thời hạn sử dụng cho key để giảm thiểu rủi ro khi bị lộ.
- Dùng API Key chủ yếu cho xác thực **server-to-server**, quản lý nội bộ, hoặc cấp quyền cho đối tác tin cậy.
- Không dùng API Key để xác thực người dùng cuối (end-user).

#### 3.1.2. OAuth 2.0

**OAuth 2.0** là tiêu chuẩn phân quyền (authorization) phổ biến, cho phép ứng dụng bên thứ ba truy cập tài nguyên của người dùng mà **không cần** người dùng tiết lộ mật khẩu.

`access_token` sinh ra từ luồng OAuth 2.0 thường có thời gian sống ngắn (vài phút đến vài giờ) để giảm thiểu rủi ro bảo mật nếu token bị đánh cắp.

```bash
# Bật plugin OAuth2 cho service movies
# Cấp quyền cho bên thứ 3 truy cập vào scope read_profile và read_history
curl -X POST http://localhost:8001/services/movies/plugins \
  --data "name=oauth2" \
  --data "config.enable_authorization_code=true" \
  --data "config.token_expiration=240" \
  --data "config.scopes=read_profile,read_history"
```

> **Phân biệt Authentication vs Authorization:**
> 
> - **Authentication (Xác thực):** Xác minh danh tính — "Bạn là ai?"
> - **Authorization (Phân quyền):** Kiểm tra quyền hạn — "Bạn được làm gì?" OAuth 2.0 xử lý phần **authorization**, thường kết hợp với OpenID Connect để xử lý cả **authentication**.

#### 3.1.3. JWT (JSON Web Token)

**JWT** là phương pháp xác thực phổ biến nhất hiện nay. Một JWT là một chuỗi mã hoá gồm ba phần được phân tách bởi dấu `.` :

- **Header:** Thông tin về thuật toán mã hoá (ví dụ: HS256, RS256).
- **Payload:** Dữ liệu cần truyền tải (thông tin người dùng, quyền truy cập, thời hạn hết hạn...).
- **Signature:** Chữ ký số đảm bảo token không bị giả mạo hoặc chỉnh sửa.

```bash
# Bật JWT plugin cho service movies
curl -X POST http://localhost:8001/services/movies/plugins \
  --data "name=jwt" \
  --data "config.claims_to_verify=exp"
```

**Lưu ý:** API Gateway xác minh chữ ký JWT tại cổng vào, giúp các service phía sau không cần tự làm việc này, giảm thiểu trùng lặp logic xác thực.

### 3.2. Rate Limiting (Giới hạn tần suất)

Rate Limiting giới hạn số lượng request mà một client có thể gửi trong một khoảng thời gian nhất định. Đây là biện pháp cần thiết để:

- **Ngăn chặn lạm dụng:** Chặn các bot/crawler tự động gửi hàng nghìn request/giây, gây quá tải hệ thống.
- **Đảm bảo tính công bằng:** Phân bổ tài nguyên hợp lý giữa các client và các loại request khác nhau.
- **Bảo vệ khỏi tấn công DDoS** ở tầng ứng dụng.

Ví dụ thực tế: Giao dịch thanh toán vé (ưu tiên cao) cần giới hạn khác với việc tải trang thông tin người dùng (ưu tiên thấp).

```yaml
# Kong Gateway Demo — cấu hình rate limiting phân tầng
services:
  - name: booking-transactions       # Giao dịch quan trọng, giới hạn cao hơn
    url: http://booking.200lab.io
    plugins:
      - name: rate-limiting
        config:
          minute: 500
          policy: local

  - name: informational-queries      # Truy vấn thông thường, giới hạn thấp hơn
    url: http://user.200lab.io
    plugins:
      - name: rate-limiting
        config:
          minute: 100
          policy: local
```

Khi vượt quá giới hạn, API Gateway trả về mã lỗi **HTTP 429 Too Many Requests**.

### 3.3. Caching (Lưu bộ đệm)

**Caching** là cơ chế lưu tạm thời kết quả của một request để tái sử dụng cho các request giống nhau trong tương lai, thay vì phải truy vấn lại service backend mỗi lần.

**Lợi ích:**

- Giảm thời gian phản hồi cho client.
- Giảm tải cho các service backend.
- Tiết kiệm tài nguyên tính toán.

**Khi nào nên dùng Caching:** Phù hợp với dữ liệu ít thay đổi (danh mục sản phẩm, cấu hình hệ thống). **Không nên dùng** với dữ liệu thay đổi liên tục (số dư tài khoản, trạng thái đơn hàng thời gian thực).

```bash
# Bật proxy-cache plugin cho service movies
curl -i -X POST http://localhost:8001/services/movies/plugins \
  --data "name=proxy-cache" \
  --data "config.strategy=memory" \
  --data "config.content_type=application/json" \
  --data "config.cache_ttl=300" \
  --data "config.cache_control=true"
```

Tham số `cache_ttl=300` nghĩa là dữ liệu được giữ trong cache tối đa 300 giây (5 phút).

### 3.4. Load Balancing (Cân bằng tải)

**Load Balancing** phân phối đều các request đến nhiều instance của cùng một service, tránh để một instance nào bị quá tải trong khi các instance khác còn rảnh.

Các thuật toán cân bằng tải phổ biến:

|Thuật toán|Mô tả|
|---|---|
|**Round Robin**|Lần lượt phân phối đến từng server theo vòng|
|**Least Connections**|Ưu tiên server đang xử lý ít kết nối nhất|
|**IP Hash**|Ánh xạ IP của client đến một server cố định, đảm bảo cùng một client luôn tới cùng một server|

```bash
# Tạo upstream cho users service
curl -i -X POST http://localhost:8001/upstreams/ \
  --data "name=users.service"

# Thêm hai instance vào upstream
curl -i -X POST http://localhost:8001/upstreams/users.service/targets \
  --data "target=localhost:5000"

curl -i -X POST http://localhost:8001/upstreams/users.service/targets \
  --data "target=localhost:5001"

# Trỏ service users về upstream vừa tạo
curl -X PATCH http://localhost:8001/services/users \
  --data "host=users.service"
```

### 3.5. Protocol Translation (Chuyển đổi giao thức)

**Protocol Translation** cho phép API Gateway chuyển đổi request giữa các giao thức khác nhau. Điều này rất hữu ích khi:

- Client gửi request theo giao thức HTTP/REST, nhưng service backend dùng gRPC.
- Cần tích hợp với hệ thống cũ (legacy system) sử dụng SOAP.

```bash
# Cấu hình service backend sử dụng gRPC
curl -i -X POST http://localhost:8001/services/ \
  --data "name=ride-service" \
  --data "protocol=grpc" \
  --data "host=ride-service-backend" \
  --data "port=50051"

# Cấu hình service backend sử dụng HTTP (để tích hợp SOAP)
curl -i -X POST http://localhost:8001/services/ \
  --data "name=payment-service" \
  --data "protocol=http" \
  --data "host=payment-service-backend" \
  --data "path=/payment"
```

### 3.6. Routing (Định tuyến)

API Gateway điều hướng request đến đúng service backend dựa trên các tiêu chí như:

- **Đường dẫn URL** (ví dụ: `/api/v1/users` → User Service)
- **Phương thức HTTP** (GET, POST, PUT, DELETE...)
- **HTTP Header** (ví dụ: `Accept-Language`, `X-API-Version`)
- **Tham số truy vấn** (query parameters)

```bash
# Tạo service users và orders
curl -i -X POST http://localhost:8001/services/ \
  --data "name=users-service" \
  --data "url=http://users-service-backend:8000"

curl -i -X POST http://localhost:8001/services/ \
  --data "name=orders-service" \
  --data "url=http://orders-service-backend:8000"

# Gắn route tương ứng cho từng service
curl -i -X POST http://localhost:8001/services/users-service/routes \
  --data "paths[]=/api/v1/users"

curl -i -X POST http://localhost:8001/services/orders-service/routes \
  --data "paths[]=/api/v1/orders"
```

### 3.7. Service Discovery (Phát hiện dịch vụ)

Trong môi trường microservices, các service có thể được khởi động, dừng, hoặc thay đổi địa chỉ IP liên tục (đặc biệt khi chạy trên Kubernetes). **Service Discovery** giúp API Gateway tự động phát hiện và cập nhật địa chỉ của các service backend mà không cần cấu hình thủ công.

Các công cụ Service Discovery phổ biến: **Consul**, **etcd**, **Kubernetes DNS**.

```bash
# Cấu hình upstream tích hợp với Consul để tự động phát hiện users-service
curl -i -X POST http://localhost:8001/upstreams/ \
  --data "name=users-upstream" \
  --data "service_discovery.type=consul" \
  --data "service_discovery.name=users-service"

# Trỏ service về upstream đã tích hợp Service Discovery
curl -i -X POST http://localhost:8001/services/ \
  --data "name=users-service" \
  --data "host=users-upstream"

curl -i -X POST http://localhost:8001/services/users-service/routes \
  --data "paths[]=/api/v1/users"
```

### 3.8. Logging & Monitoring (Ghi nhật ký và giám sát)

API Gateway là điểm tập trung toàn bộ lưu lượng vào/ra của hệ thống, nên đây là vị trí lý tưởng để thu thập log và số liệu giám sát, bao gồm: số lượng request, thời gian phản hồi, tỷ lệ lỗi, phân phối theo service...

```bash
# Bật HTTP log plugin, gửi log về log server tập trung
curl -i -X POST http://localhost:8001/services/movies/plugins \
  --data "name=http-log" \
  --data "config.http_endpoint=http://your-log-server:1234" \
  --data "config.method=POST"
```

Các hệ thống API Gateway thương mại (như Kong Enterprise) còn cung cấp dashboard trực quan để theo dõi traffic theo thời gian thực.
