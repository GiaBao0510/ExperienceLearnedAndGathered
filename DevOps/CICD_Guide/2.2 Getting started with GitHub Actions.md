## 1. Từ workflow trống đến pipeline hữu ích

Ở bài trước, bạn đã tạo được một workflow chạy được nhưng chưa làm việc gì thực sự có ích (chỉ in "Hello World"). Trong bài này, chúng ta sẽ biến nó thành một **pipeline CI thật sự**: tự động kiểm tra code style (lint), sau đó build và test mỗi khi có người push code.

> **Thuật ngữ:** "pipeline" (đường ống) là cách gọi khác của một chuỗi các bước xử lý tự động nối tiếp nhau — trong GitHub Actions, một pipeline CI/CD thường chính là một workflow.

Nếu một bước kiểm tra nào đó (lint, test, build...) thất bại, GitHub sẽ hiển thị trạng thái **màu đỏ** cho lần chạy đó — đây là tín hiệu trực quan để bạn biết code vừa push có vấn đề trước khi merge.

Chúng ta sẽ lưu workflow này vào file `pipeline.yml`. Bắt đầu từ một khung sườn trống:

```yaml
name: Deployment pipeline

on:
  push:
    branches:
      - main

jobs:
```

## 2. Thiết lập môi trường cho job

Trước khi chạy được lệnh lint, chúng ta cần chuẩn bị môi trường cho job — tương tự như việc cài đặt môi trường phát triển trên máy cá nhân.

### Chọn runner

```yaml
jobs:
  simple_deployment_pipeline:
    runs-on: ubuntu-latest
```

Chúng ta chọn `ubuntu-latest` (hiện tương ứng với Ubuntu 24.04) vì đây cũng là hệ điều hành dùng ở môi trường production. **Đây là một nguyên tắc quan trọng của CI:** môi trường CI càng giống môi trường production, càng tránh được tình trạng "chạy được trên CI nhưng lỗi khi lên production" (hoặc ngược lại) — vốn là vấn đề làm mất đi ý nghĩa của việc dùng CI.

### Checkout mã nguồn

Như đã biết ở bài trước, runner mặc định **không có sẵn mã nguồn** của bạn. Vì vậy, bước đầu tiên trong job luôn là lấy mã nguồn về:

```yaml
jobs:
  simple_deployment_pipeline:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
```

Từ khóa [`uses`](https://docs.github.com/en/free-pro-team@latest/actions/reference/workflow-syntax-for-github-actions#jobsjob_idstepsuses) yêu cầu step chạy một **Action** có sẵn thay vì một lệnh shell. Action giống như một hàm (function) có thể tái sử dụng — có thể do bạn tự viết trong repository, hoặc lấy từ kho công khai trên GitHub.

Ở đây ta dùng action công khai [`actions/checkout`](https://github.com/actions/checkout), ghim đúng phiên bản `@v6` để tránh bị ảnh hưởng nếu action này có breaking change ở phiên bản mới hơn. Action `checkout` làm đúng như tên gọi: clone mã nguồn từ Git về runner.

### Cài đặt Node.js

Dự án là ứng dụng JavaScript, nên cần cài Node.js trước khi chạy được các script trong `package.json`. Dùng action [`actions/setup-node`](https://github.com/actions/setup-node):

```yaml
jobs:
  simple_deployment_pipeline:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6     # Checkout the repository
      - uses: actions/setup-node@v6   # Thiết lập môi trường Node.js
        with:
          node-version: '24'          # Chọn phiên bản Node.js
```

Từ khóa [`with`](https://docs.github.com/en/free-pro-team@latest/actions/reference/workflow-syntax-for-github-actions#jobsjob_idstepswith) dùng để truyền "tham số" vào action — ở đây là phiên bản Node.js muốn dùng. Ta chọn Node 24 vì đây cũng là phiên bản đang chạy ở production (nhắc lại nguyên tắc "CI giống production" ở trên).

> **Với dự án Go:** bước tương đương sẽ là dùng action `actions/setup-go` với `go-version` thay vì `actions/setup-node` — xem lại ví dụ ở bài trước.

### Cài đặt dependencies

```yaml
jobs:
  simple_deployment_pipeline:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v6
        with:
          node-version: '24'
      - name: Install dependencies      # Cài đặt các dependencies
        run: npm install                # Cài đặt các dependencies từ package.json
```

Đến đây, môi trường đã sẵn sàng để chạy các tác vụ thực sự: lint, build, test.

## 3. Thêm bước Lint

Khi môi trường đã sẵn sàng, bạn có thể chạy bất kỳ script nào đã khai báo trong `package.json`, y hệt như khi làm trên máy cá nhân — chỉ cần thêm một step mới với `run`:

```yaml
jobs:
  simple_deployment_pipeline:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v6
        with:
          node-version: '24'
      - name: Install dependencies
        run: npm install
      - name: Check style
        run: npm run lint
```

> **Lưu ý về tên script:** ở bài tập trước, script lint trong `package.json` của dự án mẫu được đặt tên là `eslint` (chạy bằng `npm run eslint`). Ở đây ví dụ dùng `npm run lint`. Đây là hai tên script khác nhau — **hãy kiểm tra đúng tên script thật trong `package.json` của bạn** trước khi copy đoạn YAML này, để tránh lỗi "missing script".

Bạn có thể bỏ trường `name` nếu muốn — khi đó GitHub sẽ tự dùng câu lệnh (`run: ...`) làm tên hiển thị mặc định cho step:

```yaml
- run: npm run lint
```

## 7. Kiểm thử end-to-end với Playwright

> **Thuật ngữ:**
> 
> - **End-to-end test (e2e)**: kiểm thử toàn bộ hệ thống từ góc nhìn người dùng thật (mở trình duyệt, click, kiểm tra nội dung hiển thị) — khác với **unit test** (Jest) chỉ kiểm thử từng thành phần riêng lẻ.
> - **[Playwright](https://playwright.dev/)**: thư viện tự động hóa trình duyệt, phổ biến để viết e2e test cho ứng dụng web.

Bộ test hiện tại dùng Jest để kiểm thử các component React một cách độc lập — cách làm tương tự như đã học ở [phần 5 của khóa học](https://fullstackopen.com/en/part5/testing_react_apps) (phần đó dùng [Vitest](https://vitest.dev/), về cách dùng thì gần như tương đương Jest).

Kiểm thử từng component riêng lẻ là chưa đủ để đảm bảo _toàn bộ hệ thống_ hoạt động đúng. Vì vậy, ta sẽ viết thêm vài e2e test đơn giản bằng Playwright, tương tự cách đã làm ở [phần 5](https://fullstackopen.com/en/part5/).

Các bước cần thực hiện, theo thứ tự:

**Bước 1 — Cấu hình Jest để bỏ qua thư mục e2e:**

Giả sử bạn đặt các e2e test trong thư mục `e2e-tests`, cần khai báo trong `package.json` để Jest không cố chạy nhầm các file này:

```json
{
  "jest": {
    "testEnvironment": "jsdom",
    "setupFiles": ["<rootDir>/jest.setup.js"],
    "testPathIgnorePatterns": ["e2e-tests"]
  }
}
```

> **Đã sửa lỗi cú pháp:** bản gốc thiếu dấu phẩy sau `"setupFiles": [...]`, khiến đoạn JSON này không hợp lệ nếu copy trực tiếp vào file — đã thêm dấu phẩy ở trên. Ngoài ra, JSON chuẩn không hỗ trợ comment (`//`), nên phần `// ...` biểu thị "còn các cấu hình khác" trong bản gốc đã được bỏ để đoạn code chạy được ngay khi copy.

**Bước 2 — Cài đặt Playwright:**

Làm theo hướng dẫn tại [phần 5 — End to end testing với Playwright](https://fullstackopen.com/en/part5/end_to_end_testing_playwright). Khác với phần 5, lần này bạn cài Playwright **ngay trong cùng project** với phần còn lại của mã nguồn (không tách repo riêng).

**Bước 3 — Viết test đầu tiên:**

```js
const { test, describe, expect, beforeEach } = require('@playwright/test')

describe('Pokedex', () => {
  test('front page can be opened', async ({ page }) => {
     await page.goto('')
    await expect(page.getByText('ivysaur')).toBeVisible()
    await expect(page.getByText('Pokémon and Pokémon character names are trademarks of Nintendo.')).toBeVisible()
  })
})
```

> **Lưu ý:** giao diện hiển thị tên Pokémon viết hoa chữ cái đầu (ví dụ "Ivysaur"), nhưng trong mã nguồn/dữ liệu gốc lại là chữ thường (`ivysaur`) — việc viết hoa chỉ là hiệu ứng CSS. Vì `getByText` mặc định so khớp đúng nội dung text, hãy kiểm tra `ivysaur`, không phải `Ivysaur`.

**Bước 4 — Thêm script `test:e2e`** vào `package.json` để chạy e2e test từ dòng lệnh.

**Bước 5 — Tự động khởi động app khi test:** Playwright yêu cầu ứng dụng phải đang chạy khi test thực thi. Thay vì tự khởi động app thủ công, hãy cấu hình mục `webServer` trong file cấu hình Playwright (`playwright.config.js`) để Playwright tự khởi động app trước khi chạy test — xem hướng dẫn trong tài liệu chính thức của [Playwright: Web server](https://playwright.dev/docs/test-webserver).

**Bước 6 — Xác nhận chạy được trên máy cục bộ**, sau đó tích hợp bước e2e test này vào workflow GitHub Actions (thêm một step mới chạy `npm run test:e2e`, tương tự các step lint/test/build đã có).

**Bước 7 — Viết thêm một test điều hướng:** kiểm tra việc di chuyển từ trang chính sang trang chi tiết của một Pokémon cụ thể (ví dụ `ivysaur`). Chỉ cần xác minh trang chi tiết hiển thị đúng nội dung liên quan, ví dụ chuỗi `chlorophyll` (thuộc tính/ability của ivysaur). Cũng viết bằng chữ thường như lưu ý ở Bước 3, vì việc viết hoa chỉ do CSS xử lý.

### Mở rộng

- **Caching dependencies** (`actions/cache`) — cache `node_modules`/Go module cache để các lần chạy sau nhanh hơn, thay vì `npm install`/`go mod download` lại từ đầu mỗi lần.
- **Ma trận (matrix) test** — chạy lint/test/build song song trên nhiều phiên bản Node.js hoặc nhiều hệ điều hành.
- **Chia nhỏ job** — tách lint, test, build thành các job riêng chạy song song thay vì gộp vào một job tuần tự, giúp pipeline nhanh hơn và dễ đọc log hơn.
- **Status checks bắt buộc** — cấu hình branch protection rule để chặn merge pull request nếu pipeline chưa xanh.
- **Playwright trên CI** — cấu hình cài đặt trình duyệt headless (`npx playwright install --with-deps`) đúng cách trên runner Ubuntu.
- **Với dự án Go**: viết e2e test bằng công cụ như `httpexpect` hoặc `testcontainers-go` để kiểm thử API thật kèm database thật trong container, thay vì mock.
- **Coverage report** — xuất báo cáo độ phủ test (`--coverage` với Jest, `go test -cover` với Go) và hiển thị badge coverage trên README.
