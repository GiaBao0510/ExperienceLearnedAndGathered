# gRPC Overview

Với xu hướng chuyển đổi sang kiến trúc microservices và distributed systems, vấn đề giao tiếp giữa các service (inter-service communication) trở thành một thách thức lớn. Các giải pháp truyền thống không đáp ứng tốt các đòi hỏi về hiệu năng, khả năng mở rộng và streaming thời gian thực. Chính trong bối cảnh đó, **gRPC** — một RPC framework mã nguồn mở, hiệu năng cao, do Google phát triển — ra đời.

Sử dụng **HTTP/2** làm giao thức vận chuyển và **Protocol Buffers** để serialize dữ liệu, [gRPC](https://grpc.io/) mang lại nhiều ưu điểm vượt trội về hiệu năng (performance), khả năng mở rộng (scalability) và bảo mật (security). Bài viết này sẽ đi sâu vào công nghệ này và cách ứng dụng nó để xây dựng các ứng dụng phân tán, microservices hiệu quả.

![gRPC](https://encrypted-tbn0.gstatic.com/images?q=tbn:ANd9GcRElobEXndRmyF5XHcR5tY6ZX1aBrvv6blFCsTsOTQrcA&s=10)

## gRPC Là Gì?

gRPC là một framework dựa trên nền tảng RPC (gọi thủ tục từ xa), dùng để xây dựng các API có tốc độ cao, khả năng mở rộng tốt. Nó cho phép client và server giao tiếp với nhau một cách minh bạch, giúp việc phát triển các hệ thống được kết nối trở nên đơn giản hơn. Rất nhiều công ty công nghệ lớn đã áp dụng gRPC, như Google, Netflix, Square, IBM, Cisco, Dropbox.

Một số lý do chính khiến gRPC đáng được chú ý:

- Hỗ trợ streaming đa luồng (multiplexing) hiệu quả, dựa trên nền tảng HTTP/2.
- Mã hóa dữ liệu nhị phân, hiệu năng cao, nhờ Protocol Buffers.
- Tích hợp sẵn các tính năng bảo mật mạnh: authentication, mã hóa SSL/TLS.
- Hỗ trợ đa nền tảng, có thư viện (library) cho nhiều ngôn ngữ lập trình phổ biến.
- Khả năng mở rộng và tính sẵn sàng cao, phù hợp cho kiến trúc microservices, hệ thống phân tán quy mô lớn.

Nhờ những ưu điểm kỹ thuật vượt trội trên, gRPC trở thành một trong những lựa chọn hàng đầu để xây dựng các ứng dụng phân tán, microservices vừa hiệu quả vừa bảo mật.

## Sự Khác Biệt Giữa gRPC Với RPC "Truyền Thống"

gRPC bản chất cũng là một dạng hiện thực của RPC, nhưng có một số đặc điểm khác biệt đáng chú ý so với các dạng RPC truyền thống (ví dụ XML-RPC, JSON-RPC, hay `net/rpc` trong Go):

![Phân tích về những yếu tố khác biệt](https://cdn2.fptshop.com.vn/unsafe/Uploads/images/tin-tuc/175380/Originals/grpc-la-gi-2.jpg)

### Giao thức truyền tải

- Các dạng RPC truyền thống thường dùng HTTP/1.1 kết hợp với một định dạng dữ liệu dạng text như XML (XML-RPC) hoặc JSON (JSON-RPC) để trao đổi dữ liệu.
- gRPC dùng **HTTP/2** làm giao thức vận chuyển, tận dụng được các tính năng như multiplexing, giúp truyền dữ liệu hiệu quả hơn nhiều (xem chi tiết ở phần "HTTP/2" bên dưới).

### Tuần tự hóa (Serialization)

- RPC truyền thống thường dùng các định dạng văn bản như XML, JSON để tuần tự hóa (serialize) và giải tuần tự hóa (deserialize) dữ liệu — dễ đọc nhưng dung lượng lớn, xử lý chậm hơn.
- gRPC dùng **Protocol Buffers (Protobuf)** — định dạng nhị phân gọn nhẹ, hiệu năng cao, và hỗ trợ sẵn cho nhiều ngôn ngữ lập trình (xem chi tiết ở phần "Protocol Buffers" bên dưới).

### Cơ chế gọi hàm

- RPC truyền thống thường dùng cơ chế đồng bộ (synchronous): client gửi yêu cầu và phải chờ tới khi server trả kết quả mới tiếp tục.
- gRPC hỗ trợ cả cơ chế đồng bộ lẫn bất đồng bộ (asynchronous), và còn hỗ trợ **streaming** — cho phép gửi/nhận nhiều thông điệp liên tục trong cùng một lời gọi, thay vì chỉ một cặp request/response duy nhất (xem chi tiết ở phần "Streaming" bên dưới).

## gRPC Concepts

Phần lớn các khái niệm cốt lõi của gRPC xoay quanh hai nền tảng chính: **Protocol Buffers** (cách dữ liệu được mô tả và mã hóa) và **HTTP/2** (cách dữ liệu được truyền tải qua mạng). Cùng với đó là hai khái niệm quan trọng khác: **Streaming** và **Channel**.

### Protocol Buffers

**Protocol Buffers (Protobuf)** là định dạng tuần tự hóa (serialization) dữ liệu do Google phát triển, cho phép định nghĩa cấu trúc dữ liệu và service, từ đó tự động sinh ra các client library tương ứng cho nhiều ngôn ngữ. gRPC dùng Protobuf làm **IDL (Interface Definition Language — ngôn ngữ định nghĩa giao diện)**. Phiên bản hiện hành là **proto3**, với cú pháp đơn giản, dễ dùng hơn phiên bản trước (proto2).

So với JSON và XML, Protobuf có lợi thế rõ rệt: việc phân tích cú pháp (parse) tốn ít tài nguyên CPU hơn (vì dữ liệu đã ở dạng nhị phân, không cần parse text), và thông điệp sau khi mã hóa có kích thước nhỏ hơn đáng kể. Nhờ kích thước nhỏ, việc trao đổi dữ liệu diễn ra nhanh hơn, kể cả trên các thiết bị có CPU yếu hơn (như điện thoại di động).

Xem chi tiết về [Protocol Buffers tại đây](https://github.com/GiaBao0510/ExperienceLearnedAndGathered/tree/main/API_Architectures/gRPC/1.Protocol%20Buffers).

### Streaming

![](https://encrypted-tbn0.gstatic.com/images?q=tbn:ANd9GcQS9MR3gEpPsdmbJzjI_Jh-rzXFqz4hK5Eapm7mEhggrg&s=10)

gRPC hỗ trợ 4 kiểu gọi hàm (RPC method), tương ứng với 4 cách client và server trao đổi dữ liệu:

- **Unary RPC** (không streaming): Kiểu cơ bản nhất — client gửi **một** request duy nhất, server xử lý và trả về **một** response duy nhất. Đây là kiểu gần giống nhất với một lời gọi hàm thông thường, và cũng là kiểu phổ biến nhất khi mới bắt đầu dùng gRPC.
![](https://blog.nashtechglobal.com/wp-content/uploads/2024/07/1.png)

- **Server-streaming RPC**: Client gửi một request duy nhất, nhưng nhận lại một **luồng (stream)** nhiều response từ server, cho tới khi server gửi hết dữ liệu.
![](https://encrypted-tbn0.gstatic.com/images?q=tbn:ANd9GcSKAOFljjYbdawoqaPjB3j7L81uh5Rl2cfmBoE2tzHFpg&s=10)

- **Client-streaming RPC**: Ngược lại với trên — client gửi một luồng nhiều request tới server, server xử lý toàn bộ rồi trả về **một** response duy nhất.
![](https://encrypted-tbn0.gstatic.com/images?q=tbn:ANd9GcR5TcTtou0KYYRjmImlC9FeV1C0XjV8aFcenk0jHt7Yzg&s=10)

- **Bidirectional-streaming RPC**: Cả client và server đều gửi luồng thông điệp cho nhau, hai chiều độc lập — mỗi bên có thể gửi message theo bất kỳ trình tự nào, nhưng thứ tự message trong từng luồng riêng vẫn được giữ nguyên.
![](https://blog.nashtechglobal.com/wp-content/uploads/2024/07/4-1024x576.png)


Ba kiểu streaming (server, client, bidirectional) đều được thực hiện nhờ khả năng multiplexing của HTTP/2 — cho phép gửi/nhận nhiều frame dữ liệu xen kẽ nhau trên cùng một kết nối TCP, mà không cần mở nhiều kết nối riêng biệt.

**Ví dụ**: Một ứng dụng chat có thể dùng Bidirectional-streaming RPC để cả client và server liên tục gửi tin nhắn qua lại trên cùng một kết nối, thay vì phải mở request mới cho mỗi tin nhắn.

### HTTP/2

gRPC được xây dựng trên nền **HTTP/2** — giao thức chính thức ra mắt năm 2015 để khắc phục các hạn chế hiệu năng của HTTP/1.1. Tuy vẫn tương thích về mặt ngữ nghĩa (method, status code...) với HTTP/1.1, HTTP/2 mang lại nhiều cải tiến quan trọng mà gRPC tận dụng triệt để:

- **Binary Framing Layer**: Dữ liệu được đóng gói thành các frame nhị phân, thay vì văn bản thuần túy.
- **Multiplexing**: Cho phép gửi/nhận nhiều luồng dữ liệu (stream) đồng thời trên một kết nối TCP duy nhất — đây chính là nền tảng giúp gRPC hiện thực được cả 3 kiểu streaming đã nêu ở trên.
- **Flow Control**: Kiểm soát tốc độ luồng dữ liệu giữa client và server, tránh tình trạng một bên gửi dữ liệu nhanh hơn khả năng xử lý của bên còn lại.
- **Header Compression (HPACK)**: Nén header giúp giảm dung lượng dữ liệu cần truyền, đặc biệt hữu ích khi có nhiều request/response liên tục.

Nhờ multiplexing của HTTP/2, gRPC có thể hỗ trợ cả các lời gọi đồng bộ lẫn bất đồng bộ, cũng như cả 4 kiểu RPC (Unary và 3 kiểu streaming) đã trình bày ở phần trên — bao gồm cả Bidirectional streaming, nơi client vừa có thể gửi request vừa nhận response gần như đồng thời trên cùng một kết nối.

Xem chi tiết về HTTP/2 [tại đây](https://github.com/GiaBao0510/ExperienceLearnedAndGathered/tree/main/API_Architectures/gRPC/0.HTTP_2).

### Channel

**Channel** là một khái niệm cốt lõi khác trong gRPC — về cơ bản, đây là một **kết nối HTTP/2 lâu dài (persistent)** giữa client và một địa chỉ server cụ thể (host + port). Client dùng Channel để tạo ra **stub** — đối tượng cung cấp các hàm để gọi RPC tới service tương ứng.

Nhờ multiplexing của HTTP/2, một Channel duy nhất có thể mang nhiều stream (nhiều lời gọi RPC) chạy đồng thời, mà không cần mở nhiều kết nối TCP riêng biệt cho từng lời gọi — giúp tiết kiệm chi phí thiết lập kết nối (handshake) so với việc mở kết nối mới cho mỗi request. Trong thực tế, một ứng dụng client thường chỉ cần tạo một Channel duy nhất tới mỗi server, rồi tái sử dụng Channel đó cho mọi lời gọi RPC tới server đó.

## Cách Client Gọi Phương Thức Từ Xa Trên Server Với gRPC

1. **Định nghĩa file `.proto`**: Khai báo cấu trúc dữ liệu (`message`) và giao diện dịch vụ (`service`, gồm các RPC method).
2. **Biên dịch file `.proto`**: Dùng trình biên dịch Protocol Buffers (`protoc`, kèm plugin gRPC cho ngôn ngữ tương ứng) để sinh ra class/interface cho cả client và server.
3. **Client gọi phương thức từ xa**: Client dùng giao diện (stub) được sinh ra từ file `.proto`, gọi phương thức như một hàm bình thường. Phía sau, gRPC tự đóng gói (marshal) tham số thành dữ liệu nhị phân và gửi request tới server.
4. **Server xử lý yêu cầu**: Server nhận request, giải mã (unmarshal) dữ liệu, xử lý logic nghiệp vụ tương ứng, rồi trả kết quả về cho client.
5. **Client nhận kết quả**: Client nhận response, gRPC tự giải mã dữ liệu, trả về giá trị để chương trình client tiếp tục xử lý — như thể vừa gọi xong một hàm cục bộ bình thường.

Ví dụ minh họa một file `.proto` định nghĩa service `Greeter` với một RPC method kiểu Unary:

```protobuf
syntax = "proto3";

package greeter;

service Greeter {
  rpc SayHello (HelloRequest) returns (HelloResponse);
}

message HelloRequest {
  string name = 1;
}

message HelloResponse {
  string message = 1;
}
```

Sau khi biên dịch file này bằng `protoc`, phía client (ví dụ viết bằng Go) có thể gọi RPC gần như một hàm bình thường:

```go
conn, _ := grpc.NewClient("localhost:50051", grpc.WithTransportCredentials(insecure.NewCredentials()))
client := greeter.NewGreeterClient(conn)

resp, err := client.SayHello(context.Background(), &greeter.HelloRequest{Name: "Simon"})
if err != nil {
    log.Fatal(err)
}
fmt.Println(resp.Message)
```

Qua quy trình trên, client có thể gọi các phương thức từ xa trên server một cách đơn giản, gần như đang gọi một hàm cục bộ — trong khi toàn bộ phần phức tạp (mã hóa, truyền qua mạng, giải mã) đều được gRPC xử lý phía sau.

## Mở Rộng

Sau khi nắm được tổng quan về gRPC, bạn có thể tìm hiểu thêm:

- **gRPC-Web**: Cách gọi gRPC từ trình duyệt (browser), vốn không hỗ trợ gọi gRPC trực tiếp như ứng dụng backend.
- **Interceptor**: Cơ chế tương tự middleware trong gRPC, dùng cho logging, authentication, metrics ở tầng client/server mà không cần sửa logic từng RPC method.
- **Deadline & Cancellation**: Cách gRPC xử lý timeout và hủy request giữa chừng — quan trọng để tránh một request bị "treo" vô thời hạn trong hệ thống phân tán.
- **Load Balancing trong gRPC**: Vì một Channel thường gắn với một địa chỉ cố định, cần cơ chế riêng (client-side load balancing, hoặc qua Service Mesh) để phân phối tải khi có nhiều instance server.
- **So sánh gRPC với REST**: Khi nào nên chọn gRPC (giao tiếp nội bộ giữa service, cần hiệu năng cao) và khi nào REST vẫn là lựa chọn hợp lý hơn (API công khai, cần dễ đọc, dễ debug qua trình duyệt).
