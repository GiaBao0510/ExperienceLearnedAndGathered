# RPC Trong Thực Tế — Ví Dụ Với Go

Về lý thuyết, cơ chế RPC đơn giản là vậy — cách nó được ứng dụng trong các hệ thống lớn (như gRPC, microservices) sẽ được đề cập ở các bài sau. Ở đây, hãy cùng xem một ví dụ nhỏ minh họa RPC, viết bằng [Go](https://go.dev/) với package chuẩn `net/rpc` có sẵn trong thư viện của ngôn ngữ này.

```go
// File Server: server/main.go
package main

import (
	"log"
	"net"
	"net/rpc"
)

type GreetingService struct{}

func (p *GreetingService) Hello(request string, reply *string) error {
	*reply = "Hello " + request

	return nil
}

func main() {
	// Đăng ký service với tên là Greeting, có kiểu là GreetingService
	rpc.RegisterName("Greeting", new(GreetingService))

	// Tạo server chạy trên port 1234
	listener, err := net.Listen("tcp", ":1234")
	if err != nil {
		log.Fatal("Can not create server because:", err)
	}

	log.Print("Server is listening on port 1234")

	for {
		// Chấp nhận connection
		conn, err := listener.Accept()
		if err != nil {
			log.Fatal("Accept error:", err)
		}

		// Phục vụ lời gọi Client trên một goroutine khác để tiếp tục nhận các lời gọi RPC khác
		go rpc.ServeConn(conn)
	}
}
```

Bạn có thể tạo một thư mục gốc chứa hai thư mục con `server` và `client`, mỗi thư mục chứa một file `main.go` riêng để chạy server và client cho ví dụ này. Trong `server/main.go`, ta tạo một service export sẵn method `Hello`, rồi đăng ký service đó (`rpc.RegisterName`) để phục vụ lời gọi RPC. Server này lắng nghe (listen) tại port `1234` để client có thể kết nối tới.

```go
// File Client: client/main.go
package main

import (
	"fmt"
	"log"
	"net/rpc"
)

func main() {
	// Tạo Client kết nối đến địa chỉ localhost:1234
	client, err := rpc.Dial("tcp", "localhost:1234")
	if err != nil {
		log.Fatal(err)
	}

	var reply string
	// Thực hiện lời gọi RPC với service là Greeting và tên method là Hello
	err = client.Call("Greeting.Hello", "Simon", &reply)
	if err != nil {
		log.Fatal(err)
	}

	fmt.Println(reply)
}
```

Trong `client/main.go`, ta tạo một client kết nối tới địa chỉ đã mở ở `server/main.go`, sau đó thực hiện lời gọi RPC tới method `Hello` của service `Greeting`, truyền tham số `"Simon"`. Sau khi thêm xong hai file này, mở hai terminal riêng để chạy server và client.

## Ưu Điểm Và Nhược Điểm Của RPC

RPC không phải lúc nào cũng là lựa chọn hoàn hảo. Bên cạnh những ưu điểm nổi trội, mô hình này cũng có một số hạn chế cần cân nhắc.

### Ưu điểm

- **Giao tiếp qua lời gọi hàm cấp cao**: RPC cho phép client giao tiếp với server bằng các lời gọi hàm ở mức trừu tượng cao (giống gọi hàm cục bộ), thay vì phải tự lập trình chi tiết ở mức socket/network.
- **Dùng được trong cả môi trường phân tán lẫn cục bộ**: RPC hoạt động tốt dù client và server nằm trên cùng máy hay trên các máy khác nhau trong mạng.
- **Ẩn đi cơ chế truyền thông điệp qua mạng**: Người dùng (lập trình viên gọi hàm) không cần quan tâm tới chi tiết việc dữ liệu được đóng gói, gửi, và giải mã qua mạng như thế nào — toàn bộ phần này được Stub và RPC Runtime xử lý phía sau.
- **Có thể tối giản để cải thiện hiệu suất**: So với một số giao thức giao tiếp nặng hơn (ví dụ SOAP với nhiều lớp XML phức tạp), một số mô hình RPC được thiết kế tinh gọn, bỏ bớt các lớp giao thức trung gian không cần thiết, giúp cải thiện hiệu suất giao tiếp.

### Nhược điểm

- **Quản lý tài nguyên phức tạp hơn**: Client và server thường chạy trong môi trường thực thi khác nhau (khác máy, đôi khi khác cả ngôn ngữ lập trình), khiến việc quản lý tài nguyên phức tạp hơn so với gọi hàm cục bộ. RPC cũng không phải lựa chọn phù hợp cho mọi kiểu truyền dữ liệu (ví dụ truyền file dung lượng lớn thường không phù hợp với mô hình request/response của RPC truyền thống).
- **Phụ thuộc vào độ tin cậy của mạng**: Vì bản chất là giao tiếp qua mạng, lời gọi RPC có thể thất bại theo nhiều cách khó lường hơn một lời gọi hàm cục bộ — mất gói tin, timeout, hay server tạm thời không phản hồi. Đây chính là một trong những vấn đề kinh điển được mô tả trong khái niệm ["The Eight Fallacies of Distributed Computing"](https://en.wikipedia.org/wiki/Fallacies_of_distributed_computing) (8 ngộ nhận phổ biến khi lập trình hệ phân tán, trong đó ngộ nhận đầu tiên chính là "mạng luôn đáng tin cậy").
- **Thiếu một tiêu chuẩn thống nhất**: Không có một chuẩn cố định chung cho RPC (khác với REST, vốn có các nguyên tắc được thống nhất rộng rãi hơn) — mỗi framework RPC (gRPC, XML-RPC, JSON-RPC...) có thể hiện thực theo cách khác nhau.
- **Tính linh hoạt bị giới hạn do tương tác chặt (coupling) giữa client và server**: Vì client thường phải biết trước "hợp đồng" (interface/schema) của hàm phía server để có thể gọi đúng, hai bên bị ràng buộc khá chặt với nhau.

## Mở Rộng

Sau ví dụ thực hành RPC cơ bản này, bạn có thể tìm hiểu thêm:

- **gRPC với Go**: Cách dùng `protoc` sinh code Go từ file `.proto`, rồi triển khai gRPC server/client thực tế — bước tiếp theo tự nhiên sau khi đã hiểu RPC cơ bản.
- **Context và Timeout trong RPC**: Cách dùng `context.Context` (Go) để đặt timeout, hủy request khi lời gọi RPC mất quá lâu — giải pháp cho vấn đề "phụ thuộc độ tin cậy mạng" đã nêu ở phần nhược điểm.
- **The Eight Fallacies of Distributed Computing**: Danh sách đầy đủ 8 ngộ nhận phổ biến khi thiết kế hệ thống phân tán, rất hữu ích khi làm việc với bất kỳ hình thức giao tiếp qua mạng nào, không riêng RPC.
- **Load balancing và Service Discovery cho RPC**: Khi có nhiều instance server cùng cung cấp một service, làm sao client biết nên gọi tới instance nào.
