## Protocol Buffers Là Gì?

**Protocol Buffers (Protobuf)** là một **ngôn ngữ mô tả giao diện dữ liệu** (IDL — Interface Definition Language), dùng để **serialize** (tuần tự hóa) và **deserialize** (giải tuần tự hóa) dữ liệu có cấu trúc theo một định dạng **nhị phân gọn nhẹ**.

Protobuf được Google phát triển và sử dụng nội bộ từ năm 2001, sau đó chính thức được phát hành mã nguồn mở lần đầu vào ngày 7/7/2008 ([Repository chính thức](https://github.com/protocolbuffers/protobuf)). Về mục đích sử dụng, Protobuf khá giống XML hoặc JSON — đều dùng để [serialize](https://en.wikipedia.org/wiki/Serialization) một đối tượng dữ liệu có cấu trúc — nhưng khác biệt ở chỗ Protobuf mã hóa dữ liệu thành **dạng nhị phân** thay vì văn bản thuần túy (plain text) như JSON/XML. Dữ liệu sau khi mã hóa có thể được serialize/[deserialize](https://en.wikipedia.org/wiki/Serialization) tự động bởi nhiều ngôn ngữ lập trình khác nhau. Protobuf được thiết kế theo hướng **language-neutral** và **platform-neutral** (không phụ thuộc vào một ngôn ngữ hay nền tảng cụ thể), đồng thời có khả năng mở rộng schema theo thời gian. Hiện tại, Protobuf hỗ trợ chính thức nhiều ngôn ngữ phổ biến như C++, C#, Java, Kotlin, Python, Go, Dart, Ruby, Objective-C, PHP, JavaScript...

Protobuf là dự án mã nguồn mở, dùng để encode dữ liệu có cấu trúc. Nó rất hữu ích khi xây dựng các chương trình cần giao tiếp với nhau qua mạng (wire), hoặc khi cần lưu trữ dữ liệu lâu dài. Về cơ bản, bạn chỉ cần định nghĩa một "message" mô tả cấu trúc dữ liệu cần serialize (tương tự khai báo một class), bằng cách viết trong một file đặc tả có đuôi `.proto`.

Từ file `.proto`, trình biên dịch của Protobuf — gọi là **`protoc`** — sẽ tự động sinh ra code để encode và phân tích cú pháp (parse) dữ liệu theo định dạng [nhị phân](https://en.wikipedia.org/wiki/Binary) hiệu quả. Tùy theo ngôn ngữ lập trình mục tiêu, `protoc` sẽ sinh ra mã nguồn tương ứng (ví dụ class Java, struct Go...).

**Ví dụ**: file `person.proto` định nghĩa một cấu trúc dữ liệu đơn giản mô tả một người:

```protobuf
syntax = "proto3";

message Person {
  int32 id = 1;
  string name = 2;
  string email = 3;
}
```

Ở đây, các số `1`, `2`, `3` không phải giá trị dữ liệu, mà là **field number** — số định danh duy nhất của từng trường trong message, dùng để mã hóa nhị phân thay vì phải gửi kèm tên trường dạng text (đây chính là một lý do giúp Protobuf nhỏ gọn hơn JSON).

## Tại Sao Protobuf Lại Phổ Biến Đến Thế?

- **Kích thước dữ liệu nhỏ gọn**: Một trong những lý do chính khiến Protobuf được ưa chuộng là kích thước output nhỏ hơn đáng kể so với JSON và XML (thứ tự thường thấy: XML > JSON > Protobuf). Nhờ dùng định dạng nhị phân, Protobuf giảm thiểu dữ liệu cần truyền tải, tiết kiệm băng thông và tăng hiệu suất ứng dụng.
- **Hiệu suất cao**: Quá trình serialize và deserialize của Protobuf nhanh hơn nhiều so với JSON và XML. Điều này giúp cải thiện hiệu suất các hệ thống có lưu lượng dữ liệu lớn, như microservices, gRPC, IoT, hay streaming data.
- **Định nghĩa dữ liệu chặt chẽ (schema-first)**: Protobuf yêu cầu định nghĩa rõ ràng schema trước khi sử dụng, giúp giảm lỗi do dữ liệu không hợp lệ và tăng khả năng kiểm soát dữ liệu. Ví dụ, nếu một trường bị thiếu hoặc có kiểu dữ liệu sai ngay từ lúc biên dịch `.proto`, lỗi sẽ được phát hiện sớm thay vì chỉ lộ ra khi chạy chương trình.
- **Hỗ trợ đa ngôn ngữ**: Protobuf hỗ trợ nhiều ngôn ngữ lập trình như Java, Kotlin, Python, Go, C++, C#, Ruby, Objective-C... giúp các đội phát triển làm việc với nhiều công nghệ khác nhau mà vẫn đảm bảo tính nhất quán của dữ liệu trao đổi.
- **Tích hợp tốt với gRPC**: Protobuf là định dạng mặc định của **gRPC** — framework Remote Procedure Call (RPC) hiệu suất cao do Google phát triển. Nhờ đó, các hệ thống microservices có thể giao tiếp nhanh và tối ưu hơn nhiều so với RESTful API truyền thống dùng JSON.
- **Hỗ trợ tương thích xuôi và ngược (forward & backward compatibility)**: Protobuf được thiết kế để hỗ trợ tương thích cả hai chiều — bạn có thể cập nhật schema (thêm trường mới) mà không làm hỏng các service đang chạy phiên bản cũ.

**Ví dụ**: nếu thêm một trường mới vào `Person.proto`:

```protobuf
syntax = "proto3";

message Person {
  int32 id = 1;
  string name = 2;
  string email = 3;
  string phone_number = 4;  // Trường mới được thêm vào
}
```

Các service vẫn đang chạy phiên bản schema cũ (chưa có `phone_number`) vẫn xử lý được dữ liệu mới này bình thường — chúng chỉ đơn giản là bỏ qua trường mà mình không biết, không bị lỗi hay crash.

## Một Số Best Practices Với Protobuf

### a. Thiết kế schema hợp lý

- **Đặt tên rõ ràng, nhất quán**: Tên message và field nên theo quy ước đặt tên rõ ràng, dễ hiểu — ví dụ dùng `snake_case` cho tên field trong file `.proto` (theo quy ước chính thức của Protobuf), các công cụ sinh code sẽ tự chuyển sang `camelCase` hoặc kiểu phù hợp với từng ngôn ngữ đích khi cần.
- **Chọn đúng kiểu dữ liệu**: Ví dụ, nếu chỉ cần lưu số nguyên nhỏ, dùng `int32` thay vì `int64` để tiết kiệm dung lượng.
- **Tránh thay đổi field number đã dùng**: Field number là định danh duy nhất, gắn liền với cách dữ liệu được mã hóa nhị phân. Thay đổi field number của một field đã được dùng trong production có thể khiến dữ liệu cũ bị đọc sai hoàn toàn.

### b. Tối ưu hóa kích thước dữ liệu

- **Dùng `repeated` cho danh sách dữ liệu**: Khi cần lưu một danh sách các giá trị hoặc message, hãy dùng từ khóa `repeated` (ví dụ `repeated string tags = 5;`), thay vì tự "giả lập" danh sách bằng cách khai báo nhiều field đánh số thủ công (`tag1`, `tag2`, `tag3`...).
- **Chọn kiểu dữ liệu tối ưu**: Protobuf cung cấp nhiều kiểu số khác nhau (`int32`, `int64`, `sint32`, `fixed32`, `float`, `double`...) — mỗi kiểu tối ưu cho một phạm vi giá trị khác nhau. Chọn đúng kiểu giúp tiết kiệm không gian lưu trữ khi mã hóa.

### c. Quản lý versioning và tương thích

- **Đảm bảo tương thích xuôi/ngược khi sửa schema**: Khi thêm field mới, hãy để nó có giá trị mặc định hợp lý để tránh lỗi khi các bên chưa cập nhật schema mới đọc phải dữ liệu này.
- **Dùng `reserved` khi xóa field**: Nếu xóa một field, hãy đánh dấu field number (và tên, nếu cần) đó là `reserved`, để tránh vô tình dùng lại field number này cho một field khác trong tương lai — việc dùng lại dễ gây xung đột và lỗi tương thích ngầm, khó phát hiện.

### d. Tích hợp với gRPC

- Dùng Protobuf làm ngôn ngữ mô tả dữ liệu cho gRPC: định nghĩa cả `service` (các RPC method) và `message` (cấu trúc dữ liệu) ngay trong cùng file `.proto`.
- Kết hợp Protobuf với gRPC giúp tăng tốc độ truyền tải và giảm độ trễ trong các hệ thống phân tán, nhờ cả hai cùng tối ưu cho giao tiếp nhị phân, hiệu suất cao.

### e. Debug và testing

- **Chuyển đổi Protobuf sang JSON khi debug**: `protoc` và các thư viện Protobuf runtime của nhiều ngôn ngữ hỗ trợ chuyển đổi qua lại giữa dữ liệu nhị phân Protobuf và JSON, giúp dễ đọc và kiểm tra dữ liệu hơn trong lúc debug.
- **Viết unit test cho schema**: Đảm bảo việc serialize/deserialize hoạt động đúng, đặc biệt sau mỗi lần thay đổi schema (thêm/xóa field).

## So Sánh Protobuf Với JSON Và XML

#### Protobuf

1. Dữ liệu rất dày đặc, đầu ra nhỏ gọn.
2. Khó decode nếu không có schema — định dạng dữ liệu (binary) không tự mô tả, cần có file `.proto` tương ứng mới đọc hiểu được.
3. Phù hợp với các gói dữ liệu có cấu trúc, dung lượng lên tới vài megabyte (không khuyến khích dùng cho các payload cực lớn, cỡ hàng trăm MB trở lên).
4. Phù hợp cho cả truyền dữ liệu qua mạng lẫn lưu trữ dữ liệu dài hạn (long-term data).
5. Xử lý rất nhanh — nhỏ hơn và nhanh hơn 3-10 lần so với XML hoặc JSON trong nhiều benchmark.
6. Không thân thiện để con người đọc trực tiếp, vì là dữ liệu nhị phân.
7. Sinh ra code truy cập dữ liệu (generated class/struct) dễ dùng hơn khi lập trình, so với việc tự parse JSON/XML thủ công.

#### JSON

1. Con người có thể đọc và chỉnh sửa trực tiếp, dễ dàng.
2. Có thể phân tích cú pháp (parse) mà không cần biết trước schema.
3. Được hầu hết trình duyệt và ngôn ngữ lập trình hỗ trợ sẵn.
4. Ít dài dòng (verbose) hơn XML.

#### XML

1. Con người có thể đọc và chỉnh sửa trực tiếp, dễ dàng.
2. Có thể phân tích cú pháp mà không cần biết trước schema.
3. Là tiêu chuẩn dữ liệu cho SOAP và nhiều hệ thống doanh nghiệp cũ.
4. Được hỗ trợ tốt bởi nhiều công cụ đi kèm như XSD, XSLT, SAX, DOM...

### Khi nào KHÔNG nên dùng Protobuf?

Protobuf rất nhanh và nhỏ gọn, nhưng có những tình huống không nên dùng nó, ví dụ:

1. Khi bạn cần hoặc muốn dữ liệu ở dạng con người đọc được trực tiếp (ví dụ file cấu hình cần chỉnh sửa thủ công).
2. Dữ liệu từ service được browser sử dụng trực tiếp (browser xử lý JSON tự nhiên hơn nhiều so với parse binary Protobuf, dù vẫn có thể làm được qua gRPC-Web).
3. Server của bạn viết bằng ngôn ngữ chưa có (hoặc hỗ trợ kém) thư viện Protobuf chính thức, ví dụ một số ngôn ngữ/runtime ít phổ biến.
4. Chi phí vận hành để triển khai thêm một tầng công nghệ mới (biên dịch `.proto`, quản lý version schema...) là quá lớn so với lợi ích mang lại cho quy mô hệ thống hiện tại.

## Hạn Chế Của Protobuf

Không có công nghệ nào hoàn hảo — Protobuf cũng có một số điểm cần cân nhắc:

- **Khó đọc trực tiếp**: Vì là định dạng nhị phân, Protobuf không dễ đọc như JSON hay XML, có thể gây khó khăn khi debug nếu không dùng công cụ hỗ trợ chuyển đổi sang dạng text.
- **Thêm một bước biên dịch**: Cần công cụ `protoc` để biên dịch file `.proto` thành mã nguồn phù hợp cho từng ngôn ngữ — thêm một bước vào quy trình build, so với JSON vốn không cần bước này.
- **Không phải lúc nào cũng cần thiết**: Nếu hệ thống không yêu cầu hiệu suất cực cao, hoặc chỉ xử lý dữ liệu nhỏ, ít traffic, thì JSON vẫn là lựa chọn đơn giản, phổ biến, và dễ tiếp cận hơn.

## Mở Rộng

Sau khi nắm được kiến thức cơ bản về Protobuf, bạn có thể tìm hiểu thêm:

- **gRPC**: Framework RPC dùng Protobuf làm định dạng mặc định để định nghĩa cả service lẫn message — nội dung tiếp theo trong series này.
- **proto2 vs proto3**: Sự khác biệt về cú pháp và ngữ nghĩa (ví dụ: proto3 bỏ khái niệm "required field" bắt buộc từng có ở proto3, mặc định các field đều optional).
- **Protobuf Well-Known Types**: Các message dựng sẵn của Google như `google.protobuf.Timestamp`, `google.protobuf.Duration`, `google.protobuf.Any` — dùng để biểu diễn các kiểu dữ liệu phổ biến một cách chuẩn hóa.
- **Buf**: Bộ công cụ hiện đại giúp quản lý, lint, và kiểm tra breaking change cho các file `.proto` trong dự án lớn.
- **Các định dạng serialize nhị phân khác**: Apache Thrift, Apache Avro, FlatBuffers, MessagePack — mỗi định dạng có đánh đổi khác nhau về hiệu suất, tính linh hoạt của schema, và hệ sinh thái hỗ trợ.
