# Protobuf Căn Bản (Syntax)

## Proto2 Và Proto3 — Nên Dùng Phiên Bản Nào?

Khi làm việc với Protobuf, bạn có hai lựa chọn cú pháp (syntax version):

- **Proto2**: Phiên bản ra đời trước, dùng để mã hóa dữ liệu có cấu trúc, hỗ trợ sinh code cho nhiều ngôn ngữ như C++, Python...
- **Proto3**: Phiên bản hiện tại, được khuyến nghị dùng cho các dự án mới. Proto3 kế thừa proto2 nhưng đơn giản hóa cú pháp và **loại bỏ một số quy tắc field gây rắc rối** — quan trọng nhất là bỏ khái niệm `required` (bắt buộc) từng có ở proto2.

> **Vì sao proto3 bỏ `required`?** Trong proto2, một field `required` bắt buộc phải luôn có giá trị — nếu thiếu, message bị coi là không hợp lệ. Vấn đề là: một khi một service đã publish một field `required`, không bên nào có thể bỏ field đó đi (dù có còn cần hay không) mà không làm hỏng khả năng tương thích với các bên khác. Đây là một trong những bài học kinh nghiệm khiến proto3 quyết định bỏ hẳn `required`, chỉ giữ lại các field ở dạng "singular" (mặc định) hoặc `repeated` — chi tiết ở phần "Field Rules" bên dưới.

Tài liệu này sẽ đi từ cú pháp file `.proto` cơ bản, tới các quy tắc field, rồi tới ví dụ hoàn chỉnh bằng proto3 (phiên bản bạn nên dùng cho dự án mới).

## Cách Sử Dụng

Mỗi file `.proto` thường bắt đầu bằng một khai báo `package`, giúp tránh xung đột đặt tên giữa các message ở những project khác nhau. Về cơ bản, bạn định nghĩa cách dữ liệu của mình được cấu trúc bằng một **message**, khai báo trong file `.proto`. File này được `protoc` biên dịch, sinh ra code đã có sẵn các phương thức để serialize/deserialize, theo ngôn ngữ bạn chỉ định (Java, Go, Python...).

Ví dụ định nghĩa một message trong file `.proto` (xem thêm tài liệu chính thức tại [Google Developers](https://developers.google.com/protocol-buffers/docs/proto)):

```protobuf
// Request message for creating a new customer
message CustomerRequest {
    int32 id = 1;  // Unique ID number for a Customer.
    string name = 2;
    string email = 3;
    string phone = 4;

    message Address {
        string street = 1;
        string city = 2;
        string state = 3;
        string zip = 4;
        bool isShippingAddress = 5;
    }

    repeated Address addresses = 5;
}

message CustomerResponse {
    int32 id = 1;
    bool success = 2;
}

message CustomerFilter {
    string keyword = 1;
}
```

Mỗi message có một hoặc nhiều field, mỗi field được đánh số duy nhất trong phạm vi message đó. Message lồng nhau (ví dụ `Address` bên trong `CustomerRequest`) có tập số riêng, độc lập với message cha. **Field type** (kiểu dữ liệu của field) có thể là kiểu vô hướng (scalar) như số (`int32`, `float`...), `bool`, `string`, `bytes`; có thể là `enum`; hoặc là một **message khác** — nhờ đó bạn có thể lồng các message vào nhau, cấu trúc dữ liệu theo dạng phân cấp tương tự như JSON cho phép.

### Field Type Và Field Rule — Hai Khái Niệm Cần Phân Biệt

Khi khai báo một field, có hai thứ tách biệt cần chỉ định:

- **Field Type** (kiểu dữ liệu): ví dụ `int32`, `float`, `string`, `bool`, `enum`, hoặc một message khác. Đây là kiểu giá trị mà field đó lưu trữ.
- **Field Rule** (quy tắc field): mô tả field xuất hiện bao nhiêu lần trong message — ví dụ `optional`, `repeated` (proto3), hoặc thêm cả `required` (chỉ có ở proto2, xem phần trước). Quy tắc này quyết định cách field được serialize và cấu trúc trong định dạng nhị phân đã mã hóa.

Định dạng nhị phân sau khi mã hóa có thể hình dung như một biểu diễn "phẳng" (flat) và nén của đối tượng dữ liệu gốc. Cách viết đặc tả `.proto` là giống hệt nhau, bất kể bạn dùng Protobuf trong Python, Java hay C++ — đây chính là điểm mạnh "language-neutral" của Protobuf.

### Field Number (Tag)

Mỗi field trong định nghĩa message có một **field number** (còn gọi là **tag**) — số định danh duy nhất. Con số này được dùng để xác định field trong định dạng nhị phân đã mã hóa, và **không nên thay đổi** một khi message đã được dùng trong thực tế.

Một số quy tắc và lưu ý quan trọng:

- Field number phải **duy nhất** trong phạm vi các field của một message.
- Field number có giá trị từ **1 đến 15** chỉ tốn **1 byte** để mã hóa (bao gồm cả số định danh và field type); field number từ **16 đến 2047** tốn **2 byte**. Vì vậy, nên dành các số từ 1 đến 15 cho những field xuất hiện thường xuyên nhất trong message, để tối ưu dung lượng dữ liệu (xem chi tiết tại [Protocol Buffer Encoding](https://protobuf.dev/programming-guides/encoding/#structure)).
- Field number nhỏ nhất có thể dùng là **1**, lớn nhất là **2²⁹ − 1 = 536.870.911**.
- Không được dùng các số từ **19000 đến 19999** — dải số này được Protobuf dành riêng cho nội bộ; `protoc` sẽ báo lỗi nếu bạn cố dùng.
- Không được dùng lại các số nằm trong danh sách `reserved`, hoặc số đã được khai báo trong `extensions` (xem phần "Reserved Fields" bên dưới).
- **Không được thay đổi field number khi message đã dùng trong production**, vì Protobuf dùng chính con số này để encode/decode dữ liệu nhị phân. Đổi field number tương đương với việc xóa field cũ và tạo một field hoàn toàn mới — dữ liệu cũ đã lưu/gửi đi trước đó sẽ không còn đọc đúng được nữa.

### Packed Encoding Cho Repeated Scalar Field

Với các field `repeated` chứa kiểu dữ liệu số vô hướng (scalar numeric — ví dụ `int32`, `float`...), Protobuf hỗ trợ một cách mã hóa gọn hơn gọi là **packed encoding**.

```protobuf
repeated int32 samples = 4 [packed = true];
```

> **Lưu ý theo phiên bản**: Ở **proto2**, bạn cần khai báo tường minh `[packed = true]` như trên để bật cách mã hóa tối ưu này. Ở **proto3**, packed encoding đã là **mặc định** cho các repeated field kiểu số vô hướng — bạn không cần khai báo gì thêm để có được lợi ích này (nhưng vẫn có thể viết tường minh nếu muốn, hoặc dùng `[packed = false]` để tắt nếu có lý do đặc biệt).

### Enumerations

Khi định nghĩa một message, có lúc bạn muốn một field chỉ nhận một trong số các giá trị được liệt kê sẵn — dùng `enum`:

```protobuf
enum Foo {
  FIRST_VALUE = 0;
  SECOND_VALUE = 1;
}
```

> **Quy tắc riêng của proto3**: Giá trị enum đầu tiên khai báo **bắt buộc phải bằng 0**, và giá trị này đóng vai trò là giá trị mặc định khi field enum không được gán giá trị nào khác. Ví dụ trên đã tuân thủ đúng quy tắc này (`FIRST_VALUE = 0`).

## Message — Ví Dụ Hoàn Chỉnh Với Proto3

Dưới đây là ví dụ về một message **Person**, định nghĩa theo cú pháp proto3:

```protobuf
syntax = "proto3";

message Person {
  string name = 1;
  int32 id = 2;
  string email = 3;
}
```

Dòng đầu tiên `syntax = "proto3";` khai báo phiên bản Protobuf được dùng cho file này. Message `Person` có ba field: `name` và `email` kiểu `string`, `id` kiểu `int32`. Khi khai báo field, bạn **luôn bắt buộc** chỉ định tên và kiểu dữ liệu (field type) cho field đó — đây chính là ví dụ áp dụng khái niệm Field Number đã giải thích ở phần trên (`1, 2, 3`).

### Field Rules (Proto3)

Khác với proto2 (có `required`/`optional`/`repeated`), field trong **proto3** có các rule sau:

- **`singular`** (mặc định, không cần khai báo gì): nếu field không được gán giá trị, nó sẽ nhận **giá trị mặc định** theo kiểu dữ liệu (xem phần "Default Values" bên dưới) thay vì báo lỗi như `required` ở proto2.
- **`optional`**: tương tự `singular` về giá trị mặc định, nhưng Protobuf sẽ theo dõi thêm việc field đó **có được set giá trị hay không** (kể cả khi giá trị được set trùng với giá trị mặc định). Nếu field được set giá trị, nó sẽ được đưa vào dữ liệu mã hóa (encode); nếu không được set, nó sẽ không xuất hiện trong dữ liệu mã hóa. Nói đơn giản: field này _có thể có hoặc không có mặt_ trong dữ liệu đã encode, và code phía nhận có thể kiểm tra được điều đó (ví dụ bằng hàm `has_<field>()` tùy ngôn ngữ).
- **`repeated`**: field có thể xuất hiện lặp lại với số lần bất kỳ (kể cả 0 lần) trong một message hợp lệ. Thứ tự các giá trị lặp lại được giữ nguyên.
- **`map`**: field kiểu key/value, ví dụ `map<string, int32> scores = 1;`.

### Comments

Thêm comment vào file `.proto` bằng `//` (một dòng) hoặc `/* ... */` (nhiều dòng):

```protobuf
syntax = "proto3";

/* This is message Person */

message Person {
  string name = 1; // Name of the person
  int32 id = 2;
  string email = 3;
}
```

### Reserved Fields

Khi cập nhật một message bằng cách xóa (hoặc comment) một field bất kỳ, có rủi ro là một developer khác trong tương lai vô tình dùng lại đúng field number (hoặc tên field) đã bị xóa đó cho một field mới — gây xung đột dữ liệu ngầm, rất khó phát hiện. Để tránh tình huống này, khi xóa field, hãy thêm field number (và tên field, nếu dữ liệu còn được trao đổi ở dạng JSON/text) vào danh sách `reserved`.

```protobuf
message Employer {
  reserved 2, 15, 9 to 11;
  reserved "name", "email";
}
```

Ví dụ trên: các field number `2, 15, 9, 10, 11` bị đánh dấu reserved (không được dùng lại), và hai field `name`, `email` cũng được reserved theo tên — đảm bảo nếu dữ liệu từng được biểu diễn dưới dạng JSON/text với hai tên field này, chúng vẫn không bị xung đột nếu ai đó cố định nghĩa lại field trùng tên trong tương lai.

### Values Type

Protobuf hỗ trợ hầu hết các kiểu dữ liệu phổ biến: số nguyên (`int32`, `int64`...), số thực (`float`, `double`), `bool`, `string`, `bytes`, `enum`, `map`... Các kiểu này độc lập với ngôn ngữ lập trình, cho phép các chương trình viết bằng những ngôn ngữ khác nhau vẫn có thể trao đổi dữ liệu với nhau một cách đáng tin cậy.

### Default Values

Khi một message được phân tích (parse), nếu field không được gán giá trị, Protobuf sẽ dùng giá trị mặc định tương ứng với từng kiểu dữ liệu:

- `string`: chuỗi rỗng (empty string).
- `bytes`: dữ liệu byte rỗng.
- `bool`: `false`.
- Kiểu số (`int32`, `int64`, `float`, `double`...): `0`.
- `message` (kiểu message lồng): nếu field kiểu message không được set, giá trị mặc định là "chưa được set" (không phải một instance rỗng) — cách xử lý cụ thể (ví dụ trả về `null`, `None`, hay một instance rỗng) sẽ tùy theo ngôn ngữ lập trình khi compile.

## Mở Rộng

Sau khi nắm được syntax cơ bản, bạn có thể tìm hiểu thêm:

- **Protobuf Encoding chi tiết**: Cách các field number, wire type được mã hóa thành byte thực tế — tài liệu chính thức tại [protobuf.dev/programming-guides/encoding](https://protobuf.dev/programming-guides/encoding/).
- **`oneof`**: Cú pháp cho phép một message chỉ có tối đa một trong số nhiều field được set tại một thời điểm — hữu ích khi mô hình hóa dữ liệu dạng "hoặc cái này, hoặc cái kia".
- **Well-Known Types**: Các message dựng sẵn của Google như `google.protobuf.Timestamp`, `google.protobuf.Any`, `google.protobuf.Empty`.
- **gRPC**: Cách kết hợp file `.proto` để định nghĩa cả `service` (RPC method) bên cạnh `message`, làm nền tảng giao tiếp cho gRPC.
- **Buf**: Công cụ hiện đại hỗ trợ lint, format, và phát hiện breaking change giữa các phiên bản file `.proto`.
