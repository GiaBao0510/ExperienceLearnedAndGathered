## Giới Thiệu

Hai bài trước đã giới thiệu SSH và thực hành kết nối thật vào EC2 Instance. Bài này tổng hợp **các lỗi SSH phổ biến nhất** mà người học thường gặp, cùng cách chẩn đoán và khắc phục theo từng trường hợp cụ thể — giúp bạn tự xử lý thay vì bị kẹt lại ở bước kết nối.

## 1. Lỗi Connection Timeout (Hết Thời Gian Chờ Kết Nối)

**Triệu chứng:** gõ lệnh `ssh` xong, terminal treo im lặng một lúc lâu rồi báo lỗi hết thời gian chờ (timeout), không có phản hồi gì từ phía server.

**Nguyên nhân phổ biến nhất:** cấu hình sai **Security Group** — rule SSH (cổng 22) chưa được thêm, hoặc Security Group chứa rule đó chưa được gán đúng cho EC2 Instance. Hãy kiểm tra rule inbound SSH được cấu hình đúng như hình dưới:

![](https://i.ibb.co/mr2ty8vr/image.png)

> **Lưu ý:** timeout khi kết nối không phải lúc nào cũng do SSH riêng — bất kỳ giao thức nào (HTTP, RDP...) bị chặn cũng gây ra hiện tượng y hệt. Nguyên nhân phổ biến nhất là Security Group, nhưng trong một số trường hợp hiếm hơn, Network ACL cấp subnet hoặc route table thiếu đường đến Internet Gateway cũng có thể gây timeout tương tự.

## 2. Vẫn Gặp Connection Timeout Dù Security Group Đã Đúng

Nếu đã kiểm tra kỹ và Security Group được cấu hình chính xác như trên mà vẫn bị timeout, nhiều khả năng vấn đề nằm **ngoài phía AWS** — cụ thể là **tường lửa mạng nội bộ (công ty, trường học) hoặc tường lửa cá nhân trên máy bạn** đang chặn cổng 22 ra ngoài Internet. Đây là tình huống bạn không thể tự sửa từ phía AWS.

**Cách xử lý:** chuyển sang dùng **EC2 Instance Connect** (kết nối qua trình duyệt, không cần mở cổng 22 từ máy cá nhân — xem lại bài "Tổng Quan Về SSH").

## 3. SSH Không Hoạt Động Trên Windows

**Triệu chứng:** gõ lệnh `ssh` trong terminal nhưng hệ thống báo lỗi `ssh: command not found` (không tìm thấy lệnh ssh).

Lỗi này thường xảy ra trên các phiên bản **Windows cũ** (trước Windows 10 bản 1809), vốn chưa tích hợp sẵn OpenSSH Client. Nếu máy bạn rơi vào trường hợp này, hãy dùng **PuTTY** thay thế — xem lại bài hướng dẫn PuTTY.

> Nếu bạn đang dùng Windows 10 (bản 1809 trở lên) hoặc Windows 11 mà vẫn gặp lỗi này, có thể OpenSSH Client chưa được bật — xem lại bài "Thực Hành: SSH Vào EC2 Instance" để cài đặt.

Nếu đã thử PuTTY mà vẫn không kết nối được, hãy chuyển sang dùng **EC2 Instance Connect**.

## 4. Lỗi Connection Refused (Từ Chối Kết Nối)

**Triệu chứng:** khác với timeout (không có phản hồi), lỗi này báo **"connection refused"** — nghĩa là gói tin của bạn **đã đến được** instance (Security Group không chặn), nhưng **không có dịch vụ SSH nào đang lắng nghe** ở cổng 22 trên instance đó (dịch vụ SSH daemon có thể chưa khởi động xong, hoặc instance đang gặp sự cố nội bộ).

**Cách khắc phục theo thứ tự:**

1. Thử **khởi động lại (reboot)** instance — đôi khi dịch vụ SSH chỉ cần thêm thời gian để khởi động hoàn tất.
2. Nếu vẫn không được, **chấm dứt (terminate)** instance hiện tại và **tạo instance mới**. Đảm bảo bạn chọn đúng AMI **Amazon Linux 2** (hoặc Amazon Linux 2023) để đồng bộ với các bài Hands-On trong khóa học.

## 5. Lỗi Permission Denied (publickey, gssapi-keyex, gssapi-with-mic)

Đây là thông báo liệt kê các **phương thức xác thực** mà SSH đã thử nhưng đều thất bại. Có hai nguyên nhân phổ biến nhất:

- **Sai Key Pair (private key):** bạn đang dùng nhầm file `.pem`/`.ppk`, hoặc không chỉ định key nào cả (thiếu cờ `-i`). Hãy kiểm tra lại trong Console: vào chi tiết EC2 Instance để xem đúng tên Key Pair đã gán cho instance, rồi đối chiếu với file key bạn đang dùng.
- **Sai username:** instance chạy Amazon Linux (2 hoặc 2023) luôn dùng user mặc định là **`ec2-user`**. Cú pháp đầy đủ: `ec2-user@<public-ip>` — ví dụ `ec2-user@35.180.242.162`. Lỗi này cũng thường gặp khi bạn vô tình gõ `root@...` hoặc `ubuntu@...` (user mặc định của AMI khác, như Ubuntu).

## 6. Không Cách Nào Hoạt Động Cả

Nếu đã thử hết các cách trên mà vẫn không kết nối được — đừng lo lắng, đây là tình huống khá phổ biến với người mới. Giải pháp cuối cùng: dùng **EC2 Instance Connect**, chỉ cần đảm bảo instance của bạn chạy Amazon Linux (2 hoặc 2023), bạn sẽ kết nối được ngay qua trình duyệt mà không cần quan tâm đến key pair hay cấu hình SSH client nữa.

## Mở Rộng

- **VPC Flow Logs** — công cụ để xem chi tiết gói tin nào bị chặn (và bị chặn bởi Security Group hay Network ACL), thay vì chỉ đoán qua hiện tượng timeout.
- **AWS Systems Manager Session Manager** — cách kết nối vào instance hoàn toàn không cần SSH, không cần mở cổng 22, phù hợp khi tường lửa công ty chặn cổng này vĩnh viễn.
- **`ssh -v` (verbose mode)** — thêm cờ `-v` (hoặc `-vvv` để chi tiết hơn) vào lệnh SSH giúp xem từng bước quá trình xác thực, rất hữu ích khi debug lỗi `Permission denied`.
- **Kiểm tra trạng thái SSH daemon trên instance** — qua EC2 Instance Connect hoặc Session Manager, dùng lệnh `sudo systemctl status sshd` để xác nhận dịch vụ SSH có đang chạy hay không.
