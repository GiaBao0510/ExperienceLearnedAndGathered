## Mục Tiêu Bài Thực Hành

Tiếp nối phần lý thuyết Security Group, bài này thực hành trực tiếp trên EC2 Instance đã tạo ở bài trước: xem các rule hiện có, chủ động xóa một rule để quan sát hậu quả (timeout), rồi thêm lại để khôi phục truy cập. Đây là cách tốt nhất để "cảm" được Security Group hoạt động ra sao trong thực tế, thay vì chỉ học lý thuyết.

## Bước 1: Xem Security Group Gắn Với Instance

Vào chi tiết EC2 Instance đã tạo, chọn tab **Security** để xem nhanh các Security Group đang gắn với instance, cùng inbound/outbound rules.

![](https://i.ibb.co/S2PdBmt/image.png)

## Bước 2: Xem Danh Sách Đầy Đủ Security Group

Để xem đầy đủ hơn, vào mục **Security Groups** trong nhóm **Network & Security** ở menu bên trái.

![](https://i.ibb.co/vrhrbrp/image.png) ![](https://i.ibb.co/Zpkf6Hg1/image.png)

Ở đây có **hai Security Group**:

1. **`default`** — Security Group mặc định, tồn tại sẵn trong mọi VPC (không phải do bạn chủ động tạo).
2. **`launch-wizard-1`** — Security Group được **tự động tạo** khi bạn khởi chạy EC2 Instance qua giao diện Console (như ở bài Hands-On trước), chứa các rule SSH và HTTP mà bạn đã cấu hình lúc tạo instance.

![](https://i.ibb.co/Xdmtrvy/image.png)

Mỗi Security Group có một **ID riêng** (dạng `sg-xxxxxxxx`) — tương tự như mỗi EC2 Instance có một Instance ID riêng.

![](https://i.ibb.co/Rnzjsp3/image.png)

## Bước 3: Kiểm Tra Inbound Rules

Chọn Security Group `launch-wizard-1`, xem tab **Inbound rules** — đây là các rule quyết định lưu lượng nào từ bên ngoài được phép kết nối **vào** instance. Có hai rule:

- **SSH** — cho phép lưu lượng trên **cổng 22**.
- **HTTP** — cho phép lưu lượng trên **cổng 80**.

![](https://i.ibb.co/27s8yNp6/image.png)

Nhấn **Edit inbound rules** để xem chi tiết: rule SSH cho phép từ `0.0.0.0/0` (tức **mọi nơi**), rule HTTP cũng cho phép từ `0.0.0.0/0`. Chính rule HTTP này là thứ đang cho phép bạn truy cập web server đã dựng ở bài trước.

![](https://i.ibb.co/rKZXh2bQ/image.png)

## Bước 4: Thí Nghiệm — Xóa Rule HTTP Và Quan Sát Hậu Quả

Quay lại trang chi tiết Instance, lấy **địa chỉ Public IPv4** và mở trang web đang chạy để xác nhận nó vẫn hoạt động bình thường (nhờ rule cổng 80 ở trên).

![](https://i.ibb.co/bjF1G1jB/image.png) ![](https://i.ibb.co/xt67fSWp/image.png) ![](https://i.ibb.co/6cv3jww2/image.png)

Bây giờ, quay lại Security Group, **xóa rule HTTP** (cổng 80) và nhấn **Save rules**. Sau khi xóa, Security Group chỉ còn lại đúng một rule: SSH (cổng 22).

![](https://i.ibb.co/MxZDfr2y/image.png)

Quay lại tab trình duyệt đang mở trang web, nhấn **làm mới (refresh)**. Lần này trang sẽ **tải mãi không xong** (màn hình loading vô hạn) — vì bạn thực sự **đã mất quyền truy cập** vào instance qua cổng 80.

![](https://i.ibb.co/N2KjmGwP/image.png)

### Mẹo quan trọng: nhận diện lỗi Timeout

Đây là một quy tắc thực hành rất hữu ích: khi bạn cố gắng kết nối đến EC2 Instance bằng bất kỳ cách nào (SSH, truy vấn HTTP...) mà gặp **timeout** (trình duyệt/terminal cứ chờ mãi, cuối cùng báo lỗi hết thời gian), nguyên nhân **rất thường gặp** là do **Security Group đang chặn kết nối đó**. Khi gặp tình huống này, việc đầu tiên nên kiểm tra là các rule trong Security Group của instance.

> 🛠️ **Lưu ý nhỏ:** Trên thực tế, Security Group là nguyên nhân phổ biến nhất gây timeout, nhưng **không phải nguyên nhân duy nhất có thể xảy ra** — timeout cũng có thể do Network ACL chặn ở cấp subnet, do route table thiếu đường đến Internet Gateway, hoặc do một firewall chạy ngay trong hệ điều hành của instance (ví dụ `iptables` trên Linux). Với một instance mới dựng theo đúng các bước mặc định như trong khóa học này (không chỉnh NACL, không chỉnh route table), khả năng cao nhất vẫn là do Security Group — nhưng về lâu dài, khi gặp timeout, hãy kiểm tra Security Group **trước tiên**, rồi mới xét đến các khả năng khác nếu vẫn không khắc phục được.

## Bước 5: Thêm Lại Rule HTTP

Để khôi phục, quay lại Security Group, thêm lại một rule mới:

- **Type:** chọn **HTTP** từ menu sổ xuống — Console sẽ tự động điền cổng **80**.
- **Source:** chọn **Anywhere-IPv4** (`0.0.0.0/0`).

Nhấn **Save rules**.

![](https://i.ibb.co/604TTMsf/image.png) ![](https://i.ibb.co/h0110n3/image.png)

Quay lại tab trình duyệt, làm mới trang — trang web giờ **hoạt động trở lại bình thường**.

![](https://i.ibb.co/k7KF53X/image.png)

## Các Tùy Chọn Khi Tạo Rule

Khi thêm một inbound rule, bạn có thể:

- **Chọn cổng tùy ý** — ví dụ gõ trực tiếp `443` cho HTTPS.
- **Chọn nhanh từ menu Type** — ví dụ chọn sẵn "HTTPS", Console sẽ tự điền cổng 443 tương ứng, không cần nhớ số cổng.
- **Chọn nguồn (Source) theo nhiều cách khác nhau:**
    - **CIDR block tùy chỉnh** — ví dụ `0.0.0.0/0` (mọi nơi) hoặc một dải IP cụ thể.
    - **My IP** — Console tự động điền đúng địa chỉ IP công khai hiện tại của máy bạn, chỉ cho phép truy cập từ chính IP đó.
    - **Một Security Group khác** — đã học ở bài lý thuyết (tham chiếu Security Group lẫn nhau).
    - **Prefix list** — một nhóm CIDR được AWS hoặc bạn định nghĩa sẵn, sẽ tìm hiểu kỹ hơn sau trong khóa học.

![](https://i.ibb.co/QFgLZx1R/image.png)

> ⚠️ **Lưu ý khi chọn "My IP":** nếu địa chỉ IP công khai của bạn **thay đổi** sau đó (ví dụ do nhà mạng cấp IP động, hoặc bạn đổi mạng Wi-Fi), rule cũ sẽ không còn khớp với IP mới của bạn nữa — bạn sẽ gặp **timeout** y hệt thí nghiệm ở Bước 4, và cần cập nhật lại rule với IP mới.

## Bước 6: Kiểm Tra Outbound Rules

Cuối cùng, xem tab **Outbound rules** của Security Group: mặc định cho phép **toàn bộ lưu lượng** (`All traffic`) trên **IPv4**, đến **mọi nơi** (`0.0.0.0/0`). Đây chính là điều giúp EC2 Instance có kết nối Internet đầy đủ ra bên ngoài.

## Một Instance Có Thể Gắn Nhiều Security Group

Như đã thấy, instance này hiện có **hai** Security Group (`default` và `launch-wizard-1`). Trên thực tế, một EC2 Instance có thể gắn **nhiều Security Group cùng lúc** — mặc định AWS cho phép tối đa **5 Security Group trên mỗi network interface** (có thể xin tăng lên tới 16) [^1]. Khi một instance gắn nhiều Security Group, **các rule sẽ được cộng dồn (additive)** với nhau — nghĩa là lưu lượng được phép nếu **bất kỳ** Security Group nào trong số đó có rule cho phép.

Tương tự, một Security Group như `launch-wizard-1` không chỉ dùng cho riêng instance này — bạn hoàn toàn có thể **gắn nó vào các EC2 Instance khác**. Tóm lại: quan hệ giữa Security Group và Instance là **nhiều-nhiều (many-to-many)** — một Instance có thể có nhiều Security Group, và một Security Group có thể gắn cho nhiều Instance.

## Mở Rộng

- **Giới hạn số rule mỗi Security Group** — mặc định 60 inbound + 60 outbound rule cho mỗi Security Group, có thể xin tăng [^1].
- **Prefix List** — tìm hiểu sâu hơn cách dùng Prefix List để quản lý nhiều dải CIDR như một nhóm, thay vì khai báo lặp lại nhiều rule.
- **AWS CLI cho Security Group** — các lệnh như `aws ec2 authorize-security-group-ingress` để tự động hóa việc thêm/xóa rule thay vì thao tác tay trên Console.
- **Debug kết nối nâng cao** — dùng **VPC Flow Logs** để xem chi tiết lưu lượng nào bị Security Group hoặc Network ACL chặn, thay vì chỉ đoán qua hiện tượng timeout.
- **Elastic IP** — giải pháp cho vấn đề "My IP thay đổi" ở phía EC2 Instance (địa chỉ IP của instance cố định); còn phía máy cá nhân của bạn, có thể cân nhắc VPN với IP tĩnh nếu cần truy cập ổn định lâu dài.
