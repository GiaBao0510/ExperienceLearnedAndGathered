## Giới Thiệu Security Group

**Security Group** là nền tảng của bảo mật mạng trong AWS — đóng vai trò như một **"tường lửa" (firewall)** bao quanh EC2 Instance.

- Chúng kiểm soát lưu lượng mạng được phép **đi vào (inbound)** hoặc **đi ra (outbound)** khỏi instance.
- Security Group **chỉ chứa các quy tắc cho phép (Allow)** — không có khái niệm "quy tắc từ chối" trong Security Group. Bất cứ điều gì không được liệt kê rõ trong quy tắc Allow thì mặc định bị chặn.
- Một quy tắc trong Security Group có thể tham chiếu theo **địa chỉ IP** hoặc theo **một Security Group khác** — các Security Group hoàn toàn có thể tham chiếu lẫn nhau (sẽ tìm hiểu chi tiết ở phần sau).

**Ví dụ dễ hình dung:** Bạn đang ngồi ở nhà, dùng máy tính cá nhân kết nối Internet công cộng, và muốn truy cập vào một EC2 Instance trên AWS. Bạn tạo một Security Group bao quanh EC2 Instance đó — đây chính là "tường lửa" của instance. Security Group này có các quy tắc quyết định: lưu lượng từ bên ngoài (như máy tính của bạn) có được phép **vào** instance hay không, và instance có được phép gửi lưu lượng **ra** ngoài Internet hay không.

## Security Group Hoạt Động Như Thế Nào?

Security Group kiểm soát:

- Quyền truy cập vào các **cổng (port)** cụ thể.
- Các dải địa chỉ IP được cấp quyền — cả **IPv4** lẫn **IPv6**.
- Lưu lượng **đi vào** (inbound — từ bên ngoài đến instance).
- Lưu lượng **đi ra** (outbound — từ instance ra bên ngoài).

## Cấu Trúc Một Quy Tắc (Rule)

Một quy tắc Security Group thường gồm các trường sau:

| Trường                                                    | Ý nghĩa                                                      |
| --------------------------------------------------------- | ------------------------------------------------------------ |
| **Type**                                                  | Loại lưu lượng (ví dụ: SSH, HTTP, Custom TCP...)             |
| **Protocol**                                              | Giao thức mạng, ví dụ: TCP                                   |
| **Port Range**                                            | Cổng (hoặc dải cổng) cho phép lưu lượng đi qua trên instance |
| **Source** (với inbound) / **Destination** (với outbound) | Dải địa chỉ IP áp dụng quy tắc                               |

Về trường Source/Destination: `0.0.0.0/0` nghĩa là **toàn bộ địa chỉ IPv4** (tất cả mọi nơi trên Internet), trong khi một địa chỉ dạng `203.0.113.25/32` chỉ đại diện cho **đúng một địa chỉ IP** duy nhất.

## Sơ Đồ Minh Họa

![](https://iili.io/nYuD6nn.png)

EC2 Instance được gắn với một Security Group, gồm hai nhóm quy tắc tách biệt: **inbound rules** (quy tắc đi vào) và **outbound rules** (quy tắc đi ra).

**Ví dụ inbound:** máy tính của bạn được cấp quyền trên cổng 22 (SSH), nên lưu lượng có thể đi từ máy bạn đến EC2 Instance. Nhưng nếu một người khác — với địa chỉ IP khác — cố truy cập vào cùng instance đó, họ sẽ **không vượt qua được**: tường lửa sẽ chặn kết nối, và kết quả là họ gặp lỗi **timeout** (hết thời gian chờ).

**Về outbound:** theo mặc định, Security Group cho phép **mọi lưu lượng đi ra ngoài**. Vì vậy nếu EC2 Instance của bạn cố gắng kết nối đến một website nào đó, kết nối đó sẽ được Security Group cho phép mà không cần cấu hình gì thêm.

> 📌 **Bổ sung khái niệm quan trọng — Security Group là "stateful" (có trạng thái):** nếu một kết nối **đi vào** được Security Group cho phép (ví dụ: ai đó SSH vào instance ở cổng 22), thì lưu lượng **phản hồi đi ra** cho đúng kết nối đó sẽ **tự động được cho phép**, dù outbound rule của bạn không có quy tắc tương ứng nào cho cổng đó [^1]. Đây là lý do vì sao bạn ít khi phải cấu hình tay outbound rule riêng cho từng kết nối — chỉ cần inbound đúng là đủ. Tính chất này khác hẳn với **Network ACL** (sẽ nhắc ở phần Mở rộng) — vốn _stateless_ (không trạng thái), nên phải khai báo rule cho cả hai chiều.

## Những Điều Cần Biết (Good To Know)

- **Không có quan hệ một-một** giữa Security Group và Instance: một Security Group có thể gắn cho **nhiều instance**, và ngược lại, **một instance cũng có thể gắn nhiều Security Group** cùng lúc.
- Security Group bị giới hạn trong **một cặp Region + VPC cụ thể**. Nếu bạn chuyển sang region khác, hoặc dùng một VPC khác (khái niệm VPC sẽ học ở bài sau), bạn **phải tạo lại** Security Group tương ứng — không thể tái sử dụng Security Group giữa các Region/VPC khác nhau.
- Security Group hoạt động **"bên ngoài"** EC2 Instance: nếu lưu lượng bị chặn, instance **thậm chí không nhận được** gói dữ liệu đó. Đây khác với một firewall chạy như một ứng dụng bên trong instance (ví dụ `iptables` trên Linux) — Security Group là một lớp chắn hoàn toàn tách biệt, nằm ngoài hệ điều hành của instance.
- **Nên tách riêng một Security Group chỉ dành cho SSH.** Truy cập SSH thường là phần nhạy cảm nhất cần kiểm soát chặt, nên tách biệt giúp bạn dễ audit và điều chỉnh mà không ảnh hưởng các rule khác.
- **Mẹo debug quan trọng — phân biệt 2 loại lỗi:**
    - Nếu bạn kết nối đến một cổng và máy tính **treo, chờ mãi không phản hồi** (timeout) → gần như chắc chắn là do **Security Group đang chặn**.
    - Nếu bạn nhận được lỗi **"connection refused"** (từ chối kết nối) ngay lập tức → đó là do **ứng dụng** (ứng dụng chưa chạy, hoặc không lắng nghe đúng cổng), **không phải** do Security Group.
- **Mặc định:** mọi lưu lượng **inbound bị chặn**, mọi lưu lượng **outbound được cho phép**.

## Tham Chiếu Security Group Lẫn Nhau

![](https://iili.io/nYubyRp.png)

Đây là một tính năng nâng cao nhưng khá phổ biến, đặc biệt khi làm việc với Load Balancer. Cách hoạt động:

Giả sử EC2 Instance đầu tiên có gắn **Security Group #1**. Trong inbound rule của Security Group #1, thay vì chỉ định một địa chỉ IP cụ thể, ta chỉ định: **"cho phép lưu lượng đến từ bất kỳ resource nào đang gắn Security Group #2."**

**Vì sao làm vậy?** Khi bạn khởi chạy một EC2 Instance khác và gắn **Security Group #2** cho nó, instance thứ hai này **ngay lập tức** được phép kết nối tới instance đầu tiên qua đúng cổng đã cấu hình trong rule — mà **không cần biết địa chỉ IP** của instance thứ hai là gì. Dù IP của các instance có thay đổi (ví dụ sau khi stop/start — xem lại bài Hands-On EC2), việc kết nối vẫn hoạt động bình thường, miễn là Security Group phù hợp vẫn được gắn.

Ngược lại, nếu bạn khởi chạy một EC2 Instance thứ ba và gắn **Security Group #3** — vì Security Group #3 **không** được liệt kê trong inbound rule của Security Group #1, kết nối từ instance thứ ba sẽ **bị từ chối**.

> 💡 Hãy nhớ kỹ sơ đồ trên: đây là mẫu (pattern) rất thường gặp trong thực tế — ví dụ: chỉ cho phép các EC2 Instance đứng sau một Load Balancer nhận lưu lượng, bằng cách tham chiếu đến Security Group của chính Load Balancer đó, thay vì liệt kê IP.

## Các Cổng (Port) Kinh Điển Cần Nhớ

| Port     | Giao thức                             | Dùng để                                                                                                                                |
| -------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **22**   | **SSH** (Secure Shell)                | Đăng nhập từ xa vào instance **Linux**                                                                                                 |
| **22**   | **SFTP** (SSH File Transfer Protocol) | Tải file lên/xuống một cách an toàn — chạy trên **cùng cổng 22**, vì SFTP thực chất là một giao thức truyền file chạy **bên trên SSH** |
| **21**   | **FTP** (File Transfer Protocol)      | Tải file lên một file share — đây là giao thức truyền file **không mã hóa**, ít được khuyến khích dùng cho dữ liệu nhạy cảm            |
| **80**   | **HTTP**                              | Truy cập website **không mã hóa** (không bảo mật)                                                                                      |
| **443**  | **HTTPS**                             | Truy cập website **có mã hóa** (bảo mật)                                                                                               |
| **3389** | **RDP** (Remote Desktop Protocol)     | Đăng nhập từ xa vào instance **Windows**                                                                                               |

> 📌 Chú ý: **SSH và SFTP dùng chung cổng 22** — đây không phải lỗi trùng lặp, mà vì SFTP vốn được thiết kế để chạy như một tính năng con của giao thức SSH.

## Mở Rộng

- **Network ACL (NACL)** — một lớp tường lửa khác của AWS, hoạt động ở cấp **subnet** (thay vì cấp instance như Security Group), hỗ trợ cả rule Allow lẫn Deny, và có tính chất **stateless** (không tự động cho phép chiều ngược lại) [^1]. Bảng so sánh nhanh:

|               | Security Group                       | Network ACL               |
| ------------- | ------------------------------------ | ------------------------- |
| Cấp độ        | Instance                             | Subnet                    |
| Loại rule     | Chỉ Allow                            | Allow và Deny             |
| Tính chất     | Stateful                             | Stateless                 |
| Đánh giá rule | Xét tất cả rule trước khi quyết định | Xử lý theo thứ tự số rule |

- **VPC (Virtual Private Cloud)** — khái niệm sẽ học ở bài tiếp theo, là "ranh giới mạng riêng" mà Security Group bị giới hạn bên trong.
    
- **AWS Systems Manager Session Manager / EC2 Instance Connect** — cách truy cập instance mà không cần mở cổng 22 (SSH) cho toàn bộ hoặc một phần Internet.
    
- **Elastic Load Balancer (ELB)** — nơi kỹ thuật "tham chiếu Security Group lẫn nhau" được ứng dụng phổ biến nhất trong thực tế.
    
- **Giới hạn số lượng Security Group / rule** — AWS mặc định giới hạn số Security Group gắn cho một network interface, và số rule tối đa trong một Security Group; có thể yêu cầu tăng giới hạn (quota increase) nếu cần.
