# JWT và REST API: Xác thực an toàn


## REST API là gì?

**REST (Representational State Transfer)** là một kiến trúc thiết kế cho các hệ thống phân tán, được Roy Thomas Fielding giới thiệu vào năm 2000 trong luận văn tiến sĩ của ông (đồng sáng lập giao thức HTTP). REST API sử dụng các phương thức HTTP chuẩn (GET, POST, PUT, DELETE) để thao tác trên tài nguyên (resources) thông qua các URL. REST tuân theo các nguyên tắc chính như:

- **Stateless:** Mỗi yêu cầu (request) từ client đến server phải chứa đủ thông tin để xử lý, không phụ thuộc vào trạng thái trước đó.
- **Client-Server:** Tách biệt giữa client (giao diện người dùng) và server (xử lý dữ liệu).
- **Dùng HTTP chuẩn:** Sử dụng các phương thức HTTP để thực hiện các thao tác CRUD (Create, Read, Update, Delete).

**Ví dụ:** Một REST API để lấy danh sách người dùng có thể là: `GET https://api.example.com/users`.

## JWT là gì?

**JSON Web Token (JWT)** là một chuẩn mở (RFC 7519) để truyền thông tin giữa các bên dưới dạng đối tượng JSON. JWT bao gồm ba phần chính (Header, Payload, Signature), được mã hóa Base64Url và phân tách bằng dấu chấm (`.`). Thông tin trong JWT được **ký số** để đảm bảo tính toàn vẹn và xác thực, sử dụng thuật toán như HMAC hoặc cặp khóa public/private (RSA/ECDSA).

**Cấu trúc JWT:** `xxxxx.yyyyy.zzzzz` tương đương `header.payload.signature`
- **Header:** Chứa thuật toán ký (ví dụ: HS256) và loại token (JWT).
- **Payload:** Chứa thông tin người dùng (claims) như ID, vai trò, thời gian hết hạn.
- **Signature:** Chữ ký để xác minh token không bị thay đổi.

**Lưu ý:** Payload của JWT không được mã hóa, bất kỳ ai cũng có thể đọc được. Để mã hóa payload, cần sử dụng **JWE (JSON Web Encryption)**.

**Ví dụ JWT:**
```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkdpYSBCYW8iLCJyb2xlIjoiYWRtaW4ifQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

## Tại sao sử dụng JWT để xác thực REST API?

REST API thường được sử dụng để cung cấp dữ liệu cho client (web, mobile). Nếu không có xác thực, bất kỳ ai cũng có thể truy cập các endpoint nhạy cảm, dẫn đến rủi ro bảo mật.

**Ví dụ:**  
API `GET https://api.example.com/users` trả về danh sách tất cả người dùng. Nếu không có xác thực, kẻ xấu có thể lấy thông tin nhạy cảm. JWT giúp giải quyết vấn đề này bằng cách:

- **Xác thực người dùng:** Chỉ người dùng có token hợp lệ mới được truy cập.
- **Phân quyền:** Token có thể chứa thông tin vai trò (role) để kiểm tra quyền truy cập.
- **Stateless:** Server không cần lưu trữ session, giúp hệ thống dễ mở rộng.

**So sánh với các phương pháp khác:**

| Phương pháp       | Ưu điểm                             | Nhược điểm                                     |
| ----------------- | ----------------------------------- | ---------------------------------------------- |
| **JWT**           | Stateless, dễ mở rộng, đa nền tảng  | Không dễ thu hồi, rủi ro nếu lưu không an toàn |
| **Session-based** | Dễ thu hồi session                  | Stateful, cần lưu trữ server                   |
| **OAuth 2.0**     | Linh hoạt, hỗ trợ ủy quyền phức tạp | Phức tạp hơn, cần server ủy quyền              |

## Quy trình xác thực REST API với JWT

Dưới đây là quy trình xác thực với JWT, bao gồm cả Access Token và Refresh Token:

1. **Đăng nhập:**  
   Client gửi thông tin đăng nhập (username, password) đến server qua endpoint như `POST /api/login`.

2. **Tạo token:**  
Nếu thông tin hợp lệ, server tạo:
   - **Access Token:** JWT chứa thông tin người dùng (ID, vai trò) và thời gian hết hạn ngắn (ví dụ: 15 phút).
   - **Refresh Token:** Chuỗi ngẫu nhiên để làm mới Access Token, có thời gian sống dài hơn (ví dụ: 7 ngày).  
   Server gửi cả hai token về client.

3. **Lưu token:**  
   Client lưu token an toàn:
   - Access Token: Trong `localStorage` hoặc `sessionStorage` (cho web) hoặc bộ nhớ ứng dụng (cho mobile).
   - Refresh Token: Trong `HttpOnly cookies` để tăng bảo mật, tránh bị tấn công XSS.

4. **Gửi request với token:**  
   Khi gọi API (ví dụ: `GET /api/users`), client gửi Access Token trong header:   ==Authorization: Bearer <access_token>==

5. **Xác minh token:**  
  Server kiểm tra token:
- Xác minh chữ ký (signature) để đảm bảo token không bị giả mạo.
- Kiểm tra thời gian hết hạn (`exp`), issuer (`iss`), audience (`aud`).
- Nếu token hợp lệ, server xử lý request và trả về dữ liệu.
- Nếu token hết hạn, client sử dụng Refresh Token để yêu cầu Access Token mới qua endpoint như `POST /api/refresh`.

6. **Làm mới token:**  
Client gửi Refresh Token đến server. Server kiểm tra Refresh Token (thường lưu trong database/Redis) và cấp Access Token mới nếu hợp lệ.

## Lưu ý bảo mật khi sử dụng JWT

1. **Sử dụng HTTPS:** Truyền JWT qua HTTPS để ngăn chặn tấn công man-in-the-middle.
2. **Đặt TTL ngắn cho Access Token:** Access Token nên có thời gian sống ngắn (15 phút - 1 giờ) để giảm rủi ro nếu bị lộ.
3. **Lưu trữ token an toàn:**
    - Access Token: Có thể lưu trong localStorage (nhưng cần chống XSS).
    - Refresh Token: Lưu trong HttpOnly cookies để tránh bị đánh cắp qua JavaScript.
4. **Kiểm tra chữ ký và thuật toán:** Server phải kiểm tra chữ ký và từ chối token với thuật toán không mong muốn (ví dụ: "none").
5. **Sử dụng Refresh Token:** Dùng Refresh Token để làm mới Access Token, tránh yêu cầu đăng nhập lại.
6. **Không lưu thông tin nhạy cảm trong Payload:** Payload có thể được đọc, nên tránh chứa dữ liệu như mật khẩu hoặc số thẻ tín dụng.
7. **Quản lý Refresh Token:** Lưu Refresh Token trong database/Redis và kiểm tra tính hợp lệ khi làm mới token.
