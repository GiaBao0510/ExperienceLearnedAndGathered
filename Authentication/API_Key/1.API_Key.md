# API Key

## API Key là gì?

**API (Application Programming Interface)** là lớp trung gian cho phép các ứng dụng giao tiếp và trao đổi dữ liệu với nhau theo một giao thức xác định. **API Key** là cơ chế xác thực đi kèm — một chuỗi ký tự định danh duy nhất do nhà cung cấp API cấp phát, dùng để xác thực nguồn gốc của mỗi request và kiểm soát quyền truy cập vào tài nguyên API.

Cụ thể, API Key là một chuỗi ký tự (thường là alphanumeric) được nhà cung cấp sinh ra và gắn với một ứng dụng hoặc tài khoản cụ thể. Khi client gửi request đến API, key được đính kèm để server có thể:

- Xác định request đến từ ứng dụng/dự án nào.
- Kiểm tra quyền truy cập tài nguyên tương ứng.
- Thực thi các chính sách giới hạn lưu lượng (rate limiting) theo từng key.

API Key **không xác thực danh tính người dùng** — đây là điểm khác biệt cốt lõi so với các cơ chế xác thực người dùng như OAuth 2.0 hay JWT. API Key xác định _ứng dụng_ đang gọi API, không phải _người dùng_ đang thao tác.

## Tại sao dùng API Key?

**Xác thực ứng dụng (Authentication):** API Key xác định ứng dụng hoặc dự án đang thực hiện request, giúp server từ chối các request không có key hợp lệ hoặc từ nguồn không được phép.

**Kiểm soát lưu lượng (Rate Limiting):** Mỗi key có thể bị giới hạn số lượng request trong một khoảng thời gian nhất định (ví dụ: 1.000 request/giờ). Điều này ngăn chặn lạm dụng tài nguyên và đảm bảo dịch vụ phân bổ công bằng giữa các client.

**Giám sát và phân tích sử dụng:** Mỗi request được gắn với một key cụ thể, cho phép nhà cung cấp theo dõi lưu lượng, thống kê tỷ lệ thành công/thất bại, và phát hiện hành vi bất thường (ví dụ: spike đột ngột từ một key).

**Phân quyền truy cập (Authorization):** Các key khác nhau có thể được cấu hình với các mức quyền khác nhau — ví dụ: key chỉ đọc (read-only) hoặc key có quyền ghi (read-write), hoặc chỉ được truy cập vào một tập hợp endpoint cụ thể.

## API Key hoạt động như thế nào?

API Key là một chuỗi ký tự được sinh ngẫu nhiên, gắn với một ứng dụng hoặc tài khoản cụ thể trên hệ thống của nhà cung cấp. Quy trình xử lý một request có API Key như sau:

**Bước 1 — Client gửi request**

Client gửi HTTP request đến API endpoint, kèm API Key trong header hoặc query parameter.

Cách đính kèm phổ biến nhất là qua HTTP header:

```
GET /v1/data
Authorization: Bearer YOUR_API_KEY
```

Một số API cũng chấp nhận key qua query parameter (ít bảo mật hơn vì key xuất hiện trong URL và có thể bị lưu trong access log):

```
GET /v1/data?api_key=YOUR_API_KEY
```

**Bước 2 — Server xác thực key**

Server nhận request và kiểm tra tuần tự:

1. Key có tồn tại trong hệ thống không?
2. Key có còn hiệu lực không (chưa bị thu hồi hoặc hết hạn)?
3. Key có quyền truy cập endpoint này không?
4. Key có còn trong hạn mức request (rate limit) không?

**Bước 3 — Server trả về phản hồi**

- Key hợp lệ và đủ quyền → trả về dữ liệu yêu cầu (`200 OK`).
- Key không tồn tại hoặc không hợp lệ → `401 Unauthorized`.
- Key hợp lệ nhưng không đủ quyền → `403 Forbidden`.
- Key hợp lệ nhưng vượt rate limit → `429 Too Many Requests`.

Ngoài xác thực cơ bản, API Key còn được dùng để kiểm soát chi tiết hơn:

- **Rate limiting theo cấp dịch vụ:** Các key khác nhau có thể có hạn mức khác nhau tùy theo gói dịch vụ (free tier, paid tier).
- **Phân quyền theo tài nguyên:** Key chỉ được phép thực hiện một số thao tác nhất định (read-only, read-write) hoặc chỉ truy cập một tập endpoint cụ thể.
- **Lọc theo phạm vi địa lý hoặc IP:** Một số hệ thống gắn key với whitelist IP hoặc giới hạn khu vực địa lý.

## Lưu trữ và bảo mật API Key phía server

Khi cấp phát API Key cho người dùng, phía server cần có cơ chế lưu trữ để xác minh mỗi khi nhận request. Thực hành chuẩn là **không lưu plaintext API Key** trong database mà chỉ lưu giá trị băm (hash):

```
# Quy trình cấp phát
api_key = generate_random_string(32)       # sinh key ngẫu nhiên
key_hash = bcrypt(api_key) hoặc SHA-256(api_key)
lưu key_hash vào database

# Trả về key gốc cho người dùng một lần duy nhất
# Server không lưu key gốc — nếu người dùng mất key, phải cấp key mới

# Quy trình xác thực
incoming_key = lấy từ request header
tìm hash khớp trong database → xác thực thành công / thất bại
```

Một số điểm cần lưu ý:

- Với API Key, thường dùng **SHA-256** (nhanh, phù hợp cho lookup thường xuyên) thay vì bcrypt (chậm hơn, thiết kế cho mật khẩu người dùng).
- Nên lưu kèm metadata: ngày tạo, ngày hết hạn, trạng thái (active/revoked), scope quyền, và ID của người dùng/ứng dụng sở hữu key.
- Cho phép người dùng thu hồi (revoke) key bất cứ lúc nào mà không ảnh hưởng đến tài khoản.

## API Key kết hợp với Access Token

Câu hỏi thực tế: **Nếu API đã yêu cầu Access Token để xác thực, có cần thêm API Key không?**

Câu trả lời phụ thuộc vào mục đích của từng cơ chế:

|Tiêu chí|API Key|Access Token (OAuth / JWT)|
|---|---|---|
|Xác định|Ứng dụng / dự án|Người dùng cụ thể|
|Thời hạn|Dài (không hết hạn hoặc hết hạn sau nhiều tháng)|Ngắn (thường 15 phút — vài giờ)|
|Revoke|Thủ công|Tự động khi hết hạn; có thể revoke sớm|
|Phù hợp cho|Server-to-server, public API|Ứng dụng cần xác thực người dùng|

Trong thực tế, hai cơ chế này có thể **kết hợp với nhau**:

- API Key xác định _ứng dụng_ nào đang gọi và kiểm soát rate limit.
- Access Token xác định _người dùng_ nào trong ứng dụng đó đang thực hiện hành động.

Ví dụ: Một ứng dụng mobile gọi API với cả API Key (để xác định ứng dụng và áp rate limit) và Bearer Token (để xác định người dùng đang đăng nhập).

Ngược lại, nếu API chỉ phục vụ giao tiếp server-to-server (không có user context), API Key đơn độc là đủ và Access Token là không cần thiết.

## Nên và không nên dùng API Key trong trường hợp nào?

### Nên dùng

**Giao tiếp server-to-server (M2M):** Khi một service backend gọi API của service khác mà không có user context (ví dụ: microservice gọi payment API, backend gọi SMS gateway), API Key là phương thức xác thực phù hợp và đủ.

**Public API với kiểm soát lưu lượng:** Khi cần phân biệt các ứng dụng/developer đang sử dụng API để áp dụng rate limit, thống kê, và billing theo từng client.

**Tích hợp với dịch vụ bên thứ ba:** Google Maps API, Stripe, Twilio, OpenAI — tất cả đều dùng API Key để xác định ứng dụng tích hợp.

**Phát hiện và debug sự cố tích hợp:** Mỗi key tương ứng với một ứng dụng cụ thể, giúp nhanh chóng khoanh vùng nguồn gốc của request lỗi hoặc lưu lượng bất thường.

### Không nên dùng

**Xác thực danh tính người dùng cuối:** API Key không liên kết với một người dùng cụ thể. Để xác thực user, cần dùng OAuth 2.0, JWT, hoặc session-based authentication. Dùng API Key cho mục đích này là sai về mặt thiết kế và tiềm ẩn rủi ro bảo mật.

**Trong môi trường có nhiều người dùng chia sẻ cùng một key:** Nếu nhiều người dùng dùng chung một API Key, không thể phân biệt hành động của từng người, không thể revoke quyền của một cá nhân mà không ảnh hưởng những người khác.

**Truyền qua URL (query parameter) với dữ liệu nhạy cảm:** Key trong URL xuất hiện trong server access log, browser history, và có thể bị lộ qua Referer header. Với tài nguyên nhạy cảm, luôn truyền key qua HTTP header.

## Ưu và nhược điểm

### Ưu điểm

- Đơn giản để triển khai — client chỉ cần đính kèm một chuỗi vào header.
- Không cần quy trình xác thực phức tạp như OAuth flow.
- Phù hợp cho giao tiếp server-to-server không cần user context.
- Dễ dàng thu hồi (revoke) một key cụ thể khi bị lộ mà không ảnh hưởng các key khác.
- Hỗ trợ kiểm soát lưu lượng và billing theo từng client một cách tự nhiên.

### Nhược điểm

- Không xác thực danh tính người dùng — chỉ xác định ứng dụng.
- Nếu key bị lộ, bất kỳ ai có key đó đều có thể sử dụng API với toàn bộ quyền của key đó cho đến khi bị revoke.
- Không có cơ chế hết hạn tự động như JWT — key sống mãi trừ khi bị thu hồi thủ công.
- Không phù hợp cho các luồng yêu cầu xác thực người dùng (user-facing authentication).

## Lỗi phổ biến khi dùng API Key

### Commit key lên version control

Đây là lỗi thường gặp nhất: developer hardcode API Key trong source code hoặc file config và vô tình commit lên repository public (GitHub, GitLab).

Hậu quả:

- Key bị bot tự động quét và lạm dụng trong vòng vài phút sau khi commit.
- API bị spam, vượt quota, phát sinh chi phí ngoài dự kiến.
- Tài khoản có thể bị khóa do vi phạm điều khoản dịch vụ.

Thực hành đúng: Lưu API Key trong **biến môi trường (environment variable)** hoặc **secret management system** (HashiCorp Vault, AWS Secrets Manager, GitHub Actions Secrets), không bao giờ hardcode trong source code.

```bash
# Sai
api_key := "sk-abc123xyz..."

# Đúng
api_key := os.Getenv("THIRD_PARTY_API_KEY")
```

Nếu đã lỡ commit key lên repository: **revoke key ngay lập tức** trước khi làm bất cứ điều gì khác, kể cả xóa commit — vì key đã có thể bị thu thập trước khi xóa.

### Các lỗi phổ biến khác

**Dùng chung một key cho nhiều môi trường:** Key production và staging nên tách biệt. Nếu key staging bị lộ, production không bị ảnh hưởng.

**Không thiết lập hạn mức và cảnh báo:** Nên cấu hình rate limit và alert khi lưu lượng đột biến để phát hiện sớm khi key bị lạm dụng.

**Không giới hạn scope của key:** Nếu API Key chỉ cần quyền đọc, không cấp quyền ghi. Nguyên tắc least privilege áp dụng cho API Key giống như với mọi loại credential khác.

**Không rotate key định kỳ:** Key nên được thay thế định kỳ (key rotation), đặc biệt với các hệ thống có yêu cầu bảo mật cao, để giảm thiểu rủi ro nếu key đã bị lộ mà chưa phát hiện.

## Đề xuất cải thiện thêm

### 1. So sánh API Key với các cơ chế xác thực khác

Tài liệu sẽ đầy đủ hơn nếu có bảng so sánh nhanh giữa các phương thức xác thực phổ biến:

|Cơ chế|Xác định|Thời hạn|Phù hợp cho|
|---|---|---|---|
|API Key|Ứng dụng|Dài / vĩnh viễn|M2M, public API|
|JWT (Bearer Token)|Người dùng|Ngắn (tự hết hạn)|User auth, stateless API|
|OAuth 2.0|Người dùng + ứng dụng|Ngắn + Refresh Token|Third-party delegation|
|Basic Auth|Người dùng|Không hết hạn|Nội bộ, legacy|
|mTLS|Cả hai phía|Certificate lifecycle|High-security M2M|

### 2. Sử dụng Secret Management System trong production

Với môi trường production, không nên lưu API Key (cả của bên mình cấp phát và của bên thứ ba mình sử dụng) trong biến môi trường đơn thuần mà nên dùng hệ thống quản lý secret chuyên dụng:

- **HashiCorp Vault:** Self-hosted, hỗ trợ dynamic secrets và automatic rotation.
- **AWS Secrets Manager / GCP Secret Manager:** Managed service, tích hợp sẵn với hạ tầng cloud.
- **Doppler, Infisical:** Developer-friendly secret management với hỗ trợ nhiều môi trường.

### 3. Implement API Key trong Golang

Với đối tượng đọc là Golang backend developer, có thể bổ sung ví dụ triển khai middleware xác thực API Key:

```go
func APIKeyMiddleware(validKeys map[string]bool) gin.HandlerFunc {
    return func(c *gin.Context) {
        key := c.GetHeader("X-API-Key")
        if key == "" {
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{
                "error": "API key required",
            })
            return
        }

        // So sánh hash, không so sánh plaintext
        keyHash := sha256.Sum256([]byte(key))
        hashStr := hex.EncodeToString(keyHash[:])

        if !validKeys[hashStr] {
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{
                "error": "Invalid API key",
            })
            return
        }

        c.Next()
    }
}
```
