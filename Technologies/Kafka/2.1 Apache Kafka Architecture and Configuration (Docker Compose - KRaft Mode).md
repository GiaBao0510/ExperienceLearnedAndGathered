Trước khi đi vào từng biến, hãy cùng nhìn **kiến trúc tổng thể** của Kafka ở chế độ KRaft. Hiểu được điều này thì mọi biến cấu hình đều trở nên logic.

```
┌───────────────────── KAFKA CLUSTER ─────────────────────┐
│                                                         │
│  ┌─────────────┐    Controller Quorum    ┌─────────────┐│
│  │  Node 1     │◄──────────────────────► │  Node 2     ││
│  │ Broker+Ctrl │  Metadata Sync (9093)   │ Broker+Ctrl ││
│  └──────┬──────┘                         └──────┬──────┘│
│         │                                       │       │
│         ▼                                       ▼       │
│    [Data Plane: 9092]                     [Data Plane]  │
│         │                                      │        │
│         └──────────► LOG DIRS ◄────────────────┘        │
│                         │                               │
│                         ▼                               │
│              Internal Topics                            │
│              ┌─────────────────────┐                    │
│              │ __consumer_offsets  │                    │
│              │ __transaction_state │                    │
│              │ __cluster_metadata  │                    │
│              └─────────────────────┘                    │
└─────────────────────────────────────────────────────────┘
                    ▲                     ▲
                    │ 9092                │ 9092
               ┌────┴────┐           ┌────┴────┐
               │Producer │           │Consumer │
               └─────────┘           └─────────┘
```

Có **3 mặt phẳng (planes)** trong Kafka:

- **Control Plane (9093)**: Quorum Controllers nói chuyện với nhau để quản lý metadata
- **Data Plane (9092)**: Clients (producer/consumer) giao tiếp với brokers, brokers sync data với nhau
- **Local Storage**: LOG DIRS, nơi data được ghi xuống đĩa

## CLUSTER IDENTITY

**Property tương ứng**: Không phải property trong `server.properties` — đây là tham số đặc biệt của **Docker image / `kafka-storage.sh`**, dùng để `format` thư mục log trước khi broker khởi động lần đầu.

**Dùng để làm gì?** 
Một chuỗi định danh duy nhất cho toàn bộ Kafka cluster. Mỗi cluster có một ID riêng, không trùng nhau.

![](https://encrypted-tbn0.gstatic.com/images?q=tbn:ANd9GcQ1L3rU-Q-7-LvGxJ4JbESD0aqHoFJQV_64WAP-jbq_b0UhMqWDzRnQcLDO&s=10)

**Vấn đề Kafka giải quyết:** Trước KRaft, cluster ID được ZooKeeper sinh ra khi format. Với KRaft (không có ZooKeeper), Kafka cần một cách "bootstrap" để nhận ra: "những node nào thuộc về cùng một cluster?" Nếu bạn vô tình trỏ hai cluster khác nhau vào cùng volume hoặc network, cluster ID sẽ ngăn chúng merge nhầm.

**Tại sao Kafka cần?** Khi node mới khởi động, nó đọc `meta.properties` trong LOG DIR. Nếu file này có cluster ID khác với `CLUSTER_ID` được truyền vào → Kafka **từ chối khởi động** để tránh phá hoại data.

**Cách Kafka sử dụng trong thực tế:**
```
Container khởi động
   ↓
Đọc LOG DIRs (/var/lib/kafka/data)
   ↓
Kiểm tra meta.properties → có cluster ID không?
   ├── Có: so sánh với CLUSTER_ID biến môi trường → khớp thì OK
   └── Không: ghi CLUSTER_ID vào meta.properties → cluster mới được tạo
```

**Giá trị mẫu & ý nghĩa:** `CLUSTER_ID: "my-kafka-cluster-1"`
- Chỉ cho phép: chữ cái, số, dấu gạch ngang, dấu gạch dưới (base64 URL-safe)
- Thường người ta sinh bằng: `kafka-storage.sh random-uuid`

**Khi nào nên thay đổi?**
- **Không bao giờ** thay đổi sau khi cluster đã chạy (sẽ khiến tất cả node không nhận ra cluster cũ → mất data)
- Không có "default" — **bắt buộc phải tự cấp** vì không tồn tại giá trị mặc định cho một chuỗi định danh duy nhất.
- Chỉ đặt khi khởi tạo cluster mới

**Nếu cấu hình sai:** `ERROR: Cluster ID 'abc' does not match stored ID 'xyz' in meta.properties`

→ Kafka **refuse to start**, bạn sẽ mất nhiều giờ để debug nếu không biết nguyên nhân.

**Ảnh hưởng**: Toàn bộ cluster.

**Liên kết với:**
- `KAFKA_LOG_DIRS` (nơi lưu cluster ID)
- `KAFKA_NODE_ID` (định danh từng node trong cùng cluster)

**Ví dụ thực tế:** Giả sử bạn có 2 môi trường staging và production cùng dùng 1 subnet Docker. Nếu cả 2 cluster có CLUSTER_ID giống nhau, các node có thể "nói chuyện nhầm" và phá hoại data của nhau.

**Ví dụ Docker Compose:**
```yaml
environment:
  CLUSTER_ID: "my-kafka-cluster-1"
volumes:
  - kafka_data:/var/lib/kafka/data   # ID này được "khắc" vào đây khi format lần đầu
```

### `KAFKA_NODE_ID` — "Số thẻ của từng node"

**Dùng để làm gì?** Một số nguyên **duy nhất** cho mỗi Kafka process trong cluster.

![](https://encrypted-tbn0.gstatic.com/images?q=tbn:ANd9GcT7X4iZbAKWDrowflqI5k-4eQCH7UEvhENt4AUg-Gxqsx_qZuIGnSafxPwH&s=10)

**Vấn đề Kafka giải quyết:** Trong cluster có nhiều node, Kafka cần phân biệt: "đây là node 1, kia là node 2". Nếu 2 node cùng `KAFKA_NODE_ID`, metadata sẽ bị conflict — Kafka không biết ai là ai.

**Tại sao Kafka cần?**

- Để Controller Quorum biết node nào đang bầu cử
- Để broker routing biết partition nào đang nằm ở node nào
- Để replication: "partition P-X có leader là node 2, replicas là node 1 và 3"

**Cách Kafka sử dụng:** Khi broker khởi động, nó broadcast: "Tôi là node 2, tôi sẵn sàng nhận partition". Controller cập nhật metadata → khi producer hỏi "partition P-0 ở đâu?", controller trả lời "ở node 2".

**Giá trị mẫu:**
```yaml
 KAFKA_NODE_ID: 1        # Node đầu tiên
KAFKA_NODE_ID: 2        # Node thứ 2
KAFKA_NODE_ID: 3        # Node thứ 3
```

- Phải là số nguyên ≥ 0
- Phải **unique** trong toàn cluster

**Khi nào nên thay đổi?** 
- Chỉ thay đổi khi **thêm node mới** vào cluster. Không đổi node đang chạy.
- Không có default — bắt buộc khai báo tường minh trong KRaft mode. Khi thêm broker/controller thứ 2, 3... phải đặt ID khác nhau (2, 3...).

**Ảnh hưởng**: Broker + Controller (vì cùng namespace ID).

**Nếu cấu hình sai:**
- 2 node cùng ID: Controller election bị split-brain, dữ liệu có thể corrupt
- ID âm hoặc quá lớn (>2^31): Kafka từ chối khởi động

**Liên kết với:**
- `KAFKA_CONTROLLER_QUORUM_VOTERS` (phải tham chiếu đúng node ID)

---
### `KAFKA_PROCESS_ROLES` — "Nghề nghiệp của node"

**Dùng để làm gì?** Xác định node này đóng vai trò gì trong KRaft mode:

- `broker`: lưu trữ data, phục vụ producer/consumer
- `controller`: quản lý metadata, leader election
- `broker,controller`: làm cả hai (thường dùng trong dev hoặc cluster nhỏ)

**Vấn đề Kafka giải quyết:** Trước KRaft, ZooKeeper làm controller, Kafka chỉ làm broker → 2 hệ thống tách biệt. KRaft gộp controller vào Kafka process. Nhưng không phải node nào cũng nên làm controller (tốn CPU, tốn memory cho Raft).

![](https://images.ctfassets.net/gt6dp23g0g38/7gQZn9CnRAT60NeyYBYflL/b144fee6dad28ce97c3e91e6d09d1167/20230616-Diagram-KRaft.jpg)

**Tại sao Kafka cần?**
- Controller cần CPU mạnh, network ổn định (Raft consensus)
- Broker cần disk IO mạnh, nhiều partition
- Tách riêng → scale độc lập

**Cách Kafka sử dụng:**
```
KAFKA_PROCESS_ROLES=broker        → node chỉ tham gia data plane (9092)
KAFKA_PROCESS_ROLES=controller    → node chỉ tham gia control plane (9093)
KAFKA_PROCESS_ROLES=broker,controller → làm cả hai
```

**Giá trị mẫu cho cluster 3-node production:**
```yaml
# Node 1, 2, 3: dedicated controllers
KAFKA_PROCESS_ROLES: controller

# Node 4, 5, 6, 7: dedicated brokers
KAFKA_PROCESS_ROLES: broker
```

**Khi nào nên thay đổi?**
- Dev/local: dùng `broker,controller` cho đơn giản 
- Production (>5 brokers): tách riêng dedicated controllers (3 node) và brokers
- Không có default. Ở production nên **tách riêng** `controller` và `broker` (dedicated mode) thay vì combined; combined mode chỉ phù hợp học tập/dev vì đơn giản hóa vận hành nhưng không cô lập được lỗi giữa 2 mặt phẳng.

**Nếu cấu hình sai:**
- Chỉ có `controller` mà không có `broker` nào → không có ai lưu data
- Có `broker` mà không có đủ `controller` quorum → cluster không thể elect leader → **paralyzed**

**Liên kết với:**
- `KAFKA_CONTROLLER_QUORUM_VOTERS` (phải liệt kê đúng các node có role controller)
- `KAFKA_LISTENERS` (controller cần listener riêng)

### `KAFKA_CONTROLLER_QUORUM_VOTERS` — "Danh sách cử tri"

![](https://cdn.confluent.io/wp-content/uploads/quorum.png)

**Dùng để làm gì?** Khai báo tất cả các node có quyền **bỏ phiếu bầu Leader Controller** trong KRaft.

**Vấn đề Kafka giải quyết:** KRaft dùng **Raft consensus algorithm (thuật toán đồng thuận)** - cần một danh sách tường minh "ai là ứng viên tham gia bầu cử controller" ngay từ lúc khởi động (bootstrap), vì tại thời điểm đó chưa có metadata log nào tồn tại để tự khám phá lẫn nhau — đây là bài toán con gà quả trứng kinh điển trong hệ phân tán, và ==quorum voters chính là cách giải: "hard-code" danh sách ứng viên ban đầu==. Để bầu leader, cần biết "những ai được bầu?". Đây chính là danh sách cử tri (voters).

**Tại sao Kafka cần?**
- Raft cần biết: "cluster có 3 voters, cần 2 đồng ý để elect leader"
- Khi có node chết, các voters còn lại vẫn bầu được leader mới
- Prevents split-brain (không có 2 leader cùng lúc)

**Cách Kafka sử dụng — Format đặc biệt:**
```yaml
KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka-1:9093,2@kafka-2:9093,3@kafka-3:9093
```

Ý nghĩa từng phần:
- `1`: **Node ID** (trùng với `KAFKA_NODE_ID` của node đó)
- `@`: dấu phân cách
- `kafka-1`: **hostname** (chính là tên service Docker Compose, tự resolve DNS nội bộ) (phải resolve được trong network)
- `:9093`: **port** dùng cho controller communication

**Ảnh hưởng**: Control Plane toàn cluster — nếu sai, **toàn bộ cluster không khởi động được**, kể cả broker cũng không lên được vì không tìm ra active controller để đăng ký.

**⚠️ Lưu ý quan trọng về hostname:**

- `kafka-1` phải là tên DNS resolve được từ TẤT CẢ các node
- Trong Docker Compose, dùng **tên service** (`kafka-1`, `kafka-2`) — Docker DNS tự resolve
- Trong production K8s/VM: dùng DNS nội bộ (`kafka-1.internal.company.com`)
- **KHÔNG** dùng IP tĩnh — khi restart container IP đổi → quorum chết

**Khi nào nên thay đổi?**

- Chỉ khi thêm/xóa controller node
- Khi thay đổi hostname/DNS

**Nếu cấu hình sai — các tình huống phổ biến:**
```
# Sai 1: hostname không resolve được
1@localhost:9093    # ❌ chỉ node đó thấy chính nó
Kafka will fail to form quorum → cluster stuck

# Sai 2: thiếu node trong quorum
KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093   # chỉ có 1 voter
→ mất fault tolerance (1 node chết = mất cluster)

# Sai 3: ID không khớp KAFKA_NODE_ID
Node có KAFKA_NODE_ID=2 nhưng trong voters ghi 1@kafka:9093
→ node này không được coi là voter → không tham gia bầu cử
```

**Liên kết với:**

- `KAFKA_NODE_ID` (phải khớp)
- `KAFKA_CONTROLLER_LISTENER_NAMES` (port phải là port controller đang nghe)
- `KAFKA_PROCESS_ROLES` (chỉ các node có role=controller mới cần nằm trong voters)

**💡 Best practice:** Luôn dùng **số lẻ** voters (1, 3, 5, 7) để tránh split-brain. 3 voters chịu được 1 node chết; 5 voters chịu được 2 nodes chết.

**Góc nhìn kiến trúc:** Đây là bước đầu tiên trong toàn bộ chuỗi khởi động Kafka — trước khi bất kỳ Producer/Consumer nào có thể kết nối, quorum phải bầu xong active controller, active controller phải sẵn sàng nhận đăng ký broker, rồi broker mới publish metadata (danh sách topic/partition) ra ngoài qua listener client.
