Dưới đây là các config mà **ai triển khai Kafka production cũng cần biết**

### `KAFKA_LOG_DIRS` — "Nơi lưu data"

```yaml
KAFKA_LOG_DIRS: /var/lib/kafka/data
```

- Đường dẫn đến thư mục lưu partition data
- **Nên mount volume** (bạn đang làm đúng với `kafka_data`)
- Có thể comma-separated cho nhiều disk → Kafka tự balance
- Nếu không mount volume: data mất khi container restart
- **Pro tip**: Dùng XFS filesystem (không dùng ext4) cho performance tốt hơn

### `KAFKA_NUM_PARTITIONS` — "Partition mặc định"

Số partition mặc định khi 1 topic được **tự động tạo** (qua `AllowAutoTopicCreation: true` trong producer Go) mà không chỉ định rõ. File của bạn chưa set biến này → topic `don-hang` bạn đang test **chỉ có 1 partition**, đây chính là lý do trong bản đánh giá trước, phần "Partitioning" bị xếp loại _"có lý thuyết nhưng thiếu thực hành"_ — về mặt hạ tầng,
.
```yaml
KAFKA_DEFAULT_REPLICATION_FACTOR: 3   # production
```

- Số partition mặc định khi topic được tạo tự động
- Ảnh hưởng đến parallelism tối đa của consumer group
- **Nên set ≥ số consumer trong group lớn nhất dự kiến**

### `KAFKA_DEFAULT_REPLICATION_FACTOR`

```yaml
KAFKA_DEFAULT_REPLICATION_FACTOR: 3   # production
```

- Replication factor mặc định cho topic auto-created
- Nên ≥ 3 trong production
- **Khác hoàn toàn** với `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR` ở Nhóm 4 — đây là replication factor cho **topic nghiệp vụ của bạn** (`orders`, `don-hang`...), không phải topic nội bộ Kafka. Với 1 broker, chỉ có thể set `1`.

### `KAFKA_AUTO_CREATE_TOPICS_ENABLE`

```yaml
KAFKA_AUTO_CREATE_TOPICS_ENABLE: false   # production
KAFKA_AUTO_CREATE_TOPICS_ENABLE: true    # dev
```

- **Cực kỳ quan trọng trong production**
- Bật = bất kỳ producer nào cũng có thể tạo topic mới → **rắc rối về governance**
- Production: `false` + tạo topic thủ công với `kafka-topics.sh`
- Cho phép topic tự sinh khi Producer/Consumer gọi tới tên topic chưa tồn tại — tiện cho học tập, nhưng **production luôn tắt** (`false`) vì dễ tạo topic rác do lỗi chính tả tên topic từ code, mất kiểm soát về partition/replication chuẩn hóa.

**Tại sao nên tắt trong production?**
- Topic typo (`oder-events` thay vì `order-events`) → tạo rác
- Không control được partition count, replication factor
- Security risk: bất kỳ app nào có quyền producer đều tạo topic

### `KAFKA_LOG_RETENTION_HOURS` / `KAFKA_LOG_RETENTION_BYTES`

```
KAFKA_LOG_RETENTION_HOURS: 168       # 7 ngày
KAFKA_LOG_RETENTION_BYTES: -1        # -1 = không giới hạn
KAFKA_LOG_RETENTION_CHECK_INTERVAL_MS: 300000   # kiểm tra mỗi 5 phút
```
- Bao lâu thì Kafka xóa data cũ
- **Rất quan trọng về disk space planning**
- Log aggregation topic: giữ lâu (vài tháng)
- Event stream: có thể 7 ngày
- Audit log: `retention.ms=-1` (vĩnh viễn)

### `KAFKA_MESSAGE_MAX_BYTES` và `KAFKA_REPLICA_FETCH_MAX_BYTES`

```yaml
KAFKA_MESSAGE_MAX_BYTES: 1048576        # 1MB - max size 1 message
KAFKA_REPLICA_FETCH_MAX_BYTES: 1048576  # phải ≥ MESSAGE_MAX_BYTES
```
- Nếu producer gửi message 2MB mà broker chỉ accept 1MB → `RecordTooLargeException`
- Nếu replica fetch nhỏ hơn message → replica không replicate được → ISR shrink

**Quy tắc:** `KAFKA_REPLICA_FETCH_MAX_BYTES ≥ KAFKA_MESSAGE_MAX_BYTES`

### `KAFKA_NUM_NETWORK_THREADS` & `KAFKA_NUM_IO_THREADS`

```yaml
KAFKA_NUM_NETWORK_THREADS: 3    # thread xử lý network request
KAFKA_NUM_IO_THREADS: 8         # thread xử lý disk I/O
```

- Network threads: accept connection, parse request → push vào queue
- IO threads: lấy request từ queue, xử lý (đọc/ghi disk)
- **Tuning quan trọng** cho high-throughput cluster
- Quy tắc: `IO threads ≥ Network threads`, thường `IO threads = 2x CPU cores`

### `KAFKA_MIN_INSYNC_REPLICAS` (cho user topics)

```yaml
# Set ở topic level, nhưng có thể default:
KAFKA_MIN_INSYNC_REPLICAS: 2
```
- Quan trọng khi producer dùng `acks=all`
- Phải set `min.insync.replicas` + `replication.factor=3` để chịu được 1 node chết

## DỮ LIỆU ĐI QUA CÁC CONFIG NHƯ THẾ NÀO?

Hãy theo dõi hành trình của 1 message từ producer → lưu vào disk:

```
┌─────────────────────────────────────────────────────────────────┐
│  PRODUCER (client máy host)                                     │
│  - Kết nối đến localhost:9092 (do ADVERTISED_LISTENERS)         │
│  - Dùng PLAINTEXT protocol (do SECURITY_PROTOCOL_MAP)           │
└──────────────────────┬──────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────────────────┐
│  BROKER 1 (container kafka, KAFKA_NODE_ID=1)                    │
│  - Listener PLAINTEXT://:9092 (do KAFKA_LISTENERS)              │
│  - Nhận message                                                  │
│  - Xác định partition (hash key)                                │
└──────────────────────┬──────────────────────────────────────────┘
                       │
          ┌────────────┴────────────┐
          ▼                          ▼
┌─────────────────────┐    ┌────────────────────────┐
│  Ghi xuống đĩa      │    │ Replicate sang Broker 2│
│  KAFKA_LOG_DIRS:    │    │ Qua port 19092         │
│  /var/lib/kafka/data│    │ (INTER_BROKER_LISTENER)│
│  - Sequential write │    └────────────┬───────────┘
│  - Zero-copy read   │                 │
└─────────────────────┘                 ▼
                                ┌──────────────────┐
                                │  Broker 2 (ISR)  │
                                │  Ack khi đã ghi  │
                                └──────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────────────────┐
│  CONSUMER GROUP commit offset                                   │
│  → ghi vào topic __consumer_offsets                              │
│  → topic này có REPLICATION_FACTOR=3                            │
│  → MIN_ISR=2 bảo đảm durability                                 │
└─────────────────────────────────────────────────────────────────┘
```

**Các config được trigger theo thứ tự:**

1. `KAFKA_ADVERTISED_LISTENERS` → producer biết connect ở đâu
2. `KAFKA_LISTENERS` → broker accept connection
3. `KAFKA_LISTENER_SECURITY_PROTOCOL_MAP` → broker biết protocol
4. `KAFKA_NODE_ID` + `CLUSTER_ID` → xác thực node thuộc cluster
5. `KAFKA_LOG_DIRS` → data được ghi xuống
6. `KAFKA_INTER_BROKER_LISTENER_NAME` → replication traffic
7. `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR` → offset durability
8. `KAFKA_CONTROLLER_QUORUM_VOTERS` → controller metadata update (nếu có topic change)

## 🚨 CÁC SAI LẦM PHỔ BIẾN KHI CẤU HÌNH

### Sai lầm 1: "Container chạy OK nhưng client không connect được"

**Nguyên nhân:** `KAFKA_ADVERTISED_LISTENERS` không match với cách client kết nối.

**Fix:**
- Client trên host → `PLAINTEXT://localhost:9092`
- Client trong Docker → `PLAINTEXT://kafka:9092`
- Client ngoài Internet → `SSL://kafka.company.com:9093`

### Sai lầm 2: "Producer timeout khi gửi message"

**Nguyên nhân:** `KAFKA_LISTENERS` có host cụ thể (như `kafka:9092`) nhưng `ADVERTISED` không có → broker metadata trả về không đúng.

**Fix:** Đảm bảo `ADVERTISED_LISTENERS` bao gồm TẤT CẢ listener name có trong `LISTENERS` mà client cần biết.

### Sai lầm 3: "Cluster không start được sau khi restart"

**Nguyên nhân:** `CLUSTER_ID` thay đổi, hoặc LOG_DIRS volume không mount → `meta.properties` mất.

**Fix:**
- Luôn mount volume cho `KAFKA_LOG_DIRS`
- Không thay đổi `CLUSTER_ID` sau khi chạy

### Sai lầm 4: "Replica không sync, ISR shrink"

**Nguyên nhân:** `REPLICATION_FACTOR` > số broker available, hoặc `MIN_ISR` quá cao.

**Fix:**
- `REPLICATION_FACTOR ≤ số broker`
- `MIN_ISR = REPLICATION_FACTOR - 1`

### Sai lầm 5: "Consumer lag tăng đột biến"

**Nguyên nhân:** Network thread quá ít, hoặc `MAX_POLL_RECORDS` quá thấp.

**Fix:**
- Tăng `KAFKA_NUM_NETWORK_THREADS` (theo CPU cores)
- Tăng `KAFKA_NUM_IO_THREADS`

```yaml
KAFKA_NODE_ID: 1

KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT

KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
```

```yaml
# Mỗi broker có file riêng, ví dụ broker-1:
```
