# Chương 4: Tạo Index, Thao Tác CRUD và Mapping

---

## 4.1 Giới Thiệu

Khi làm việc với Elasticsearch, hai thao tác quan trọng nhất là:

- **Index (Lập chỉ mục):** Quá trình nhận dữ liệu (document) và lưu trữ vào index để có thể tìm kiếm sau này
- **Search (Tìm kiếm):** Truy xuất dữ liệu từ index dựa trên các truy vấn (query)

Trước khi đưa dữ liệu vào, ta cần hiểu cách Elasticsearch **tổ chức và định nghĩa cấu trúc dữ liệu** thông qua **Mapping** — tương tự như việc định nghĩa schema trong cơ sở dữ liệu quan hệ.

## 4.3 Mapping – Định Nghĩa Cấu Trúc Dữ Liệu

### 4.3.1 Mapping là gì?

**Mapping** là quá trình định nghĩa cấu trúc của một index: mỗi field có tên gì, kiểu dữ liệu gì, và được lập chỉ mục như thế nào.

Có **2 loại mapping:**

|Loại|Mô tả|Khi nào dùng|
|---|---|---|
|**Dynamic Mapping**|Elasticsearch tự động phát hiện và gán kiểu dữ liệu khi document đầu tiên được thêm vào|Phát triển nhanh, dữ liệu đơn giản|
|**Explicit Mapping**|Người dùng tự định nghĩa kiểu dữ liệu trước khi thêm dữ liệu|Yêu cầu chính xác, dữ liệu phức tạp|

> **Khuyến nghị:** Trong môi trường production (thực tế), nên dùng **Explicit Mapping** để kiểm soát chính xác kiểu dữ liệu và tránh các lỗi không mong muốn.

---

### 4.3.2 Các Kiểu Dữ Liệu Cơ Bản Trong Elasticsearch

Elasticsearch hỗ trợ nhiều kiểu dữ liệu. Dưới đây là các kiểu thường dùng nhất:

**Nhóm văn bản (Text types):**

| Kiểu      | Mô tả                                                                                     | Ví dụ dùng                        |
| --------- | ----------------------------------------------------------------------------------------- | --------------------------------- |
| `text`    | Văn bản được phân tích (analyzed) để tìm kiếm full-text. Không thể dùng để sort/aggregate | Nội dung bài viết, mô tả sản phẩm |
| `keyword` | Chuỗi không được phân tích, dùng để lọc chính xác, sort, aggregate                        | Email, mã sản phẩm, trạng thái    |

**Nhóm số (Numeric types):**

|Kiểu|Mô tả|Phạm vi|
|---|---|---|
|`byte`|Số nguyên 8-bit|-128 đến 127|
|`short`|Số nguyên 16-bit|-32,768 đến 32,767|
|`integer`|Số nguyên 32-bit|-2^31 đến 2^31-1|
|`long`|Số nguyên 64-bit|-2^63 đến 2^63-1|
|`float`|Số thực 32-bit|Số thập phân độ chính xác đơn|
|`double`|Số thực 64-bit|Số thập phân độ chính xác kép|

**Nhóm ngày giờ & logic:**

|Kiểu|Mô tả|Ví dụ|
|---|---|---|
|`date`|Ngày/giờ, hỗ trợ nhiều định dạng|`"2026-04-03"`, `"2026-04-03T10:00:00Z"`|
|`boolean`|Giá trị đúng/sai|`true`, `false`|

**Nhóm đặc biệt:**

|Kiểu|Mô tả|Ví dụ dùng|
|---|---|---|
|`object`|JSON object lồng nhau|Địa chỉ có `street`, `city`, `zip`|
|`nested`|Mảng các object, mỗi object được lập chỉ mục độc lập|Danh sách đơn hàng trong một người dùng|
|`ip`|Địa chỉ IPv4 hoặc IPv6|`"192.168.1.1"`|
|`geo_point`|Tọa độ địa lý (latitude, longitude)|Vị trí cửa hàng trên bản đồ|
|`binary`|Dữ liệu nhị phân dạng Base64|File đính kèm|

> **Lưu ý về `text` vs `keyword`:** Khi Elasticsearch tự động tạo mapping (Dynamic Mapping), các trường chuỗi thường được tạo với **cả hai kiểu** — `text` để tìm kiếm full-text và `keyword` để lọc chính xác. Đây được gọi là **multi-field mapping**.

---

### 4.3.3 Tạo Index Với Explicit Mapping (Khuyến Nghị)

Cách tốt nhất là tạo index và định nghĩa mapping **trước** khi thêm dữ liệu:

```
PUT facephone
{
  "mappings": {
    "properties": {
      "uuid":     { "type": "keyword" },
      "username": { "type": "text" },
      "email":    { "type": "keyword" },
      "age":      { "type": "integer" }
    }
  }
}
```

**Giải thích:**

- `uuid` dùng `keyword` vì ta chỉ cần so sánh chính xác, không cần tìm kiếm full-text
- `username` dùng `text` vì ta có thể cần tìm kiếm theo tên
- `email` dùng `keyword` vì email luôn được so sánh chính xác
- `age` dùng `integer` vì tuổi là số nguyên

**Output:**

```json
{
  "acknowledged": true,
  "shards_acknowledged": true,
  "index": "facephone"
}
```

---

### 4.3.4 Xem Mapping Của Index

```
GET facephone/_mapping
```

**Output (sau khi thêm dữ liệu với Dynamic Mapping):**

```json
{
  "facephone": {
    "mappings": {
      "properties": {
        "age": {
          "type": "long"
        },
        "email": {
          "type": "text",
          "fields": {
            "keyword": {
              "type": "keyword",
              "ignore_above": 256
            }
          }
        },
        "number": {
          "type": "integer"
        },
        "username": {
          "type": "text",
          "fields": {
            "keyword": {
              "type": "keyword",
              "ignore_above": 256
            }
          }
        },
        "uuid": {
          "type": "text",
          "fields": {
            "keyword": {
              "type": "keyword",
              "ignore_above": 256
            }
          }
        }
      }
    }
  }
}
```

**Giải thích `ignore_above: 256`:** Các chuỗi dài hơn 256 ký tự sẽ không được lập chỉ mục trong trường `keyword`. Điều này giúp tránh lỗi khi lưu văn bản quá dài vào trường keyword.

---

### 4.3.5 Thêm Field Mới Vào Mapping

Ta có thể thêm field mới vào mapping của index đã có:

```
PUT facephone/_mapping
{
  "properties": {
    "number": {
      "type": "integer"
    }
  }
}
```

**Output:**

```json
{
  "acknowledged": true
}
```

> **Lưu ý quan trọng:** Elasticsearch **không cho phép thay đổi kiểu dữ liệu** của field đã tồn tại (ví dụ: không thể đổi `text` sang `integer`). Nếu muốn thay đổi, bạn phải xóa index và tạo lại, hoặc dùng **Reindex API**.

---

### 4.3.6 Tắt Dynamic Mapping

Nếu muốn Elasticsearch **từ chối** các field không có trong mapping (không tự động tạo mapping mới), ta dùng cài đặt cluster:

```
PUT facephone/_mapping
{
  "dynamic": "strict"
}
```

Các giá trị của `dynamic`:

|Giá trị|Hành vi|
|---|---|
|`true` (mặc định)|Tự động thêm field mới vào mapping|
|`false`|Chấp nhận document nhưng không lập chỉ mục field mới|
|`"strict"`|Từ chối document nếu có field không khai báo trong mapping|

## 4.4 Các Thao Tác CRUD

### 4.4.1 Tạo Document (Create)

Elasticsearch cung cấp **3 cách** để tạo document. Hiểu rõ sự khác biệt giúp tránh lỗi không mong muốn.

---

#### Cách 1: `PUT _doc/<id>` — Tạo hoặc Ghi Đè

```
PUT facephone/_doc/1001
{
  "uuid": "68c76bb5-ff3d-467d-a826-3bbe58335678",
  "username": "m10",
  "email": "m10@gmail.com"
}
```

**Đặc điểm:**

- Nếu ID `1001` **chưa tồn tại** → tạo mới document
- Nếu ID `1001` **đã tồn tại** → **ghi đè toàn bộ** document (không phải cập nhật từng field)

**Output (tạo mới):**

```json
{
  "_index": "facephone",
  "_id": "1001",
  "_version": 1,
  "result": "created",
  "_shards": {
    "total": 2,
    "successful": 1,
    "failed": 0
  },
  "_seq_no": 0,
  "_primary_term": 1
}
```

Nếu chạy lại với cùng ID `1001` nhưng thay đổi dữ liệu:

```
PUT facephone/_doc/1001
{
  "uuid": "68c76bb5-ff3d-467d-a826-3bbe58335678",
  "username": "cr7",
  "email": "cr7@gmail.com"
}
```

**Output (ghi đè):**

```json
{
  "_index": "facephone",
  "_id": "1001",
  "_version": 2,
  "result": "updated",
  ...
}
```

> **Lưu ý:** `_version` tăng từ `1` lên `2` và `result` là `"updated"` chứ không phải `"created"`. Toàn bộ nội dung document đã bị **thay thế hoàn toàn**.

---

#### Cách 2: `PUT _create/<id>` — Chỉ Tạo Mới (Không Ghi Đè)

```
PUT facephone/_create/1002
{
  "uuid": "f9bb2327-5e8c-448a-b5b7-8d8f567de5af",
  "username": "m10",
  "age": 38
}
```

**Đặc điểm:**

- Nếu ID **chưa tồn tại** → tạo mới thành công
- Nếu ID **đã tồn tại** → **báo lỗi**, không ghi đè

**Output (tạo thành công):**

```json
{
  "_index": "facephone",
  "_id": "1002",
  "_version": 1,
  "result": "created",
  ...
}
```

**Output (lỗi khi ID đã tồn tại):**

```
PUT facephone/_create/1001
{
  "uuid": "f9bb2327-5e8c-448a-b5b7-8d8f567de5af",
  "username": "m10",
  "age": 38
}
```

```json
{
  "error": {
    "root_cause": [
      {
        "type": "version_conflict_engine_exception",
        "reason": "[1001]: version conflict, document already exists (current version [3])",
        "index_uuid": "Gy7x-IzXRA62-xU-foQGtA",
        "shard": "0",
        "index": "facephone"
      }
    ],
    "type": "version_conflict_engine_exception",
    "reason": "[1001]: version conflict, document already exists (current version [3])"
  },
  "status": 409
}
```

**Giải thích lỗi:**

- `version_conflict_engine_exception` — xung đột phiên bản, document đã tồn tại
- `status: 409` — HTTP 409 Conflict, nghĩa là tài nguyên đã tồn tại
- `current version [3]` — document hiện tại đang ở phiên bản 3

---
#### Cách 3: `PUT _doc/<id>?op_type=create` — Tương Đương Cách 2

```
PUT facephone/_doc/1003?op_type=create
{
  "uuid": "33dd5734-d350-4e7c-bd38-9547061b841c",
  "username": "Nguyen Van A",
  "age": 40
}
```

Cách này có hành vi **giống hệt `_create`** — chỉ tạo mới, báo lỗi nếu ID đã tồn tại. Đây là cú pháp thay thế cho tiện dùng trong một số trường hợp lập trình.

**Output:**

```json
{
  "_index": "facephone",
  "_id": "1003",
  "_version": 1,
  "result": "created",
  ...
}
```

---
#### Cách 4: `POST _doc` — Tạo Với ID Tự Động

Khi không cần chỉ định ID cụ thể, dùng `POST` để Elasticsearch tự sinh ID:

```
POST facephone/_doc
{
  "uuid": "33dd5734-d350-4e7c-bd38-9547061b841c",
  "username": "Nguyen Van C",
  "age": 42
}
```

**Output:**

```json
{
  "_index": "facephone",
  "_id": "5qNEV50B-Y3bcxk-PqNR",
  "_version": 1,
  "result": "created",
  ...
}
```

> ID được sinh tự động (`5qNEV50B-Y3bcxk-PqNR`) là một chuỗi ngẫu nhiên duy nhất, định dạng Base64URL.

---

#### Tổng Kết 4 Cách Tạo Document

|Cách|Cú pháp|Hành vi khi ID đã tồn tại|
|---|---|---|
|1|`PUT _doc/<id>`|Ghi đè toàn bộ document|
|2|`PUT _create/<id>`|Báo lỗi 409|
|3|`PUT _doc/<id>?op_type=create`|Báo lỗi 409 (giống cách 2)|
|4|`POST _doc` (không có ID)|Luôn tạo mới với ID tự sinh|

### 4.4.2 Đọc Document (Read)

#### Đọc Một Document Theo ID

```
GET facephone/_doc/1003
```

**Output:**

```json
{
  "_index": "facephone",
  "_id": "1003",
  "_version": 1,
  "_seq_no": 4,
  "_primary_term": 1,
  "found": true,
  "_source": {
    "uuid": "33dd5734-d350-4e7c-bd38-9547061b841c",
    "username": "Nguyen Van A",
    "age": 40
  }
}
```

**Giải thích:**

- `found: true` — tìm thấy document
- `_source` — nội dung gốc của document

---

#### Đọc Chỉ Một Số Field Cụ Thể

Khi document có nhiều field nhưng chỉ cần một số trường, dùng tham số `_source`:

```
GET facephone/_doc/1003?_source=uuid,username
```

**Output:**

```json
{
  "_index": "facephone",
  "_id": "1003",
  "_version": 1,
  "_seq_no": 4,
  "_primary_term": 1,
  "found": true,
  "_source": {
    "uuid": "33dd5734-d350-4e7c-bd38-9547061b841c",
    "username": "Nguyen Van A"
  }
}
```

> **Ứng dụng thực tế:** Khi document có nhiều field nặng (ví dụ: trường `description` dài), việc chỉ lấy các field cần thiết giúp giảm băng thông và tăng tốc độ.

---

#### Đọc Nhiều Document Cùng Lúc (Multi-Get)

Thay vì gọi nhiều request riêng lẻ, dùng `_mget` để lấy nhiều document trong một lần:

```
GET _mget
{
  "docs": [
    { "_index": "facephone", "_id": 1001 },
    { "_index": "facephone", "_id": 1002 },
    { "_index": "facephone", "_id": 1003 }
  ]
}
```

**Output:**

```json
{
  "docs": [
    {
      "_index": "facephone",
      "_id": "1001",
      "_version": 3,
      "found": true,
      "_source": {
        "uuid": "68c76bb5-ff3d-467d-a826-3bbe58335678",
        "username": "cr7",
        "email": "cr7@gmail.com",
        "age": 40
      }
    },
    {
      "_index": "facephone",
      "_id": "1002",
      "found": true,
      "_source": {
        "uuid": "f9bb2327-5e8c-448a-b5b7-8d8f567de5af",
        "username": "m10",
        "age": 38
      }
    },
    {
      "_index": "facephone",
      "_id": "1003",
      "found": true,
      "_source": {
        "uuid": "33dd5734-d350-4e7c-bd38-9547061b841c",
        "username": "Nguyen Van A",
        "age": 40
      }
    }
  ]
}
```

> **Lưu ý:** Nếu một ID không tồn tại, Elasticsearch vẫn trả về kết quả cho các ID khác, chỉ riêng ID đó có `"found": false` thay vì báo lỗi toàn bộ request.

---

#### Kiểm Tra Document Có Tồn Tại Không (HEAD)

Dùng `HEAD` để kiểm tra sự tồn tại mà không cần tải nội dung document (nhẹ hơn `GET`):

```
HEAD facephone/_doc/1001
```

- Nếu tồn tại → `200 - OK`
- Nếu không tồn tại → `404 - Not Found`

> **Ứng dụng:** Dùng `HEAD` khi chỉ cần kiểm tra tồn tại (ví dụ: trước khi insert để tránh trùng lặp), không cần lấy toàn bộ dữ liệu về.

---

### 4.4.3 Cập Nhật Document (Update)

Có **2 cách** cập nhật document:

---

#### Cách 1: Cập Nhật Một Phần — `POST _update/<id>` (Khuyến Nghị)

Chỉ cập nhật **các field được chỉ định**, giữ nguyên các field còn lại:

```
POST facephone/_update/1001
{
  "doc": {
    "username": "ronaldo",
    "age": 39
  }
}
```

**Output:**

```json
{
  "_index": "facephone",
  "_id": "1001",
  "_version": 3,
  "result": "updated",
  "_shards": {
    "total": 2,
    "successful": 1,
    "failed": 0
  }
}
```

> **Ưu điểm:** Chỉ gửi đúng các field cần thay đổi, an toàn hơn `PUT _doc` vì không làm mất các field khác.

---

#### Cách 2: Ghi Đè Toàn Bộ — `PUT _doc/<id>`

Như đã đề cập ở phần Create, `PUT _doc/<id>` với ID đã tồn tại sẽ **thay thế hoàn toàn** document. Cách này **không được khuyến nghị** để cập nhật vì dễ mất dữ liệu.

---

### 4.4.4 Xóa Document (Delete)

#### Xóa Theo ID

```
DELETE facephone/_doc/1001
```

**Output:**

```json
{
  "_index": "facephone",
  "_id": "1001",
  "_version": 4,
  "result": "deleted",
  "_shards": {
    "total": 2,
    "successful": 1,
    "failed": 0
  },
  "_seq_no": 7,
  "_primary_term": 1
}
```

**Giải thích:**

- `result: "deleted"` — xóa thành công
- `_version` tăng lên 4 — mỗi thao tác (kể cả xóa) đều tăng version

---

#### Xóa Theo Điều Kiện Query — `_delete_by_query`

Xóa tất cả document thỏa mãn một điều kiện nhất định:

```
POST facephone/_delete_by_query
{
  "query": {
    "match": { "age": "38" }
  }
}
```

**Output:**

```json
{
  "took": 66,
  "timed_out": false,
  "total": 1,
  "deleted": 1,
  "batches": 1,
  "version_conflicts": 0,
  "noops": 0,
  "retries": {
    "bulk": 0,
    "search": 0
  },
  "throttled_millis": 0,
  "requests_per_second": -1,
  "throttled_until_millis": 0,
  "failures": []
}
```

**Giải thích output:**

|Trường|Ý nghĩa|
|---|---|
|`total`|Số document tìm thấy thỏa điều kiện|
|`deleted`|Số document đã xóa thành công|
|`version_conflicts`|Số document bị xung đột version (không xóa được)|
|`failures`|Danh sách lỗi (nếu có)|

> **Cẩn thận:** `_delete_by_query` có thể xóa **nhiều document cùng lúc** nếu điều kiện query khớp nhiều bản ghi. Nên test query bằng `GET _search` trước khi xóa.

### 4.4.5 Thêm Nhiều Documents Cùng Lúc — Bulk API

Dùng `_bulk` để insert nhiều documents trong một request, tăng hiệu suất đáng kể so với gửi từng request riêng lẻ:

```
POST facephone/_bulk
{"create":{}}
{"uuid":"001", "username":"a01", "email":"a01@gmail.com", "age": 24}
{"create":{}}
{"uuid":"002", "username":"a02", "email":"a02@gmail.com", "age": 25}
{"create":{}}
{"uuid":"003", "username":"a03", "email":"a03@gmail.com", "age": 26}
{"create":{}}
{"uuid":"004", "username":"a04", "email":"a04@gmail.com", "age": 27}
```

**Output (rút gọn):**

```json
{
  "errors": false,
  "took": 17,
  "items": [
    {
      "create": {
        "_index": "facephone",
        "_id": "56NxV50B-Y3bcxk-1qOT",
        "_version": 1,
        "result": "created",
        "status": 201
      }
    },
    {
      "create": {
        "_index": "facephone",
        "_id": "6KNxV50B-Y3bcxk-1qOT",
        "_version": 1,
        "result": "created",
        "status": 201

  ]

```

> **Quy tắc bắt buộc của Bulk API:**
> 
> - Mỗi document gồm **đúng 2 dòng**: dòng action và dòng data
> - **Không được có dòng trống** giữa các cặp — Elasticsearch sẽ báo lỗi parse

## 4.5 Kiểm Tra Sự Tồn Tại

### Kiểm Tra Index Có Tồn Tại Không

```

- Không tồn tại → `404 - Not Found`

```

- Tồn tại → `200 - OK`

## 4.6 Tổng Kết Các Câu Lệnh Chương 4

|Thao tác|Câu lệnh|Ghi chú|
|---|---|---|
|Kiểm tra cluster|`GET /`|Xem thông tin Elasticsearch|
|Tạo index với mapping|`PUT <index>` + body mapping|Explicit mapping|
|Xem mapping|`GET <index>/_mapping`||
|Thêm field vào mapping|`PUT <index>/_mapping` + body|Không thể đổi kiểu dữ liệu cũ|
|Tạo/ghi đè document|`PUT <index>/_doc/<id>`|Ghi đè nếu ID đã tồn tại|
|Tạo mới (không ghi đè)|`PUT <index>/_create/<id>`|Lỗi 409 nếu ID đã tồn tại|
|Tạo mới (không ghi đè)|`PUT <index>/_doc/<id>?op_type=create`|Tương đương `_create`|
|Tạo với ID tự sinh|`POST <index>/_doc`|ID được sinh tự động|
|Đọc document theo ID|`GET <index>/_doc/<id>`||
|Đọc một số field|`GET <index>/_doc/<id>?_source=field1,field2`||
|Đọc nhiều document|`GET _mget` + body||
|Cập nhật một phần|`POST <index>/_update/<id>` + `"doc":{...}`|Giữ nguyên field không nhắc đến|
|Xóa theo ID|`DELETE <index>/_doc/<id>`||
|Xóa theo điều kiện|`POST <index>/_delete_by_query` + query|Cẩn thận, xóa nhiều cùng lúc|
|Thêm nhiều documents|`POST <index>/_bulk`|Hiệu suất cao|
|Đếm documents|`GET <index>/_count`||
|Kiểm tra tồn tại index|`HEAD <index>`|Nhẹ hơn GET|
|Kiểm tra tồn tại document|`HEAD <index>/_doc/<id>`|Nhẹ hơn GET|

## 4.7 Một Số Lỗi Thường Gặp

|Lỗi|Nguyên nhân|Cách xử lý|
|---|---|---|
|`version_conflict_engine_exception` (409)|Dùng `_create` hoặc `op_type=create` nhưng ID đã tồn tại|Kiểm tra ID trước bằng `HEAD`, hoặc dùng `PUT _doc` nếu muốn ghi đè|
|`mapper_parsing_exception`|Dữ liệu không đúng kiểu mapping đã định nghĩa|Kiểm tra lại kiểu dữ liệu của field trong mapping|
|`strict_dynamic_mapping_exception`|Thêm field mới khi dynamic mapping đang là `strict`|Thêm field vào mapping trước bằng `PUT _mapping`|
|`index_not_found_exception`|Index chưa tồn tại|Tạo index trước hoặc kiểm tra tên index|
|Bulk API parse error|Có dòng trống hoặc sai định dạng trong body `_bulk`|Đảm bảo mỗi cặp action-data liền nhau, không có dòng trống|
