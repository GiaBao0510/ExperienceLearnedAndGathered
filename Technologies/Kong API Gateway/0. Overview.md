## Kong Gateway Là Gì?

**Kong Gateway** là một **API Gateway** mã nguồn mở, được xây dựng cho các hệ thống cloud-native (thiết kế để chạy tốt trên container, Kubernetes, hạ tầng có khả năng scale linh hoạt). Về bản chất, Kong hoạt động như một **Reverse Proxy**: tiếp nhận request từ client, rồi định tuyến (route) tới đúng API hoặc service phía sau. Kong có thể xử lý nhiều loại traffic tùy cấu hình: HTTP/HTTPS, TCP/TLS, và gRPC/gRPCS.

Điểm đáng chú ý của Kong nằm ở khả năng **quản lý traffic và áp dụng chính sách tập trung**. Thay vì để từng API tự xử lý Authentication (xác thực), Rate Limiting (giới hạn tần suất request) hay các quy tắc liên quan tới request, những tác vụ này có thể được thực hiện ngay tại Gateway, thông qua cơ chế **Plugin**.

Kong **không thay thế** các API hoặc microservice phía sau — các service vẫn đảm nhiệm logic nghiệp vụ riêng của mình. Kong chỉ đứng ở lớp truy cập (access layer), tiếp nhận và kiểm soát traffic trước khi request đi tới backend. Trong một hệ thống có nhiều microservice, cách tiếp cận này giúp giảm sự phụ thuộc trực tiếp giữa client và từng service: client chỉ cần gọi tới các endpoint do Gateway cung cấp, còn việc request nên đi tới service nào được quyết định bởi cấu hình của Kong.

Cũng giống như các API Gateway khác, Kong được thiết kế nhẹ, độ trễ thấp, hiệu suất cao, và có khả năng mở rộng (scalability) tốt — phù hợp cho các hệ thống microservices.

## Cách Thức Hoạt Động

Kong Gateway đứng giữa client và các API/microservice phía sau. Khi client gửi request, Kong tiếp nhận, kiểm tra, rồi quyết định request cần được chuyển tới đâu. Quá trình này thường gồm 6 bước:

**Bước 1 — Client gửi request tới Kong Gateway**

Client không gọi trực tiếp tới từng API hay microservice. Mọi request đều được gửi tới địa chỉ của Kong Gateway.

**Bước 2 — Kong kiểm tra thông tin request**

Kong phân tích các thông tin trong request: Host, Path, HTTP Method, Header, Protocol. Dựa trên các thông tin này, thành phần **Router** của Kong tìm ra **Route** phù hợp — Route giúp Kong xác định request đang muốn truy cập API nào, và cần chuyển tới **Service** nào.

**Bước 3 — Kong xác định backend cần gọi**

**Service** trong Kong đại diện cho API hoặc ứng dụng nằm phía sau Gateway. Nếu Service chỉ có một backend, Kong chuyển request trực tiếp tới địa chỉ đó. Nếu Service có nhiều instance, Kong dùng **Upstream** và **Target** để phân phối request giữa các instance — đây chính là cơ chế load balancing của Kong, giúp giảm tải cho từng máy chủ và giữ hệ thống ổn định hơn.

**Bước 4 — Kong áp dụng các chính sách đã cấu hình**

Trước khi chuyển request tới backend, Kong có thể chạy một số kiểm tra thông qua **Plugin**, ví dụ:

- Kiểm tra thông tin đăng nhập hoặc token bằng plugin Authentication.
- Giới hạn số lượng request bằng plugin Rate Limiting.
- Ghi lại thông tin request để phục vụ theo dõi và phân tích (logging).
- Điều chỉnh một số dữ liệu trong request nếu cần (transformation).

Nếu request không đáp ứng điều kiện, Kong có thể từ chối ngay tại Gateway mà không chuyển tiếp tới backend.

**Bước 5 — Kong chuyển request tới backend**

Khi request vượt qua các bước kiểm tra, Kong chuyển nó tới Service hoặc instance phù hợp. Backend tiếp nhận và xử lý logic nghiệp vụ như bình thường.

**Bước 6 — Kong trả response về client**

Sau khi backend xử lý xong, response được gửi ngược về Kong. Gateway có thể tiếp tục áp dụng Plugin để ghi log, thay đổi response, hoặc bổ sung chính sách khác trước khi trả kết quả cuối cùng về client.

Nhờ quy trình này, Kong tách phần quản lý request/traffic khỏi logic nghiệp vụ của backend. Các microservice không cần tự triển khai lặp lại những chức năng như xác thực, giới hạn request hay định tuyến — những chính sách dùng chung được quản lý tập trung tại Gateway.

## Các Tính Năng Chính

- **API Routing**: Kong dựa trên nhiều thuộc tính của request (Host, Path, Method...) để xác định backend phù hợp — đặc biệt hữu ích khi một Gateway đứng trước nhiều dịch vụ khác nhau trong hệ thống microservices.
    
- **Load Balancing**: Thực hiện thông qua Upstream và Target. Khi một API chạy trên nhiều instance, traffic được phân phối giữa các instance thay vì dồn vào một backend duy nhất, giúp hệ thống tận dụng nhiều tài nguyên xử lý và dễ mở rộng hơn.
    
- **Bảo mật**: Kong cung cấp nhiều plugin cho Authentication và kiểm soát quyền truy cập. Việc tập trung chính sách bảo mật tại Gateway giúp giảm phần logic phải triển khai lặp lại trong từng service.
    
- **Rate Limiting**: Giới hạn số request từ một client hoặc một nhóm client trong một khoảng thời gian nhất định. Khi traffic vượt ngưỡng cấu hình, Gateway xử lý theo chính sách đã thiết lập thay vì để toàn bộ traffic đi tiếp vào backend.
    
- **Request/Response Transformation**: Khi cấu trúc request từ client không hoàn toàn khớp với những gì backend mong muốn, Plugin có thể thay đổi một số thông tin trước khi chuyển request tới Service. Response cũng có thể được điều chỉnh trước khi trả về client.
    
- **Mở rộng qua Plugin**: Có thể dùng plugin có sẵn hoặc tự xây dựng plugin riêng cho nhu cầu đặc thù. Tuy nhiên, không nên đưa toàn bộ logic nghiệp vụ vào Plugin — Gateway nên tập trung vào các tác vụ liên quan tới traffic, chính sách API, và kiểm soát truy cập; logic nghiệp vụ vẫn nên nằm ở backend.

## Các Mô Hình Triển Khai Phổ Biến

Kong hỗ trợ nhiều cách triển khai, tùy vào yêu cầu về database, quản lý cấu hình và kiến trúc hạ tầng. Bốn mô hình thường gặp: **Traditional**, **DB-less**, **Hybrid**, và **Konnect**.

### Traditional Mode

Kong sử dụng database để lưu trữ cấu hình — thông tin về Service, Route, Plugin và các entity liên quan được lưu trong database để các node Gateway cùng đọc. Mô hình này phù hợp khi bạn muốn quản lý cấu hình tập trung qua database. Tuy nhiên, database trở thành một thành phần quan trọng trong kiến trúc, cần được triển khai với khả năng sẵn sàng (high availability) phù hợp với yêu cầu hệ thống.

> **Lưu ý về database hỗ trợ**: Ở các phiên bản Kong cũ, bạn có thể chọn giữa PostgreSQL và Cassandra làm datastore. Tuy nhiên, Kong đã **loại bỏ hoàn toàn hỗ trợ Cassandra kể từ phiên bản 3.4** (quá trình phasing-out bắt đầu từ bản 2.7). Ở các phiên bản hiện tại, **PostgreSQL là lựa chọn database duy nhất** cho Traditional Mode — nếu cần một mô hình phân tán, nhiều khu vực, Kong khuyến nghị dùng Hybrid Mode thay vì Cassandra.

### DB-less Mode

Kong không dùng database để lưu cấu hình. Thay vào đó, cấu hình được quản lý theo **Declarative Configuration** — khai báo trong một file YAML hoặc JSON rồi nạp vào Kong. Cách này phù hợp với các đội DevOps, vì cấu hình Gateway có thể được quản lý như code, lưu trong hệ thống kiểm soát phiên bản (Git), và đưa vào quy trình CI/CD. Đổi lại, DB-less Mode có một số giới hạn so với mô hình dùng database, đặc biệt với các plugin cần lưu trạng thái vào database.

Ví dụ một file cấu hình khai báo tối giản (`kong.yml`), định nghĩa một Service và một Route:

```yaml
_format_version: "3.0"

services:
  - name: order-service
    url: http://order-service.internal:8080
    routes:
      - name: order-route
        paths:
          - /orders
        methods:
          - GET
          - POST
```

### Hybrid Mode

Tách Kong thành **Control Plane** (chịu trách nhiệm quản lý cấu hình) và **Data Plane** (trực tiếp xử lý traffic của người dùng). Hai phần có vai trò khác nhau nhưng phối hợp để Gateway hoạt động thống nhất. Mô hình này hữu ích khi bạn cần triển khai nhiều Data Plane ở các khu vực hoặc môi trường khác nhau: Control Plane quản lý cấu hình tập trung, còn Data Plane đặt gần nơi phát sinh traffic để giảm độ trễ.

### Konnect

Nền tảng dịch vụ quản lý của Kong, trong đó Control Plane do chính Kong vận hành. Bạn vẫn tự triển khai Data Plane để xử lý traffic, nhưng giảm được phần công việc vận hành Control Plane và một số thành phần quản trị khác.

Việc chọn mô hình nào cần dựa trên cách bạn vận hành hệ thống: một hệ thống nhỏ có thể không cần kiến trúc Hybrid phức tạp; ngược lại, môi trường có nhiều cloud hoặc data center thường cần tách Control Plane và Data Plane để dễ quản lý.

## Khi Nào Nên Dùng Kong Gateway?

Kong phù hợp khi bạn có nhiều API hoặc microservices và cần một lớp trung gian quản lý traffic tập trung. Thay vì để từng service tự xử lý Authentication, Rate Limiting hay Routing, các chính sách này có thể được triển khai tại Gateway. Khi số lượng API tăng, Kong giúp việc định tuyến linh hoạt hơn qua các Route dựa trên Path, Host, hoặc HTTP Method; Gateway cũng có thể phân phối request tới nhiều instance của cùng một Service qua Upstream và Target.

Kong đặc biệt hữu ích với hệ thống có yêu cầu kiểm soát truy cập và lưu lượng: các plugin hỗ trợ xác thực, giới hạn request, ghi log, hoặc biến đổi request/response.

Với hệ thống vận hành trên nhiều cloud hoặc data center, Kong có thể triển khai theo Hybrid Mode để tách phần quản lý cấu hình khỏi nơi xử lý traffic. DB-less Mode phù hợp với đội DevOps muốn quản lý cấu hình Gateway qua file và quy trình CI/CD.

Ngược lại, nếu hệ thống chỉ có vài API, traffic thấp, và chưa cần quản lý chính sách tập trung, việc thêm Kong có thể khiến kiến trúc phức tạp không cần thiết. Chỉ nên dùng Kong khi quy mô và yêu cầu quản lý API thực sự cần tới một API Gateway.

## Ưu Điểm Của Kong

**Khả năng mở rộng dễ dàng**

Kong server là **stateless** (không lưu trạng thái riêng ở từng node) — bạn có thể thêm hoặc bớt bao nhiêu node tùy ý, miễn là chúng cùng trỏ vào một datastore. Ở Traditional Mode, PostgreSQL là lựa chọn datastore mặc định và hiện là lựa chọn duy nhất được hỗ trợ chính thức (xem lưu ý về Cassandra ở phần trên).

**Hiệu năng cao**

Trong các bài test performance, Kong nằm trong nhóm API Gateway có hiệu năng cao, có thể xử lý được lượng lớn request mỗi giây.

**Nhiều plugin**

Kong hỗ trợ nhiều plugin theo từng nhóm chức năng: authentication, logging, traffic control, analytics & monitoring... giúp quản lý và theo dõi microservices hiệu quả hơn, thay vì Gateway chỉ đảm nhận mỗi việc routing request.

**Miễn phí**

Kong có bản mã nguồn mở (Kong Gateway OSS), miễn phí. Tuy nhiên bản này không đi kèm GUI (giao diện quản trị dạng web) chính thức.

> **Lưu ý về GUI cho Kong**: **Kong Manager** (GUI chính thức, đầy đủ tính năng) hiện thuộc gói Kong Enterprise, không có sẵn miễn phí. **Konga** — công cụ GUI mã nguồn mở, không chính thức, được cộng đồng phát triển — có thể dùng thay thế, nhưng dự án này gần như không còn được cập nhật tích cực và khả năng tương thích với các phiên bản Kong mới (3.x trở lên) không được đảm bảo. Nên kiểm tra kỹ trước khi đưa vào môi trường production.

## Thiết Lập Và Sử Dụng Kong Gateway

### 1. Thêm một Service

Để kết nối Kong với một server API, bạn cần khai báo một **Service**. Một số tham số quan trọng:

- **name**: tên của service.
- **protocol**: giao thức, ví dụ `http` hoặc `https`.
- **host**: tên (hoặc địa chỉ) của upstream — server thực sự xử lý request.
- **port**: port của server, mặc định là 80.
- **path**: đường dẫn tới service trên upstream.
- **retries**: số lần thử lại khi Kong không gọi được tới upstream.

Ví dụ tạo Service bằng Admin API (dùng `curl`):

```bash
curl -i -X POST http://localhost:8001/services \
  --data name=order-service \
  --data url=http://order-service.internal:8080
```

### 2. Thêm Route cho Service

**Route** là tập hợp các quy tắc để Kong match request tới đúng API trên Service mà nó cần tới. Sau khi tạo Service, bạn thêm Route để điều hướng request tới đúng API bên trong Service đó — có thể tạo một Route cho mỗi API, hoặc cấu hình Route match theo pattern đường dẫn chung. Các tham số cần lưu ý:

- **name**: tên của route.
- **protocols**: giao thức được chấp nhận, ví dụ `http`, `https`.
- **paths**: danh sách path được match với route, có thể dùng regex.
- **methods**: danh sách HTTP method được chấp nhận.
- **strip_path**: có xóa phần prefix của path hay không trước khi chuyển request tới upstream.

Ví dụ tạo Route bằng Admin API, gắn vào Service `order-service` vừa tạo:

```bash
curl -i -X POST http://localhost:8001/services/order-service/routes \
  --data 'paths[]=/orders' \
  --data name=order-route
```

### 3. Cấu hình Plugin

Kong cung cấp nhiều plugin dựng sẵn, cả miễn phí lẫn trả phí (thuộc Kong Enterprise). Plugin có thể áp dụng cho toàn bộ Kong, hoặc chỉ cho một Service/Route cụ thể thông qua name hoặc id. Một số nhóm plugin nổi bật:

- **Authentication**: xác thực request (ví dụ: Key Auth, JWT, OAuth2).
- **Traffic Control**: quản lý lưu lượng request đầu vào/đầu ra (ví dụ: Rate Limiting).
- **Analytics**: hỗ trợ giám sát, thống kê traffic.
- **Transformations**: chuyển đổi trực tiếp dữ liệu trong request và response.
- **Logging**: ghi nhật ký request/response phục vụ theo dõi và debug.

Ví dụ bật plugin Rate Limiting cho Route `order-route`, giới hạn 100 request/phút:

```bash
curl -i -X POST http://localhost:8001/routes/order-route/plugins \
  --data name=rate-limiting \
  --data config.minute=100
```

Sau ba bước trên, mọi request gửi tới `http://localhost:8000/orders` sẽ được Kong xác thực theo Route đã khai báo, kiểm tra giới hạn rate limiting, rồi mới chuyển tiếp tới `order-service` thực tế phía sau.

## Mở Rộng

Sau khi nắm được tổng quan về Kong Gateway, bạn có thể tìm hiểu thêm:

- **So sánh Kong với các API Gateway khác**: Nginx, Traefik, AWS API Gateway, Apache APISIX — mỗi giải pháp có điểm mạnh/yếu khác nhau tùy hạ tầng và quy mô.
- **Kong Manager và Kong Enterprise**: Các tính năng nâng cao chỉ có ở bản trả phí, như GUI chính thức, RBAC (phân quyền theo vai trò), Vitals (giám sát nâng cao).
- **Triển khai Kong trên Kubernetes**: Dùng Kong Ingress Controller để quản lý routing cho các service chạy trong cluster Kubernetes.
- **Viết Custom Plugin cho Kong**: Kong hỗ trợ viết plugin bằng Lua (ngôn ngữ gốc) hoặc qua PDK (Plugin Development Kit) cho các ngôn ngữ khác.
- **Service Mesh vs API Gateway**: Phân biệt vai trò của Kong (quản lý traffic North-South, tức traffic từ bên ngoài vào hệ thống) với các service mesh như Istio (quản lý traffic East-West, tức traffic giữa các service nội bộ).
- **Observability với Kong**: Tích hợp Kong với Prometheus, Grafana, hoặc các công cụ distributed tracing để giám sát traffic đi qua Gateway.
