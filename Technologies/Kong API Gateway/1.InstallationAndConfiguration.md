# Cài đặt và cấu hình Kong API Gateway (kèm Konga) bằng Docker Compose

Tài liệu này hướng dẫn dựng một môi trường Kong API Gateway cơ bản cho kiến trúc Microservice, sử dụng PostgreSQL làm datastore và Konga làm giao diện quản trị. Hệ thống gồm 5 service:

| Service | Vai trò | Vòng đời |
|---|---|---|
| `kong-database` | PostgreSQL, datastore chung cho Kong và Konga | Chạy liên tục |
| `kong-migrations` | Khởi tạo schema (bảng) cho Kong trong database | Chạy 1 lần rồi thoát |
| `kong` | API Gateway chính; lưu và áp dụng services, routes, plugins, consumers... | Chạy liên tục |
| `konga-prepare` | Khởi tạo schema cho Konga trong database riêng `konga_db` | Chạy 1 lần rồi thoát |
| `konga` | Giao diện web quản trị Kong (gọi tới Kong Admin API) | Chạy liên tục |

```yml
services:

  #######################################
  # Postgres: Database dùng chung cho Kong và Konga
  #######################################
  kong-database:
    image: postgres:16
    container_name: kong-database
    restart: always
    # Konga dùng driver Postgres cũ, không hỗ trợ xác thực SCRAM-SHA-256
    # (mặc định từ Postgres 14). Ép lưu mật khẩu dạng md5 để Konga kết nối được.
    command: ["postgres", "-c", "password_encryption=md5"]
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: gateway123
      POSTGRES_DB: kong
      POSTGRES_HOST_AUTH_METHOD: md5
    ports:
      - "127.0.0.1:5433:5432"
    volumes:
      - kong-db-data:/var/lib/postgresql/data
    networks:
      - kong-net
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "admin", "-d", "kong"]
      interval: 5s
      timeout: 5s
      retries: 5

  #######################################
  # Kong database migration
  #######################################
  kong-migrations:
    image: kong:3.8
    command: kong migrations bootstrap
    restart: on-failure
    environment:
      KONG_DATABASE: postgres
      KONG_PG_HOST: kong-database
      KONG_PG_PORT: 5432
      KONG_PG_USER: admin
      KONG_PG_PASSWORD: gateway123
      KONG_PG_DATABASE: kong
    networks:
      - kong-net
    depends_on:
      kong-database:
        condition: service_healthy

  #######################################
  # Kong: The API Gateway
  #######################################
  kong:
    image: kong:3.8
    container_name: kong
    restart: always
    networks:
      - kong-net
    environment:
      KONG_DATABASE: postgres
      KONG_PG_HOST: kong-database
      KONG_PG_PORT: 5432
      KONG_PG_USER: admin
      KONG_PG_PASSWORD: gateway123
      KONG_PG_DATABASE: kong
      KONG_PROXY_ACCESS_LOG: /dev/stdout
      KONG_ADMIN_ACCESS_LOG: /dev/stdout
      KONG_PROXY_ERROR_LOG: /dev/stderr
      KONG_ADMIN_ERROR_LOG: /dev/stderr
      KONG_PROXY_LISTEN: "0.0.0.0:8000, 0.0.0.0:8443 ssl"
      KONG_ADMIN_LISTEN: "0.0.0.0:8001, 0.0.0.0:8444 ssl"
    depends_on:
      kong-database:
        condition: service_healthy
      kong-migrations:
        condition: service_completed_successfully
    healthcheck:
      test: ["CMD", "kong", "health"]
      interval: 10s
      timeout: 5s
      retries: 10
    ports:
      - "8000:8000"             # Kong proxy (HTTP)
      - "8443:8443"             # Kong proxy (HTTPS)
      - "127.0.0.1:8001:8001"   # Kong Admin API (HTTP)
      - "127.0.0.1:8444:8444"   # Kong Admin API (HTTPS)

  #######################################
  # Konga database prepare
  #######################################
  konga-prepare:
    image: pantsel/konga:0.14.9
    command: "-c prepare -a postgres -u postgresql://admin:gateway123@kong-database:5432/konga_db"
    restart: on-failure
    networks:
      - kong-net
    depends_on:
      kong-database:
        condition: service_healthy

  #######################################
  # Konga: Kong GUI
  #######################################
  konga:
    image: pantsel/konga:0.14.9
    container_name: konga
    restart: always
    networks:
      - kong-net
    environment:
      NODE_ENV: production
      DB_ADAPTER: postgres
      DB_HOST: kong-database
      DB_PORT: 5432
      DB_USER: admin
      DB_PASSWORD: gateway123
      DB_DATABASE: konga_db
      TOKEN_SECRET: thay-bang-chuoi-ngau-nhien-du-dai
    depends_on:
      kong:
        condition: service_healthy
      konga-prepare:
        condition: service_completed_successfully
    ports:
      - "127.0.0.1:1337:1337"

volumes:
  kong-db-data:

networks:
  kong-net:
    driver: bridge
```

---

*Giải thích:*

**kong-database**
- Overview: PostgreSQL làm datastore cho Kong (database `kong`) và Konga (database `konga_db`).
- Details: Dữ liệu được lưu bền vững trong volume `kong-db-data`. Healthcheck `pg_isready` giúp các service phụ thuộc chỉ khởi động khi Postgres đã sẵn sàng nhận kết nối. Tham số `password_encryption=md5` chỉ cần thiết vì Konga; nếu không dùng Konga có thể bỏ.
- Environment:
  - `POSTGRES_USER` / `POSTGRES_PASSWORD`: tài khoản superuser được tạo khi khởi tạo database lần đầu.
  - `POSTGRES_DB`: database được tạo sẵn (`kong`).
  - `POSTGRES_HOST_AUTH_METHOD`: phương thức xác thực cho kết nối qua mạng.
  - Lưu ý: các biến này chỉ có tác dụng khi volume còn trống. Nếu đổi mật khẩu sau khi đã chạy, cần xóa volume (`docker compose down -v`) hoặc đổi trực tiếp trong Postgres.

**kong-migrations**
- Overview: Tạo schema (bảng) mà Kong cần trong database `kong`.
- Details: Chạy một lần rồi thoát với mã 0. Chạy lại `bootstrap` trên database đã khởi tạo sẽ không làm hỏng dữ liệu. Khi nâng cấp phiên bản Kong, dùng `kong migrations up` và `kong migrations finish` thay cho `bootstrap`.
- Environment: Các biến `KONG_PG_*` phải trùng với thông tin kết nối của `kong-database`.

**kong**
- Overview: Kong Gateway, nhận request từ client và định tuyến tới các microservice phía sau.
- Details: Gồm hai mặt phẳng:
  - Proxy (8000/8443): nơi client gọi vào.
  - Admin API (8001/8444): nơi cấu hình services, routes, plugins, consumers. Konga thực chất chỉ là giao diện gọi tới Admin API này.
- Environment:
  - `KONG_DATABASE`, `KONG_PG_*`: thông tin kết nối datastore.
  - `KONG_PROXY_LISTEN` / `KONG_ADMIN_LISTEN`: địa chỉ và cổng lắng nghe; `0.0.0.0` để nhận kết nối từ ngoài container.
  - `KONG_*_ACCESS_LOG` / `KONG_*_ERROR_LOG`: đẩy log ra stdout/stderr để xem bằng `docker compose logs kong`.

**konga-prepare**
- Overview: Tạo database `konga_db` và schema cho Konga.
- Details: Chạy một lần rồi thoát. Tham số: `-c prepare` (lệnh khởi tạo), `-a postgres` (adapter), `-u` (connection string).

**konga**
- Overview: Giao diện web quản trị Kong.
- Details: Konga lưu tài khoản đăng nhập và danh sách kết nối tới Kong trong `konga_db`; cấu hình thực tế của gateway vẫn nằm trong database của Kong.
- Environment:
  - `DB_*`: kết nối tới `konga_db`.
  - `TOKEN_SECRET`: khóa ký phiên đăng nhập; phải là chuỗi ngẫu nhiên, không dùng giá trị mẫu.
  - `NODE_ENV: production`: tắt tự động migrate, dùng schema do `konga-prepare` tạo.

### Cài đặt Kong

Khởi chạy toàn bộ hệ thống:

```bash
docker compose up -d
```

Kiểm tra trạng thái các container:

```bash
docker compose ps -a
```

Kết quả mong đợi: `kong-database`, `kong`, `konga` ở trạng thái `running` (`kong` có thêm `healthy`); `kong-migrations` và `konga-prepare` ở trạng thái `Exited (0)`. Nếu có container lỗi, xem log bằng `docker compose logs <tên-service>`.

Kiểm tra Kong Admin API đã hoạt động:

```bash
curl -i http://localhost:8001
```

Response `HTTP/1.1 200 OK` kèm JSON thông tin cấu hình của Kong là thành công.

### Kiểm tra định tuyến qua Kong

Tạo một service trỏ tới API mẫu và một route cho service đó:

```bash
curl -i -X POST http://localhost:8001/services \
  --data name=example-service \
  --data url=https://httpbin.org

curl -i -X POST http://localhost:8001/services/example-service/routes \
  --data name=example-route \
  --data 'paths[]=/example'
```

Gửi request qua cổng proxy:

```bash
curl -i http://localhost:8000/example/get
```

Nếu nhận được response từ httpbin, Kong đã định tuyến đúng: request `/example/get` được chuyển tiếp tới `https://httpbin.org/get` (mặc định `strip_path=true` nên tiền tố `/example` bị bỏ đi).

### Kết nối Konga với Kong

Truy cập Konga tại `http://localhost:1337`. Lần đầu, Konga yêu cầu tạo tài khoản Admin.

Sau khi đăng nhập, tạo kết nối tới Kong (mục Connections):
- Name: tên tùy ý, ví dụ `local-kong`.
- Kong Admin URL: `http://kong:8001`.

> Lưu ý: Bổ sung bước kết nối vì đây là lỗi thường gặp. Phải dùng `http://kong:8001` (tên service trong mạng Docker), không dùng `http://localhost:8001`: bên trong container Konga, `localhost` trỏ về chính container Konga chứ không phải Kong.

## Mở rộng

Các đề xuất dưới đây không áp dụng trực tiếp vào tài liệu, để người đọc cân nhắc theo nhu cầu.

**1. Thay Konga bằng Kong Manager OSS**
- Konga đã ngừng phát triển nhiều năm, được thiết kế cho Kong 1.x/2.x; với Kong 3.x một số chức năng có thể hiển thị sai hoặc không hoạt động, và nó buộc database phải dùng xác thực md5 cũ.
- Từ Kong 3.4, Kong Manager (giao diện quản trị chính thức) đã có trong bản Open Source, chạy ngay trong container `kong` tại cổng 8002. Chỉ cần thêm `KONG_ADMIN_GUI_LISTEN: "0.0.0.0:8002"` và map port `8002`, sau đó có thể bỏ hai service `konga-prepare`, `konga` và cấu hình md5 của Postgres.
- Đánh đổi: Kong Manager OSS chưa có một số tính năng tiện ích của Konga (quản lý nhiều kết nối, tài khoản người dùng riêng), nhưng được Kong duy trì và tương thích chắc chắn với Kong 3.x.

**2. Cấu hình khai báo (declarative) với decK hoặc chế độ DB-less**
- Cấu hình qua giao diện web khó review, khó tái lập giữa các môi trường. `decK` cho phép lưu toàn bộ services/routes/plugins thành file YAML, đưa vào Git và đồng bộ bằng `deck gateway sync`.
- Nếu không cần thay đổi cấu hình lúc runtime, chế độ DB-less (`KONG_DATABASE: "off"` + `KONG_DECLARATIVE_CONFIG`) loại bỏ hẳn Postgres và service migrations, giảm số thành phần phải vận hành. Đánh đổi: không cấu hình được qua Admin API khi đang chạy và một số plugin cần database sẽ không dùng được.

**3. Tách thông tin nhạy cảm ra file `.env`**
- Mật khẩu và `TOKEN_SECRET` đang viết cứng và lặp lại ở nhiều service. Đưa vào file `.env` (không commit lên Git) và tham chiếu bằng `${POSTGRES_PASSWORD}` giúp đổi mật khẩu ở một chỗ và tránh lộ thông tin khi chia sẻ repository.
