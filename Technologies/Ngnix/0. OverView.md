# Nginx là gì?

Nginx (phát âm là "engine-x") là một phần mềm mã nguồn mở đa năng, được sử dụng làm máy chủ web, reverse proxy, HTTP cache và load balancer. Nginx nổi bật nhờ <mark>kiến trúc bất đồng bộ hướng sự kiện</mark> (event-driven asynchronous architecture), cho phép xử lý hàng chục nghìn kết nối đồng thời với mức tiêu thụ bộ nhớ thấp.

Nginx không chỉ phục vụ nội dung tĩnh mà còn hỗ trợ các giao thức <mark>HTTPS, WebSocket, TCP, UDP</mark> — đóng vai trò trung gian linh hoạt giữa người dùng cuối và các ứng dụng backend. Với hiệu suất cao và cấu hình tương đối đơn giản, Nginx là lựa chọn hàng đầu cho các hệ thống web hiện đại cần xử lý lưu lượng lớn.

## Các phiên bản NGINX

Nginx tồn tại dưới ba dạng chính:

**Nginx Open Source:** <mark>Phiên bản mã nguồn mở miễn phí</mark>, cung cấp đầy đủ các tính năng cốt lõi (web server, reverse proxy, load balancer, cache). Đây là phiên bản phổ biến nhất trong cộng đồng và hầu hết các dự án thực tế.

**Nginx Plus:** <mark>Phiên bản thương mại</mark> của Nginx Inc. (nay thuộc F5). Bổ sung thêm các tính năng dành cho doanh nghiệp: active health checks, session persistence, JWT authentication, dashboard giám sát thời gian thực, và hỗ trợ kỹ thuật chính thức qua email và điện thoại. Nginx Plus phù hợp với các tổ chức cần SLA và hỗ trợ chuyên sâu.

**Nginx Unit:** Một sản phẩm riêng biệt — application server đa ngôn ngữ (Go, Python, PHP, Node.js, Ruby, Java, Perl) có khả năng cấu hình lại không cần reload. <mark>Nginx Unit không phải là web server truyền thống mà là môi trường thực thi ứng dụng,</mark> thường được dùng cùng với Nginx Open Source.

## Các ứng dụng phổ biến của Nginx trong thực tế

Với tính linh hoạt cao, Nginx được ứng dụng rộng rãi trong nhiều kịch bản khác nhau.

### Web server cho nội dung tĩnh

Nginx xuất sắc trong việc phục vụ nội dung tĩnh: HTML, CSS, JavaScript và hình ảnh. Nhờ sử dụng system call `sendfile()` cho phép truyền file trực tiếp từ kernel space đến network socket (bỏ qua user space), Nginx phục vụ nội dung tĩnh nhanh hơn Apache đáng kể trong các benchmark thực tế.

Use case điển hình: blog, landing page, trang thông tin doanh nghiệp, và các thành phần tĩnh của ứng dụng Single Page Application (SPA) như React, Vue, Angular.

### Reverse proxy trong hệ thống nhiều tầng

Nginx thường đứng ở tầng ngoài cùng của hệ thống, tiếp nhận mọi request từ internet và chuyển tiếp đến các ứng dụng backend phù hợp (Node.js, Python/Django, Java/Spring, Go). Cách tiếp cận này:

- Ẩn thông tin về backend server, tăng cường bảo mật.
- Cho phép Nginx xử lý SSL termination, nén response, và caching — giảm tải cho backend.
- Tạo điểm trung tâm để áp dụng các chính sách bảo mật (rate limiting, IP filtering, request validation).

### Load balancer trong hệ thống microservices và cloud-native

Nginx phân phối traffic giữa nhiều instance của cùng một dịch vụ, đặc biệt quan trọng trong kiến trúc microservices nơi mỗi service có thể chạy nhiều bản sao song song. Nginx hỗ trợ nhiều thuật toán cân bằng tải:

- **Round Robin (mặc định):** Phân phối đều lần lượt.
- **Least Connections:** Ưu tiên server có ít kết nối active nhất.
- **IP Hash:** Đảm bảo cùng một client luôn được định tuyến đến cùng một server (session persistence).
- **Weighted:** Phân phối theo trọng số, ưu tiên server có năng lực cao hơn.

## Tại sao nên sử dụng Nginx trong dự án

### 1. Kiến trúc bất đồng bộ — xử lý concurrency hiệu quả

Nginx giải quyết bài toán **C10K** (xử lý 10.000 kết nối đồng thời) thông qua event-driven architecture. Thay vì tạo một thread hoặc process riêng cho mỗi request (như Apache theo mô hình prefork), Nginx dùng một số lượng nhỏ worker process, mỗi worker vận hành một event loop xử lý hàng nghìn kết nối không đồng bộ.

Kết quả thực tế: Nginx sử dụng khoảng 2.5 MB RAM để xử lý 10.000 kết nối đồng thời, trong khi Apache có thể cần vài trăm MB cho cùng số lượng kết nối.

### 2. Tăng tốc ứng dụng qua caching và compression

Nginx có thể cache response từ backend server, giảm đáng kể số request đến ứng dụng cho các endpoint có dữ liệu ít thay đổi. Ngoài ra, Nginx hỗ trợ gzip/brotli compression trước khi gửi response về client, giảm kích thước dữ liệu truyền tải.

### 3. Cân bằng tải không cần phần cứng chuyên dụng

Nginx thay thế hoàn toàn các load balancer phần cứng đắt tiền cho hầu hết use case. Ví dụ cấu hình load balancing cơ bản:

```nginx
http {
    upstream backend_servers {
        server server1.example.com weight=3;  # Nhận 3/4 traffic
        server server2.example.com weight=1;  # Nhận 1/4 traffic
        server server3.example.com backup;    # Chỉ dùng khi 2 server trên đều down
    }

    server {
        listen 80;
        server_name example.com;

        location / {
            proxy_pass http://backend_servers;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;

            # Timeout settings quan trọng cho production
            proxy_connect_timeout 5s;
            proxy_read_timeout 60s;
            proxy_send_timeout 60s;
        }
    }
}
```

### 4. Khả năng mở rộng theo chiều ngang

Với event-driven architecture, Nginx không bị giới hạn về số kết nối đồng thời như Apache. Khi cần tăng capacity, chỉ cần thêm worker process (tương ứng với số CPU core) hoặc scale theo chiều ngang thêm nhiều instance Nginx.

### 5. Hot reload và zero-downtime upgrade

Nginx cho phép reload cấu hình và thậm chí nâng cấp binary mà không cần dừng service:

```bash
# Reload cấu hình — worker mới thay thế worker cũ sau khi hoàn thành request hiện tại
nginx -s reload

# Kiểm tra cấu hình trước khi reload (quan trọng để tránh lỗi)
nginx -t

# Hot upgrade binary (zero-downtime)
kill -USR2 $(cat /var/run/nginx.pid)
```

### 6. Hiệu quả tài nguyên trên phần cứng thấp

Nginx hoạt động tốt ngay cả trên các server cấu hình thấp (1 CPU, 512 MB RAM). Với cài đặt mặc định, Nginx đã cung cấp hiệu suất vượt trội so với nhiều giải pháp khác — không cần tinh chỉnh phức tạp để đạt hiệu quả cơ bản.

### 7. Cấu hình rõ ràng, dễ đọc

Cú pháp cấu hình Nginx theo dạng block lồng nhau (`server`, `location`, `upstream`) rất trực quan sau khi làm quen. Khác với Apache sử dụng `.htaccess` phân tán ở nhiều thư mục, Nginx tập trung toàn bộ cấu hình vào `nginx.conf` và các file include — dễ kiểm soát và version control.

## Nginx hoạt động như thế nào?

Có thể hình dung Nginx như một **dispatcher thông minh** đứng ở cổng vào của hệ thống. Nginx xử lý trực tiếp các request cho nội dung tĩnh (HTML, CSS, JS, hình ảnh), và chuyển tiếp các request cần xử lý động đến ứng dụng backend tương ứng.

**Phân biệt nội dung tĩnh và động:**

- **Nội dung tĩnh (static content):** File có sẵn trên server, nội dung cố định, Nginx đọc và trả về trực tiếp. Ví dụ: `index.html`, `style.css`, `logo.png`.
- **Nội dung động (dynamic content):** Cần xử lý logic và truy vấn database để tạo ra response tùy theo từng request. Ví dụ: trang profile người dùng, kết quả tìm kiếm, giỏ hàng.

Nginx không thể tự thực thi code PHP, Python hay Go — nó cần chuyển request đến process/service có khả năng đó.

![](https://images.viblo.asia/46a691e2-ae68-4e8a-a920-325215b95a77.png)

**Luồng xử lý request PHP (ví dụ điển hình):**

1. Browser gửi HTTP request đến Nginx.
2. Nginx nhận request, xác định đây là file `.php`, chuyển tiếp đến **PHP-FPM** qua FastCGI protocol.
3. PHP-FPM thực thi file `.php`, truy vấn database nếu cần.
4. PHP-FPM trả kết quả (HTML đã render) về Nginx qua FastCGI.
5. Nginx trả response về browser.

**PHP-FPM (FastCGI Process Manager)** là process manager cho PHP, hoạt động như một "phiên dịch viên" giữa Nginx và PHP. Nginx giao tiếp với PHP-FPM qua **TCP socket** (ví dụ: `127.0.0.1:9000`) hoặc **Unix domain socket** (ví dụ: `/var/run/php/php8.1-fpm.sock`) — Unix socket nhanh hơn TCP socket khi cả hai chạy cùng một máy do tránh được overhead của network stack.

**Tương tự với Golang backend:**

Thay vì PHP-FPM, ứng dụng Go chạy như một HTTP server độc lập (ví dụ: lắng nghe trên port 8080). Nginx chuyển tiếp request đến ứng dụng Go qua `proxy_pass`:

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
```

## So sánh Nginx với Apache và HAProxy

| Tiêu chí             | Nginx                                  | Apache                                     | HAProxy                               |
| -------------------- | -------------------------------------- | ------------------------------------------ | ------------------------------------- |
| Mô hình xử lý        | Event-driven, async                    | Process/thread per request (mặc định)      | Event-driven                          |
| Chuyên về            | Web server + Reverse proxy + LB        | Web server, module ecosystem phong phú     | Load balancing + HA                   |
| Static file serving  | Rất nhanh (sendfile)                   | Chậm hơn Nginx                             | Không phục vụ static file             |
| Dynamic content      | Qua FastCGI/proxy                      | Tích hợp trực tiếp (mod_php)               | Không thực thi code                   |
| Memory usage         | Thấp (event loop)                      | Cao hơn (thread/process model)             | Thấp                                  |
| SSL/TLS              | Có (SSL termination)                   | Có (mod_ssl)                               | Có (SSL termination)                  |
| Layer 7 (HTTP) LB    | Có                                     | Có (mod_proxy_balancer)                    | Rất mạnh                              |
| Layer 4 (TCP/UDP) LB | Có (stream module)                     | Không                                      | Rất mạnh                              |
| Health checks        | Thụ động (passive)                     | Thụ động                                   | Chủ động (active) chi tiết            |
| Hot reload           | Có                                     | Có nhưng phức tạp hơn                      | Có (runtime API)                      |
| Phù hợp cho          | Web server, reverse proxy, moderate LB | .htaccess, shared hosting, mod_* ecosystem | High-performance, mission-critical LB |

**Khi nào chọn cái nào:**

- **Chọn Nginx** khi cần web server + reverse proxy + load balancer trong một giải pháp, ưu tiên hiệu năng cao với tài nguyên thấp.
- **Chọn Apache** khi cần `.htaccess` cho shared hosting, phụ thuộc vào module Apache cụ thể (mod_php, mod_rewrite legacy), hoặc đã có infrastructure Apache cần duy trì.
- **Chọn HAProxy** khi ưu tiên load balancing với active health checks, TCP load balancing phức tạp, hoặc cần runtime API để quản lý backend pool mà không reload.

## Các thành phần chính của kiến trúc Nginx

![](https://rivercrane.vn/wp-content/uploads/2024/12/infographic-Inside-NGINX_process-model.png)

Nginx sử dụng mô hình multi-process kết hợp event-driven, gồm các process sau:

### Master Process

- Quản lý toàn bộ vòng đời của Nginx.
- Đọc và validate file cấu hình (`nginx.conf`).
- Khởi tạo và quản lý các worker process.
- Xử lý tín hiệu từ OS: `SIGHUP` (reload), `SIGTERM` (shutdown gracefully), `SIGUSR2` (hot upgrade binary).
- Không trực tiếp xử lý request từ client.

### Worker Processes

- Thực sự xử lý mọi request từ client: phục vụ static content, proxy_pass đến backend, xử lý SSL.
- Mỗi worker chạy một event loop (dùng `epoll` trên Linux, `kqueue` trên macOS/BSD) xử lý hàng nghìn kết nối đồng thời.
- Số lượng worker nên bằng số CPU core để tận dụng tối đa tài nguyên:

```nginx
worker_processes auto;  # Tự động detect số CPU core
```

### Cache Loader Process (tùy chọn)

- Chạy một lần khi Nginx khởi động: quét disk cache và nạp metadata vào shared memory để worker có thể tra cứu nhanh.

### Cache Manager Process (tùy chọn)

- Chạy định kỳ trong background: kiểm tra dung lượng cache, xóa các entry hết hạn hoặc ít được dùng nhất (LRU policy) để duy trì cache trong giới hạn cấu hình.

**Lợi thế của sendfile():** Nginx phục vụ file tĩnh cực nhanh nhờ system call `sendfile()` — cho phép kernel copy file trực tiếp từ page cache đến socket buffer, bỏ qua hoàn toàn việc copy dữ liệu qua user space. Điều này giảm số lần context switch và lượng data copy so với cách đọc file thông thường (read + write).

## Các tính năng chính của Nginx

### 1. Hệ thống Module linh hoạt

Kiến trúc Nginx hỗ trợ module tĩnh (biên dịch vào binary) và dynamic module (load khi runtime từ Nginx 1.9.11+). Dynamic module cho phép thêm tính năng mà không cần biên dịch lại toàn bộ Nginx.

Ví dụ biên dịch với module SSL và gzip:

```bash
./configure --with-http_ssl_module --with-http_gzip_static_module --with-http_v2_module
make && make install
```

Ví dụ load dynamic module trong `nginx.conf`:

```nginx
load_module modules/ngx_http_brotli_filter_module.so;
```

### 2. Kiến trúc bất đồng bộ hướng sự kiện (Event-Driven Architecture)

<mark>Nginx không tạo thread mới cho mỗi connection </mark>như Apache (mô hình thread-per-connection). Thay vào đó, mỗi worker process vận hành một event loop:

- Nhận event (new connection, data available, socket writable) từ OS qua `epoll` (Linux) hoặc `kqueue` (BSD/macOS).
- Xử lý event và ngay lập tức chuyển sang event tiếp theo — không block chờ I/O.
- Một worker có thể xử lý hàng nghìn connection đồng thời mà không cần tạo thread mới.

![](https://statics.cdn.200lab.io/2024/09/nginx-la-gi-asynchronous.png?width=800)

So sánh trực quan: Để xử lý 1.000 request đồng thời, Apache prefork cần 1.000 process/thread. Nginx chỉ cần số worker bằng số CPU core (thường 4-8 worker) vì mỗi worker xử lý hàng trăm connection qua event loop.

### 3. Hỗ trợ đa giao thức

Nginx không giới hạn ở HTTP. Danh sách giao thức được hỗ trợ:

- **HTTP/1.0, HTTP/1.1, HTTP/2, HTTP/3 (QUIC — từ Nginx 1.25+)**
- **HTTPS** (TLS 1.2, TLS 1.3)
- **WebSocket** (qua HTTP Upgrade)
- **TCP và UDP** (stream module — load balancing ở Layer 4)
- **gRPC** (HTTP/2 proxying)
- **IMAP, POP3, SMTP** (mail proxy module)

### 4. Reverse Proxy và Load Balancing

Nginx phân phối request theo URI, header, hoặc các điều kiện khác — không phụ thuộc vào cấu trúc file system. Hỗ trợ cả Layer 7 (HTTP) và Layer 4 (TCP/UDP) load balancing.

![](https://statics.cdn.200lab.io/2024/09/nginx-la-gi-load-balancer-1.jpeg)

### 5. SSL Termination

Nginx xử lý mã hóa/giải mã TLS tại tầng proxy, sau đó chuyển tiếp request đến backend qua kết nối không mã hóa (hoặc mã hóa nội bộ nếu cần). Cách này:

- Giảm tải CPU cho backend server (TLS handshake tốn CPU đáng kể).
- Tập trung quản lý certificate tại một nơi.
- Cho phép backend đơn giản hơn khi không cần xử lý TLS.

![](https://statics.cdn.200lab.io/2024/09/nginx-la-gi-nginx-ssl.jpg)

### 6. Streaming Media

Nginx hỗ trợ streaming video qua các module `ngx_http_mp4_module` và `ngx_http_flv_module`, cho phép seek (tua) trong file video mà không cần tải toàn bộ file về trước. Nginx RTMP module (bên thứ ba) hỗ trợ thêm live streaming qua RTMP.

### 7. Hot Reload và Zero-Downtime Upgrade

Nginx cho phép:

- **Reload cấu hình:** Worker mới đọc config mới, worker cũ hoàn thành request hiện tại rồi mới thoát — không có connection nào bị ngắt.
- **Upgrade binary không downtime:** Dùng tín hiệu `SIGUSR2` để khởi động master process mới song song với master cũ, sau đó dần dần chuyển traffic sang worker mới.

### 8. Nginx Plus (phiên bản thương mại)

Bổ sung so với Open Source: active health checks (phát hiện backend failure ngay cả khi không có request), dynamic upstream reconfiguration qua API, session persistence nâng cao, JWT authentication, và dashboard giám sát thời gian thực.

### 9. Logging linh hoạt

Nginx ghi hai loại log:

- **Access log:** Mỗi request — thời gian, client IP, method, URI, status code, bytes sent, referrer, user agent. Định dạng có thể tùy chỉnh.
- **Error log:** Lỗi ở nhiều mức độ: `debug`, `info`, `notice`, `warn`, `error`, `crit`, `alert`, `emerg`.

Trong production, nên đặt error log ở mức `warn` hoặc `error` để tránh log quá nhiều:

```nginx
error_log /var/log/nginx/error.log warn;
access_log /var/log/nginx/access.log main buffer=16k;  # Buffer giảm I/O
```

### 10. Reload cấu hình không gián đoạn

```bash
nginx -t          # Kiểm tra cấu hình trước khi apply (bắt buộc trước mỗi lần reload)
nginx -s reload   # Reload cấu hình, worker cũ hoàn thành request trước khi thoát
nginx -s quit     # Graceful shutdown
nginx -s stop     # Immediate shutdown
```

## Ưu và nhược điểm

### Ưu điểm

**Hiệu suất cao với tài nguyên thấp:** Event-driven architecture xử lý hàng chục nghìn concurrent connection với footprint bộ nhớ nhỏ.

**Phục vụ static file nhanh:** `sendfile()` system call cho phép zero-copy transfer từ kernel page cache đến socket.

**Khả năng mở rộng tốt:** Scale theo chiều ngang dễ dàng; số worker process tỷ lệ với số CPU core.

**Đa năng:** Một binary duy nhất có thể đảm nhận vai trò web server, reverse proxy, load balancer, SSL terminator, và cache server.

**Hot reload không downtime:** Thay đổi cấu hình mà không ngắt connection đang active.

**Cộng đồng lớn và tài liệu phong phú:** Nginx là web server phổ biến nhất theo nhiều thống kê (Netcraft, W3Techs), có nghĩa là hầu hết vấn đề đã có giải pháp được tài liệu hóa.

### Nhược điểm

**Không có dynamic module tích hợp sâu như Apache:** Apache cho phép mod_php chạy PHP trực tiếp trong cùng process — đơn giản hơn cho shared hosting. Nginx luôn cần process riêng (PHP-FPM, uWSGI) để xử lý dynamic content.

**Active health check chỉ có trong Nginx Plus:** Open Source chỉ hỗ trợ passive health check (phát hiện lỗi khi có request thất bại). Muốn proactive check phải dùng giải pháp bên ngoài hoặc nâng cấp lên Plus.

**Không có GUI quản lý tích hợp:** Toàn bộ cấu hình qua file text. Một số người dùng không quen với CLI có thể thấy khó khăn ban đầu (mặc dù đây cũng là ưu điểm cho automation/IaC).

**Debug phức tạp hơn Apache trong một số trường hợp:** Đặc biệt với các vấn đề liên quan đến rewrite rule và proxy header khi migrate từ Apache.

**HTTP/3 còn đang phát triển:** Hỗ trợ QUIC/HTTP/3 đã có từ Nginx 1.25+ nhưng vẫn được đánh dấu là experimental trong một số tính năng.

## Đề xuất cải thiện thêm

### 1. Cấu hình Nginx chuẩn cho production

Một số cài đặt quan trọng thường bị bỏ qua trong cấu hình mặc định:

```nginx
# /etc/nginx/nginx.conf

worker_processes auto;                   # Tự detect số CPU core
worker_rlimit_nofile 65535;             # Giới hạn file descriptor cho mỗi worker

events {
    worker_connections 4096;             # Connection tối đa mỗi worker
    use epoll;                          # Sử dụng epoll trên Linux (thường auto-detect)
    multi_accept on;                    # Accept nhiều connection trong một lần
}

http {
    # Security headers
    server_tokens off;                  # Ẩn version Nginx trong response header

    # Performance
    sendfile on;
    tcp_nopush on;                      # Gửi header và file đầu trong cùng packet
    tcp_nodelay on;                     # Giảm latency cho keep-alive connection
    keepalive_timeout 65;

    # Compression
    gzip on;
    gzip_vary on;
    gzip_proxied any;
    gzip_types text/plain text/css application/json application/javascript;

    # Timeouts
    client_header_timeout 10s;
    client_body_timeout 10s;
    send_timeout 10s;
}
```

### 2. Nginx trong môi trường containerized (Docker/Kubernetes)

Khi chạy Nginx trong container, cần lưu ý:

- Dùng `nginx:alpine` image (khoảng 40 MB thay vì 180 MB).
- Trong Kubernetes, Nginx thường được deploy dưới dạng **Ingress Controller** (ingress-nginx) để quản lý routing cho toàn cluster.
- Log nên ghi ra stdout/stderr thay vì file để tích hợp với logging infrastructure của container platform.

### 3. Nginx với Golang — cấu hình reverse proxy tối ưu

Cho ứng dụng Go (Gin, Fiber, Chi):

```nginx
upstream golang_app {
    server 127.0.0.1:8080;
    keepalive 32;  # Duy trì keepalive connection đến backend Go
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    location / {
        proxy_pass http://golang_app;
        proxy_http_version 1.1;          # Cần cho keepalive
        proxy_set_header Connection "";  # Cần cho keepalive
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Buffers
        proxy_buffering on;
        proxy_buffer_size 4k;
        proxy_buffers 8 4k;
    }
}
```

### 4. Rate Limiting và bảo mật cơ bản

```nginx
# Định nghĩa rate limit zone (10 MB lưu trữ trạng thái cho IP)
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=100r/m;

server {
    location /api/ {
        limit_req zone=api_limit burst=20 nodelay;
        limit_req_status 429;  # Trả về 429 Too Many Requests
        proxy_pass http://backend;
    }
}
```

### 5. Công cụ liên quan nên biết

- **Certbot (Let's Encrypt):** Tự động cấp phát và renew SSL certificate miễn phí cho Nginx.
- **nginx-amplify:** Monitoring dashboard cho Nginx (miễn phí với giới hạn).
- **ingress-nginx:** Nginx Ingress Controller chính thức cho Kubernetes.
- **OpenResty:** Nginx mở rộng với Lua scripting — cho phép viết logic phức tạp trực tiếp trong Nginx.
- **ModSecurity:** Web Application Firewall có thể tích hợp với Nginx.
