# SQL Injection: Nhận biết, nguyên nhân, cách phòng chống và thực hành với Go

## 1. Tóm tắt nhanh

**SQL Injection** là một trong những lỗ hổng bảo mật ứng dụng web phổ biến và nguy hiểm nhất. Lỗ hổng này xảy ra khi ứng dụng đưa dữ liệu người dùng nhập vào câu lệnh SQL mà không xử lý an toàn, khiến dữ liệu đó bị database hiểu nhầm như một phần của câu lệnh SQL.

Hậu quả có thể bao gồm:

- Bypass đăng nhập.
- Đọc dữ liệu nhạy cảm.
- Sửa hoặc xóa dữ liệu.
- Thực thi lệnh trái phép trên database.
- Chiếm quyền kiểm soát một phần hoặc toàn bộ hệ thống.

Cách phòng chống quan trọng nhất là:

```text
Không nối chuỗi dữ liệu người dùng vào câu lệnh SQL.
Hãy dùng Prepared Statement / Parameterized Query.
```

Trong Go, các thư viện như `database/sql`, `pgx`, `sqlc`, `sqlx` đều hỗ trợ parameterized query nếu được dùng đúng cách.

## 2. SQL Injection là gì?

SQL Injection, thường viết tắt là SQLi, là kỹ thuật tấn công trong đó kẻ tấn công chèn dữ liệu độc hại vào đầu vào của ứng dụng. Dữ liệu này sau đó được ứng dụng ghép vào câu lệnh SQL, làm thay đổi ý nghĩa ban đầu của câu lệnh.

Ví dụ, ứng dụng dự định thực hiện:

```sql
SELECT *
FROM users
WHERE username = 'an'
  AND password = '123456';
```

Nhưng nếu người dùng nhập:

```text
' OR '1'='1
```

Câu lệnh có thể bị biến đổi thành:

```sql
SELECT *
FROM users
WHERE username = '' OR '1'='1' AND password = '';
```

Vì `'1'='1'` luôn đúng, câu lệnh có thể trả về dữ liệu người dùng dù kẻ tấn công không biết mật khẩu.

## 3. Nguyên nhân gốc rễ

Nguyên nhân cốt lõi của SQL Injection là:

```text
Ứng dụng trộn lẫn dữ liệu người dùng với cú pháp SQL.
```

Nói cách khác, database không phân biệt được:

- Đâu là câu lệnh SQL do lập trình viên viết.
- Đâu là dữ liệu người dùng nhập vào.

Điều này thường xảy ra khi lập trình viên nối chuỗi trực tiếp:

```go
query := "SELECT * FROM users WHERE username = '" + username + "'"
```

Nếu `username` chứa ký tự đặc biệt như `'`, `"`, `--`, `;`, câu lệnh SQL cuối cùng có thể bị thay đổi cấu trúc.

### 3.1 Ví dụ nguyên nhân

Code không an toàn:

```go
query := fmt.Sprintf(
    "SELECT * FROM users WHERE username = '%s'",
    username,
)
```

Nếu `username` là:

```text
an' OR '1'='1
```

Câu lệnh SQL trở thành:

```sql
SELECT * FROM users WHERE username = 'an' OR '1'='1'
```

Điều kiện này luôn đúng với nhiều dòng dữ liệu, dẫn đến rò rỉ dữ liệu hoặc bypass xác thực.

## 4. Vì sao SQL Injection nguy hiểm?

SQL Injection nguy hiểm vì database thường có quyền truy cập trực tiếp vào dữ liệu quan trọng của hệ thống.

Nếu khai thác thành công, kẻ tấn công có thể:

### 4.1 Bypass đăng nhập

Kẻ tấn công không cần biết mật khẩu thật nhưng vẫn đăng nhập được vào hệ thống.

### 4.2 Đọc dữ liệu nhạy cảm

Ví dụ:

- Thông tin người dùng.
- Email.
- Số điện thoại.
- Địa chỉ.
- Lịch sử giao dịch.
- Token hoặc dữ liệu nội bộ.

### 4.3 Sửa dữ liệu

Kẻ tấn công có thể cập nhật dữ liệu trái phép nếu database user có quyền `UPDATE`.

Ví dụ:

```sql
UPDATE users
SET role = 'admin'
WHERE id = 123;
```

### 4.4 Xóa dữ liệu

Nếu database user có quyền `DELETE` hoặc `DROP`, kẻ tấn công có thể xóa bảng hoặc dữ liệu.

Ví dụ:

```sql
DROP TABLE users;
```

### 4.5 Thực thi lệnh mở rộng

Tùy vào database và cấu hình hệ thống, kẻ tấn công có thể:

- Đọc file.
- Ghi file.
- Chạy lệnh hệ thống.
- Tấn công sang máy chủ khác trong mạng nội bộ.
- Leo thang đặc quyền.

## 5. Ví dụ kinh điển: bypass đăng nhập

Giả sử ứng dụng có câu lệnh đăng nhập như sau:

```go
query := fmt.Sprintf(
    "SELECT * FROM users WHERE username = '%s' AND password = '%s'",
    username,
    password,
)
```

Trường hợp bình thường:

```text
username = an
password = 123456
```

Câu lệnh SQL:

```sql
SELECT *
FROM users
WHERE username = 'an'
  AND password = '123456';
```

Trường hợp tấn công:

```text
username = ' OR '1'='1
password = bất kỳ
```

Câu lệnh SQL có thể trở thành:

```sql
SELECT *
FROM users
WHERE username = '' OR '1'='1' AND password = '';
```

Do `'1'='1'` luôn đúng, điều kiện `WHERE` có thể trả về dữ liệu người dùng, khiến kẻ tấn công đăng nhập thành công mà không cần mật khẩu hợp lệ.

### 5.1 Lưu ý quan trọng về mật khẩu

Trong ví dụ trên, mật khẩu đang được so sánh dạng plaintext để dễ hiểu. Trong thực tế, bạn không bao giờ lưu mật khẩu plaintext.

Mật khẩu nên được hash bằng các thuật toán phù hợp như:

- bcrypt.
- scrypt.
- Argon2.

Tuy nhiên, dù bạn có hash mật khẩu đúng cách, SQL Injection vẫn có thể bypass đăng nhập nếu câu lệnh SQL bị tiêm mã độc.

## 6. Các dạng SQL Injection phổ biến

SQL Injection không chỉ có một dạng duy nhất. Dưới đây là các nhóm phổ biến.

## 6.1 In-band SQL Injection

In-band SQL Injection là dạng tấn công mà kẻ tấn công dùng cùng một kênh giao tiếp để gửi payload và nhận kết quả.

Hai kỹ thuật phổ biến là:

- Union-based SQL Injection.
- Error-based SQL Injection.

### 6.1.1 Union-based SQL Injection

Kỹ thuật này dùng toán tử `UNION` để ghép kết quả của câu lệnh gốc với dữ liệu từ bảng khác.

Ví dụ ứng dụng có truy vấn tìm sản phẩm:

```go
query := fmt.Sprintf(
    "SELECT name, price FROM products WHERE name LIKE '%%%s%%'",
    input,
)
```

Nếu người dùng nhập:

```text
' UNION SELECT username, password FROM users --
```

Câu lệnh SQL có thể trở thành:

```sql
SELECT name, price
FROM products
WHERE name LIKE '%'
UNION
SELECT username, password
FROM users --%';
```

Ký tự `--` là comment trong SQL, dùng để vô hiệu hóa phần còn lại của câu lệnh gốc.

Nếu ứng dụng hiển thị kết quả truy vấn ra màn hình, kẻ tấn công có thể thấy dữ liệu từ bảng `users`.

### 6.1.2 Error-based SQL Injection

Kỹ thuật này lợi dụng thông báo lỗi của database để lấy thông tin.

Ví dụ, kẻ tấn công cố tình gây lỗi cú pháp hoặc ép database trả về lỗi có chứa:

- Tên bảng.
- Tên cột.
- Kiểu dữ liệu.
- Phiên bản database.

Thông tin lỗi giúp kẻ tấn công hiểu cấu trúc database và tiếp tục khai thác.

Vì vậy, production không nên hiển thị lỗi SQL chi tiết cho người dùng cuối.

## 6.2 Inferential SQL Injection / Blind SQL Injection

Blind SQL Injection xảy ra khi ứng dụng không hiển thị trực tiếp dữ liệu hoặc lỗi SQL cho kẻ tấn công. Kẻ tấn công vẫn có thể khai thác bằng cách quan sát hành vi của ứng dụng.

Hai kỹ thuật phổ biến:

- Boolean-based Blind SQLi.
- Time-based Blind SQLi.

### 6.2.1 Boolean-based Blind SQL Injection

Kẻ tấn công gửi các điều kiện đúng/sai và quan sát phản hồi của ứng dụng.

Ví dụ:

```text
?id=1 AND 1=1
?id=1 AND 1=2
```

Nếu ứng dụng trả về kết quả khác nhau giữa hai trường hợp, kẻ tấn công có thể suy luận dữ liệu.

Ví dụ:

```text
?id=1 AND SUBSTRING(username, 1, 1) = 'a'
```

Từ đó, kẻ tấn công có thể dò từng ký tự của dữ liệu.

### 6.2.2 Time-based Blind SQL Injection

Nếu ứng dụng không thay đổi nội dung phản hồi, kẻ tấn công có thể dùng thời gian phản hồi để suy luận.

Ví dụ với PostgreSQL:

```sql
SELECT CASE
    WHEN (condition) THEN pg_sleep(5)
    ELSE pg_sleep(0)
END;
```

Nếu câu lệnh đúng và server phản hồi chậm hơn 5 giây, kẻ tấn công biết điều kiện đúng.

Với MySQL, kỹ thuật tương tự có thể dùng:

```sql
SLEEP(5)
```

Time-based Blind SQL Injection rất nguy hiểm vì không cần ứng dụng hiển thị dữ liệu hay lỗi.

## 6.3 Out-of-band SQL Injection

Out-of-band SQL Injection xảy ra khi kẻ tấn công không dùng trực tiếp kênh HTTP response để nhận dữ liệu, mà buộc database gửi request đến một hệ thống khác.

Ví dụ:

- DNS request.
- HTTP request.
- SMB request.
- Email hoặc webhook trong một số cấu hình đặc biệt.

Dạng này ít phổ biến hơn và phụ thuộc vào tính năng của từng database cũng như cấu hình mạng.

## 6.4 Second-order SQL Injection

Second-order SQL Injection là dạng tấn công mà payload không được thực thi ngay khi người dùng gửi input.

Thay vào đó:

1. Ứng dụng lưu dữ liệu độc hại vào database.
2. Sau này, một chức năng khác đọc dữ liệu đó ra.
3. Dữ liệu đó tiếp tục được đưa vào câu lệnh SQL không an toàn.
4. SQL Injection xảy ra ở bước sau.

Ví dụ:

```text
Người dùng đăng ký username:
admin'--
```

Nếu username này được lưu vào database, sau đó một job nội bộ dùng username để dựng câu lệnh SQL:

```go
query := fmt.Sprintf(
    "SELECT * FROM users WHERE username = '%s'",
    usernameFromDB,
)
```

Lỗ hổng vẫn có thể xảy ra dù bước đăng ký ban đầu có vẻ đã validate.

Đây là lý do vì sao parameterized query cần được áp dụng ở mọi nơi truy vấn database, không chỉ ở endpoint nhận input trực tiếp từ người dùng.

## 7. Cách phát hiện SQL Injection

Lưu ý quan trọng:

```text
Chỉ kiểm thử SQL Injection trên hệ thống bạn sở hữu hoặc được phép kiểm thử.
Tấn công hệ thống trái phép là hành vi vi phạm pháp luật.
```

## 7.1 Phát hiện thủ công

Một số payload đơn giản thường được dùng để kiểm tra nhanh:

### 7.1.1 Kiểm tra ký tự quote

```text
'
```

Nếu ứng dụng trả về lỗi SQL hoặc hành vi bất thường, có thể input đang được ghép trực tiếp vào câu lệnh SQL.

### 7.1.2 Kiểm tra điều kiện luôn đúng

```text
' OR '1'='1
```

hoặc:

```text
" OR "1"="1
```

Nếu kết quả thay đổi bất thường, cần kiểm tra thêm.

### 7.1.3 Kiểm tra comment SQL

```text
--
#
/*
```

Comment có thể làm thay đổi phần còn lại của câu lệnh SQL.

### 7.1.4 Kiểm tra UNION

```text
' UNION SELECT NULL --
```

Sau đó tăng dần số cột:

```text
' UNION SELECT NULL, NULL --
' UNION SELECT NULL, NULL, NULL --
```

Nếu câu lệnh không còn lỗi, có thể số cột đã khớp với truy vấn gốc.

### 7.1.5 Kiểm tra time-based

Ví dụ PostgreSQL:

```text
'; SELECT pg_sleep(5); --
```

Nếu phản hồi chậm bất thường, có thể tồn tại blind SQL injection.

## 7.2 Phát hiện bằng công cụ

Một số công cụ phổ biến:

| Công cụ | Mục đích |
|---|---|
| sqlmap | Tự động phát hiện và khai thác SQL Injection trong môi trường được phép |
| Burp Suite | Kiểm thử bảo mật web, intercept request, scan lỗ hổng |
| OWASP ZAP | Công cụ scan bảo mật mã nguồn mở |
| Nuclei | Scan lỗ hổng dựa trên template |
| Postman | Hỗ trợ gửi request thủ công khi kiểm thử API |

Lưu ý:

- Công cụ tự động có thể bỏ sót lỗ hổng.
- Không nên phụ thuộc hoàn toàn vào scanner.
- Kiểm thử thủ công vẫn rất quan trọng.

## 8. Cách phòng chống SQL Injection

## 8.1 Dùng Prepared Statement / Parameterized Query

Đây là biện pháp quan trọng nhất.

Prepared Statement tách biệt câu lệnh SQL và dữ liệu đầu vào.

Thay vì:

```go
query := fmt.Sprintf(
    "SELECT * FROM users WHERE username = '%s'",
    username,
)
```

Hãy viết:

```go
query := "SELECT * FROM users WHERE username = $1"
row := db.QueryRowContext(ctx, query, username)
```

Khi đó:

- Câu lệnh SQL được gửi trước.
- Dữ liệu người dùng được gửi riêng.
- Database luôn coi dữ liệu là giá trị, không coi là cú pháp SQL.

### 8.1.1 Vì sao parameterized query hiệu quả?

Nếu người dùng nhập:

```text
' OR '1'='1
```

Database sẽ tìm một username đúng bằng chuỗi đó, thay vì hiểu chuỗi này như một phần của điều kiện SQL.

Nói cách khác:

```text
Nối chuỗi: dữ liệu có thể trở thành code.
Parameterized query: dữ liệu luôn chỉ là dữ liệu.
```

## 8.2 Dùng ORM / Query Builder đúng cách

Các thư viện như:

- GORM.
- sqlc.
- sqlx.
- Ent.
- Bun.

thường hỗ trợ parameterized query. Tuy nhiên, bạn vẫn cần cẩn thận khi dùng raw SQL.

Ví dụ GORM raw không an toàn nếu tự nối chuỗi:

```go
db.Raw(
    fmt.Sprintf("SELECT * FROM users WHERE username = '%s'", username),
).Scan(&users)
```

Cách an toàn hơn:

```go
db.Raw(
    "SELECT * FROM users WHERE username = ?",
    username,
).Scan(&users)
```

## 8.3 Không dùng placeholder cho tên bảng hoặc tên cột

Placeholder thường chỉ dùng cho giá trị, không dùng cho identifier như:

- Tên bảng.
- Tên cột.
- Hướng sắp xếp `ASC`, `DESC`.
- Tên schema.

Ví dụ sau thường không hoạt động như mong muốn:

```sql
SELECT * FROM $1
```

hoặc:

```sql
ORDER BY $1
```

Với các trường hợp này, cần dùng whitelist.

Ví dụ:

```go
allowedSortColumns := map[string]string{
    "name":       "name",
    "created_at": "created_at",
    "price":      "price",
}

sortColumn, ok := allowedSortColumns[req.SortBy]
if !ok {
    return errors.New("invalid sort column")
}

query := fmt.Sprintf(
    "SELECT id, name, price FROM products ORDER BY %s ASC",
    sortColumn,
)
```

Cách này an toàn hơn vì `sortColumn` chỉ nhận giá trị đã được kiểm soát, không lấy trực tiếp từ input người dùng.

## 8.4 Validate dữ liệu đầu vào

Validate input không thay thế được parameterized query, nhưng giúp giảm bề mặt tấn công.

Ví dụ:

- Email phải đúng định dạng email.
- Số điện thoại chỉ chứa chữ số.
- ID phải là số hoặc UUID hợp lệ.
- Enum chỉ nhận các giá trị cho phép.
- Page size có giới hạn tối đa.

Ví dụ:

```go
if page <= 0 {
    page = 1
}

if pageSize <= 0 || pageSize > 100 {
    pageSize = 20
}
```

Lưu ý:

```text
Validate input là lớp phòng thủ bổ sung.
Không nên xem validate input là biện pháp duy nhất chống SQL Injection.
```

## 8.5 Áp dụng nguyên tắc Least Privilege

Tài khoản database mà ứng dụng sử dụng chỉ nên có quyền tối thiểu cần thiết.

Ví dụ:

- API đọc dữ liệu chỉ cần `SELECT`.
- API tạo đơn hàng cần `INSERT`, `SELECT`.
- API cập nhật hồ sơ cần `UPDATE`, `SELECT`.
- Không nên dùng tài khoản `root`, `sa`, `postgres` cho ứng dụng web nếu không cần thiết.

Nếu ứng dụng bị SQL Injection nhưng tài khoản database không có quyền `DROP TABLE`, thiệt hại sẽ được giới hạn đáng kể.

## 8.6 Không hiển thị lỗi SQL cho người dùng

Không trả về thông báo lỗi chi tiết như:

```text
ERROR: syntax error at or near "SELECT"
relation "users" does not exist
```

Thay vào đó:

- Trả về lỗi chung chung cho client.
- Log lỗi chi tiết vào hệ thống log nội bộ.
- Giám sát lỗi database bất thường.

Ví dụ response:

```json
{
  "message": "internal server error"
}
```

## 8.7 Cẩn thận với stored procedure

Stored procedure không tự động an toàn.

Nếu stored procedure có dynamic SQL:

```sql
EXEC('SELECT * FROM users WHERE username = ''' + @username + '''')
```

Nó vẫn có thể bị SQL Injection.

Stored procedure chỉ an toàn khi:

- Không dựng SQL động từ input.
- Dùng parameter đúng cách.
- Quyền database được giới hạn.

## 8.8 Dùng WAF và monitoring

WAF không thay thế được code an toàn, nhưng có thể giúp:

- Chặn payload phổ biến.
- Phát hiện hành vi bất thường.
- Giảm rủi ro từ scanner tự động.
- Cảnh báo tấn công.

Ngoài ra, nên monitor:

- Số lượng lỗi SQL tăng bất thường.
- Query chậm bất thường.
- Request chứa ký tự đáng ngờ.
- Access pattern lạ.

## 9. Thực hành với Go

## 9.1 Code không an toàn

```go
package main

import (
	"fmt"
)

func getUserQuery(username string) string {
	return fmt.Sprintf(
		"SELECT * FROM users WHERE username = '%s'",
		username,
	)
}
```

Nếu `username` là:

```text
admin' OR '1'='1
```

Câu lệnh có thể bị tiêm SQL.

## 9.2 Code an toàn với database/sql

```go
package main

import (
	"context"
	"database/sql"
)

type UserRepository struct {
	db *sql.DB
}

func (r *UserRepository) GetByUsername(ctx context.Context, username string) (*User, error) {
	query := `
		SELECT id, username, email, password_hash
		FROM users
		WHERE username = $1
	`

	row := r.db.QueryRowContext(ctx, query, username)

	var user User
	err := row.Scan(
		&user.ID,
		&user.Username,
		&user.Email,
		&user.PasswordHash,
	)
	if err != nil {
		return nil, err
	}

	return &user, nil
}
```

Lưu ý:

- `$1` là placeholder.
- Giá trị `username` được truyền riêng.
- Database không coi `username` là cú pháp SQL.

## 9.3 Code an toàn với pgx

package main

import (

type UserRepository struct {

## 9.4 Login an toàn hơn: không so mật khẩu trực tiếp trong SQL

Thay vì:

```go
query := `
	SELECT *
	FROM users
	WHERE username = $1
	  AND password_hash = $2
`
```

Cách tốt hơn là:

1. Tìm user theo username bằng parameterized query.
2. Lấy `password_hash`.
3. So sánh hash bằng thư viện bảo mật.

Ví dụ:

```go
package main

import (
	"context"
	"errors"

	"golang.org/x/crypto/bcrypt"
)

var ErrInvalidCredential = errors.New("invalid username or password")

func (s *AuthService) Login(ctx context.Context, username, password string) error {
	user, err := s.userRepo.GetByUsername(ctx, username)
	if err != nil {
		return ErrInvalidCredential
	}

	err = bcrypt.CompareHashAndPassword(
		[]byte(user.PasswordHash),
		[]byte(password),
	)
	if err != nil {
		return ErrInvalidCredential
	}

	return nil
}
```

Cách này giúp:

- Tránh so sánh mật khẩu trực tiếp trong SQL.
- Hỗ trợ hash password đúng cách.
- Giảm rủi ro logic xác thực bị bypass.

## 9.5 Dùng sqlc

`sqlc` sinh ra code Go từ file SQL. Nếu file SQL được viết đúng cách, code sinh ra thường dùng parameterized query.

Ví dụ file SQL:

```sql
-- name: GetUserByUsername :one
SELECT id, username, email, password_hash
FROM users
WHERE username = $1
LIMIT 1;
```

Code Go do sqlc sinh ra sẽ nhận `username` như một tham số riêng, không nối chuỗi vào SQL.

Tuy nhiên, nếu bạn tự viết raw query ngoài sqlc và dùng `fmt.Sprintf`, lỗ hổng vẫn có thể xuất hiện.

## 9.6 Sắp xếp động với whitelist

Nhiều API cho phép client truyền `sort_by`. Đây là vị trí dễ bị SQL Injection nếu xử lý sai.

Không nên:

```go
query := fmt.Sprintf(
    "SELECT * FROM products ORDER BY %s",
    req.SortBy,
)
```

Nên:

```go
allowedSortColumns := map[string]string{
    "name":       "name",
    "price":      "price",
    "created_at": "created_at",
}

sortColumn, ok := allowedSortColumns[req.SortBy]
if !ok {
    return errors.New("invalid sort column")
}

query := fmt.Sprintf(
    "SELECT id, name, price, created_at FROM products ORDER BY %s ASC",
    sortColumn,
)
```

Vì `sortColumn` chỉ nhận giá trị trong whitelist, input người dùng không thể trực tiếp thay đổi câu lệnh SQL.

## 10. Checklist phòng chống SQL Injection

Bạn có thể dùng checklist sau khi review code:

- [ ] Có dùng prepared statement / parameterized query không?
- [ ] Có chỗ nào dùng `fmt.Sprintf` để dựng SQL không?
- [ ] Có raw SQL trong ORM/query builder không?
- [ ] Có dynamic column/table/order-by không?
- [ ] Nếu có dynamic identifier, đã dùng whitelist chưa?
- [ ] Tài khoản database có quyền tối thiểu không?
- [ ] Lỗi SQL có bị trả về client không?
- [ ] Input đã được validate theo định dạng mong đợi chưa?
- [ ] Stored procedure có dựng dynamic SQL không?
- [ ] Có test case cho input chứa `'`, `--`, `UNION` không?
- [ ] Có logging/monitoring cho lỗi database bất thường không?
- [ ] Có áp dụng rate limit cho endpoint nhạy cảm không?
- [ ] Có chạy security scanner trong CI không?
- [ ] Có review các truy vấn phức tạp như report, filter, search không?

## 11. Những hiểu lầm thường gặp

### 11.1 “Chỉ cần escape ký tự đặc biệt là đủ”

Escaping có thể hữu ích trong một số ngữ cảnh, nhưng dễ làm sai và dễ bỏ sót. Parameterized query là giải pháp an toàn hơn.

### 11.2 “Dùng ORM là tự động an toàn”

ORM thường an toàn khi dùng đúng cách. Nhưng nếu dùng raw SQL và tự nối chuỗi, ứng dụng vẫn có thể bị SQL Injection.

### 11.3 “API nội bộ thì không cần bảo mật”

API nội bộ vẫn có thể bị tấn công thông qua SSRF, máy chủ bị xâm nhập, hoặc dịch vụ khác trong hệ thống.

### 11.4 “Validate input là đủ chống SQL Injection”

Validate input là lớp phòng thủ bổ sung, không phải biện pháp thay thế parameterized query.

### 11.5 “Stored procedure là an toàn tuyệt đối”

Stored procedure vẫn có thể bị SQL Injection nếu bên trong nó dựng dynamic SQL từ input không an toàn.

## 12. Câu hỏi phỏng vấn thường gặp

### Câu 1. SQL Injection là gì?

SQL Injection là kỹ thuật tấn công chèn dữ liệu độc hại vào đầu vào của ứng dụng, khiến dữ liệu đó bị database hiểu nhầm như một phần của câu lệnh SQL.

### Câu 2. Nguyên nhân gốc rễ của SQL Injection là gì?

Nguyên nhân gốc rễ là ứng dụng trộn lẫn dữ liệu người dùng với cú pháp SQL, thường do nối chuỗi trực tiếp để tạo câu lệnh SQL.

### Câu 3. Vì sao `' OR '1'='1` có thể bypass đăng nhập?

Vì `'1'='1'` luôn đúng. Khi chuỗi này được đưa vào điều kiện `WHERE`, điều kiện có thể trở thành đúng với nhiều dòng dữ liệu, khiến hệ thống trả về user dù kẻ tấn công không biết mật khẩu.

### Câu 4. Prepared Statement là gì?

Prepared Statement là kỹ thuật gửi câu lệnh SQL và dữ liệu đầu vào tách biệt. Database sẽ xử lý dữ liệu đầu vào như giá trị thuần túy, không diễn giải thành cú pháp SQL.

### Câu 5. Vì sao Prepared Statement chống được SQL Injection?

Vì nó tách biệt code và data. Dù dữ liệu chứa ký tự đặc biệt như `'`, `--`, `;`, database vẫn chỉ coi đó là giá trị, không coi là câu lệnh SQL.

### Câu 6. Placeholder có dùng cho tên bảng hoặc tên cột được không?

Thường là không. Với tên bảng, tên cột, hướng sắp xếp, cần dùng whitelist hoặc ánh xạ giá trị hợp lệ, không nên truyền trực tiếp input người dùng vào SQL.

### Câu 7. Second-order SQL Injection là gì?

Là dạng SQL Injection mà payload được lưu vào database trước, sau đó được một truy vấn khác sử dụng lại và gây ra lỗ hổng ở bước sau.

### Câu 8. Blind SQL Injection là gì?

Là dạng SQL Injection mà kẻ tấn công không nhận trực tiếp dữ liệu hoặc lỗi SQL. Thay vào đó, kẻ tấn công suy luận dựa vào sự khác biệt phản hồi, ví dụ boolean-based hoặc time-based.

### Câu 9. Least Privilege giúp gì trong SQL Injection?

Nếu ứng dụng bị SQL Injection, tài khoản database có quyền hạn tối thiểu sẽ giới hạn thiệt hại. Ví dụ, nếu tài khoản chỉ có `SELECT`, kẻ tấn công không thể `DROP TABLE`.

### Câu 10. Trong Go, vì sao sqlc thường an toàn hơn?

Vì sqlc sinh code từ file SQL có tham số hóa, dữ liệu được truyền như tham số riêng thay vì nối chuỗi vào câu lệnh SQL. Tuy nhiên, nếu lập trình viên tự viết raw SQL không an toàn ở nơi khác, lỗ hổng vẫn có thể tồn tại.

## 13. Kết luận

SQL Injection là lỗ hổng lâu đời nhưng vẫn rất nguy hiểm. Nguyên nhân cốt lõi là ứng dụng không tách biệt rõ ràng giữa câu lệnh SQL và dữ liệu người dùng.

Để phòng chống hiệu quả, cần áp dụng phòng thủ nhiều lớp:

1. Dùng parameterized query cho mọi truy vấn.
2. Không nối chuỗi input vào SQL.
3. Dùng whitelist cho dynamic identifier.
4. Validate dữ liệu đầu vào.
5. Áp dụng least privilege cho database user.
6. Không hiển thị lỗi SQL chi tiết.
7. Monitor và phát hiện hành vi bất thường.
8. Kiểm thử bảo mật định kỳ.

Với lập trình viên backend, đặc biệt là người dùng Go, việc hiểu và áp dụng đúng prepared statement là yêu cầu cơ bản nhưng cực kỳ quan trọng.

### Mở rộng

Sau khi nắm vững SQL Injection cơ bản, bạn có thể tìm hiểu thêm các chủ đề sau:

- **Blind SQL Injection nâng cao**: boolean-based, time-based, binary search extraction.
- **Second-order SQL Injection**: payload được lưu trước và thực thi sau.
- **Out-of-band SQL Injection**: khai thác qua DNS, HTTP request từ database.
- **Database fingerprinting**: nhận biết loại database dựa trên lỗi hoặc hàm đặc trưng.
- **UNION-based exploitation**: xác định số cột, kiểu dữ liệu để khai thác.
- **Stacked Queries**: thực thi nhiều câu lệnh SQL nối tiếp nhau.
- **Dynamic SQL trong stored procedure**: rủi ro và cách viết an toàn.
- **SQL Injection trong ORM**: các trường hợp raw query, `Raw()`, `Exec()`, `Order()`.
- **SQL Injection trong NoSQL**: NoSQL injection trong MongoDB hoặc các database khác.
- **Parameter pollution**: kết hợp nhiều tham số để bypass validation.
- **WAF bypass**: các kỹ thuật bypass Web Application Firewall, chỉ dùng trong kiểm thử được phép.
- **sqlmap nâng cao**: tamper script, level, risk, technique.
- **Burp Suite Professional**: scanner, repeater, intruder.
- **OWASP Top 10**: nhóm Injection và các lỗ hổng liên quan.
- **Secure coding review**: checklist review code bảo mật cho backend.
- **Least Privilege database design**: thiết kế role, permission, schema separation.
- **Audit logging**: ghi nhận truy cập dữ liệu nhạy cảm.
- **Secrets management**: không hardcode DB credential trong source code.
- **Password hashing**: bcrypt, scrypt, Argon2.
- **Rate limiting**: giảm brute force và scan tự động.
- **Threat modeling**: xác định bề mặt tấn công của hệ thống.
- **Fuzz testing**: sinh input ngẫu nhiên để kiểm thử endpoint.
- **Static Analysis Security Testing**: quét code tìm lỗi bảo mật.
- **Dynamic Application Security Testing**: quét ứng dụng đang chạy.
- **Zero Trust Architecture**: không tin cậy mặc định bất kỳ thành phần nào trong hệ thống.s
