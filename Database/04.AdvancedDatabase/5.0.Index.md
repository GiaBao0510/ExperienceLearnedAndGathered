## **Indexing — từ cơ bản đến chuyên sâu**

Dữ liệu mẫu để thực hành (bảng lớn hơn 1 chút để thấy rõ hiệu quả của index):

```sql
CREATE TABLE products (
    id          SERIAL PRIMARY KEY,
    sku         VARCHAR(20),
    name        VARCHAR(200),
    category_id INT,
    price       NUMERIC(10,2),
    stock_qty   INT,
    created_at  TIMESTAMP DEFAULT now()
);

-- Sinh 1,000,000 dòng dữ liệu giả để test hiệu năng thật
INSERT INTO products (sku, name, category_id, price, stock_qty, created_at)
SELECT
    'SKU-' || i,
    'Product ' || i,
    (i % 20) + 1,                          -- 20 category khác nhau
    (random() * 10000000)::numeric(10,2),
    (random() * 100)::int,
    now() - (random() * 365 || ' days')::interval
FROM generate_series(1, 1000000) AS i;
```

---
## **Index là gì?**

**Index (chỉ mục) trong database** ==là một cấu trúc dữ liệu đặc biệt thường là B-tree) giúp tăng tốc độ truy xuất thông tin==. Nó hoạt động tương tự như phần mục lục ở cuối một cuốn sách: thay vì phải đọc lướt toàn bộ các trang để tìm một chủ đề, hệ thống sẽ tra cứu mục lục và trỏ thẳng đến vị trí lưu trữ dữ liệu chính xác. Index được xây dựng trên 1 hoặc nhiều cột của bảng, giúp DB **tìm dữ liệu nhanh hơn** mà không cần quét toàn bộ bảng (**Full Table Scan** / **Sequential Scan**).

![](https://dev-yyh.github.io/assets/img/posts/DB/1/1.webp)

**Phép so sánh dễ hình dung:** Index giống như mục lục (index) ở cuối 1 cuốn sách. Không có mục lục, bạn phải lật từng trang để tìm 1 từ khóa (Sequential Scan). Có mục lục, bạn tra thẳng đến trang cần tìm (Index Scan).

---
## **Tại sao Index lại quan trọng?**

Sử dụng **Index** trong database ==để tăng tốc độ truy xuất dữ liệu==, hoạt động tương tự như bảng mục lục ở cuối sách. Thay vì quét toàn bộ bảng (Full Table Scan) làm tốn thời gian, database dùng Index để tìm kiếm trực tiếp vị trí vật lý của hàng dữ liệu cần thiết.

Những lý do chính cần sử dụng Index bao gồm:

- **Tăng tốc độ tìm kiếm:** Giúp hệ thống tìm kiếm thông tin theo điều kiện (mệnh đề WHERE) nhanh chóng hơn.
- **Tối ưu hóa các thao tác kết nối và sắp xếp:** Đẩy nhanh tốc độ xử lý các câu lệnh JOIN bảng và sắp xếp dữ liệu (ORDER BY, GROUP BY).
- **Đảm bảo tính duy nhất:** Các Index dạng _Unique_ ngăn chặn việc trùng lặp dữ liệu trên các cột yêu cầu sự duy nhất như Email, Mã nhân viên.

Mặc dù mang lại hiệu suất đọc vượt trội, bạn cần lưu ý rằng Index sẽ làm giảm tốc độ ghi (thêm, sửa, xóa) và tiêu tốn thêm dung lượng lưu trữ do database phải liên tục cập nhật cấu trúc index mỗi khi bảng thay đổi

**Kiểm chứng bằng `EXPLAIN ANALYZE`** — công cụ quan trọng nhất để hiểu index có hiệu quả hay không

```sql
-- Chưa có index trên category_id
explain analyse
select * from products where category_id = 5;
```

***Output:***
```
Seq Scan on products  (cost=0.00..23729.00 rows=49933 width=52) (actual time=0.026..3465.828 rows=50000 loops=1)
Filter: (category_id = 5)
Rows Removed by Filter: 950000
Planning Time: 0.336 ms
Execution Time: 3469.613 ms
```
Kết quả sẽ hiện `Seq Scan on products` — DB phải quét qua toàn bộ 1,000,000 dòng để tìm các dòng khớp `category_id = 5`.


```sql
-- Tạo index
create index idx_products_category on products(category_id);

-- Chạy kiểm tra
explain analyse
select * from products where category_id = 5;
```

***Output:***
```
Bitmap Heap Scan on products  (cost=434.71..12287.87 rows=49933 width=52) (actual time=5.608..26.020 rows=50000 loops=1)
Recheck Cond: (category_id = 5)
Heap Blocks: exact=11228
  ->  Bitmap Index Scan on idx_products_category  (cost=0.00..422.22 rows=49933 width=0) (actual time=3.953..3.953 rows=50000 loops=1)
          Index Cond: (category_id = 5)
Planning Time: 1.596 ms
Execution Time: 28.202 ms
```

Giờ kết quả hiện `Bitmap Heap Scan` hoặc `Index Scan using idx_products_category` — nhanh hơn đáng kể vì DB dùng cấu trúc B-tree để nhảy thẳng tới dòng cần tìm.

**Trade-off của Index (câu hỏi phỏng vấn cực kỳ phổ biến):**

- ✅ Tăng tốc độ đọc (`SELECT`, `WHERE`, `JOIN`, `ORDER BY`).
- ❌ Giảm tốc độ ghi (`INSERT`/`UPDATE`/`DELETE`) — vì mỗi lần ghi dữ liệu, DB phải cập nhật **cả bảng chính lẫn mọi index liên quan**.
- ❌ Tốn thêm dung lượng lưu trữ (index cũng chiếm ổ đĩa).

→ **Nguyên tắc chung:** không nên tạo index tùy tiện trên mọi cột. Chỉ index những cột thường xuyên dùng trong `WHERE`, `JOIN`, `ORDER BY` với tần suất đọc cao.

---
## **Cách thức hoạt động**
Khi thực hiện một câu truy vấn tìm kiếm (ví dụ: dùng mệnh đề `WHERE` trong SQL), nếu không có index, cơ sở dữ liệu sẽ phải duyệt qua từng dòng dữ liệu một (gọi là _Full Table Scan_). Điều này rất chậm và tốn tài nguyên đối với các bảng lớn.  
Khi có index, hệ thống sẽ dò tìm trên cấu trúc index (thường là dạng B-Tree hoặc Hash) để lấy ra vị trí vật lý của dòng dữ liệu đó và truy cập trực tiếp vào đĩa cứng

---
## **Phân loại Index phổ biến**

- **Single-column Index:** Chỉ mục được tạo trên một cột duy nhất.
- **Composite Index:** Chỉ mục được tạo trên sự kết hợp của nhiều cột.
- **Unique Index:** Đảm bảo tính duy nhất cho các giá trị trong cột (không được có dữ liệu trùng lặp).
- **Clustered Index & Non-Clustered Index:** Khác biệt về cách sắp xếp và lưu trữ vật lý của bảng dữ liệu so với cây index.

---
## **Ưu/nhược điểm**

Ưu điểm và Nhược điểm

- **Ưu điểm:**
    - Tăng tốc độ tìm kiếm, lọc dữ liệu (các câu lệnh `WHERE`, `JOIN`).
    - Cải thiện hiệu suất khi sắp xếp (`ORDER BY`) và nhóm dữ liệu (`GROUP BY`). 
- **Nhược điểm (Tác dụng phụ):**
    - **Tốn dung lượng ổ cứng:** Index được lưu trữ như một bảng phụ.
    - **Làm chậm các thao tác ghi:** Mỗi khi bạn thêm (`INSERT`), sửa (`UPDATE`), hoặc xóa (`DELETE`) dữ liệu, hệ thống sẽ phải cập nhật lại cấu trúc index, làm tốn thêm thời gian xử lý.
---
## **Khi nào nên sử dụng?**

Chúng ta nên đánh index cho các cột thường xuyên được dùng để tìm kiếm, các cột khóa ngoại (Foreign Key) để nối bảng (`JOIN`), và các bảng chứa khối lượng dữ liệu lớn. Không nên lạm dụng index cho các cột ít dữ liệu trùng lặp hoặc các bảng có lượng ghi/xóa liên tục
