## **Khi nào Index KHÔNG được dùng dù đã tạo? (rất hay hỏi phỏng vấn)**

Đây là phần thể hiện tư duy debug thực tế, không chỉ học thuộc lý thuyết. Một số tình huống query optimizer quyết định KHÔNG dùng index dù có sẵn:

**a) Áp dụng hàm lên cột trong WHERE — làm hỏng khả năng dùng index:**

```sql
-- ❌ Index trên created_at KHÔNG được dùng, vì hàm DATE() bọc ngoài cột
SELECT * FROM products WHERE DATE(created_at) = '2026-01-15';

-- ✅ Viết lại theo khoảng để index vẫn dùng được
SELECT * FROM products
WHERE created_at >= '2026-01-15' AND created_at < '2026-01-16';
```

**b) Bảng quá nhỏ:** optimizer thấy Seq Scan trên bảng chỉ vài trăm dòng còn nhanh hơn overhead của việc tra index → tự động bỏ qua index.

**c) Query trả về phần lớn bảng (VD: filter ra >20-30% tổng số dòng):** lúc này Seq Scan đọc tuần tự liền mạch trên đĩa còn nhanh hơn Index Scan phải nhảy lung tung (random I/O) giữa index và bảng chính.

**d) Thống kê (statistics) của bảng bị lỗi thời:** Postgres dựa vào statistics (thu thập qua ANALYZE) để ước lượng nên dùng index hay không. Nếu lâu chưa ANALYZE sau khi dữ liệu thay đổi nhiều, optimizer có thể đưa ra quyết định sai lệch.

``sql
ANALYZE products;  -- cập nhật lại thống kê để optimizer quyết định chính xác hơn
```

Cách kiểm tra index có thực sự được dùng hay không: luôn dùng EXPLAIN ANALYZE, không đoán mò.

```sql
EXPLAIN ANALYZE SELECT * FROM products WHERE category_id = 5;
```

Đọc kết quả: tìm dòng Index Scan / Index Only Scan / Bitmap Index Scan (có dùng index) so với Seq Scan (không dùng index).

---
**1. Index là gì? Trade-off khi tạo index là gì?**

Index là cấu trúc dữ liệu phụ trợ (thường B-tree) giúp DB tìm dữ liệu nhanh hơn thay vì quét toàn bộ bảng. Trade-off: tăng tốc độ đọc nhưng làm chậm tốc độ ghi (vì mỗi lần INSERT/UPDATE/DELETE phải cập nhật cả bảng chính lẫn mọi index liên quan), và tốn thêm dung lượng lưu trữ. Vì vậy không nên tạo index tùy tiện trên mọi cột, chỉ nên index các cột thường filter/join/sort với tần suất đọc cao.

**2. B-tree Index và Hash Index khác nhau thế nào? Khi nào dùng loại nào?**

B-tree tổ chức dữ liệu theo cấu trúc cây có thứ tự, hỗ trợ được =, <, >, BETWEEN, ORDER BY. Hash Index dùng hàm băm, chỉ hỗ trợ so sánh bằng (=), không hỗ trợ khoảng giá trị hay sắp xếp vì hash phá vỡ thứ tự gốc của dữ liệu. Thực tế, B-tree gần như luôn là lựa chọn mặc định vì linh hoạt hơn; Hash Index ít khi cần thiết trong PostgreSQL hiện đại.

**3. Giải thích quy tắc "Left-most prefix" trong Composite Index.**

Với Composite Index trên nhiều cột (VD: (a, b, c)), index chỉ được dùng hiệu quả khi câu query filter theo đúng tiền tố từ trái sang — có thể chỉ dùng cột a, hoặc a và b, hoặc cả a, b, c, nhưng không thể chỉ dùng riêng b hoặc c mà bỏ qua a một cách hiệu quả. Giống cấu trúc danh bạ sắp theo (Họ, Tên) — tra theo Họ nhanh, nhưng tra riêng theo Tên thì không tận dụng được thứ tự đó.

**4. Covering Index / Index-Only Scan là gì? Lợi ích so với Index Scan thông thường?**

Covering Index là index chứa đủ mọi cột mà câu query cần (qua INCLUDE trong Postgres), giúp DB trả lời truy vấn hoàn toàn từ index mà không cần quay lại đọc bảng chính (Heap) — gọi là Index-Only Scan. Lợi ích: tiết kiệm 1 bước I/O so với Index Scan thông thường (vốn phải tra index rồi quay lại bảng chính lấy các cột còn thiếu), giúp query nhanh hơn đáng kể với các bảng lớn.

**5. Tại sao WHERE DATE(created_at) = '2026-01-15' không dùng được index trên created_at, dù đã tạo index? Cách viết lại cho đúng.**

Vì hàm DATE() được áp lên cột created_at trước khi so sánh, khiến optimizer phải tính toán giá trị hàm cho từng dòng thay vì tra thẳng theo giá trị gốc đã được index — index B-tree được xây dựng trên giá trị gốc của cột, không phải trên kết quả của hàm áp lên cột đó. Cách viết lại: chuyển thành khoảng so sánh trực tiếp trên cột gốc, VD created_at >= '2026-01-15' AND created_at < '2026-01-16', để optimizer dùng được index bình thường.

**6. Vì sao đôi khi DB "cố tình" không dùng index dù đã tạo sẵn? Nêu 2-3 lý do.**

Một số lý do: (1) bảng quá nhỏ, Seq Scan còn nhanh hơn overhead tra index; (2) query trả về phần lớn bảng (VD >20-30%), Seq Scan đọc tuần tự nhanh hơn Index Scan phải nhảy random I/O; (3) thống kê (statistics) của bảng bị lỗi thời do lâu chưa chạy ANALYZE, khiến optimizer ước lượng sai và chọn nhầm chiến lược thực thi.

**7. Làm sao biết chắc 1 câu query có thực sự dùng index hay không, thay vì đoán mò?**

Dùng EXPLAIN ANALYZE trước câu query để xem execution plan thực tế — tìm các từ khóa Index Scan, Index Only Scan, Bitmap Index Scan (có dùng index) so với Seq Scan (quét toàn bảng, không dùng index). Đây là công cụ bắt buộc phải dùng khi debug hiệu năng query, không nên chỉ dựa vào việc "đã tạo index" để giả định query sẽ nhanh.

**8. Unique Index khác gì so với Index thông thường?**

Unique Index vừa có chức năng tăng tốc tìm kiếm như index thông thường, vừa đóng vai trò ràng buộc toàn vẹn dữ liệu — không cho phép 2 dòng có cùng giá trị ở cột được index (trừ giá trị NULL, có thể xuất hiện nhiều lần tùy DB). Khi khai báo PRIMARY KEY hoặc UNIQUE trong schema, DB tự động tạo Unique Index tương ứng phía sau, không cần tạo thủ công thêm.
