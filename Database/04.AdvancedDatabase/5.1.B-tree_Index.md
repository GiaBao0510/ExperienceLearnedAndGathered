
**Định nghĩa:** ==là cấu trúc dữ liệu chỉ mục mặc định phổ biến nhất trong các hệ quản trị cơ sở dữ liệu== (như MySQL, PostgreSQL, SQL Server),, tổ chức dữ liệu theo cấu trúc cây cân bằng (Balanced Tree) — dữ liệu được **sắp xếp** để tìm kiếm theo kiểu chia đôi (giống binary search), độ phức tạp tìm kiếm là O(log n).

![](https://images.viblo.asia/295b94f1-4f23-4591-86ea-9ecec1218fdc.jpeg)

**B-Tree** lưu trữ dữ liệu theo kiểu mỗi node lưu trữ key theo thứ tự tăng dần, mỗi node này lại chứa 2 liên kết đến những node trước và sau nó. Node bên trái có key <= key node hiện tại, còn node bên phải thì có key >= key của node hiện tại. Nếu một node mà có n keys thì nó sẽ có tối đa là n + 1 node con.

**B-Tree** index tăng tốc độ truy vấn dữ liệu vì storage engine không phải duyệt cả bảng để tìm kiếm dữ liệu mà nó sẽ đi từ node root. các vị trí root node sẽ chưa con trỏ tới những node con, nó tìm đúng con trỏ bằng cách nhìn vào các giá trị trong node con và bằng việc xác định các giới hạn trên và dưới của một node, giúp storage engine dễ dàng tìm kiếm sự tồn tại hay không của một giá trị.

### **Nguyên lý hoạt động**

Về cấu trúc của B-Tree khá phức tạp vì nó không chỉ lưu trữ index mà còn lưu trữ cả value liên kết với index ấy, giá trị này liên kết đến record dữ liệu thực tế trong database, cặp đôi key-value này được gọi là payload.

![](https://images.viblo.asia/63545e58-9965-4ab0-8eee-4b1f0794d15c.jpeg)

Cấu trúc cây B-tree chia nhỏ dữ liệu thành các khối (node) và sắp xếp tăng dần. Khi bạn cần tìm một bản ghi: 
- Nó bắt đầu từ **Root node** (nút gốc) và so sánh giá trị.
- Đi qua các **Internal node** (nút nhánh) để rẽ nhánh.
- Dừng lại ở **Leaf node** (nút lá) chứa dữ liệu hoặc con trỏ trỏ đến dòng dữ liệu thực tế trên ổ cứng.
- Nhờ cơ chế này, database không cần phải quét qua toàn bộ bảng (Full Table Scan) mà chỉ cần đọc một vài trang dữ liệu để tìm ra kết quả
---
```sql
create index idx_products_price on products(price);
```

**B-tree phù hợp với các toán tử:** `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, và `ORDER BY`.
```sql
explain analyse
select * from products where price between 100000 and 500000 order by price;
```

***OutPut:***
```
Index Scan using idx_products_price on products  (cost=0.42..21872.82 rows=393195 width=52) (actual time=2.604..4576.763 rows=399083 loops=1)
Index Cond: ((price >= '100000'::numeric) AND (price <= '500000'::numeric))
Planning Time: 5.553 ms
Execution Time: 4596.227 ms
```

⚠️ B-tree **không tối ưu** cho tìm kiếm dạng `LIKE '%keyword%'` (chứa keyword ở giữa) vì dữ liệu được sắp theo thứ tự alphabet từ đầu chuỗi, không giúp ích khi cần tìm chuỗi con ở giữa

```sql
-- B-tree VẪN dùng được (vì bắt đầu bằng chuỗi cố định)
select * from products where name like 'Product 1%';

-- B-tree KHÔNG dùng được hiệu quả (vì % ở đầu)
select * from products where name like 'Product %100%'; -- vẫn Seq Scan
```


---
### **Ưu điểm nổi bật**
- **Truy vấn phạm vi (Range queries):** B-tree là lựa chọn tối ưu cho các lệnh tìm kiếm lớn hơn (>), nhỏ hơn (<), hoặc nằm trong khoảng (`BETWEEN`).
- **Sắp xếp (Sorting):** Vì các khóa luôn được lưu trữ theo thứ tự, việc sử dụng `ORDER BY` sẽ nhanh hơn rất nhiều.
- **Cân bằng tự động (Balanced tree):** Cây B-tree tự động cân bằng khi dữ liệu bị thay đổi, duy trì hiệu suất ổn định theo thời gian

---
### **Khi nào nên và không nên sử dụng?**
- **NÊN dùng:** Cho các cột được dùng thường xuyên trong mệnh đề `WHERE`, `ORDER BY`, hoặc cột có tính chọn lọc cao (dữ liệu phân tán rộng như email, mã định danh, ngày tháng).
- **KHÔNG NÊN dùng:** Cho các cột có rất ít giá trị trùng lặp (ví dụ: cột giới tính chỉ có Nam/Nữ), hoặc cho các bảng quá nhỏ, bởi database sẽ mất thêm tài nguyên để cập nhật index mỗi khi có lệnh `INSERT`, `UPDATE`, `DELETE`.

_(Lưu ý: Hầu hết các hệ cơ sở dữ liệu thực tế như MySQL hay Postgres sử dụng phiên bản cải tiến là **B+Tree**, nơi các nút lá chứa liên kết trực tiếp với nhau để quét phạm vi nhanh hơn, còn các nút nhánh chỉ chứa khóa tìm kiếm)._
